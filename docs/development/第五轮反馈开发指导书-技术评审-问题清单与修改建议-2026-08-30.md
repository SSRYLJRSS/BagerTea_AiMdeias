## 0. 总体结论

**文档质量高，可以施工，但存在 4 个设计级问题建议先修订再动工**（A1、A2、A4、C1），全部集中在超级搜索与模型发现。沉浸全屏、视频播放器、披露按钮三部分的根因分析与方案均与代码事实吻合，无阻塞问题。

对用户三个核心问题的直接回答：

1. **超级搜索能不能实现你的要求？** 大体能。单一概念协议 + 后端生成 QueryExpr + 本地确定性守卫，能消除截图里的四类错误（整句关键词、同义双条件、空标签行、无依据 assetType）。但文档当前的 OR 语义（A1）和"未映射概念硬性 AND 进描述搜索"（A2）两处按现方案会得到"能执行、但结果可能不符直觉"的行为，建议先按 A1/A2 修订协议。
2. **能不能提高搜索效率？** 能。零结果错误和"看不懂为什么没结果"的情况会显著减少；瓶颈本来就不在执行层（259 个素材，SQLite FTS 绰绰有余），而在解析质量与召回率——A2、A6 直接决定召回，建议优先处理。
3. **后台 AI 提示词到底对不对？** 现有 prompt 的病根确认属实：tags/concepts/unresolved 多源并存、unresolved 整句拼接进 search、规则堆成一大段、词典实际不含别名。文档 §9.2 的十条硬规则方向正确，但缺 A1 的分组表达、A7 的概念原子性约束，且未随 V2 结构给出新的 JSON Schema（结构化输出层会先于 prompt 拦截或放行字段）。三层防御（结构校验 / 本地语义守卫 / expr 校验）的设计是对的。

**根因核实结果汇总**：文档 §2 的根因描述 10 项中 9 项属实（含 FB5-01/02/03/04 全部），仅 §2.5 问题 F 的后半段（"空行写入 expr 导致后端报错"）与代码不符，另有 1 处文件路径写错，详见第 5 节勘误表。

## 1. 高优先级问题（建议修订文档后再施工）

### A1. relation=or 的扁平 OR 语义是错的，且文档测试用例会把错误语义固化为回归基准 【P0·设计缺陷】

**位置**：指导书 §9.1（SearchIntentV2 只有全局 `relation: String`）、§9.5 规则 3（"relation=or：positive root 为 OR"）、§13.7 测试表第 2 行。

**问题**：输入 `晚上拍的树或者白天拍的建筑`，模型只能输出 concepts `[夜间, 树, 白天, 建筑]` + `relation=or`，按 §9.5 生成 `OR(夜间, 树, 白天, 建筑)`。这匹配"任何夜景素材、或任何有树的素材、或任何白天素材、或任何建筑"——远宽于用户直觉的 `(夜间 AND 树) OR (白天 AND 建筑)`。单个全局 relation 字符串在结构上就无法表达"子句内 AND、子句间 OR"。

更严重的是 §13.7 该行期望只写了"relation OR 被实际写入 expr"，没有断言分组语义，等于把错误语义写进了回归基准。

**建议**（二选一，推荐前者）：

- 给 `SearchConceptV2` 增加可选字段 `group: u32`（缺省 0）。prompt 要求模型把同一子句的概念标同一 group 号；expr 生成规则改为：**组内 AND、组间 OR**，exclude 概念仍套 `AND(positiveRoot, NOT…)`。§13.7 该行期望同步改为断言 `(夜间 AND 树) OR (白天 AND 建筑)` 的树形。
- 若不想扩协议：本地守卫在 `relation=or` 且概念跨多个 role/facet 时，降级为 and 并输出 warning"『或』关系无法准确分组，已按全部满足执行"。这是保守降级（结果偏少但不出错），并要在 §13.7 增加对应用例。

### A2. 未映射概念的"描述硬 AND"有系统性零结果风险 【P1·召回缺陷】

**位置**：指导书 §9.4（"confidence ≥ 0.55：转为 scope=description 的单概念 search leaf"）、§13.7 测试行"银杏树下的老人"。

**问题**：一句话描述上限 20 字，天然只能覆盖画面的一小部分概念。把"银杏树"作为 description-scope 的硬 AND leaf 与"老人"标签条件并列，意味着**描述里没写"银杏树"三个字的素材全部被排除**——即使它画面正确、标签正确。描述越简短，这个模式的零结果概率越高；而这正是文档自己设计的数据形态。§15.6 验收"若库中确有同时满足条件的已打标素材，应返回结果"在实践中会不稳定通过。

**建议**：

- 方案一（推荐）：description-scope leaf 编译为 `OR(description命中, fileName命中)`，即 scope 实际是"内容文字"而非仅描述列——文件名常含拍摄场景信息，作为软兜底可显著降低零结果率；chip 上仍标注"内容：银杏树"。
- 方案二（最小改动）：保留硬 AND，但把该类 leaf 单独渲染成**可一键移除的 chip**，并在查询返回 0 结果时提示"尝试移除未命中的内容条件：银杏树"。这需要写进 §9.7 与 FilterChips 规格，当前文档没有。

### A3. scope 的 SQL 编译策略完全缺失，且 ≤2 字查询不走 FTS 的暗坑 【P1·规格缺口】

**位置**：指导书 §8.1/§8.2 只定义了 scope 枚举和"FTS 谓词默认搜索三列"，未定义编译细节。

**问题**：当前 `build_search_predicate`（`src-tauri/src/db/search.rs:41`）只有一套无列前缀的 MATCH/LIKE 产物。实现 scope 必须明确：

- FTS 列过滤要用 MATCH 列前缀语法：`content_description:"银杏 杏树"`；`chunk_and_predicate`（search.rs:73）的每个 2 字块都要加列前缀，不是只加一次。
- `like_predicate`（search.rs:99）目前覆盖 file_name + 标签名两处，需要按 scope 拆成三套变体（fileName-only / description-only / all），其中 all 变体要新增 `a.content_description LIKE ?`。
- **最容易漏的暗坑**：≤2 字的查询（如"夜景"）**从不走 FTS，只走 LIKE 路径**（search.rs:47-49）。如果实现者只给 FTS 加了列而忘了改 like_predicate，两字中文词将永远搜不到描述。同理 scope=description 的两字词也完全依赖 LIKE 变体。

**建议**：文档 §8.1 补一小节"编译规格"：`build_search_predicate(conn, raw, scope)` 的签名变化、各 scope × 各长度路径的产物矩阵，并在 §13.6 加"2 字词通过描述命中素材"的测试（现有测试清单没有覆盖 ≤2 字 × description 组合）。

### A4. FilterChips 与 expr 双源不一致：OR 查询下 chips 展示错误，删一个 chip 会丢掉全部 AI 条件 【P1·既有 bug，文档未覆盖】

**位置**：指导书 §9.6 只改了 store 取 `result.expr`，§10.4 对 FilterChips 只要求"描述/文件名 scope 可读文案"。

**问题**（两处，均为当前代码实际行为，V2 改造若不专门处理会原样带入）：

1. **展示与执行不一致**：replace 模式同时设置 `query = result.query`（扁平、恒为 AND 语义）和 `expr = result.expr`（可能是 OR/NOT 树）。FilterChips 读的是 `query.facetFilters`（FilterChips.tsx L42-50），OR 查询时 chips 显示的是 AND 语义的条件列表，而实际执行的是 OR——文档第 0 节决定 7"expr 为唯一执行事实源"在 UI 层被违反。另外 `syncQueryFromExpr`（`src/utils/queryExprUtils.ts:108`）只提取 AND 顶层叶子，OR/NOT 根会被静默丢弃，append 模式走这条路径时 chips 会直接显示为空。
2. **删除 chip 清空整棵树**：FilterChips 删除任一 chip 调 `setQuery`，而 `setQuery` 会 `set({ query: next, expr: undefined, … })`（superSearchStore.ts:113）——**删一个条件等于丢掉全部 AI 条件**，expr 被清空后回退到扁平 query 执行。

**建议**：文档 §9.6/§10.4 必须补一条硬规格：**chips 的渲染与删除都以 expr 为源**——渲染时递归遍历 expr 树（OR 组显示"任一组：A / B"或按组渲染，NOT 显示"排除"），删除时从树中摘除对应 leaf 后 `setExpr`，禁止 chips 直接调 `setQuery`。同时 `syncQueryFromExpr` 对不可扁平化的树应保留 expr 并给 chips 一个"复杂条件（N 项）"的兜底展示，而不是产出空条件列表。

### C1. 删除旧 `ai_list_models` 与 AiTaggingPage 存在未交代的矛盾 【P1·会直接编译失败或功能回退】

**位置**：指导书 §6.1"确认无调用后删除旧 ai_list_models"、§6.5"AiTaggingPage 也应复用纯 ModelCombobox，但由它自己的 wrapper 提供数据"。

**问题**：`AiTaggingPage.tsx:431-437` 当前用 `ModelSelect`，传的是 **legacy profile 的明文 apiKey**（`activeProfile.apiKey`，来自旧 settings 结构），不是连接档案，**没有 connectionId**。新命令 `DiscoverAiModelsInput` 靠 connectionId 从 keyring 取密钥、或靠 `input.apiKey` 传临时密钥——文档没有说明 AiTaggingPage 的 wrapper 该走哪条路。实现者按 §6.1 删掉旧命令后，AiTaggingPage 要么编译失败，要么模型列表功能静默失效。另有一个字段映射坑：legacy profile 的 `apiMode` 取值是 `"openai" | "anthropic"`，而新协议是 `"openai_chat" | "anthropic_messages"`，需要显式映射。

**建议**：文档 §6.5 明确写出：AiTaggingPage 的 wrapper 调 `discover_ai_models({ deployment: profile.isLocal ? "local" : "cloud", protocol: apiModeToProtocol(profile.apiMode), baseUrl: profile.baseUrl, apiKey: profile.apiKey })`，即走 `input.apiKey` 临时密钥路径；并注明 apiMode→protocol 的映射规则。

## 2. 中优先级问题

### A5. 既有"同分面多概念合并为 any（OR）"的语义错误未被文档列为根因 【P2】

当前 `resolve_query`（super_search_ai.rs:368-391）把同一分面的多个概念合并进一个 `ResolvedFacet` 且 `mode: "any"`——输入"有树还有花"会执行 `树 OR 花` 而不是 `树 AND 花`。V2 的"每概念独立 leaf + AND 根"隐式修复了它，但文档 §2.5 的六个问题里没有这一条。**风险**：实现者如果在 expr 生成时仍沿用"按分面合并"的旧习惯，这个 bug 会原样保留。建议在 §9.9 禁止项和 §13.7 测试表加一条"同分面两个不同概念（树+花）必须是 AND"。

### A6. 词典实际不含别名，prompt 规则 2 的前提不成立 【P2】

`collect_tag_dictionary`（super_search_ai.rs:442-463）的 SQL 只 `SELECT t.name`，**没有 join tag_aliases**——函数注释和文档 §2.5 都声称"每分面 30 个 + 别名"，与实现不符。§9.2 规则 2"同义概念根据词典选择一个（多人/人群）"依赖词典里能看到同义词；词典只有规范名时，模型无从知道"人群"和"多人"是同义，只能靠后端 tagId 去重兜底。建议本轮把 searchable alias 一并写进词典行（如 `多人 (people) / 人群`），同时把每分面上限从 30 提到 50（259 个素材的库，词典体积不构成 prompt 压力）。

### A7. prompt 规则与结构化 Schema 需要同步补齐的缺口 【P2】

§9.2 十条规则方向正确，建议补充：

1. **概念原子性**：每个 concept.text 必须是 1-4 字的规范名词（"树"、"夜间"、"多人"），禁止把短语（"晚上拍的树"）作为一个概念。现有规则只靠例子暗示，模型对长输入容易整段搬运。
2. **连接词表扩展**：规则 1 的列表缺"和、与、并且、再、上面、中间、旁边"等高频连接/方位词；建议直接给一份封闭停用词表，并让本地守卫 §9.3 concept 清洗复用同一张表（单一事实源，两边不会漂移）。
3. **V2 JSON Schema 未给出**：现有 `intent_schema()`（super_search_ai.rs:565）是 `additionalProperties: false` + 全字段 required 的严格结构，删掉 `search/tags/excludeTags/unresolved`、新增 `textTerms/polarity` 后必须整体重写，且 `SearchConceptV2.confidence`、`IntentTextTerm.scope` 等字段要进 schema。文档只给了 Rust struct，没给 schema 规格——这是"结构化输出、宽容解析、本地守卫三层"的第一层，漏掉会直接在第一层被拒或放行未知字段。
4. **A1 的 group 字段**（若采纳）也要进 schema 与 prompt 规则。

### B1. fallback 全屏的 z-index 层级未验证 【P2】

§4.1 要求 fallback 模式 `fixed inset-0 z-50` 覆盖 TitleBar/BottomBar，但文档未核对应用 TitleBar 的实际 z-index/stacking context。若 TitleBar 使用更高 z 值或独立 portal，沉浸模式会露边。建议 §15.1 验收加一条"fallback 下 TitleBar 不可见且其控件不可被 Tab 聚焦"，并在实现时先读一遍 App 布局的 z 值分布。

### B2. Esc × native fullscreen 的测试策略不成立 【P2】

§13.1 要求测试"Esc 分别退出 native/fallback"，但 jsdom 里 Esc 不会触发浏览器原生退出全屏，`escapeShouldExitFullscreen`（shortcuts.ts:42）依赖的 `document.fullscreenElement` 需要 mock。现有 ViewerPage.test 已有 fullscreenchange 的 mock 手段，文档应明确：native 退出的测试通过**派发 mock 的 `fullscreenchange` 事件**驱动状态机，keydown Esc 只测 fallback 分支，避免实现者写出一个永远过不了的真原生 Esc 测试。

### C2. 连接测试与模型列表的基址语义不同步 【P2】

§6.3 说连接测试复用同一 base join helper（/messages），模型列表追加 /models。OpenAI 兼容用户若填了不带 `/v1` 的根地址，`/messages` 探活会 404 而 `/models` 可能 200（或相反，取决于中转站）。文档已有"不擅自加 /v1"的正确决定，但建议补一条产品文案规则：连接测试 404 时提示"服务地址可能需要补全 /v1 路径"，把两个探针的不一致转化为可诊断信息，而不是让用户以为连接坏了。

### D1. V17 迁移幂等细节未给全 【P2】

§7.2 说"迁移必须幂等，使用现有 add_column_if_missing"，但触发器删除/重建、assets_fts 虚表重建只写了顺序，没写幂等防御：应明确 `DROP TRIGGER IF EXISTS`、`DROP TABLE IF EXISTS`（虚表）、`CREATE TRIGGER IF NOT EXISTS`，并保持"先重建对象、最后 set user_version=17"的既有模式（仓库 v3 迁移已验证过这套顺序的崩溃可重入性，照抄即可）。另注意：`ALTER TABLE fts_content ADD COLUMN content_description TEXT NOT NULL DEFAULT ''` 在 SQLite 中合法（常量默认值），但旧行会以 '' 填充，步骤 7 的回填 UPDATE 会触发重建后的 trg_fc_au——触发器必须在回填前就位，文档顺序正确，只是要在实施清单里显式标注这个依赖顺序不可调换。

### D2. assets UPDATE 触发器的 OF 列清单是必改点 【P2】

`trg_assets_au` 现为 `AFTER UPDATE OF file_name`（migrations.rs:93）。描述落库走的是 assets 行 UPDATE，若不把触发器改为 `UPDATE OF file_name, content_description`，**改描述后 FTS 不会更新**（除非恰逢 file_name 同时变更）。§7.2 步骤 5 说了"fileName 与 contentDescription 都写入 fts_content"，但没有点名这条触发器的 OF 列变更——这是最容易漏的一处，建议在 §10.3 migrations.rs 行加上"含 trg_assets_au OF 列扩展"字样（§13.6 已有对应测试"仅改描述后 FTS 立即可搜"，很好，保留）。

### E1. 普通素材库搜索行为会随 V17 静默改变 【P2·全局联动】

`build_search_predicate` 的无前缀 MATCH 默认搜索全部列，V17 给 assets_fts 加了 content_description 列之后，**普通素材库搜索（libraryStore 链路，不经超级搜索）的结果集会自动扩大**（开始命中描述）。这是 §8.1 明示的意图，但属于"不改代码却改行为"的全局联动点：建议 §13 测试清单补普通搜索的回归用例（描述命中不出现在旧断言里的测试要更新），并在验收时对普通搜索框做一次真机抽查，避免上线后被当"搜索变宽松"的 bug 报回来。

### E2. 实施顺序第 6/8 步之间有依赖倒置 【P2】

§11 把 V17+FTS（第 6 步）排在 SearchIntent V2（第 8 步）之前，但 §8.2 的 `Search.scope` 依赖 query_expr.rs 的 Rust 类型变更（第 8 步才动 query_expr.rs）。建议明确切分：第 6 步交付"三列默认搜索 + LIKE 兜底"（scope 无关），`Search.scope` 字段与编译支持随第 8 步交付；或者干脆把 scope 的 Rust/TS 类型前置到第 6 步。二选一写死，避免中间态 typecheck 归属不清。

## 4. 超级搜索专项：多轮审查结论汇总

按"输入 → prompt → 模型输出 → 解析 → 守卫 → tagId 解析 → expr 生成 → 前端应用 → SQL 执行 → FTS 召回"全链路走查后的结论：

**文档诊断属实的部分**（均已对照代码确认）：

- 问题 A（tags+concepts 双源）：`intent_schema()` 与 `compile_concepts` 确实并存两条表达路径（super_search_ai.rs:585-640、327-351）。
- 问题 B（只按文字去重）：`compile_concepts` 去重仅比较 `normalize_name(text)`（super_search_ai.rs:333-340）。
- 问题 C（unresolved 整句进 search）：super_search_ai.rs:317-325，截图里"关键词：晚上拍的然后有树还有多人"的路径确认。
- 问题 D（FTS 无描述列）：migrations.rs:60-66，assets_fts 仅 file_name+tag_names。
- 问题 E（relation 不执行）：store L150 `resolvedQueryToExpr(result.query)` 固定 AND（queryExprUtils.ts:36-57），relation 只进 chips 头部文案。
- 问题 F 前半段（AI tagId 不在 tagStore 快照 → select 显示"选择标签"）：QueryBuilder options 来自 `tagStore.tree` 扁平化，确认存在。

**文档方案正确的部分**：

- 单概念事实源 + 删除多源字段，是对问题 A/B 的正解。
- 后端生成 expr、前端原样执行（§9.5/9.6），是对问题 E 的正解，且后端执行层已就绪（assets.rs:326-339 有 expr 时以表达式编译为准，AND/OR/NOT 递归编译 + 参数偏移均已实现并有测试）。
- 本地确定性守卫（§9.3 assetType/relation/concept 清洗）是对"不信任模型"的正确姿势；现有 `validate_intent` 白名单校验提供了成熟模板。
- `missingFacetKeys` 删除合理：该字段当前只在类型与 defaultQuery 里流转，删除成本低。
- 三层降级请求（Structured→JsonObject→Plain，ai_cloud.rs:573-635）沿用即可，V2 只需换 schema。

**文档方案需要修订的部分**：见 A1（OR 分组）、A2（描述硬 AND）、A3（scope 编译规格）、A4（chips 与 expr 同源）、A6（词典别名）、A7（schema 与 prompt 补齐）。
