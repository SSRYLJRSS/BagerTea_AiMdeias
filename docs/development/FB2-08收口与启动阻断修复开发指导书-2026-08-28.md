## 1. 实测基线（`3f27a12`，2026-08-28 复测）

### 1.1 最严重的事实：**生产库起不来**

上一份报告说「软件本体（`cargo build`、`npm run build`、`tauri dev`）全部正常」，**这个结论是错的**。用真实用户库（`%APPDATA%\bagertea_ai_media_v2\library.db`，259 条素材，`user_version = 15`）复现：

```text
user_version = 15
tag_facets 列 = [key, display_name, description, selection_mode, max_items,
                 sort_order, is_system, status, applies_to, created_at, updated_at]
tag_facets 有 hint 列 = False        ← 关键
assets 已有 palette_json / palette_version / palette_scanned_at
                / dominant_hue / dominant_sat / dominant_lum  ← 半成品状态
color 分面 status = inactive          ← 半成品状态

按 migrate_v16 的顺序逐句重放：
  ① add_column_if_missing × 6      → OK（列已存在，幂等）
  ② UPDATE tag_facets SET status='inactive' WHERE key='color'  → OK
  ③ UPDATE tag_facets SET hint = hint || '。风格描述…'         → *** no such column: hint
```

→ `migrate_v16` 返回 `Err` → `migrate()` 中断，**`user_version` 永远停在 15** → `db::init()` 返回 `Err` → `lib.rs:44` 的 `panic!("数据库初始化失败: {e}")`。

**用户说的「软件编译不了、各种报错」，主体是这个：应用启动即 panic。** 上一份报告只把它当成"V16 测试 fixture 缺列"（其 B-1），完全没有意识到 `tag_facets` 表在**真实 schema 里也没有 `hint` 列**——`hint` 从来只存在于 `settings` JSON 的 `aiFacetConfigs[].hint`（`settings.rs:14`），从未进过 `tag_facets` 表（V8 建表 `migrations.rs:317-330`、V13 重建 `migrations.rs:676-691` 都没有它，全仓库也没有任何 `ALTER TABLE tag_facets ADD COLUMN hint`）。

> 注意 ② 已经执行成功过（真实库里 `color` 已是 `inactive`，6 列也已加上）——迁移不是原子的，`migrate_v16` 没有包事务。所以现在生产库处于**"V16 做了一半、版本号还是 15"**的状态，每次启动都在同一句挂掉。

### 2.2 必须纠正的三处

**纠正 1（最重要）：B-1 的诊断与修法都错了。**

报告说「测试用最小 fixture 手工建 `tag_facets` 表，建表语句里没有 `hint` 列」，给的方案是**给 fixture 补 `hint` 列**。照这个方案改，结果是：`cargo test v16` 变绿，**而生产库继续 panic**——因为真实 `tag_facets` 也没有 `hint` 列。这是"把体温计调好让病人显示不发烧"。

正解见 FX-01：`hint` 不是 `tag_facets` 的字段，它属于 `settings` JSON 的 `aiFacetConfigs[]`。`migrate_v16` 第 2b 步的整句 SQL 从一开始就写错了对象，必须改成去写 settings JSON（和同一函数第 3 步一样的读-改-写），而不是给表补一个语义上不该存在的列。

**纠正 2：D-1「黑白照片主色永远是空」——现象成立，但给的回退方案会引入新问题，且优先级判断偏低。**

报告的方案是「剩余样本 < 原样本 10% → 回退全样本」。这个阈值在实测里挡不住真实场景：一张 60% 天空过曝（`lum > 0.96 && sat < 0.05` 命中）+ 40% 正常曝光的风景照，剩余样本是 40%，远大于 10%，不触发回退，但天空这一大块信息被整体丢掉，主色偏移。而且这条不是 P1 的"设计缺陷"，它会**直接毁掉验收标准里的"抽查 10 张观感一致"**（《第二轮指导书》§14.13）。见 FX-04：改成"分层预筛 + 有条件回退"，并把阈值提到 35%。

**纠正 3：D-2「累计舍入损失精度」——结论对，但漏了同一函数里更严重的一个 bug。**

`merge_clusters`（`palette.rs:175`）的合并条件是 `delta_(...) < EPSILON && m.ratio >= c.ratio`。报告说 `m.ratio >= c.ratio` "因输入已降序恒真，可以删掉"。**这句话在合并开始前成立，合并过程中不成立**：`m.ratio` 只增不减，而 `c` 是按原降序取的，所以 `m.ratio >= c.ratio` 确实恒真——这部分对。但报告没看到：**合并只比较 `c` 与已保留簇，`absorbed` 后 `break`，导致 `merged` 内部两两之间可能仍然 ΔE < 6**（A 吸收了 B 后 A 的代表色不变，但 C 可能与 A' 距离 > 6 而与 B 距离 < 6，于是 C 自己占一格；反过来若 C 与 A 距离 5.9、与 D 距离 3，也会被 A 抢走）。结果是色条上仍可能出现两块肉眼无差别的分段——这正是《第二轮指导书》§14.13 明确要求排除的"单色照片不返回 6 个几乎相同的色块"。见 FX-15。

### 2.5 已核实"不是 bug"（不要改）

- **hue 环绕双区间 OR**（`search_query.rs:361-368`）实现正确。实测：`min > max` 编译成 `(expr >= ?1 OR expr <= ?2)`，且在有统计信息时能命中 `MULTI-INDEX OR` 双索引搜索。
- **后端 `dominant_from_rgb`（`palette.rs:192`）与前端 `rgbToHsv`（`ColorStrip.tsx:32`）数值一致**。用 12 组代表色逐一比对，hue/sat/lum 三值全部相同，无需统一。
- **`COLUMNS` 与 `from_row` 的列序对齐**：42 列 vs 索引 0~41，逐项核对无偏移。上一份报告建议"趁机改成 `row.get("name")` 按名取"，**本轮不做**——那是无收益的大面积改动，且会掩盖未来的真实错位（按位取值时错位会立刻炸，按名取会静默拿到 NULL）。
- **`ai_cloud.rs:122-147` 的停用分面丢弃 + warning** 实现与《第二轮指导书》§14.3② 一致。
- **`kmeans_colors` 空簇导致除零**：曾怀疑 `palette.rs:113-121` 的 `ag.r / ag.count`（`count == 0` 会整数除零 panic）。写了独立探针程序（三轮共 7720 张合成图：随机梯度、紧簇+抖动、极端偏斜分布、样本数 2~46 的小图）**未能构造出空桶**——`get_kmeans_hamerly` 的 `recalculate_centroids_hamerly` 会把饿死的质心重随机，且 `indices` 只记录实际最近质心，`buckets` 的洞在实测中不出现。**不改，但要加防御性测试**（FX-15 附带）。

## 5. 代码规范（本轮强制，补充《第二轮指导书》§4）

### 5.1 Rust

沿用《第二轮指导书》§4.3 全部条款，本轮额外强制四条：

1. **迁移里的每一条 SQL，动的列必须先确认存在。** 本轮 FX-01 的根因就是这一条被违反：`hint` 从来不在 `tag_facets` 表里。写迁移时的自查动作：
   ```bash
   # 你要写的列，在 SCHEMA_V1/V8/V13 建表语句或某个 add_column_if_missing 里能找到吗？
   grep -n "hint" src-tauri/src/db/migrations.rs
   ```
   找不到就说明你在写一个不存在的列。**只增列的迁移不需要 `has_column` 判断**（`add_column_if_missing` 已代劳），但 `UPDATE`/`SELECT` 引用的列必须自己确认。

2. **迁移函数内多步写操作必须包事务。** `migrate_v16` 现状没有事务，所以生产库停在"做了一半"的状态。本轮 FX-01 顺带补上：
   ```rust
   fn migrate_v16(conn: &Connection) -> AppResult<()> {
       // 只增列在事务外（ALTER 天然幂等且不参与回滚语义）
       for (col, ty) in V16_COLUMNS { add_column_if_missing(conn, "assets", col, ty)?; }
       conn.execute_batch(V16_INDEXES)?;
       let tx = conn.unchecked_transaction()?;   // 范式：importer.rs:694
       // …数据写操作…
       tx.commit()?;
       Ok(())
   }
   ```
   **新写的 V17 也必须遵守这条。**

3. **不得嵌套 `imaging::acquire()`。** `decode_thumb`（`imaging.rs:400-401`）自己会 acquire。调用方只在**不经过 `decode_thumb` 的路径**（如 `video::extract_frame`）才需要显式 acquire。现有正确范式：`thumbnail.rs:118`（视频抽帧，不走 decode_thumb）、`preview.rs:49`（同）。现有错误范式：`media_refill.rs:250`（走 decode_thumb 却又 acquire，FX-08 要修）。

4. **回填/回算类批处理的计数必须三分：`success` / `skipped` / `failed`。** 语义边界：
   - `success` = 算出结果并成功写库；
   - `skipped` = 素材本身不适用（不是图片、色板为空、行已删除）——**不是错误**，UI 不得渲染成失败；
   - `failed` = 真错误（解码失败、写库失败、文件缺失）。
   混计会让"全库黑白摄影"显示成大面积失败，用户会来报 bug。

### 5.2 TypeScript / React

沿用《第二轮指导书》§4.2 全部条款，本轮额外强制两条：

1. **色条渲染必须做条件短路**，顺序是 `enabled && 位置开关 && palette?.length`（`AssetCard.tsx:137` 现状正确）。`toPaletteSegments` 只能出现在这个条件**之后**——它对每段都做一次 `rgbToHsv`，在虚拟滚动的可见卡片上是每帧成本。

## 6. FX-01【P0 阻断】`migrate_v16` 写不存在的 `tag_facets.hint`

### 6.1 根因

`migrations.rs:942-945`：

```rust
conn.execute(
    "UPDATE tag_facets SET hint = hint || '。风格描述不包含颜色（颜色由算法主色呈现）', updated_at = ?1 WHERE key = 'style' AND instr(hint, '不包含颜色') = 0",
    rusqlite::params![now],
)?;
```

`tag_facets` 表**没有 `hint` 列**，从 V8 建表（`migrations.rs:317-330`）到 V13 重建（`migrations.rs:676-691`）都没有；`TagFacet` struct（`tag_facets.rs:24-36`）与 `FACET_COLS`（`tag_facets.rs:78-79`）也都没有。`hint` 的唯一归属是 `settings` JSON 的 `aiFacetConfigs[].hint`（Rust 侧 `settings.rs:14`，前端 `src/types/settings.ts`）。

SQLite 在 `prepare` 阶段就解析列名，**即使 `WHERE` 一行都不匹配也会报错**（已实测确认）。所以这条语句在任何库上都必然失败。

### 6.2 修改方案

把第 2b 步从"改表"改为"改 settings JSON"，与同函数第 3 步（`migrations.rs:947-983`）合并成一次读-改-写。改完后 `migrate_v16` 的数据写操作变成两块：`tag_facets.status`（表）+ `settings` JSON（`aiFacetConfigs` 里 color 的两个 flag ＋ style 的 hint 追加）。

```rust
/// V16 迁移：加色板列 + 索引 + color 分面停用（AI 侧摘除，见 §14.3）。
fn migrate_v16(conn: &Connection) -> AppResult<()> {
    // 1. 只增列 + 索引（ALTER / CREATE INDEX IF NOT EXISTS 天然幂等，放事务外）
    for (col, ty) in V16_COLUMNS {
        add_column_if_missing(conn, "assets", col, ty)?;
    }
    conn.execute_batch(V16_INDEXES)?;

    let now = chrono::Utc::now().timestamp_millis();
    // 数据写操作包事务：否则中途失败会留下"做了一半、版本号未升"的库，
    // 每次启动都在同一句报错（FX-01 的生产表现）。
    let tx = conn.unchecked_transaction()?;

    // 2. color 分面停用（'deprecated' 语义已在 V13 收敛到 'inactive'）
    tx.execute(
        "UPDATE tag_facets SET status = 'inactive', updated_at = ?1 WHERE key = 'color'",
        rusqlite::params![now],
    )?;

    // 3. settings JSON（camelCase）一次读-改-写：
    //    - color: enabledForAi=false + visibleInWorkbench=false；
    //    - style: hint 追加「不包含颜色」——hint 是 settings JSON 的字段（settings.rs:14），
    //      tag_facets 表里从来没有这一列，写表会 no such column（FX-01）。
    if let Some(raw) = tx
        .query_row(
            "SELECT value FROM settings WHERE key = 'app_settings'",
            [],
            |r| r.get::<_, Option<String>>(0),
        )
        .optional()?
        .flatten()
    {
        if let Ok(mut v) = serde_json::from_str::<serde_json::Value>(&raw) {
            let mut changed = false;
            if let Some(arr) = v.get_mut("aiFacetConfigs").and_then(|c| c.as_array_mut()) {
                for cfg in arr.iter_mut() {
                    let key = cfg.get("facetKey").and_then(|k| k.as_str()).unwrap_or("");
                    match key {
                        "color" => {
                            if let Some(o) = cfg.as_object_mut() {
                                o.insert("enabledForAi".into(), serde_json::Value::Bool(false));
                                o.insert("visibleInWorkbench".into(), serde_json::Value::Bool(false));
                                changed = true;
                            }
                        }
                        "style" => {
                            let old = cfg.get("hint").and_then(|h| h.as_str()).unwrap_or("");
                            if !old.contains("不包含颜色") {
                                let next = if old.trim().is_empty() {
                                    "风格描述不包含颜色（颜色由算法主色呈现）".to_string()
                                } else {
                                    format!("{old}。风格描述不包含颜色（颜色由算法主色呈现）")
                                };
                                if let Some(o) = cfg.as_object_mut() {
                                    o.insert("hint".into(), serde_json::Value::String(next));
                                    changed = true;
                                }
                            }
                        }
                        _ => {}
                    }
                }
            }
            if changed {
                if let Ok(s) = serde_json::to_string(&v) {
                    tx.execute(
                        "UPDATE settings SET value = ?1 WHERE key = 'app_settings'",
                        [&s],
                    )?;
                }
            }
        }
    }
    tx.commit()?;
    Ok(())
}
```

需要在 `migrations.rs` 顶部确认已 `use rusqlite::OptionalExtension;`（若无则加——`query_row` 在无 `app_settings` 行时会返回 `QueryReturnedNoRows`，原代码用 `if let Ok(raw)` 吞掉了这个错误，语义上能跑但不清晰；换成 `.optional()?` 更直白）。

### 6.3 为什么不需要"数据修复脚本"

生产库现在是 `user_version = 15` + 6 列已加 + `color` 已 inactive。修好这一句后：

- `migrate()` 从 `version < 16` 重新进 `migrate_v16`；
- 第 1 步 `add_column_if_missing` 见列已存在，跳过；索引 `IF NOT EXISTS`，跳过；

## 8. FX-03 + FX-04【P0】极端像素预筛：测试矛盾与无回退

### 8.1 现状

`palette.rs:50` 的预筛：

```rust

```

- 纯黑 `(0,0,0)`：lum=0、sat=0 → 丢；
- 纯白 `(255,255,255)`：lum=1、sat=0 → 丢；
- 于是 `half_black_half_white_yields_two_clusters`（`palette.rs:225-240`）的图**所有像素被丢光**，`compute_palette` 返回空 vec，`assert!(!p.is_empty())` 必失败。同文件 `all_black_returns_empty_not_panic`（`:243`）反而确认了"全黑 → 空"是有意语义。两个用例互相矛盾。

更要紧的是**没有回退**（FX-04）：

| 真实场景 | 当前结果 |
|---|---|
| 黑白摄影（全图低饱和） | 大部分像素被丢 → 色板为空或只剩零星噪点色 |
| 大面积过曝天空（`lum>0.96 && sat<0.05`） | 天空整体消失 → 主色偏向地面，与观感不符 |
| 夜景（大面积近黑） | 暗部整体消失 → 主色偏向零星灯光 |

这三种都会直接毁掉《第二轮指导书》§14.13 的"抽查 10 张观感一致"验收。

### 8.2 修改方案（FX-04）

**分层预筛 + 有条件回退**。原则：预筛的目的是"别让黑边/白底吃掉主色"，不是"删掉暗部与高光"。所以只有当预筛**没有把图变成空/近空**时才生效。

```rust
/// 极端像素预筛的保留下限：过筛后样本少于原样本的这个比例，说明这张图本身
/// 就以极端亮度为主体（黑白摄影 / 夜景 / 大面积过曝），此时预筛在删主体而不是删边框，
/// 必须回退用全样本 —— 黑白照片的"主色"就是黑/白/灰，这是正确答案而不是缺陷。
/// 取 0.35 而不是 0.1：0.1 挡不住"60% 过曝天空 + 40% 正常曝光"这类真实构图。
const PRESCREEN_KEEP_MIN: f32 = 0.35;

pub fn compute_palette(img: &DynamicImage) -> Vec<PaletteEntry> {
    let rgba = img.to_rgba8();
    let total_px = rgba.pixels().len();
    if total_px == 0 {
        return Vec::new();
    }
    let mut all: Vec<[u8; 3]> = Vec::with_capacity(total_px);
    let mut kept: Vec<[u8; 3]> = Vec::with_capacity(total_px);
    for px in rgba.pixels() {
        let rgb = [px[0], px[1], px[2]];
        all.push(rgb);
        let r = px[0] as f32 / 255.0;
        let g = px[1] as f32 / 255.0;
        let b = px[2] as f32 / 255.0;
        let lum = 0.2126 * r + 0.7152 * g + 0.0722 * b;
        let maxc = r.max(g).max(b);
        let minc = r.min(g).min(b);
        let sat = if maxc == 0.0 { 0.0 } else { (maxc - minc) / maxc };
        if (lum < 0.02 && sat < 0.5) || (lum > 0.96 && sat < 0.05) {
            continue;
        }
        kept.push(rgb);
    }
    let rgb_samples = if (kept.len() as f32) < (total_px as f32 * PRESCREEN_KEEP_MIN) {
        all
    } else {
        kept
    };
    if rgb_samples.is_empty() {
        return Vec::new();
    }
    // …以下不变（sRGB→Lab / k-means / 聚合 / 排序 / 合并 / 输出）…
}
```

同时删除现有的 `discarded` 计数与 `let _ = discarded;`（`palette.rs:39,51,59`）——它从来没被用过。

**语义变化必须记录在提交说明里**：全黑图不再返回空色板，而是返回单簇黑色（`#000000`，ratio≈1.0）。这是**更正确**的行为（黑图的主色就是黑），但它会让 `all_black_returns_empty_not_panic` 的断言反转。

## 10. FX-05【P0】读取链路缺 6 列 + palette DTO

### 10.1 现状

### 10.2 修改方案

**关键设计决策：`palette_json` 不直接暴露给前端。** `Asset` 上派生的 `#[serde(rename_all = "camelCase")]` 会把 `palette_json: Option<String>` 序列化成 `paletteJson`（一个 JSON 字符串），而前端 `src/types/asset.ts:49` 期望的是 `palette: PaletteSegmentDto[]`（已解析的数组）。**在 Rust 侧解析，不要让前端 `JSON.parse`**——259 张 × 8 段的解析成本要么在 Rust 里一次（零成本），要么在渲染路径上每帧一次。

```rust
/// FB2-08：色板单段（与前端 PaletteSegmentDto 同形）。
/// palette_json 在 from_row 里解析成这个结构，前端不做 JSON.parse。
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct PaletteSegmentDto {
    pub hex: String,
    pub r: u8,
    pub g: u8,
    pub b: u8,
    pub ratio: f32,
}
```

`Asset` 追加四个字段（**注意不是六个**）：

```rust

    // dominant_* 是索引列，供超级搜索按颜色筛选。
    #[serde(default)]
    pub palette: Option<Vec<PaletteSegmentDto>>,
    pub dominant_hue: Option<i64>,
    pub dominant_sat: Option<i64>,
    pub dominant_lum: Option<i64>,
```

`palette_version` / `palette_scanned_at` **不进 `Asset`**——前端没有任何消费方（`src/types/asset.ts` 也没有），加了就是无用负载。`palette_version` 的用途是"换算法时批量识别需重算的行"，那是 SQL 层的事（`WHERE palette_version < N`），不需要走 DTO。

`COLUMNS` 追加 4 列（顺序必须与 `from_row` 索引一致）：

```rust

        tags: Vec::new(),
```

后果：
1. 所有无缩略图的视频，`dominant_hue` 全部落在 60（或 210），**"按颜色搜索"会把一堆无关视频搜出来**；
2. 这些行的 `palette_json` 非空 → `missing` scope 认为它们已算过，**永远不会被重算**（即使用户后来装了 ffmpeg）；
3. 色条上显示一条与素材毫无关系的灰白+蓝色带。

这是**数据污染**，比"算不出来"严重：算不出来是安静缺失，算错了是主动误导。

## 13. FX-08【P1】`imaging::acquire()` 嵌套双持 permit

## 15. FX-12【P2】两条回填命令共用取消标志

### 15.1 现状

`state.rs:25` 只有一个 `media_refill_cancel`。`rescan_asset_metadata`（`media_cmd.rs:40-41`）与 `rescan_asset_palette`（`media_cmd.rs:84-85`）都 `Arc::clone` 它并 `store(false)`。后果：

- A 跑着，用户启动 B → B 的 `store(false)` 把 A 的取消能力复位（用户点了取消也停不下来）；
- 用户点"取消元数据回填" → 正在跑的色板回算一起被取消。

### 15.2 修改方案（选互斥，不选双标志）

**用一个"是否有回填在跑"的互斥闸，而不是拆成两个取消标志。** 理由：两个长任务同时跑会争抢 4 个解码许可与 DB 锁，本来就不该并发；拆标志是允许并发，互斥是禁止并发——后者更符合当前架构，改动也更小。

`state.rs` 追加：

```rust
    /// 回填类长任务互斥闸（元数据回填 / 色板回算共用一条，同一时刻只允许一个）。
    /// 不拆成两个取消标志：两者都吃解码许可与 DB 锁，并发只会互相拖慢（FX-12）。
    pub refill_running: Arc<AtomicBool>,
```

`media_cmd.rs` 两条命令开头统一加：

```rust
    // FX-12：compare_exchange 抢闸 —— 已有回填在跑时明确拒绝，不静默复位对方的取消标志
    if state
        .refill_running
        .compare_exchange(false, true, Ordering::AcqRel, Ordering::Acquire)
        .is_err()
    {
        return Err(AppError::msg(
            "已有回填任务进行中（媒体元数据回填或色板回算），请等待完成或先取消",
        ));
    }
```

**释放必须覆盖所有退出路径**，包括 `spawn_blocking` panic 与 `?` 提前返回。用 RAII guard（不要靠手写 `store(false)`——一定会漏一条路径）：

```rust
/// 回填闸 RAII：Drop 时释放，保证 panic / 提前 return 都不会永久占闸。
struct RefillGuard(Arc<AtomicBool>);
impl Drop for RefillGuard {
    fn drop(&mut self) {
        self.0.store(false, Ordering::Release);
    }
}
```

抢到闸后立刻 `let _guard = RefillGuard(Arc::clone(&state.refill_running));`，并把它 move 进 `spawn_blocking` 的闭包（否则 guard 在 `await` 前就 drop 了，闸白抢）。

`cancel_media_refill`（`media_cmd.rs:111-115`）**不改**：它取消"当前那个"回填，因为同时只可能有一个，语义自然正确。命令名与前端 `cancelMediaRefill` 也不用改。

### 15.3 测试

Tauri command 的 `State` 不便单测，**改为测 guard 语义**：

```rust

#[test]
fn refill_gate_is_exclusive_and_self_releasing() {
    let gate = Arc::new(AtomicBool::new(false));
    {
        assert!(gate.compare_exchange(false, true, Ordering::AcqRel, Ordering::Acquire).is_ok());
        let _g = RefillGuard(Arc::clone(&gate));
        assert!(gate.compare_exchange(false, true, Ordering::AcqRel, Ordering::Acquire).is_err(),
                "第二个任务必须抢不到闸");
        assert!(gate.load(Ordering::Acquire), "抢闸失败不得复位闸");

    assert!(!gate.load(Ordering::Acquire), "guard drop 后闸应释放");
}
```

### 15.4 验收标准

- 启动元数据回填，立刻点色板回算 → 前端显示「已有回填任务进行中…」，不是静默无反应。
- 回算过程中强制关闭应用再启动 → 闸不残留（`AtomicBool` 在内存里，重启天然清零）。
- 取消按钮对正在跑的那个任务有效。

### 17.2 条件构造（关键算法）

点击主色段拿到 `PaletteSegment { hue, sat, lum }`（前端现算，`ColorStrip.tsx:20-27`）。构造两条 `MetadataFilter`：

```ts
/** FB2-08（§14.9）：由主色段构造"同色系"检索条件。
 *  hue ±15° 是色相环上"同色系"的经验窗口（12 段色名映射每段约 30°，取半段）。
 *  跨 0° 时故意让 min > max —— 后端 compile_number 对 dominant_hue 的 min>max
 *  编译成双区间 OR（search_query.rs:363），这是环形量的正确表达，不是参数错误。
 *  sat 窗口宽得多（±25）：同色系允许饱和度差异，卡太紧会漏掉大量素材。
 *  lum 不加约束 —— 深蓝与浅蓝都是"蓝色系"。 */
const HUE_WINDOW = 15;
const SAT_WINDOW = 25;

export function dominantFiltersFor(seg: { hue: number; sat: number }): MetadataFilter[] {
  const lo = ((seg.hue - HUE_WINDOW) % 360 + 360) % 360;
  const hi = (seg.hue + HUE_WINDOW) % 360;
  const filters: MetadataFilter[] = [
    { key: "dominant_hue", op: "between", min: lo, max: hi },
  ];
  // 低饱和（灰阶）主色：hue 无意义，只按饱和度筛，否则会搜出一堆无关色相
  if (seg.sat < 10) {
    return [{ key: "dominant_sat", op: "lte", value: 10 }];
  }
  filters.push({
    key: "dominant_sat",
    op: "between",
    min: Math.max(0, seg.sat - SAT_WINDOW),
    max: Math.min(100, seg.sat + SAT_WINDOW),
  });
  return filters;
}
```

放 `src/utils/dominantFilter.ts`，**必须配单测**（《第二轮指导书》§4.2：纯函数抽出并单测）。用例：

| 输入 | 期望 |
|---|---|
| `{hue: 210, sat: 80}` | `dominant_hue between 195~225` + `dominant_sat between 55~100`（105 被钳到 100） |
| `{hue: 5, sat: 80}` | `dominant_hue between 350~20`（**min > max**，交给后端双区间 OR） |
| `{hue: 355, sat: 80}` | `dominant_hue between 340~10`（min > max） |
| `{hue: 60, sat: 3}` | 只有一条 `dominant_sat lte 10`，**不含 hue 条件** |
| `{hue: 210, sat: 20}` | `dominant_sat between 0~45`（下界钳到 0） |

### 17.3 写入筛选器

已核实 store API（`src/stores/libraryStore.ts:103-127`）：**只有 `setFilter(patch: Partial<LibraryFilter>)` 一个入口**，它内部会做"值未变则 no-op"（F18 修复）、清空选中（B09）、并触发 `refresh()`。**沿用它，不要新增 setter。**

参照现有分面点击的写法（`MetadataPanel.tsx:90`）：

```ts
  // LibraryPage（或 SuperSearchPage）里提供
  const { filter, setFilter } = useLibraryStore(
    useShallow((s) => ({ filter: s.filter, setFilter: s.setFilter })),
  );
  const onSearchDominant = useCallback((seg: PaletteSegment) => {
    const next = dominantFiltersFor(seg);
    const keys = new Set(next.map((f) => f.key));
    // 同 key 的旧条件必须替换而不是叠加：两个不相交的 hue 区间 AND 起来恒为空集。
    // untaggedOnly / trashOnly 一并复位，与 MetadataPanel.tsx:90 的分面点击语义一致。
    setFilter({
      metadataFilters: [...(filter.metadataFilters ?? []).filter((f) => !keys.has(f.key)), ...next],
      untaggedOnly: false,
      trashOnly: false,
    });

```

**注意 `setFilter` 的 no-op 判断用 `JSON.stringify` 比对 `metadataFilters`**（`libraryStore.ts:116`）。所以连点**同一个**主色段两次不会重复刷新——这是想要的行为，不要绕过。

## 19. FX-14【P1】`dominant_*` 索引不被选用

### 19.1 现状与实测证据

V16 建了三个单列索引（`migrations.rs:919-923`）。但**真实生产库没有 `sqlite_stat1`**（实测 `SELECT COUNT(*) FROM sqlite_master WHERE name='sqlite_stat1'` = 0，全仓库 grep 无 `ANALYZE`）。无统计信息时 SQLite 的代价模型偏向已知选择性高的索引，实测 EXPLAIN：

```text
【无统计信息】
  COUNT(*) … dominant_hue >= 200 AND <= 250
    → SEARCH a USING INDEX idx_assets_deleted (deleted_at=?)      ← 没用色相索引
  分页查询（含 ORDER BY created_at DESC LIMIT 200）
    → SEARCH a USING INDEX idx_assets_deleted + USE TEMP B-TREE FOR ORDER BY

【PRAGMA optimize / ANALYZE 之后】
  COUNT(*) → SEARCH a USING INDEX idx_assets_dominant_hue (dominant_hue>? AND dominant_hue<?)   ✅
  跨 0° 的 OR 形式（无 ORDER BY / COUNT）
    → MULTI-INDEX OR
        INDEX 1: SEARCH a USING INDEX idx_assets_dominant_hue (dominant_hue>?)
        INDEX 2: SEARCH a USING INDEX idx_assets_dominant_hue (dominant_hue<?)   ✅
```

所以《第二轮指导书》§14.13 的验收项「`EXPLAIN QUERY PLAN` 确认命中 `idx_assets_dominant_hue`」在当前代码上**过不了**——不是索引没建，是优化器不选。

另外实测：分页查询即使有统计信息，`ORDER BY a.created_at DESC` 仍会 `USE TEMP B-TREE FOR ORDER BY`；加复合索引 `(dominant_hue, created_at DESC)` 只帮到 COUNT 查询，帮不到分页排序（因为 hue 是范围条件，范围列之后的排序列用不上）。**所以不要加复合索引**——259 项规模下 temp b-tree 成本可忽略，加了是纯负债。

### 19.2 修改方案

**启动时跑一次 `PRAGMA optimize`，放在非关键路径的后台维护里。**

`lib.rs` 的 `setup` 闭包里已有 `spawn_maintenance` 范式（`lib.rs:84`「preset-tags-cleanup」、`:97`「thumbnail-lru-cleanup」）。追加第三个：

```rust
            // FX-14：SQLite 无统计信息时不会选用 dominant_* 等窄索引（实测：按主色筛选会退化成
            // idx_assets_deleted 全扫）。PRAGMA optimize 增量更新 sqlite_stat1，成本与库规模成正比、
            // 259 项量级是毫秒级。放后台维护线程：它不在启动关键路径上（§5.2）。
            let opt_db = std::sync::Arc::clone(&state.db);
            spawn_maintenance("sqlite-optimize", move || {
                if let Ok(c) = opt_db.lock().map_err(|_| AppError::msg("数据库锁中毒")) {
                    if let Err(e) = c.pragma_update(None, "optimize", ()) {
                        tracing::warn!("PRAGMA optimize 失败（不影响功能，仅查询计划可能次优）: {e}");
                    }
                }
            });
```

`pragma_update(None, "optimize", ())` 的签名以 rusqlite 实际 API 为准；若不接受 unit 值，用 `c.execute_batch("PRAGMA optimize;")`。

**为什么不在 `migrate_v16` 里 `ANALYZE`**：① 不得改已提交迁移的语义（§0.2 第 3 条）；② `ANALYZE` 全表扫描，放迁移里会拖慢首次启动；③ 统计信息会随数据增长过期，一次性 ANALYZE 解决不了长期问题，`PRAGMA optimize` 每次启动增量更新才是正解（SQLite 官方推荐用法）。

### 19.3 顺带：把验收方法写死

验收「命中索引」时**必须先确认库里有统计信息**，否则测的是无统计场景：

```bash
sqlite3 "$APPDATA/bagertea_ai_media_v2/library.db" <<'SQL'
SELECT COUNT(*) FROM sqlite_master WHERE name='sqlite_stat1';   -- 期望 1
EXPLAIN QUERY PLAN
SELECT COUNT(*) FROM assets a
 WHERE a.deleted_at IS NULL
   AND (a.dominant_hue >= 200 AND a.dominant_hue <= 250 AND a.dominant_hue IS NOT NULL);
-- 期望输出含 idx_assets_dominant_hue
SQL
```

注意 EXPLAIN 只反映**当前库的数据分布**：如果全库 `dominant_hue` 都是 NULL（还没回算），优化器同样可能不选索引。**先回算再验收。**

### 19.4 验收标准

- 启动后 `sqlite_stat1` 存在。
- 回算完成后，上面的 EXPLAIN 输出含 `idx_assets_dominant_hue`。
- 跨 0° 的 OR 查询 EXPLAIN 含 `MULTI-INDEX OR` 且两条 INDEX 分支都用 `idx_assets_dominant_hue`。
- 启动耗时无可感增加（`markStartup` 的首屏打点对比修复前后，记录进阶段报告）。

## 20. FX-11【P1】入库链路不算色板

### 20.1 现状与取舍

`compute_palette` 只被 `media_refill.rs:252`（手动回算）调用。`importer.rs` / `thumbnail.rs` 全文无引用。《第二轮指导书》§14.7 说"入库时用内存中的 placeholder 图像顺带算，几乎零额外成本"。

**但那个设计有个前提没成立**：`importer.rs:667-689` 的 placeholder 生成是 `par_iter()` 并行块，返回的是 `(id, PathBuf)`——**图像没有留在内存里**，`extract_placeholder`（`thumbnail.rs:109`）内部把它 `save_with_format` 落盘后就丢了。要在这里拿到图像，得改 `extract_placeholder` 的返回类型（影响 3 个调用点）或重新解码一次。

**本轮定案：不改导入热路径，改为"入库完成后自动跑一次 missing scope 回算"。** 理由：

- 回算走的是 placeholder 文件（256px WebP），解码成本远低于原图，259 项实测秒级；
- 导入热路径已经是全流程最脆的一段（B14/B15 的取消语义、事务边界），不值得为色板去动它；
- `missing` scope 天然幂等，重复触发无害。

### 20.2 实现

在 `importer.rs` 的 `emit_done(&task_id, &result, Some("入库完成".into()), &progress)` 之前**不做任何事**——入库函数保持纯净。改在**命令层**（`import_cmd.rs`）导入成功返回后触发：

```rust

    // 不塞进 importer 热路径：placeholder 生成是 par_iter 并行块，图像不驻留内存，
    // 要在那里取图得改 extract_placeholder 签名（影响 3 个调用点）。走 missing scope
    // 读 placeholder 文件重算，256px WebP 解码成本可忽略，且天然幂等（FX-11）。
```

## 21. FX-15【P2】`merge_clusters` 合并不彻底 + 双重舍入

### 21.1 两个问题

`palette.rs:170-189`：

```rust
    for c in clusters.drain(..) {
        let mut absorbed = false;
        for m in merged.iter_mut() {
            if delta_(m.l, m.a, m.b_v, c.l, c.a, c.b_v) < EPSILON && m.ratio >= c.ratio {
                m.ratio += c.ratio;
                m.ratio = (m.ratio * 100.0).round() / 100.0;   // ← 问题 2：过程中舍入
                absorbed = true;
                break;                                          // ← 问题 1：只吸一次，不再传播
            }
        }
        if !absorbed { merged.push(c); }
    }
```

**问题 1（合并不彻底）**：`break` 后不再检查 `merged` 内部是否仍有互相 ΔE < 6 的簇。反例：A(ΔE 到 B = 7)、B、C，其中 C 到 A 是 5、C 到 B 是 4。C 遍历 `merged` 时先遇到 A（距离 5 < 6）就被 A 吸收，B 与 A 距离 7 仍分立——但 C 本该把 A、B 桥接起来。结果色条上 A 与 B 相邻且肉眼几乎无差别（ΔE 7 在 Lab 里是"仔细看才有差别"）。这正是《第二轮指导书》§14.13 要排除的"单色照片返回 6 个几乎相同的色块"。

**问题 2（双重舍入）**：合并时舍入到两位小数，最终输出（`palette.rs:139`）又舍一次。多次合并的累积误差会让 `ratio` 总和明显偏离 1，色条宽度失真（`ColorStrip.tsx:70` 用 `total = sum(ratio)` 归一，所以不会溢出，但各段相对宽度会漂）。

`m.ratio >= c.ratio` 这个条件确实恒真（输入已降序，`m.ratio` 只增），**可以删**——上一份报告这点判断正确。

### 21.2 修改方案

改为**迭代合并到不动点**（最多 K 轮，K=6 时最多 6 轮，成本可忽略），且**过程中不舍入**：

```rust
/// 贪心合并到不动点：每轮把 ΔE < EPSILON 的最近两簇合成一簇（占比相加，代表色取占比大的那个），
/// 直到没有可合并对。单轮 break 式合并（旧实现）会漏掉"C 能桥接 A 与 B"的情况，
/// 结果色条上留下两块肉眼无差别的分段（FX-15）。
/// 舍入只在最终输出做一次（compute_palette 第 7 步）—— 过程中舍入会累积误差，
/// 让 ratio 总和偏离 1、色条宽度失真。
fn merge_clusters(mut clusters: Vec<Cluster>) -> Vec<Cluster> {
    loop {
        // 找当前最近的一对（ΔE 最小且 < EPSILON）
        let mut best: Option<(usize, usize, f32)> = None;
        for i in 0..clusters.len() {
            for j in (i + 1)..clusters.len() {
                let d = delta_(
                    clusters[i].l, clusters[i].a, clusters[i].b_v,
                    clusters[j].l, clusters[j].a, clusters[j].b_v,
                );
                if d < EPSILON && best.map(|(_, _, bd)| d < bd).unwrap_or(true) {
                    best = Some((i, j, d));
                }
            }
        }
        let Some((i, j, _)) = best else { break };
        // 保留占比大的那个作为代表色（i < j 且已降序，故 i 的占比 ≥ j）
        let victim = clusters.remove(j);
        clusters[i].ratio += victim.ratio;
        clusters.sort_by(|a, b| b.ratio.partial_cmp(&a.ratio).unwrap_or(std::cmp::Ordering::Equal));
    }
    clusters
}
```

`O(K³)` 最坏 6³=216 次距离计算，可忽略。**不要**为此引入并查集或层次聚类库。

> 注意：合并后 `clusters[i]` 的 Lab 坐标**不更新**（仍是原代表色）。这是有意的——代表色应该是某个真实簇的中心，而不是两个簇的加权中点（后者可能落在两簇之间的"没有像素"的颜色上）。在代码里留这条 WHY 注释。
