## 3. UI 设计规格总纲（本轮所有界面必须遵守）

本节把 `docs/UI_DESIGN_SYSTEM.md` 的原则**落成可执行的具体值**。原则与本节冲突时以设计系统原文为准，本节只做细化，不做覆盖。

### 3.1 可用的主题变量（唯一颜色来源）

来自 `src/styles/theme.css`。业务组件**只能**写 `var(--color-*)`，禁止硬编码任何色值（`#fff`、`gray-400`、`bg-black/50` 除外——半透明遮罩允许用 `black/x` / `white/x`，见 §3.6）。

| `--color-surface-raised` | `#ffffff` | 输入框、弹层、分段控件选中片 |

### 3.2 可复用的基础类（来自 `src/styles/index.css`）

| 类 | 用途 | 本轮用在哪 |
|---|---|---|
| `.ui-section-title` | 区块小标题（10px / 600 / letter-spacing .12em / uppercase） | ViewerTagBar 标题、设置页新小节标题 |
| `.ui-control` | 输入框/下拉框基础态（含 hover / focus ring） | 所有新增 select、number input |
| `.ui-nav-item` + `data-active` | 侧栏导航项（含左侧 2px 状态线） | 不新增，仅参考 |
| `.startup-indeterminate` | 不定进度条 | 色板回填进度可复用 |

**新增 CSS 类的门槛**：只有当同一视觉模式在 ≥3 处复用时才允许往 `index.css` 加类。本轮**只允许新增一个**：`.ui-colorstrip`（见 §12.4）。其余全部用 Tailwind 原子类 + 主题变量。

### 3.3 间距、尺寸、圆角（硬性数值）

- 页面主要区块间距 `16px`（`gap-4`）；区块内部 `12px`（`gap-3`）。
- 紧凑列表行高 `32~36px`；工具条高度沿用现状（`h-10` / `h-11`）。
- 侧栏宽度：素材库 224px、打标控制栏 252px、**Viewer 左属性栏 280px（`ViewerShell.tsx:24` 现状，不改）**。
- 卡片圆角 `rounded-md`（= `--radius-item` 量级），控件圆角 `rounded-[var(--radius-control)]`。
- **不使用胶囊形主按钮**；标签 chip、状态角标除外。
- 阴影只用于悬浮操作条与弹层；普通区块用 `border-b border-[var(--color-border)]` 分隔。

### 3.4 字体与字号

| 场景 | 字号 | 字重 |
|---|---|---|
| 页面正文 | `text-[13px]`（body 默认） | 400 |
| 区块标题 / 选中项 | `text-xs`~`text-sm` | 600 |
| 辅助信息（计数、时长、尺寸） | `text-[11px]` | 400 |
| 极小角标（格式徽标、色条 tooltip 数值） | `text-[10px]` | 400 |

- 小号文字必须用 `--color-text-secondary` 或更高对比；`--color-text-tertiary` 只给日期/数量/占位。
- **不要给新元素加 `antialiased`**（WebView2 下小号中文会发糊，见设计系统"字体与清晰度"）。

### 3.5 动效规范

- 只动 `transform` / `opacity`，**禁止动画 `height` / `width` / `top` / `left`**（会触发布局重排，这正是 FB2-06 闪烁的成因之一）。
- 时长：微交互 `120~160ms`，区块进出 `200ms`，`ease-out`。现有基准：`MediaViewport.tsx:309` 的 `transform 120ms ease-out`、`Thumbnail.tsx:108` 的 `duration-300` 淡入、`ViewerPage.tsx:177` 的 `duration-200`。
- 拖拽 / 平移进行中必须 `transition: none`（`MediaViewport.tsx:309` 已是此模式，新增缩放沿用）。
- 无障碍：不做超过 400ms 的装饰动画；不用闪烁/抖动表达状态。

### 3.6 半透明与叠层

- 媒体上方的文字/角标允许 `bg-black/55`~`bg-black/70` + `text-white`（现状：`AssetCard.tsx:75,82`、`PendingList.tsx:221`）。这是唯一允许绕过主题变量的场景，因为底下是任意用户图片。
- 卡片内描边统一用 `ring-1 ring-inset`：浅色主题 `ring-black/5`，深色主题 `ring-white/5`。**实现方式**：`ring-black/5 dark:ring-white/5` 不可用（本项目用 `data-theme` 而非 Tailwind dark 类），改为在 `theme.css` 新增变量：


- 遮罩层 z 轴：卡片内媒体层 `absolute inset-0`（无 z-index）→ 角标（无 z-index，靠 DOM 顺序）→ 页面级弹层 `z-20` → 右键菜单（`ContextMenu` 自管）。**不要新增 z-index 层级**。

## 4. 代码规范（本轮强制）

### 4.1 分层

```text
React 页面/组件 → stores / api → Tauri commands → services → db / filesystem / external process
```

- 页面只编排；交互细节沉到 `components/`；纯逻辑抽 `utils/` 或 `hooks/` 并单测。

- 改 Rust 结构体字段 → **必须同步** `src/types/`。

### 4.2 TypeScript / React

- 所有 props、API 响应、store 状态显式类型化。`any` 禁用；确实需要时写 `unknown` + 类型守卫。
- 异步错误捕获用 `unknown`，转人类可读消息后 `set({ error })` 并在页面展示。
- **原生事件监听规范**（本轮重点，历史坑）：需要 `preventDefault()` 的滚轮交互必须用原生 `addEventListener("wheel", fn, { passive: false })`。React 的 `onWheel` 在 React 19 下是 passive，`preventDefault()` 无效。参照 `MediaViewport.tsx:147-160` 的既有正确写法。

## 5. FB2-03 Step 1：入库页悬停视频完全播不出（asset 协议未放行）

### 5.1 根因（已定实，改动约 5 行）

**这是"悬停自动播放失效"的直接原因，且与前端逻辑无关。**

静态配置是空白名单：

```json
// src-tauri/tauri.conf.json（app.security.assetProtocol）
"assetProtocol": { "enable": true, "scope": [] }
```

运行期只放行三个内部目录（`src-tauri/src/lib.rs:58-80`）：`thumbnails/`、`previews/`、`proxies/`。注释 `lib.rs:56-57` 明确写了收敛意图："只放行 thumbnails/ + previews/ 子目录，不放行 data_dir 根（含 library.db）；素材原文件由 list/get 命令逐路径放行"。

素材**原文件**靠命令层逐条放行：

```rust
// src-tauri/src/commands/assets_cmd.rs:19-21
fn allow_asset(app: &tauri::AppHandle, path: &str) {
    let _ = app.asset_protocol_scope().allow_file(Path::new(path));
}
```

调用点共 4 处：`assets_cmd.rs:41`（`list_assets`）、`:53`（`dedup_scan`）、`:79`（get 详情）、`:226`（urls）。

而入库清单走的是 `inspect_import`，**它既不接 `AppHandle` 也没有调 `allow_asset`**：

```rust
// src-tauri/src/commands/import_cmd.rs:55-60
#[tauri::command]
pub async fn inspect_import(paths: Vec<String>) -> AppResult<importer::ImportPlan> {
    tauri::async_runtime::spawn_blocking(move || Ok(importer::inspect_paths(&paths)))
        .await
        .map_err(|e| AppError::msg(format!("扫描线程异常: {e}")))?
}
```

于是前端这一行必然被拒：

```tsx
// src/components/import/PendingList.tsx:172-180
<video ref={videoRef} src={convertFileSrc(item.path)} muted playsInline preload="metadata" autoPlay ... />
```

`asset://localhost/<原文件路径>` → 403 → `<video>` 触发 `error` → `PendingList.tsx:132-135` `setVidError(true)` → 退回封面并显示「无法播放 · 双击打开」。**封面能显示**是因为它来自 `previews/`（在白名单内，`api/preview.ts` 走 `get_preview`），所以症状看起来"只是不播、没报错"。

**交叉验证**：Viewer 里播视频是通的（`ViewerPage.tsx:62,129` 同样用 `convertFileSrc(current.filePath)`），因为那些素材来自 `list_assets`，路径已逐条放行。这个对比确认根因就是放行差异，不是编解码问题。

### 5.2 修改方案

`inspect_import` 改为接收 `AppHandle`，对 `plan.items` 逐条放行，**复用与 `list_assets` 完全相同的安全模型**。

```rust
// src-tauri/src/commands/import_cmd.rs
// 新增：与 assets_cmd::allow_asset 同一语义的本地放行函数
// （不跨模块复用私有 fn；两处各自一行，比导出一个 pub fn 更内聚）
fn allow_asset(app: &tauri::AppHandle, path: &str) {
    let _ = app.asset_protocol_scope().allow_file(std::path::Path::new(path));
}

/// 扫描路径生成待入库清单统计（两段式入库，不落库）
/// FB2-03：对清单内每个原文件逐路径放行 asset 协议，使入库页可在卡片内播放视频。
/// 安全边界与 list_assets 一致——只放行用户主动选择/拖入的路径，只读，不放宽 scope、不用 allow_directory。
#[tauri::command]
pub async fn inspect_import(
    app: AppHandle,
    paths: Vec<String>,
) -> AppResult<importer::ImportPlan> {
    let plan = tauri::async_runtime::spawn_blocking(move || importer::inspect_paths(&paths))
        .await
        .map_err(|e| AppError::msg(format!("扫描线程异常: {e}")))?;
    for item in &plan.items {
        allow_asset(&app, &item.path);
    }
    Ok(plan)
}
```

需要 `use tauri::AppHandle;`（`import_cmd.rs:3` 已 `use tauri::{AppHandle, Emitter, State};`，无需改）。
需要 `use tauri::Manager;` 或 `tauri::scope` 相关 trait 以调用 `asset_protocol_scope()`——照 `assets_cmd.rs` 顶部的 use 清单对齐。

前端 `src/api/import.ts` 的 `inspectImport` 调用**不需要改**：Tauri v2 的 `AppHandle` 参数由框架注入，不出现在 JS 参数里。`lib.rs:180` 的 `invoke_handler` 注册也不需要改。

### 5.3 安全评估（必须写进 PR 描述）

| 项 | 结论 |
|---|---|
| 放行范围 | 仅用户主动通过文件对话框选择或拖入的路径 |

## 6. FB2-04 + FB2-05：Viewer 高度链断裂（空白 + 图片越界，同一根因）

用户分两条提，**是同一个 CSS 高度链缺陷的两个表现**。本节先修根因（批次 1），标签区与全屏/缩放放批次 2（§10、§11）。

### 6.1 根因：舞台包裹层不是 flex 容器

```tsx
// src/components/viewer/ViewerShell.tsx:19-32（现状全文）
<div className="flex h-full min-h-0 flex-col bg-[var(--color-bg)]">
  {toolbar}
  <div className="flex min-h-0 flex-1">
    {sidebar && (
      <aside className="w-[280px] shrink-0 overflow-y-auto border-r border-[var(--color-border)] p-3">
        {sidebar}
      </aside>
    )}
    <div className="min-w-0 flex-1">{stage}</div>   {/* ← 第 28 行，问题在这里 */}
  </div>
  {filmstrip}
</div>
```

`ViewerShell.tsx:28` 这个包裹层**只有 `min-w-0 flex-1`，没有 `flex`、没有 `flex-col`、没有 `min-h-0`**。它是块级容器，高度由内容决定。于是舞台上的约束双双失效：

```tsx
// src/components/viewer/MediaViewport.tsx:282-285（图片分支）
"relative flex min-h-0 min-w-0 flex-1 select-none items-center justify-center overflow-hidden bg-[var(--color-bg)]"
```

`flex-1` 与 `min-h-0` **在非 flex 父级下无效**，舞台高度 = 内容高度。两个后果：

**后果 A（= FB2-04，下方大片空白）**：内容比可用行高矮时，舞台按内容高度顶对齐，下方留出一整段空白横跨到胶片条之前。**这不是设计留白，是布局塌陷的残留。**

**后果 B（= FB2-05，图片越界错位）**：两个分支的尺寸约束全是**百分比**：

```tsx
// MediaViewport.tsx:271（视频分支）
<div className="flex max-h-[82%] max-w-[92%] items-center justify-center"
     style={{ maxHeight: `${STAGE_HEIGHT_PCT}%`, maxWidth: `${STAGE_WIDTH_PCT}%` }}>
// MediaViewport.tsx:306（图片分支）
className="max-h-full max-w-full object-contain select-none"
```

按 CSS 规范，`max-height` 的百分比在父级高度为 `auto` 时**解析为 `none`**（MDN《max-height》：包含块高度未显式指定且元素非绝对定位时，百分比按 none 处理）。所以纵向没有任何约束。图片只受 `max-w-full` 限制，被撑到舞台宽（约 1500px），3:2 的 RAW → 高约 1000px，超过可用行高 → 压住底部胶片条。

**视频"看起来对"是运气，不是约束生效。** 16:9 在 92% 宽度下算出约 750px 高 + 45px 控制条刚好塞得进。换 4:3 或竖屏视频同样越界。

> ⚠️ **必须同一提交落地的警告**：高度链修好的**那一刻**，`max-h-[82%]` / `max-w-[92%]` 会从 `none` 突然变成生效值（因为父级终于有确定高度了），产生一次过渡性布局跳变。所以「修高度链」与「废除 92%/82% 换 padding」**必须在同一个 commit 里**，不得分两次提交。

### 6.2 改动 1：修高度链（一行，全部的前提）

```tsx
// src/components/viewer/ViewerShell.tsx:28
- <div className="min-w-0 flex-1">{stage}</div>
+ <div className="flex min-h-0 min-w-0 flex-1 flex-col">{stage}</div>
```

右列变成纵向 flex 容器。此后 `flex-1` / `min-h-0` / 百分比高度全部生效。同时把 `ViewerShellProps` 的注释更新为三段结构（见 §10.1）。

### 6.3 改动 2：抽出 `StageFrame`，图片与视频共用

**目标**：用户明确要求"图片只允许在那个区域展示"、"把视频浏览的那个区域设置搬过来"。字面照做（把 92%/82% 抄到图片分支）**无效**——百分比在 auto 父级下仍解析为 none。正解是让两者共用同一个舞台容器。

新建 `src/components/viewer/StageFrame.tsx`：

```tsx
/**
 * StageFrame：Viewer 媒体舞台的唯一尺寸容器（FB2-04/05）。
 * 图片与视频共用同一容器，保证两者的可视区域、控制条位置像素级一致。
 * 用 padding 而非百分比约束——百分比 max-height 在父级 auto 时解析为 none（历史 bug），
 * 且 82% 这个数字与控制条实际高度无关，控制条高度变化时不会跟随。
 */
import type { ReactNode, Ref } from "react";
import clsx from "clsx";

interface StageFrameProps {
  children: ReactNode;
  stageRef?: Ref<HTMLDivElement>;
  className?: string;
  /** 交互事件（图片分支挂 pointer / contextmenu；视频分支不挂） */
  handlers?: React.DOMAttributes<HTMLDivElement>;
  style?: React.CSSProperties;
}

export default function StageFrame({ children, stageRef, className, handlers, style }: StageFrameProps) {
  return (
    <div
      ref={stageRef}
      data-media-stage
      data-testid="media-viewport"
      className={clsx(
        "relative flex min-h-0 min-w-0 flex-1 items-center justify-center overflow-hidden bg-[var(--color-bg)] p-4",
        className,
      )}
      style={style}
      {...handlers}
    >
      {children}
    </div>
  );
}
```

## 7. FB2-06：超级搜索折叠一直闪烁 + 删除「快速编辑条件」

### 7.1 根因：卸载 ↔ scrollHeight 的正反馈环

四步成环：

**① 详细条件面板是条件卸载，不是动画。**

```tsx
// src/pages/SuperSearchPage.tsx:133-140
{chrome === "expanded" && (
  <div className="px-4 pt-3">
    <div className="mx-auto max-w-5xl">
      <QueryBuilder />
    </div>
  </div>
)}
```

这与 hook 顶部注释的承诺直接矛盾——`useScrollDirection.ts:5` 写的是「只返回两态，由调用方决定动画（transform/opacity），本 hook 不触发布局重排」，而调用方实际做的是整块 DOM 卸载。`QueryBuilder` 无固定高度（`QueryBuilder.tsx:69` 是 `<section className="overflow-hidden rounded-md border …">`，高度由条件行数决定），实测约 120~200px。

**② 面板与虚拟化网格共用同一个滚动容器。**

```tsx
// src/pages/SuperSearchPage.tsx:105-110
<div ref={bindScroll} data-testid="super-search-scroll"
     className="min-h-0 flex-1 overflow-y-auto" onFocusCapture={forceExpand}>
// :143-152 —— 网格把这个容器当外部滚动源
<AssetGridView ... scrollElementRef={scrollRef} {...actions} />
```

**③ 卸载面板 → `scrollHeight` 减少 H → 浏览器把 `scrollTop` 向下钳制最多 H → 产生一次负 delta。**

**④ hook 把负 delta 判为"上滚"，累计 15px 后强制展开：**

```ts
// src/hooks/useScrollDirection.ts:38-47
const dir: "down" | "up" = delta < 0 ? "up" : "down";
if (dir !== lastDir.current) { lastDir.current = dir; moved.current = 0; }
moved.current += Math.abs(delta);
if (moved.current >= thresholdRef.current) {
  moved.current = 0;
  setState(dir === "down" ? "collapsed" : "expanded");
}
```

展开 → `scrollHeight` 增加 H → 下一次滚动又收起 → **无限振荡**。

> 机制精化（不影响结论，但实现时要理解）：面板重新展开时内容插在滚动容器顶部、`scrollTop` 数值不变、**不产生 scroll 事件**。所以振荡主要在**用户持续下滚时维持**：每次下滚 tick 触发「收起 → scrollHeight 骤减 → scrollTop 被钳制产生负 delta → 判为上滚 → 强制展开」。这与用户"一直闪烁"的描述吻合。

**两个叠加触发源：**

**叠加源 1 —— 跨页滚动状态串味。** `AssetGridView` 挂载时会强行写 `scrollTop`：

```tsx
// src/components/library/AssetGridView.tsx:66-72
useEffect(() => {
  const el = containerEl;
  const saved = useLibraryStore.getState().gridScrollTop;
  if (el && saved > 0) el.scrollTop = saved;
}, []);
```

`gridScrollTop` 定义在 `libraryStore.ts:79-80,195-196`，是**素材库页**的滚动量。超级搜索页复用了同一个字段与同一个网格组件（`SuperSearchPage.tsx:143-152`）→ 先在素材库滚到一半、再进超级搜索，网格一挂载就把共享滚动容器跳到别处，立刻触发方向判定。**这条即使不修闪烁也该修**——现在两个页面的滚动位置互相污染。

**叠加源 2 —— 点结果卡片就强制展开。**

```tsx
// src/pages/SuperSearchPage.tsx:109
onFocusCapture={forceExpand}
```

`AssetCard` 是可聚焦的（`AssetCard.tsx:60` `tabIndex={0}`），点任意一张结果都会把 focus 冒泡到容器 → 强制 `expanded` → 内容增高 → 视图跳动。

**hook 本身还缺两个常规护栏**：没有"顶部区域不收起"的最小 `scrollTop` 门槛（在 `scrollTop=20` 处收起摘要条毫无意义）；阈值上下对称（15/15），边界处天然抖动。

### 7.2 方案 A（必做）：可折叠区移出滚动容器

**从根上断掉反馈环。** 结构改为：

```text
现状                              目标
────────────────────────────      ────────────────────────────
[顶栏 h-10 固定]                  [顶栏 h-10 固定]
[滚动容器 overflow-y-auto]        [header 区（shrink-0，不滚动）]
  ├ sticky 摘要条                   ├ 摘要条（搜索框 + chips + 计数 + 展开/收起开关）
  ├ 条件面板（条件卸载）← 环         └ 详细条件面板（可折叠，动画 transform/opacity）
  ├ 虚拟化网格                     [滚动容器 overflow-y-auto flex-1]
  └ 底部快速编辑浮条 ← 删              └ 虚拟化网格（唯一内容）
```

关键点：

- 折叠/展开只改 header 高度，**完全不改滚动容器的 `scrollHeight`**，浏览器不会钳制 `scrollTop`，环不成立。
- 摘要条原本是 `sticky top-0`（`SuperSearchPage.tsx:112`）。移出滚动容器后 **sticky 语义消失**，必须改为普通块级元素，并把原先的 `bg-[var(--color-bg)]/95 backdrop-blur` 简化为实底 `bg-[var(--color-bg)]`（设计系统："新界面背景不透明"；且不再需要透过内容看，backdrop-blur 纯属浪费一次合成）。保留 `border-b border-[var(--color-border)]`。
- header 展开时压缩网格可视高度，`flex-1` 自动处理；虚拟化的 `clientHeight` 变化由 `useVirtualizer` 正常处理，不产生递归。
- **这是 Gmail / Notion / Linear 处理"滚动收起顶栏"的标准做法**：收起的是壳，滚的是内容，两者不共用同一个滚动上下文。

**折叠动画规范**（对齐 §3.5：禁止动画 height）：

```tsx
{/* 详细条件面板：始终在 DOM，用 grid-template-rows 0fr↔1fr 折叠 */}
<div
  className="grid transition-[grid-template-rows] duration-200 ease-out"
  style={{ gridTemplateRows: chrome === "expanded" ? "1fr" : "0fr" }}
  aria-hidden={chrome !== "expanded"}
>
  <div className="overflow-hidden">
    <div className="mx-auto max-w-5xl px-4 pt-3">
      <QueryBuilder />
    </div>
  </div>
</div>
```

`grid-template-rows: 0fr → 1fr` 是当前唯一能对 auto 高度做平滑折叠且不需要 JS 测高的方案。**注意**：`aria-hidden` 之外还要在收起态给内层加 `pointer-events-none`，否则 0 高度容器里的 select 仍可被 Tab 聚焦。

> **测试影响**：`SuperSearchPage.test.tsx:98`「FB-06：下滚收起详细条件，上滚恢复」现在断言的是 `queryByRole("region", { name: "条件公式" })` **不在 document 中**。改为常驻 DOM 后此断言必然失败。改写为断言容器的 `gridTemplateRows` 样式或 `aria-hidden` 属性。见 §7.6。

### 7.3 方案 C（必做）：hook 加固

`src/hooks/useScrollDirection.ts` 扩展选项（**保持向后兼容**：`threshold` 继续支持，作为两个新阈值的缺省来源）：

```ts
export interface ScrollDirectionOptions {
  /** @deprecated 用 collapseThreshold / expandThreshold 替代；仍支持，作为两者缺省值 */
  threshold?: number;
  /** 收起阈值（px），缺省 24 —— 收起要滚得更多，避免误触 */
  collapseThreshold?: number;
  /** 展开阈值（px），缺省 12 —— 展开更灵敏（非对称滞回，消除边界抖动） */
  expandThreshold?: number;
  /** 低于此 scrollTop 恒为 expanded（px），缺省 48 —— 顶部区域收起毫无意义 */
  minScrollTop?: number;
  /** 程序化改变状态后忽略 scroll 事件的时长（ms），缺省 300 —— 手动设定不被滚动方向立刻覆盖 */
  suppressMs?: number;
}
```

实现要点：

1. `minScrollTop` 判定放在方向计算**之前**：`if (y < minScrollTop) { setState("expanded"); lastY.current = y; return; }`。注意仍要更新 `lastY`，否则从顶部快速滚到中段会算出一个巨大 delta。
2. `suppressMs`：`setExpanded`（对外的第三个返回值）里记录 `suppressUntil.current = Date.now() + suppressMs`；`onScroll` 的 rAF 回调开头检查 `if (Date.now() < suppressUntil.current) { lastY.current = el.scrollTop; return; }`——**同样要更新 lastY**。
3. 非对称阈值：`const need = dir === "down" ? collapseThreshold : expandThreshold;`
4. 选项用 ref 持有（现状 `thresholdRef` 已是此模式，`:27`），保证 `onScroll` 的 `useCallback([])` 依赖为空不失效。
5. `setNode(null)` 的清理路径不变（现有测试 `useScrollDirection.test.ts:65` 覆盖）。

### 9.2 隐藏缺陷（必须先修，否则比例设置不生效）

`LazyThumb` 的 className 拼接产生了 Tailwind 定位类冲突：

```tsx
// src/components/import/PendingList.tsx:67
<div ref={ref} className={clsx("relative overflow-hidden bg-[var(--color-surface)]", className)}>
// 调用处 src/components/import/PendingList.tsx:216
<LazyThumb path={item.path} kind={item.kind} className="absolute inset-0" />
```

结果这个 div 同时带 `relative` 和 `absolute`。**Tailwind v4 生成的样式表里 `relative` 排在 `absolute` 之后**（本仓库构建产物实测：`.absolute` 在字节偏移 7426、`.relative` 在 7476，tailwindcss v4.3.3），同级冲突时**级联胜出的是 `relative`**。于是：

- `LazyThumb` 不是绝对定位覆盖层，而是参与文档流的相对定位块（`position: relative` 不脱离文档流）；
- 卡片（`PendingList.tsx:209-243`）的其余子元素（视频层、角标、文件名、移除按钮）全是 `absolute`，**唯一撑高度的就是 `LazyThumb` 里那个 `h-full w-full` 的 `<img>`**（`:73-77`）；
- `h-full` 对 auto 高度的父级解析为 `auto` → **卡片高度 = 首张图片的固有比例**。

这就是入库网格里卡片呈 16:9 扁条（视频封面比例）、混排时行高不齐的机制性来源。

**修法**：把定位职责从 `LazyThumb` 的基类里拿掉，改由调用方通过独立 prop 声明，避免 clsx 拼出互斥类。

```tsx
// PendingList.tsx:30 签名改为
function LazyThumb({ path, kind, fit, className }: {
  path: string;
  kind: string;
  /** FB2-02 填充方式（cover 裁切填满 / contain 完整显示） */
  fit: "cover" | "contain";
  className?: string;
}) {
// :67 基类去掉 relative（定位完全交给调用方，杜绝互斥类拼接）
  <div ref={ref} className={clsx("overflow-hidden bg-[var(--color-surface)]", className)}>
// :73-77 的 img className 里 object-cover 改为按 fit 变量
    className={clsx(
      "h-full w-full transition-opacity duration-300",
      fit === "cover" ? "object-cover" : "object-contain",
      loaded ? "opacity-100" : "opacity-0",
    )}
```

`LazyThumb` 全仓库**只有一个调用点**（`PendingList.tsx:216`），改动安全。

> 附带说明：`clsx` 不做 Tailwind 类冲突消解（那是 `tailwind-merge` 的职责，本项目**没有**这个依赖，也不要为此引入）。所以"基类不含定位、定位由调用方给"是本项目的通用规避方式，新写组件都照此办理。

### 9.3 FB2-01：档位化缩放（不做连续缩放）

**为什么档位化**：连续缩放会让 `@tanstack/react-virtual` 每帧 `measure()` 重算全部行高，并让缩略图请求尺寸在任意值间漂移，缓存键 `${assetId}:${kind}:${size}`（`thumbnailCache.ts:25-27`）几乎必然全部 miss——等于每次滑动都重新生成一遍缩略图。档位化后缩略图尺寸只在 2~3 个固定值间切换，缓存命中率接近 100%。

档位表见 §8.1 的 `CELL_STEPS`（8 档，约 1.25× 等比，96→480px）。

**缩略图尺寸随档位分级**（把 `Thumbnail.tsx:10` 的 `SIZE` 从模块常量改为 props 入参）：

```ts
// src/components/library/Thumbnail.tsx 或新建 src/utils/thumbSize.ts
/** 格子宽 → 缩略图请求尺寸。分级而非连续，保证缓存键收敛到少数几个值。 */
export function thumbSizeForCell(cellPx: number): 512 | 1024 {
  return cellPx <= 190 ? 512 : 1024;   // 190×2(DPR) = 380 < 512；240 以上 512 在 2×DPR 下会糊
}
```

| 格子宽 | 请求尺寸 | 理由 |
|---|---|---|
| ≤ 190px | 512 | 覆盖 2× DPR |
| 240–480px | 1024 | 512 在 380px 格子上 2× DPR 会糊；1024 以上收益递减 |

> ⚠️ **视频封面的已知限制（必须在实现里显式接受并写进注释）**：后端图片 hd 缩略图按请求尺寸独立缓存（`thumbnail.rs:152` → `{asset_id}_{size}.webp`，尺寸参与文件名，请求 1024 会真生成 1024 图）；但**视频 hd 封面文件名固定为 `{asset_id}_cover.jpg`**（`thumbnail.rs:150`），**尺寸不参与缓存键，先到的尺寸决定内容**。所以给大格子请求 1024 时，视频封面不会变清晰（返回的还是先前的 512 文件）。
>
> **本轮决定：接受此限制，不改后端缓存键**。理由：改缓存键会让所有存量视频封面失效并触发全库重抽帧（每张一次 ffmpeg 调用），代价远大于收益。在 `thumbSizeForCell` 的注释与 `thumbnail.rs:150` 处各加一行说明，避免下一个人误以为是 bug。若未来要修，正解是 `{asset_id}_cover_{size}.jpg` + 一次性清理旧 `_cover.jpg`。

**事件实现**（沿用 `MediaViewport.tsx:147-160` 已验证的模式）：

```tsx
// AssetGridView 内新增 effect（挂在滚动容器上，不是网格 div —— 滚动容器才是 wheel 的落点）
useEffect(() => {
  const el = scrollElementRef?.current ?? ref.current;
  if (!el) return;
  let raf = 0;
  let lastStepAt = 0;
  const onWheel = (e: WheelEvent) => {
    // Alt（用户点名）与 Ctrl/Cmd（Eagle / Adobe Bridge / Finder / Explorer 的行业惯例）都支持。
    // Ctrl+滚轮在 Chromium/WebView2 中是可取消的 wheel 事件：passive:false + preventDefault
    // 即可完全阻止页面级缩放（Leaflet/Mapbox 拦截 Ctrl+滚轮的标准做法）。
    if (!e.altKey && !e.ctrlKey && !e.metaKey) return;
    e.preventDefault();
    const now = performance.now();
    if (now - lastStepAt < 60) return;   // 每档最小间隔，触摸板惯性一次能产生几十个 wheel 事件
    lastStepAt = now;
    cancelAnimationFrame(raf);
    raf = requestAnimationFrame(() => stepCell(e.deltaY < 0 ? 1 : -1));
  };
  el.addEventListener("wheel", onWheel, { passive: false });
  return () => {
    el.removeEventListener("wheel", onWheel);
    cancelAnimationFrame(raf);
  };
}, [/* stepCell, 容器 */]);
```

**缩放锚点保持**（否则用户"缩放后不知道自己在哪"）：档位切换**前**记录视口垂直中心对应的 item index，切换**后** `virtualizer.scrollToIndex(anchorIndex, { align: "center" })`。

```ts
// 切换前
const el = scrollElementRef?.current ?? ref.current;
const centerY = (el?.scrollTop ?? 0) + (el?.clientHeight ?? 0) / 2;
const anchorRow = Math.floor(centerY / rowHeight);
const anchorIndex = Math.min(items.length - 1, anchorRow * columns);
// 切换后（下一帧，等 virtualizer 用新 estimateSize 重算）
requestAnimationFrame(() => virtualizer.scrollToIndex(anchorIndex, { align: "center" }));
```

`scrollToIndex` 在动态测量下有轻微过冲风险，验收标准只要求"锚点不跳"（视觉上仍在同一批素材附近），不要求像素级精确。

**可发现入口**（Alt+滚轮属于隐藏手势，新用户找不到）：

**档位持久化的防抖**（重要，别漏）：滚轮连续滚动会高频改档位。**不能每次档位变化都 `save_settings`**（会高频落库）。做法：

### 9.4 FB2-02：统一比例 + 填充方式

**核心结构原则：容器统一比例 + 内容按填充方式适配。** 这是唯一能保证网格对齐的结构。当前入库页是反过来的（内容比例决定容器高度，见 §9.2），必须纠正。

**比例档位**（7 项，用户明确"只允许设置同一比例"）：

| 值 | 说明 | 适用 |
|---|---|---|
| `1:1` | 正方形 | **默认**（决策 4），混排最中性 |
| `4:3` | 传统相机 | 图片为主 |
| `3:2` | 135 画幅 | 单反/微单素材库 |
| `16:9` | 宽屏 | 视频为主的库 |
| `3:4` / `2:3` / `9:16` | 竖版 | 竖屏/手机素材 |

**不做 `auto`（瀑布流）**。理由：`AssetGridView.tsx:95-100` 的 `useVirtualizer` 是**等高行**模型（`estimateSize` 返回单一值），瀑布流需要 masonry / `lanes` 模式并逐项 `measureElement`，改造量约等于重写网格虚拟化层。视觉收益与代价不匹配。若未来需要，单独立项。

**填充方式**（3 项）：

| 值 | CSS | 视觉 | 代价 |
|---|---|---|---|
| `cover`（裁切填满） | `object-fit: cover; object-position: center` | 网格最齐最"满" | 裁掉画面边缘 |
| `contain`（完整显示） | `object-fit: contain` | 构图完整 | 比例不同的素材留边 |
| `smart`（智能） | 内容比例与容器比例相对差 < 15% 用 cover，否则 contain | 兼顾 | 同一行内可能混两种观感 |

`smart` 的判定纯函数（必须单测）：

```ts
// src/utils/cellFit.ts
/** smart 模式判定：内容比例与容器比例的相对差小于阈值时用 cover（裁掉的边缘可忽略），
 *  否则用 contain（避免把竖图裁成方图那种"砍掉半个人"的效果）。 */
export const SMART_FIT_TOLERANCE = 0.15;

export function resolveFit(
  mode: CellFit,
  contentAspect: number | null,   // width / height；未知时（尺寸列为空）返回 cover
  containerAspect: number,
): "cover" | "contain" {
  if (mode !== "smart") return mode;
  if (contentAspect == null || !Number.isFinite(contentAspect) || contentAspect <= 0) return "cover";
  const diff = Math.abs(contentAspect - containerAspect) / containerAspect;
  return diff < SMART_FIT_TOLERANCE ? "cover" : "contain";
}
```

`contentAspect` 数据来源：`Asset.width / Asset.height`（已有列）。视频同理。列为空（RAW 未解析、V12 未回填的视频）时按 `cover` 处理——这是当前行为，不引入回归。

**「别太丑」的三个关键设计决定**（这是这条需求真正的难点）：

1. **绝不拉伸。** 明确**不提供** `object-fit: fill`。拉伸变形是唯一"绝对丑"的选项——视频与图片比例本来就不同，拉伸后人脸会被压扁。用户说的"填充拉伸这些你设置好"按"填满 / 完整"两态实现，**不做形变**。
2. **`contain` 的留边背景不用纯灰。** 默认 `var(--color-surface)`；再提供 `matchDominantColor` 选项——留边填该素材主色的低饱和版本（Lab 里把 L 拉向背景、C 压到 30%）。这是 Apple Photos / Google Photos 的做法，留边不再是"缺口"而是画面的延伸。**这一项依赖批次 4 的色板**，批次 2 阶段该 Toggle 渲染为 disabled + hint「需要先在设置→色条里完成主色计算」。
3. **统一圆角与内描边。** cover 模式下深色图片贴着深色背景会失去边界。卡片加 `ring-1 ring-inset ring-[var(--color-hairline)]`（§3.6 新增变量），比加外边框干净得多。

### 11.2 补边界钳制（现有缺陷）

`MediaViewport.tsx:196-207` 的 `onPointerMove` 只做 `offset = start + delta`，**没有任何钳制**。放大后可以把媒体整个拖出视野，只剩黑屏，必须切张才能恢复。

在 `viewportMath.ts` 新增：

```ts
/** 平移钳制（FB2-05）：
 *  - 媒体缩放后若小于舞台 → 该轴居中锁定（offset = 0）；
 *  - 大于舞台 → 限制平移量，使媒体边缘不越过舞台边缘。
 *  与 pointerInStage 同样的安全返回策略：任一前提不满足返回原值，不抛异常。 */
export function clampOffset(
  scale: number,
  offsetX: number,
  offsetY: number,
  stage: StageRect | null | undefined,
  media: { width: number; height: number } | null | undefined,
): { offsetX: number; offsetY: number } {
  if (!stage || !media) return { offsetX, offsetY };
  if (!Number.isFinite(scale) || scale <= 0) return { offsetX, offsetY };
  const clampAxis = (offset: number, mediaLen: number, stageLen: number) => {
    if (!Number.isFinite(mediaLen) || !Number.isFinite(stageLen) || stageLen <= 0) return offset;
    const scaled = mediaLen * scale;
    if (scaled <= stageLen) return 0;                    // 小于舞台 → 居中锁定
    const max = (scaled - stageLen) / 2;                 // 最大可平移量
    return Math.max(-max, Math.min(max, offset));
  };
  return {
    offsetX: clampAxis(offsetX, media.width, stage.width),
    offsetY: clampAxis(offsetY, media.height, stage.height),
  };
}
```

**媒体实际渲染尺寸怎么拿**：`object-contain` 下的渲染尺寸不等于 `naturalWidth/Height`。用 `imgRef.current.getBoundingClientRect()`（scale 前的布局尺寸）——注意 `getBoundingClientRect()` 返回的是**已应用 transform 后**的尺寸，所以要用 `offsetWidth / offsetHeight`（不含 transform）。视频同理，取 `boxRef` 的 `offsetWidth/Height`。给 `MediaViewport` 加一个 `mediaRef`，在 `onPointerMove` 与 `zoomAt` 里读。

**钳制的两个调用点**（都要，漏一个就还能拖飞）：

1. `onPointerMove`（`:196-207`）：计算出 `start.offsetX + dx` 后过一遍 `clampOffset`。
2. `zoomAt`（`:124-135`）：缩小时也要重新钳制（从 4x 缩到 1.2x 时原来合法的 offset 可能已越界）。

```ts
// src/hooks/useMediaFullscreen.ts
/**
 * 媒体全屏（FB2-05）：图片与视频共用的唯一全屏实现。
 * 决策（2026-08-28）：只做 webview 内元素全屏，不调 Tauri 窗口 API —— capabilities 未放行
 * core:window:allow-set-fullscreen，调用会被 ACL 拒绝。已知限制：decorations:false 的自绘
 * 标题栏在"全屏"时仍可见，这是被接受的观感。
 *
 * 同时承担 Esc 语义仲裁：全屏态下拦截 Esc 只退出全屏，不冒泡给 ViewerPage 的 onClose。
 */
export function useMediaFullscreen(targetRef: React.RefObject<HTMLElement | null>): {
  isFullscreen: boolean;
  toggle: () => void;
  enter: () => void;
  exit: () => void;
} { ... }
```

实现要点：

1. `enter()`：`targetRef.current?.requestFullscreen()`（`Promise` 要 `.catch` 吞掉——某些环境会拒绝，不能让未捕获 rejection 冒到控制台）。
2. `exit()`：`document.exitFullscreen()`，同样 catch。
3. 监听 `fullscreenchange` 同步 `isFullscreen`（`VideoPlayer.tsx:285-289` 已有同款 effect，迁进 hook 后删掉那份）。
4. **Esc 拦截**：hook 内挂一个 `window.addEventListener("keydown", ..., { capture: true })`，在**捕获阶段**处理：`if (isFullscreen && e.key === "Escape") { e.stopPropagation(); exit(); }`。捕获阶段 + `stopPropagation` 才能拦在 `ViewerPage` 的冒泡监听（`:168` 用的是默认冒泡）之前。
   > 注意：浏览器原生也会在 Esc 时自动退出全屏。所以实际效果是"原生退出 + 我们阻止 onClose"。`exit()` 调用是幂等的（已退出时 `exitFullscreen` 会 reject，被 catch），不会出错。
5. `toggle()` 按 `isFullscreen` 分派。

**接线**：

- `MediaViewport` 内对 `stageRef`（或包裹媒体的元素）调 `useMediaFullscreen`，暴露 F 键 + 工具栏按钮。
- `VideoPlayer` 的 `toggleFullscreen`（`:189-195`）改为**接收上层传入的回调**：新增 prop `onToggleFullscreen?: () => void` 与 `fullscreen?: boolean`，删除内部的 `boxRef.current?.requestFullscreen()` 与 `fs` state 及 `:285-289` 的 effect。`:226-229` 的 `case "f"` 改为调用传入的回调。`VideoControls` 的 `fullscreen` / `onToggleFullscreen` 两个 prop（`:425,440`）改为透传上层值。
- 触发方式：**F 键 + 工具栏按钮**。**图片不用双击**——双击已被 1x↔2x 缩放占用（`MediaViewport.tsx:170-179`），冲突。
- 全屏态下隐藏侧栏与胶片条：`ViewerPage` 从 `MediaViewport` 拿到 `isFullscreen`（或把 hook 提到 `ViewerPage` 层，把 `toggle` 往下传——**推荐这个**，因为 `ViewerPage` 才是决定 shell 布局的地方），全屏时给 `ViewerShell` 传 `sidebar={null}` / `filmstrip={null}` / `tagBar={null}`。

1. **成本 ×3。** 每个视频 3 次视觉 API 调用 = 3 倍 token + 3 倍时延；本地 Ollama 单帧就要数十秒，视频批次实际不可用。
2. **第 0ms 帧质量差。** 相机视频开头常是黑场/自动曝光未稳定。夜景素材第 0 秒几乎全黑，等于白花一次 API 调用。
3. **没装 ffmpeg 就完全不能给视频打标。** `extract_keyframes` 找不到二进制直接返回空 vec（`video.rs:380-382` 的 `resolve_binary` 返回 `None` → `extract_frame` 返回 false），然后 `ai_cloud.rs:729-734` 直接报错。但**封面在入库时就已经生成好了**（`thumbnail.rs:119`），用它打标根本不需要 ffmpeg 在打标时可用。
4. **抽帧未走并发闸。** `extract_keyframes`（`video.rs:506-527`）没有 `imaging::acquire()` permit。对照 `thumbnail.rs:118` 与 `preview.rs:49` 都是正确用法。批量打标时可能同时拉起大量 ffmpeg 进程打满 CPU。

> ❌ **不要修「抽帧临时目录失败路径残留」——这个 bug 不存在。** 经核验：`ai_cloud.rs` 里 `remove_dir_all` 共两处——`:730`（frames 为空分支）与 `:741`（**无条件**，位于逐帧请求循环之后、`results.is_empty()` 判断之前）；且 `:722`（`create_dir_all`）到 `:741` 之间**没有任何 `?` 或提前 return**（单帧 API 错误被 `if let Ok(t)` 吞掉）。所以"中途 API 失败会把 webp 帧留在 temp"的情形在当前代码里**不成立**，正常失败路径清理已完备。
>
> RAII guard 只对"进程被 kill / 断电"有意义，属于**可选加固**而非缺陷修复。本轮**不做**（改动收益低于引入 Drop 语义的复杂度）。若实现者仍想加，必须在 PR 里说明这是加固不是修 bug。

### 13.5 抽帧打标（`frames`）

四处修改：

**① 帧位改为 `d * (i + 0.5) / n`**（避开首尾黑场）：

```rust
// src-tauri/src/services/video.rs:513-517 改为
// FB2-07：帧位取每段中点 —— n=3 → 16.7% / 50% / 83%，避开片头黑场与片尾字幕/淡出。
// 原公式 d*i/n 的第一帧恒为第 0ms，相机视频开头常是黑场或自动曝光未稳定。
let times: Vec<i64> = match duration_ms {
    Some(d) if d > 0 => (0..n)
        .map(|i| ((d as f64) * (i as f64 + 0.5) / (n as f64)) as i64)
        .collect(),
    // 时长未知：退化为固定间隔，跳过第 0 秒
    _ => (0..n).map(|i| 2000 + i as i64 * 5000).collect(),
};
```

注意原代码有个 `n == 1` 的特殊分支（`vec![d / 2]`）。新公式在 n=1 时自然给出 `d * 0.5`，**行为一致**，可以删掉那个分支。

**② 阈值随 n 自适应 `ceil(n / 2)`**：

```rust
// src-tauri/src/services/ai_cloud.rs:688 改为
// FB2-07：阈值随帧数自适应。固定 2 在 n=6 时过松（1/3 帧命中就通过），n=2 时又过严。
let threshold = (ok + 1) / 2;   // ceil(n/2)：n=2→1、n=3→2、n=4→2、n=6→3、n=8→4
```

**③ 抽帧循环加 `imaging::acquire()`**：

```rust
// src-tauri/src/services/video.rs 的 extract_keyframes 循环内
for (i, t) in times.iter().enumerate() {
    let frame = dir.join(format!("kframe_{i}.webp"));
    // FB2-07：走全局解码/抽帧并发闸（MAX_PERMITS=4），否则批量打标会同时拉起大量 ffmpeg 打满 CPU。
    // 对照 thumbnail.rs:118 与 preview.rs:49 的既有正确用法。
    let _permit = crate::services::imaging::acquire();
    if extract_frame(path, *t, &frame, 1280) {
        out.push(frame);
    }
}
```

> ⚠️ **循环作用域陷阱**：`let _permit = ...` 必须在**循环体内**（每帧取一次、帧结束即释放），不能提到循环外——提到外面会让整个多帧抽取只占 1 个 permit 但持有全程，反而降低吞吐。同时 `_permit` 变量名不能写成 `_`（`let _ = acquire()` 会**立即 drop**，permit 白拿）。这是 RAII guard 最经典的坑。

**④ 帧数从入参驱动**：`extract_keyframes` 的 `n` 参数已存在（`video.rs:510`），`tag_video` 里把硬编码的 `3`（`ai_cloud.rs:727`）改为 `cfg.video_frame_count.clamp(2, 8) as usize`。

### 14.4 算法选型：Lab 空间 k-means

三类主流色彩量化算法对比：

| 算法 | 代表实现 | 优点 | 对本场景的缺点 |
|---|---|---|---|
| 中位切分 MMCQ | Color Thief、`color_thief` crate | 极快、零依赖 | **不输出占比** → 色条画不出宽窄；低饱和图容易返回"泥灰"色 |
| 八叉树 Octree | 多数 GIF 量化器 | 快、内存可控 | 量化格子固定，感知上接近的颜色会被硬切成两块 |
| **k-means（Lab 空间）** | `kmeans_colors`（okaneco） | **自带占比**、Lab 欧氏距离≈人眼感知距离、簇心就是真实代表色 | 需迭代，比 MMCQ 慢（在缩略图尺度上无所谓） |

**结论：Lab 空间 k-means。** 决定性理由是**色条必须有占比**才能画出宽窄不一的分段（这才是"调色师色卡"的信息量所在），而 MMCQ 结构上就不产出占比。Lab 空间聚类的结果也更符合"调色师看到的颜色"——RGB 空间里深蓝和深紫距离很近但人眼分得很清。

**新增依赖**（`src-tauri/Cargo.toml`）：

```toml
# FB2-08 算法主色提取：Hamerly k-means + Sort::sort_indexed_colors（按占比排序，自带 percentage）
kmeans_colors = "=0.6"      # 版本以 cargo add 实测为准，必须 pin
palette = "=0.7"            # 色空间转换 sRGB ↔ Lab ↔ LCh
```

**pin 精确版本**（`=x.y`）：这两个 crate 的 API 不守严格 SemVer，本项目已有先例（`Cargo.toml` 的 `rawler = "=0.7.2"`，注释写明"API 不守 SemVer，锁精确版本"）。

**必须同步加 dev O3**（`docs/DEVELOPMENT.md` 铁律 3.3："新增图像相关 crate → 必须加进 Cargo.toml 的 dev O3 列表"）：

```toml

opt-level = 3
[profile.dev.package.palette]
opt-level = 3
```

`cargo add` 时**必须验证与 `image 0.25` 的兼容性**（`palette` 与 `image` 都有自己的颜色类型，转换要走中间字节数组，不要指望 trait 直接互通）。

### 14.5 提取流程

**在缩略图上做，不碰原图。**

```text
1. 取源图：见 §14.6 的取材策略
2. 下采样到约 100×100（≈1 万像素）—— 主色提取不需要更多样本
3. 丢弃极端像素：L* < 4（纯黑）与 L* > 96（纯白）且饱和度极低的点
   （避免整张图的主色被黑边/白底吃掉）
4. sRGB → Lab
5. k-means：k = 6，Hamerly 算法，3 次不同随机种子取评分最优的一次
   （单次 k-means 对初值敏感，多次取优是该库文档建议的做法）
6. 合并 ΔE < 6 的相邻簇（避免色条上出现两块肉眼看不出差别的分段）
7. 输出按占比降序的 hex + rgb + ratio，最多 8 条
```

**性能预算**：1 万点、k=6、Hamerly、3 run × 约 20 轮迭代 → **单张亚毫秒到几毫秒**。259 张走 `rayon`（`Cargo.toml` 已有）并行 → **整库一秒级**。

放在新文件 `src-tauri/src/services/palette.rs`。**不要**放进 `imaging.rs`（那里是解码引擎，职责是"字节→DynamicImage"；提色是消费方）。但**解码必须调 `imaging::decode_thumb`**，不得另起解码（铁律 3.3）。

### 14.6 取材策略（这条容易踩坑）

**注意**：hd 512 缩略图是**按需生成**的——入库只产出 256px placeholder（`thumbnail.rs:106-127` 的 `extract_placeholder`，`PLACEHOLDER_SIZE = 256`），hd 层是"浏览可见区按需生成"（`thumbnail.rs:20-21` 注释明确）。所以存量回填时**多数素材并没有现成 hd 文件**。

如果 `decode_thumb` 对着不存在的 hd 路径，要么现场生成（解码原图，与"不碰原图"矛盾且慢几个数量级），要么失败。**明确策略**：

| 时机 | 取材 |
|---|---|
| **入库时** | 用**内存中的 placeholder 图像**（`importer.rs:674` 调 `extract_placeholder` 时缩略图刚生成，还在内存/刚落盘）。省一次解码 |
| **存量回填** | `placeholder_path` 文件优先（256px，下采样到 100×100 后完全够用）；文件缺失才回落 hd；两者都无才解码原图（并在结果里标记该行取材质量较低） |
| **单张重算** | 同存量回填 |

**256px 对主色提取完全够用**——下采样目标是 100×100，256px 源已经超采样了。不要为了"更准"去读原图。

### 14.7 触发时机（三条路径）

| 时机 | 挂点 | 说明 |

视频取**封面帧**（`placeholder_path`）计算。v2 可选"取 3 帧平均"，本轮不做。

### 14.9 接入超级搜索

**① `MetadataFilterKey` 扩展**（`src/types/asset.ts:84-105`）：追加 `"dominant_hue" | "dominant_sat" | "dominant_lum"`。

**② `search_query.rs` 三处白名单同步**（缺一个就会报"未知元数据字段"）：

```rust
// key_spec（:55-85）
"dominant_hue" | "dominant_sat" | "dominant_lum" => KeySpec {
    kind: ValueKind::Number,
    null_guard: Some("IS NOT NULL"),
},
// allowed_ops（:88-100）
"dominant_hue" | "dominant_sat" | "dominant_lum" => &["eq", "in", "gt", "gte", "lt", "lte", "between"],
// value_expr（:103-127）
"dominant_hue" => "a.dominant_hue".into(),
"dominant_sat" => "a.dominant_sat".into(),
"dominant_lum" => "a.dominant_lum".into(),
```

**③ 色相环绕（必须处理，否则"搜红色"静默漏掉一半）**：

`dominant_hue BETWEEN 200 AND 250` 对蓝/绿成立，但**红色跨越 0°**（约 345°~15°）。必须编译为双区间 `OR`：

```sql
(a.dominant_hue >= 345 OR a.dominant_hue <= 15)
```

`compile_number` 的 `between` 分支（`search_query.rs` 内）对 `dominant_hue` **且 `min > max`** 时特殊处理：

```rust
// FB2-08：色相是环形量。min > max 表示区间跨越 0°（如红色 345~15），
// 必须编译为双区间 OR，否则 BETWEEN 345 AND 15 恒为空集，"搜红色素材"静默返回 0 条。
if f.key == "dominant_hue" && min > max {
    return Ok(Some(CompiledMetadata {
        sql: format!("({expr} >= ?1 OR {expr} <= ?2)"),
        params: vec![min.into(), max.into()],
    }.with_null_guard(null_guard)));
}
```

**④ 点击非主色分段的查询列问题（设计阶段就要定案，否则实现时必然临时拍板）**：

色条交互设计"点击某段 → 以该色搜索"，但索引列只有 `dominant_hue/sat/lum` 三列（对应 `palette[0]`）。点击第 2~N 段时没有可命中的索引列。

三个选项：

| 方案 | 代价 |
|---|---|
| **A. 只允许点击主色段**（第 1 段） | 交互受限，但零额外成本、无性能风险 |
| B. 把前 N 色的 hue 也落列 | 列数膨胀（N=6 → 18 列 + 18 索引），schema 变丑 |
| C. 非主色段降级为解析 `palette_json` 全表扫描 | 259 项可行，大库（数万项）不行 |

**本轮定案：方案 A + 一个软化措施。** 主色段可点击（`cursor-pointer` + hover 高亮）；非主色段 hover 显示 `#hex · 31%` 但**不可点击**（`cursor-default`，且 `aria-label` 里说明"仅主色可用于搜索"）。理由：色条的首要价值是**呈现**（让用户一眼看出这张图的调性），搜索是次要能力；为次要能力付 18 列的 schema 代价不划算。

如果用户后续要求"任意色都能搜"，正解是方案 C 加一层预筛（先用 `dominant_hue` 粗筛 ±60° 缩小候选集，再解析 JSON 精筛），届时单独立项。

### 14.10 色条 UI（`ColorStrip` 组件）

参考形态是**紧贴画面下沿的一条水平色带**（Behance / Cinema Palettes / 调色参考站的通用做法）。

**形态规格**：

| 项 | 值 |
|---|---|
| 结构 | 一条无缝水平色带，各段按占比分宽（`mode: "ratio"`）或等宽（`"equal"`） |
| 高度 | `thin` 6px（网格小图）/ `normal` 10px / `thick` 16px（大图浏览） |
| 位置 | **紧贴媒体下沿，无间隙**——有间隙就变成"图表"，贴着才是"色卡" |
| 圆角 | 只有底部两角跟随容器圆角（网格卡片里）；Viewer 里无圆角 |
| 边界 | 整条加 `ring-1 ring-inset ring-[var(--color-hairline)]`（§3.6）。**不要给每段加边框**——那会让色带看起来像表格 |
| hover | 单段显示 `#1B2A3C · 31%`（原生 `title` 属性即可，不要为此建 tooltip 组件） |
| 点击 | 仅主色段可点 → 以该色为条件搜索（§14.9 方案 A） |
| 无障碍 | `role="img"` + `aria-label="主色：深蓝 31%、米白 22%、橙 14%"`（用中文色名，见下） |
| 空态 | `palette_json` 为空/未计算时**不渲染**（不占位、不显示骨架）——色条是增强信息，缺失时安静消失比显示"未计算"好 |

**中文色名映射**（供 `aria-label` 用）：按 hue 分 12 段 + 低饱和归灰阶，纯函数放 `src/utils/colorName.ts`，必须单测。

```ts
/** hue/sat/lum → 中文色名。仅用于无障碍标签与 hover 文案，不参与任何逻辑判断。 */
export function colorNameZh(hue: number, sat: number, lum: number): string { ... }
// sat < 10 → 按 lum 给「黑 / 深灰 / 灰 / 浅灰 / 白」
// 否则按 hue 12 段：红/橙/黄/黄绿/绿/青绿/青/天蓝/蓝/紫/品红/玫红
// lum < 25 加前缀「深」，lum > 75 加前缀「浅」
```

**唯一允许新增的 CSS 类**（§3.2）：

```css
/* src/styles/index.css 追加 */
/* 色条（FB2-08）：无缝分段色带。段间不留缝、不加边框 —— 有缝就变成图表，
   贴合才是色卡。整条一个 inset ring 解决浅色主题下米白段"消失"的问题。 */
.ui-colorstrip {
  display: flex;
  width: 100%;
  overflow: hidden;
  box-shadow: inset 0 0 0 1px var(--color-hairline);
}
.ui-colorstrip > * {
  height: 100%;
  flex-shrink: 0;
}
```

**为什么按占比而不等宽**：等宽会让 1% 的高光色和 40% 的主色一样宽，信息量低。**默认按占比**（`mode: "ratio"`）；设置里给 `equal` 选项让用户选参考图那种观感。

**深浅主题下的可读性**：浅色主题下米白色块贴在浅背景上会"消失"。整条加 inset ring 比给每段加边框干净得多（已在 `.ui-colorstrip` 里实现）。

### 14.11 三处显示位置

| 位置 | 设置项 | 默认 | 高度 | 落点 |
|---|---|---|---|---|

### 14.13 验收标准

- 259 项整库补算在**数秒内**完成，有进度、可取消，期间 UI 不卡。
- 色条颜色与人眼观感一致（**抽查 10 张**：夜景不返回一片灰、暖调不返回冷色、单色照片不返回 6 个几乎相同的色块）。
- 三处显示位置的开关各自独立生效；关掉总开关后所有位置都不渲染**且不解析 JSON**（加临时 log 或 profiler 确认）。
- 深浅主题下色带边界都清晰；浅色主题下米白色段可见。
- 色条 `aria-label` 含中文色名与占比。
- **AI 打标不再产出 color 标签**，包括"模型主动返回 color 键"的情况（构造一个返回 `{"color":["青橙"]}` 的 mock 响应验证被丢弃且有 warning）。
- 存量 color 标签仍可搜索、可手动编辑；工作台默认收起。
- 点主色段能搜出同色系素材，查询走索引（`EXPLAIN QUERY PLAN` 确认命中 `idx_assets_dominant_hue`）。
- **红色环绕用例**：搜"红色"（hue 345~15）能同时命中 hue=350 与 hue=10 的素材。
- 非主色段 hover 显示数值但不可点击。
- 未装 ffmpeg 的机器上，图片色板正常计算（视频封面若缺失则该行标记为未计算，不报错）。
