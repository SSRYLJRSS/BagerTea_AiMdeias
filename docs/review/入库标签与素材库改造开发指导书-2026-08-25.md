## 0. 文档目的

本文件用于指导其他 AI 对项目执行实际开发。开发代理必须按照本文的阶段顺序、文件边界、UI 规范、数据契约和验收标准执行，不得只根据用户口头反馈自行重写页面或扩大改造范围。

本次改造包含：

- 入库页面连续添加文件和文件夹；
- 入库任务即时反馈与统一进度条；
- 入库和素材库图片/视频悬浮预览；
- RAW 快速预览与后台高清解析；
- 视频播放、跳转和倍速控制；
- 大批量打标分块执行；
- 基础标签分面恢复；
- 标签设置、AI 打标和超级搜索的数据源统一；
- 既有超级搜索改动的 P0 回归修复。

本次改造不包含：

- 视觉相似度搜索或 CLIP embedding；
- 保存筛选和智能文件夹；
- XMP/IPTC 双向写回；
- 新建完整的媒体编辑器；
- 重写现有数据库标签树；
- 替换现有全局图像解码引擎；
- 为了“看起来更现代”而重做全站视觉结构。

## 0.1 原计划与评审报告对比结论

原改造计划的代码诊断和产品方向基本成立，评审报告对 8 条主要代码论断逐项核验后全部确认。后续开发应保留原计划的核心目标，但按照评审结论收缩或修订实施方式。

| 议题 | 原计划 | 评审意见 | 本指导书决定 |
|---|---|---|---|
| 总体归因 | 任务、媒体、标签三条契约 | 认同，并补充撤销/审计契约 | 采用四条契约作为架构约束 |
| 工作区基线 | 作为风险提示 | 必须升格为第 0 步 | 先修超级搜索 P0 并完成全量回归 |
| 进度模型 | 后端发送 overall 和 phase | overall 容易重复制造进度倒退 | 后端只发 phase，前端按权重展示整体进度 |
| committing 阶段 | 单独列为阶段 | 与当前代码事务结构不符 | 删除 committing 阶段 |
| RAW 改造 | 可能涉及较大链路优化 | 真正明确问题集中在整文件扫描和真实样本未验收 | 先基准，后做有界扫描小修 |
| 视频播放 | 诊断后可能使用本地 HTTP | 应同时验证自定义协议与 HTTP | 两条路线各做最小 spike 后选路 |
| 视频 hover | 不兼容时生成代理 | 默认代理容易造成 ffmpeg 风暴 | 采用封面、原视频、可选代理三级策略 |
| 大批量打标 | 可新增 `ai_batch_chunks` | 首版成本过高 | 首版内存分块，重启后中断+一键续跑 |
| 撤销语义 | 只写了指标 | 缺少数据和产品语义 | 明确取消运行任务，撤销已应用标签 |
| 标签系统 | `tag_facets` 单一事实源 | 完全认同，前端迁移是最后断点 | Workbench 和设置页全面停止读取 `tagCategories` |
| 超级搜索一致性 | 需要全局规划 | 主协议已落地，无需重写 | 只修当前 P0/P1，不重做搜索架构 |

原计划中继续直接采用的内容：

- 入库清单始终提供继续添加入口；
- 页面只保留结果摘要，全局只保留一条进度条；
- RAW 先显示内嵌预览，后台再生成高清结果；
- 视频使用 HTMLMediaElement 的 `currentTime` 和 `playbackRate`；
- 用户选择的完整素材进入逻辑批次；
- 大列表和胶片条必须虚拟化；
- `tag_facets`、规范标签和 alias 是标签与搜索的共同基础；
- AI 搜索继续遵守 `SearchIntent -> ResolvedSearchQuery`；
- 所有失败都必须显式呈现，禁止静默忽略条件或素材。

## 1. 开发前必须理解的项目规则

### 1.1 当前工作区不是干净基线

当前仓库存在大量未提交改动，尤其是超级搜索、标签系统和素材库相关文件。开发代理必须把这些改动视为用户或其他开发者的有效工作，禁止回滚、覆盖或清理。

开发前必须执行：

```powershell
git status --short
git diff --stat
```

禁止使用：

```text
git reset --hard
git checkout --
git clean -fd
```

如果某个目标文件同时存在未提交修改，必须先阅读完整文件和相关 diff，再在现有实现上增量修改。不得用旧版本文件覆盖当前文件。

### 1.2 分层铁律

```text
React page
  -> component / store
  -> src/api
  -> Tauri command
  -> service
  -> db
```

必须遵守：

- `pages/` 只负责页面编排和页面级状态组合；
- 交互细节进入 `components/`；
- Zustand 状态和异步流程进入 `stores/`；
- Tauri 调用必须经过 `src/api/`；
- `commands/` 只做参数校验、状态读取、锁管理、事件转发；
- 业务逻辑进入 `services/`；
- SQL 只进入 `db/`；
- Rust 结构体字段变化必须同步 `src/types/` 和 API 类型；
- 网络请求不得持有数据库锁；
- 解码、ffmpeg、文件复制等耗时操作不得持有数据库锁。

### 1.3 图像解码唯一入口

所有图片、RAW、HEIC、TIFF 的解码必须继续走：

```text
src-tauri/src/services/imaging.rs
```

禁止在以下位置另写 RAW、TIFF 或 HEIC 解码：

- `preview.rs`；
- `thumbnail.rs`；
- `importer.rs`；
- React 组件；
- 新增的临时工具模块。

`preview.rs` 和 `thumbnail.rs` 必须保持瘦壳，只负责缓存、路径和业务调度。

### 1.4 统一错误和日志

Rust：

- 业务错误使用 `AppError::msg(...)` 和 `AppResult<T>`；
- 生产逻辑不得无理由使用 `unwrap()`；
- 单条素材失败必须使用 `tracing::warn!` 记录并继续批次；
- 不允许为每一张素材刷大量日志；
- 错误信息必须包含阶段、素材路径或素材 ID。

TypeScript：

- 异步错误进入 store 的 `error` 或页面错误状态；
- 不允许 `void invoke(...)` 后完全吞掉错误；
- 不使用未经说明的 `any`；
- 错误状态必须有可理解的用户文案。

### 1.5 依赖和样式

- 优先复用现有依赖和组件；
- 新增依赖前必须说明为什么现有依赖不能解决；
- 不为悬浮预览、任务条、视频控制器引入大型 UI 框架；
- 颜色优先使用 `src/styles/theme.css` 语义变量；
- 不在业务组件里新增无语义颜色硬编码；
- 不新增一套独立的圆角、阴影、字体系统；
- 大列表必须使用 `@tanstack/react-virtual` 或现有虚拟化方案；
- UI 控件必须保留可见 focus 状态。

### 1.6 交付三关

每个阶段结束至少执行：

```powershell
npm run typecheck
npm run build
cd src-tauri
cargo test
```

如果改动涉及前端交互，还必须执行：

```powershell
npm run test:unit
```

如果改动涉及 RAW、视频、缩略图或导入性能，还必须执行对应的真实素材性能探针，并在报告中写明样本目录、样本数量和机器配置。

## 2. 总体技术决策

评审后的最终决策如下：

| 领域 | 最终方案 |
|---|---|
| 超级搜索前置 | 先修复超级搜索两个 P0，再冻结基线 |
| 进度模型 | 后端只发送阶段进度，前端使用权重计算整体展示进度 |
| 入库阶段 | `queued / scanning / hashing / processing / previewing / done` |
| 入库 committing | 不新增独立 committing 阶段，当前代码是处理过程中的单文件写库 |
| RAW | 先真实样本验收，再修 `marker_scan_jpeg` 的有界读取，不做大重构 |
| 视频播放 | 先做 asset protocol 与 Range spike，同时验证自定义协议和本地 HTTP 两条路线 |
| 视频 hover | 首帧放大 -> 原视频静音短播 -> 可选代理预览，代理默认关闭 |
| 大批量打标 | 逻辑批次完整保留，执行时内部分块；首版不新增 chunk 表 |
| 重启恢复 | 首版将中断批次标记为 interrupted，用户一键续跑剩余 pending |
| 批次撤销 | 撤销已应用的标签操作；进行中的任务先取消，不把取消伪装成撤销 |
| 标签事实源 | `tag_facets` 唯一决定分面结构，`aiFacetConfigs` 只决定 AI 行为和提示语 |
| 旧分类 | `tagCategories` 仅作迁移输入，禁止继续作为业务渲染数据源 |
| 搜索协议 | 继续使用 `SearchIntent -> ResolvedSearchQuery` 两层协议 |

## 3. 阶段 0：修复超级搜索基线

这是正式改造的强制前置阶段。不要在超级搜索两个 P0 未修复时开始 Workbench、标签设置或搜索相关的新 UI 改造。

### 3.1 P0-1：修复构建器输入框失焦

#### 现象

`QueryBuilder.tsx` 中，输入每个字符都会：

```text
onChange
  -> updateRow
  -> commit
  -> store 更新
  -> exprToRows 重新生成 uid
  -> ConditionRow key 改变
  -> 输入框卸载重建
  -> focus 丢失
```

结果是关键词、相机、ISO 等输入框最多只能输入一个字符。

#### 推荐修法

采用“行身份与表达式值解耦 + 输入本地暂存”的方案：

1. `ConditionRow` 的稳定 ID 不能由每次 `exprToRows()` 调用重新生成；
2. 文本和数值输入先写入行本地 draft；
3. `onBlur`、Enter 或明确选择操作符后再 commit 到 store；
4. 输入过程中不得触发后端查询；
5. commit 后只更新当前行的值，不重建所有行；
6. 行结构变化时才允许重新计算表达式行。

如果当前组件结构更适合稳定行 ID，也可以只保留 `exprToRows()` 的已有 ID，但必须保证值变化不会改变 React key。不得使用内容 hash 作为唯一 key，除非证明同值行不会冲突。

#### 必须补的测试

文件：

```text
src/components/supersearch/QueryBuilder.test.tsx
```

测试至少覆盖：

- 输入 `abc` 后仍然是同一个 input；
- 输入 `abc` 后 `document.activeElement` 仍为 input；
- 输入过程中不触发三次后端查询；
- Enter 提交后查询条件正确；
- 失焦提交后查询条件正确；
- 添加新条件不会破坏已有输入行；
- 删除条件后其余行焦点和值正常。

### 3.2 P0-2：修复普通素材库数值分面回归

#### 现象

普通素材库点击 ISO、光圈或焦距分面后，前端形成：

```json
{
  "key": "iso",
  "op": "in",
  "values": ["800"]
}
```

后端数值字段不允许 `in`，同时数值解析不接受字符串，导致整次素材库查询失败。

#### 推荐修法

后端兼容现有前端语义：

1. 数值字段允许 `in`；
2. `compile_number` 同时接受 JSON number 和数字字符串；
3. 转换失败仍然返回明确错误；
4. 不在命令层偷偷转换，保持编译逻辑集中在 `search_query.rs`；
5. 前端后续可以逐步改为 number，但不能依赖前端改动才恢复旧功能。

建议支持 `in` 的数值字段：

```text
iso
aperture
focal
width
height
file_size
duration_ms
```

#### 必须补的测试

后端：

- `iso in ["800", "1600"]`；
- `iso eq 800`；
- `aperture gte 2.8`；
- 非数字字符串返回错误；
- NULL 数值不命中；
- 普通素材库 metadata facet 点击后查询成功。

前端：

- 点击 ISO 面板不会出现错误；
- 选多个 ISO 值可以合并；
- 清除 ISO 条件恢复全库；
- 既有 `MetadataPanel` 测试继续通过。

### 3.3 阶段 0 的完成定义

阶段 0 完成前不得进入阶段 1。完成标准：

- P0-1 有自动化连续输入测试；
- P0-2 有 Rust 编译测试和前端集成测试；
- `npm run typecheck` 通过；
- `npm run build` 通过；
- `npm run test:unit` 通过；
- `cd src-tauri; cargo test` 通过；
- 普通素材库的 ISO、光圈、焦距分面手动验证通过；
- 超级搜索关键词和数值条件可以连续输入。

### 3.4 阶段 0 可顺手修复但不得扩大范围的 P1

如果修改点直接相邻，可以同时修复：

- `taken_month` 上界多算一天；
- AI 搜索请求代际保护；
- OpenAI strict schema 的 required 和 `additionalProperties`；
- 查询表达式编译失败不得静默降级为全库。

如果要修复这些 P1，必须单独增加测试和在阶段报告中列出，不得混入无关 UI 重构。

## 4. 阶段 1：入库连续选择与任务反馈

### 4.1 目标文件

主要文件：

```text
src/pages/ImportPage.tsx
src/components/import/PendingList.tsx
src/api/import.ts
src/stores/taskStore.ts
src/components/layout/BottomBar.tsx
src/components/common/ProgressBar.tsx
src-tauri/src/commands/import_cmd.rs
src-tauri/src/services/importer.rs
```

除非发现明确的类型缺口，不要改动 `App.tsx` 的路由结构。

### 4.2 待入库清单 UI

当清单非空时，`PendingList` 固定头部必须提供：

- 添加文件；
- 添加文件夹；
- 列表/网格切换；
- 清空清单；
- 当前清单数量和总大小。

按钮行为：

- 添加文件调用已有文件选择器；
- 添加文件夹使用目录选择器；
- 两者都调用同一个 `stage(paths)`；
- 追加期间保留旧清单；
- 扫描失败不能清空旧清单；
- 新路径按规范化字符串去重；
- 不承诺不同路径形态的绝对去重，哈希去重仍由正式入库兜底；
- 正式入库运行中禁用添加、移除和清空。

不要在 `PendingList` 内直接调用 Tauri `invoke`。按钮事件通过 props 传给 `ImportPage`，页面再调用 API。

### 4.3 入库页面布局

推荐结构：

```text
ImportPage
  left aside
    statistics
    collection / rename options
    start import / clear list
  main
    import result summary
    error summary
    PendingList
      fixed action header
      scrollable list/grid
```

入库页只保留结果摘要，不再绘制第二条进度条。结果摘要可以显示：

```text
当前文件：IMG_0001.CR3
成功 128 · 重复 4 · 失败 2
阶段：正在生成快速预览
```

这不是进度条，不能再加入一条带百分比的 `ProgressBar`。

### 4.4 任务进度的最终契约

后端只发送阶段进度，不负责计算跨阶段整体百分比。

建议事件结构：

```ts
interface ImportProgress {
  taskId: string;
  phase: "queued" | "scanning" | "hashing" | "processing" | "previewing" | "done";
  phaseCurrent: number;
  phaseTotal: number | null;
  file?: string;
  imported: number;
  duplicates: number;
  failed: number;
  message?: string;
}
```

注意：

- 不新增 `committing` 阶段；
- 当前代码写库发生在 processing 内部，不要为了显示好看虚构阶段；
- `phaseTotal` 未知时必须使用不确定进度；
- 不允许在阶段切换时把一个全局 `current/total` 从头开始计数；
- `taskId` 用于防止旧任务事件污染新任务。

### 4.5 阶段权重

前端 `taskStore` 维护 UI 权重，例如：

```ts
const IMPORT_PHASE_WEIGHTS = {
  scanning: 0.05,
  hashing: 0.25,
  processing: 0.50,
  previewing: 0.20,
} as const;
```

权重只是 UI 展示决策，不能写入 Rust，也不能作为业务完成条件。

整体进度计算：

```text
previousPhaseWeight
  + currentPhaseWeight * phaseCurrent / phaseTotal
```

如果当前阶段或前置阶段没有可靠总量：

- 显示不确定进度；
- 显示阶段文案；
- 不伪造百分比。

### 4.6 任务条位置与状态

`BottomBar` 上方增加任务层：

```text
任务层：距离底栏上边缘 8~12px
底栏：固定高度 56px
```

任务层要求：

- 只由 `taskStore` 驱动；
- 不由页面重复订阅并绘制进度条；
- 默认一行摘要；
- 多任务时可以垂直展开；
- 任务条不得遮住底栏导航；
- 不使用纯红色背景表达失败；
- 失败任务显示文字和状态图标/符号；
- 完成后停留约 1.5 秒；
- 有失败项时保留“查看详情”能力。

### 4.7 入库任务生命周期

```text
queued
  -> scanning
  -> hashing
  -> processing
  -> previewing
  -> done
```

取消：

```text
running -> cancelling -> cancelled
```

取消不回滚已完成的入库记录。现有项目采用部分完成语义，必须保留。

### 4.8 阶段 1 完成定义

- 待入库清单非空时仍有添加文件和添加文件夹入口；
- 追加选择不会清除旧清单；
- 页面只显示结果摘要，不显示重复进度条；
- 底栏上方有唯一全局任务进度条；
- 点击开始入库后 300ms 内出现任务状态；
- 哈希阶段有阶段反馈；
- 阶段切换不会造成整体进度倒退；
- 取消、失败、重复和部分成功结果清晰；
- 入库期间素材库查询仍可执行；
- 入库相关 Rust 和前端测试通过。

## 5. 阶段 2：RAW 真实样本验收与小范围修复

这一阶段先做 spike，再决定是否修改。禁止直接把 RAW 解码器重写成新架构。

### 5.1 样本要求

准备 20 至 30 个真实 RAW 文件，至少覆盖：

- CR3；
- NEF；
- ARW；
- RAF；
- RW2；
- DNG。

样本应包含：

- 有内嵌预览；
- 内嵌预览很小；
- 没有可用内嵌预览；
- 不同分辨率；
- 至少一个大于 40MP 的样本；
- 至少一个异常或损坏样本。

### 5.2 必须记录的数据

每个样本记录：

```text
format
file_size
resolution
embedded_preview_found
embedded_preview_ms
placeholder_ms
hd_preview_ms
source_strategy
cache_hit
failure_reason
```

### 5.3 代码检查顺序

先检查 `imaging.rs`：

1. TIFF IFD 路径是否使用 seek 和局部读取；
2. CR3 box 路径是否使用 seek 跳过大 box；
3. `marker_scan_jpeg` 是否使用 `std::fs::read` 整文件读入；
4. 高清 RAW 真解码是否只在 `max_px > 320` 时执行；
5. 全局 4 许可是否仍然有效；
6. 入库占位层是否误触发真解码。

### 5.4 允许的首版修复

`marker_scan_jpeg` 可以改为有界、分块读取：

- 不得无界 `std::fs::read`；
- 读取使用固定块大小；
- 设定最大扫描字节数；
- 超过上限后返回 None，继续走通用占位图；
- 不把整个 RAW 载入内存；
- 保持现有 `embedded_preview` 策略顺序。

最大扫描值必须以常量命名并写注释说明，不允许散落魔数。

### 5.5 禁止的 RAW 改动

- 不新增第二个图像解码器；
- 不在前端解析 RAW；
- 不将 RAW 真解码移入入库占位图路径；
- 不为了追求首屏颜色而阻塞素材库列表；
- 不删除已有 RAW fallback；
- 不用合成 JPEG 样本代替真实 RAW 验收。

### 5.6 阶段 2 完成定义

- 真实样本基准报告已记录；
- 内嵌预览命中率明确；
- RAW 首屏先显示 placeholder 或内嵌预览；
- 真解码不进入入库快速占位路径；
- `marker_scan_jpeg` 不再无界整读；
- 45MP 样本高清预览目标不超过 3 秒，若未达标必须记录原因和下一步；
- `cargo test` 和性能探针通过。

## 6. 阶段 3：视频播放能力 spike

视频播放和视频 hover 预览分开处理。先保证查看器能稳定播放，再做 hover 短预览。

### 6.1 支持矩阵

至少准备：

- MP4 H.264/AAC；
- MOV H.264；
- MP4 H.265/HEVC；
- MKV H.264；
- WebM VP9；
- 大于 1GB 的视频；
- 高码率短视频；
- 损坏视频。

### 6.2 必须测量

前端记录：

- `video.canPlayType()`；
- `video.error?.code`；
- `networkState`；
- `readyState`；
- `loadedmetadata` 时间；
- `canplay` 时间；
- `stalled` 和 `waiting`；
- 通过时间轴跳转后的恢复时间。

资源层验证：

- 是否发送 Range 请求；
- 是否返回 `Accept-Ranges: bytes`；
- Range 是否返回 `206`；
- 越界是否返回 `416`；
- `Content-Range` 是否正确；
- `Content-Type` 是否正确。

### 6.3 两条资源服务路线必须同时评估

#### 路线 A：Tauri 自定义协议

验证：

- 是否能读取请求头中的 Range；
- 是否能返回 206 和 416；
- 是否复用现有路径访问校验；
- 是否能被 WebView 的 video 元素稳定消费。

优点：不开本地端口、路径权限更容易复用。  
风险：Tauri/Wry/WebView 媒体协议细节可能存在平台差异。

#### 路线 B：127.0.0.1 本地媒体服务

验证：

- 只监听 `127.0.0.1`；
- 素材通过 asset ID 映射，不接收任意绝对路径；
- 支持 Range、MIME 和错误码；
- 不触发不必要的系统防火墙弹窗；
- 应用关闭时服务正确终止。

优点：浏览器媒体栈对标准 HTTP Range 支持较成熟。  
风险：端口、生命周期和安全校验成本更高。

### 6.4 选路原则

两条路线各做最小 spike，不要先实现完整播放器。选择能够满足以下验收的方案：

- MP4 H.264 可以播放；
- 1GB 视频可以拖动；
- Range 头和状态码正确；
- 不把整视频读入 renderer 内存；
- 失败时能返回可理解错误。

如果自定义协议满足全部要求，优先选择自定义协议；否则选择 127.0.0.1 本地媒体服务。

### 6.5 视频查看器 UI

继续使用现有查看器结构，不新建独立路由。播放器控制区放在视频底部，保持固定高度，避免控制器出现后布局跳动。

控件：

- 播放/暂停；
- 后退 5 秒；
- 前进 5 秒；
- 时间轴；
- 当前时间/总时长；
- 倍速菜单：0.5x、1x、1.5x、2x；
- 静音/音量；
- 全屏。

实现要求：

- 后退使用 `currentTime = Math.max(0, currentTime - 5)`；
- 前进使用 `currentTime = Math.min(duration, currentTime + 5)`；
- 倍速使用 `playbackRate`；
- 不使用负 `playbackRate` 实现倒放；
- 播放错误必须显示错误状态和文件名；
- 控件按钮带 `aria-label` 和 tooltip/title；
- 使用现有主题变量，不使用鲜艳大色块。

## 8. 阶段 5：大批量打标队列

### 8.1 目标

取消用户感知的 100/500 张硬截断。用户选择的素材必须完整进入逻辑批次，内部执行层自行分块、限流和重试。

不得把“没有能力处理更多”表现成静默丢弃。

### 8.2 首版不新增 chunk 表

首版不新增 `ai_batch_chunks` 表，原因：

- 分块是执行层概念；
- 现有 suggestion 状态已经可以记录单素材结果；
- 新增分块表会扩大迁移、恢复和撤销复杂度；
- 用户真正需要的是剩余任务可见和一键续跑，不是查看内部第 37 个 chunk。

首版实现：

- `ai_batches` 保持逻辑批次；
- 调度器内存中按 20 至 50 张分块；
- 每个素材的结果继续写入现有 suggestion；
- 应用退出或任务中断时，将 processing 批次标记为 interrupted；
- 重新打开打标页时显示“有未完成批次，继续执行”；
- 续跑只处理仍为 pending 且没有候选的 suggestion。

### 8.3 运行参数

建议默认：

```text
云端子批大小：20~50
本地模型子批大小：根据模型能力，默认 10~20
并发数：1~3
重试次数：单项 1~2 次
退避：指数退避，设置最大等待时间
```

不要把这些参数混成用户总任务上限。设置页中的“批量上限”应改名为“执行分块大小”或“单次请求分块大小”。

如果必须保留保护上限，必须：

- 明确显示；
- 阻止提交而不是静默截断；
- 说明如何分批；
- 不能默认把用户选择变成不可见的前 N 张。

### 8.4 批次统计

UI 至少展示：

```text
总数
待处理
处理中
已生成建议
已确认
失败
已取消
```

胶片条和历史批次列表必须虚拟化，不得为数千张素材创建常驻重型 DOM。

### 8.5 撤销语义

必须明确区分：

#### 取消

- 作用于正在运行的 AI/本地任务；
- 停止尚未开始的请求；
- 已完成建议保留；
- 批次进入 cancelled/interrupted；
- 可一键续跑剩余 pending。

#### 撤销

- 作用于已经确认并写入的标签操作；
- 使用现有 `tag_ops` 和 `undoTagBatch`；
- 只撤销该批次已应用的 add/remove 操作；
- pending、rejected、失败素材不受影响；
- 进行中的请求必须先取消，不能直接把运行中任务当作可撤销。

UI 文案必须区分“取消任务”和“撤销已写入标签”。

### 8.6 阶段 5 完成定义

- 2000 张素材不会被静默截断；
- 分块执行期间界面可操作；
- 单张失败不会阻塞其他素材；
- 应用重启后能看到中断批次；
- 一键续跑只处理剩余 pending；
- 已确认标签可以按批次撤销；
- 取消和撤销文案、状态和测试清晰；
- 5000 条级别胶片条和批次列表保持可滚动。

## 9. 阶段 6：标签分面统一

这是打标页基础标签恢复的核心阶段。

### 9.1 唯一事实源

`tag_facets` 决定：

- 稳定 `facetKey`；
- 默认显示名；
- 描述；
- selection mode；
- max items；
- 排序；
- active/deprecated 状态。

`aiFacetConfigs` 只决定：

- 是否参与 AI；
- hint；
- 可选显示名覆盖。

`tagCategories`：

- 只作为旧数据迁移输入；
- 不再作为打标页、设置页或搜索页的业务渲染数据源；
- 不新增对它的读写路径。

### 9.2 Workbench 接口改造

当前 Workbench 使用 `TagCategory[]`。应改为接收稳定分面模型，例如：

```ts
interface WorkbenchFacet {
  key: string;
  displayName: string;
  description: string;
  selectionMode: "single" | "multi";
  maxItems: number | null;
  enabledForAi: boolean;
  hint: string;
}
```

前端加载链路：

```text
list_tag_facets
  + aiFacetConfigs 显示名/hint/enabledForAi 覆盖
  + 当前素材已有标签
  + 当前 AI 建议
  -> WorkbenchFacet[]
```

### 9.3 固定基础分面

即使当前素材没有标签、AI 没有返回建议、当前批次是手动模式，也必须显示系统分面：

- 主体/对象；
- 场景/地点；
- 用途；
- 风格/氛围；
- 色彩；
- 构图/视角；
- 光线/时间；
- 人物属性；
- 可用性/技术特征；
- 自定义。

当前素材或 AI 建议中的未知分类只能作为 `custom` 或候选显示，不能替换掉系统分面。

### 9.4 Workbench UI

保持现有工作台阅读顺序：

```text
主图
  -> 胶片条
  -> EXIF/状态
  -> 标签编辑区
  -> 确认操作区
```

标签编辑区要求：

- 分类名称固定宽度；
- 标签内容可换行；
- 分类之间用分隔线，不嵌套大量卡片；
- 输入框使用 `.ui-control`；
- “确认写入”是唯一主 CTA；
- “拒绝”使用次按钮，不使用红色实心；
- 已确认状态显示文字，不伪装成可点击按钮；
- maxItems 超限时显示明确的数量反馈；
- 单选分面选择新标签时替换旧值，而不是继续追加。

### 9.5 标签录入顺序

输入标签时：

1. 先按当前 facetKey 搜索规范名；
2. 再搜索 alias；
3. 展示完整路径和所属分面；
4. 显示最近使用标签；
5. 只有用户明确确认后才创建新标签；
6. AI 未知词只进入候选，不创建正式标签。

### 9.6 设置页

设置页不应继续把机器 key、显示名、hint、AI 开关、single/max 混在一行而没有层级。

建议拆成：

#### 系统分面

- 显示名称；
- 是否参与 AI；
- AI hint；
- 系统 key 只读；
- selection mode/max items 只读展示，真实来源为数据库。

#### 标签治理

- 搜索标签；
- 新建标签；
- 重命名；
- 移动；
- 合并；
- 添加别名；
- 停用；
- 查看影响范围。

后端已有的 `merge_preserve_alias`、停用和治理能力优先复用，不要重新设计数据库模型。

### 9.7 与超级搜索的同步回归

必须增加交叉测试：

- 设置页修改 facet hint；
- AI 打标读取新 hint；
- AI 超级搜索读取同一新 hint；
- 显示名改变不影响 facetKey；
- 标签别名在手动打标和超级搜索中都能命中；
- 未知搜索词只产生 warning，不创建标签。

## 10. UI 设计规范

### 10.1 视觉基调

项目是摄影素材管理工具，不是营销页面。界面必须保持：

- 暖灰画廊背景；
- 墨黑主操作；
- 低饱和状态色；
- 细分隔线；
- 内容优先；
- 少量阴影只用于弹层和浮动工具条。

### 10.2 颜色

优先使用：

```text
--color-bg
--color-surface
--color-surface-raised
--color-surface-hover
--color-border
--color-text
--color-text-secondary
--color-text-tertiary
--color-accent
--color-status
--color-success
--color-danger
```

规则：

- 主 CTA 使用 `--color-accent`；
- 进度和待确认使用 `--color-status`；
- 成功使用 `--color-success`；
- `--color-danger` 只用于错误、删除和危险反馈；
- 禁止用红色表达普通“拒绝”按钮默认态；
- 状态不能只依赖颜色，还要配合文字、图形或位置。

### 10.3 几何和响应式

- 主要区块间距 16px；
- 区块内部间距 12px；
- 紧凑列表行高 32 至 36px；
- 使用现有 `--radius-control` 和 `--radius-item`；
- 不使用大面积胶囊按钮；
- 窄窗口优先折行或滚动，不把正文缩小到不可读；
- 1366px、1920px 和最小窗口都不得发生重叠；
- 任务条、浮层、播放器控制器必须有稳定高度，避免内容出现时跳动。

### 10.4 按钮和图标

- 工具按钮优先使用熟悉图标或图标+短文本；
- 每个非文字图标按钮必须有 `aria-label` 和 `title`；
- 不为关闭、添加、播放、暂停、前进、后退等常见动作创建长文案按钮；
- 当前依赖中没有 lucide，除非有明确理由不要为了几个图标新增图标库；
- 可以沿用项目已有的简洁内联图标样式，但必须保持尺寸稳定。

### 10.5 Hover 浮层

- 不使用大面积渐变背景；
- 预览浮层是内容工具，不是装饰卡片；
- 最大尺寸固定，图片使用 `object-contain`；
- 视频和图片浮层不遮挡底栏和任务条；
- 浮层关闭不能让鼠标经过路径上的内容闪烁。

## 12. 测试要求

### 12.1 入库

- 连续选择两个文件夹；
- 清单非空时添加文件；
- 追加路径去重；
- 扫描结果为空时旧清单保留；
- 1000 个小文件；
- 大文件哈希阶段即时反馈；
- 取消后部分完成；
- 重复文件统计；
- 占位图生成失败时通用占位。

### 12.2 任务条

- 任务事件只产生一个展示条；
- 阶段切换不倒退；
- 未知 total 显示不确定进度；
- 完成停留；
- 失败保留详情；
- 页面切换后任务仍存在；
- 旧 taskId 事件不会污染新任务。

### 12.3 RAW

- 六种真实 RAW 格式；
- 内嵌预览命中；
- 无内嵌预览 fallback；
- 45MP 高清解析；
- 超大 RAW 内存保护；
- marker scan 上限；
- 损坏 RAW 不 panic。

### 12.4 视频

- H.264 MP4 播放；
- 播放暂停；
- 前进后退；
- 倍速；
- 时间轴；
- Range 206；
- Range 416；
- 大文件；
- 不支持编码错误；
- 损坏文件错误；
- hover 预览退出后停止。

### 12.5 批量打标

- 100、500、2000、5000 张；
- 单张失败继续；
- 批次取消；
- 应用重启后中断批次；
- 一键续跑剩余 pending；
- 已确认标签批次撤销；
- 取消不等于撤销；
- 胶片条虚拟滚动。

### 12.6 标签

- 新库基础分面非空；
- 手动模式可添加标签；
- AI 建议为空仍显示分面；
- facetKey 不受显示名修改影响；
- alias 搜索；
- 重命名保留 alias；
- 合并保留源名称；
- 停用标签不进入新候选；
- AI 未知词只产生 warning；
- 修改 hint 后 AI 打标和超级搜索同步。

## 13. 每阶段 AI 开发流程

开发代理每个阶段必须按以下格式工作。

### 开始前

1. 读取本文件对应阶段；
2. 读取 `ARCHITECTURE.md` 第四节和第六节；
3. 读取目标文件及调用方；
4. 执行 `git status --short`；
5. 列出准备修改和不准备修改的文件；
6. 先写测试验收点，再实施代码。

### 实施中

- 小步修改，每次只处理一个契约或一个 UI 组件；
- 使用 `apply_patch`；
- 不重排无关代码；
- 不全量格式化工作区；
- 不改变文件行尾和无关注释；
- 遇到已有未提交代码冲突时停下来分析，不回滚；
- 需要改变协议时先同步 TypeScript、Rust、测试和文档。

### 完成后

必须输出：

```text
阶段：
目标：
修改文件：
新增文件：
删除文件：
前端协议变化：
Rust 协议变化：
数据库迁移变化：
UI 变化：
测试命令：
测试结果：
手动验收：
已知问题：
下一阶段前置条件：
```

### 阶段门禁

下一阶段只有在以下条件全部满足后才能开始：

- 当前阶段完成定义满足；
- 自动化测试通过；
- 没有未解释的 TypeScript/Rust 编译错误；
- 没有未解释的数据库迁移错误；
- UI 关键流程已手动走通；
- 变更没有覆盖其他人的未提交工作；
- 文档和 `PROGRESS.md` 已更新。

## 15. 最终交付标准

整个改造完成后，必须满足：

- 入库清单可以连续添加任意多个文件夹；
- 入库点击后立即出现任务状态；
- 应用只显示一条统一任务进度条；
- 页面仍显示当前文件和成功/失败摘要；
- RAW 先显示低成本预览，后台再生成高清图；
- 图片和视频支持 300ms hover 预览；
- 视频查看器支持播放、暂停、跳转和倍速；
- 视频大文件具备可验证的 Range 读取能力；
- 2000 至 5000 张素材不会被静默截断；
- 批次可以取消、续跑和撤销已写入标签；
- 基础标签分面永远显示；
- 打标页、设置页、标签管理和超级搜索使用稳定 `facetKey`；
- AI 未知标签不污染正式标签树；
- 普通素材库 ISO、光圈和焦距筛选不回归；
- 超级搜索连续输入不丢焦点；
- `npm run typecheck`、`npm run build`、`npm run test:unit` 和 `cargo test` 全部通过；
- 真实 RAW 和视频样本验收记录完整；
- 所有阶段的已知限制和未完成事项已写入文档。
