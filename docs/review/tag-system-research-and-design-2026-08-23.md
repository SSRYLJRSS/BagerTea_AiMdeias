# 素材标签系统调研与设计建议

**项目：** 茶包素材 BagerTea V2（本地素材管理器）  
**调研日期：** 2026-08-23  
**范围：** 标签分类、层级、搜索、用户操作、AI 打标、词表治理、数据模型与落地顺序  
**本报告性质：** 调研和设计建议，不修改业务代码

## 1. 执行摘要

当前项目已经具备标签系统的关键底座：

- `tags` 支持父子层级、同级同名约束、移动、删除、合并；
- `asset_tags` 支持素材与标签多对多关联，并记录 `source`；
- `assets_fts` / `fts_content` 已把文件名和标签纳入 FTS5；
- 素材查询已经有 `tag_mode=any/all` 能力；
- AI 建议先写入 `ai_suggestions`，确认后才写入正式 `asset_tags`；
- AI 分类可在设置页自定义。

问题不在于“有没有标签”，而在于**所有信息都被建模成同一种标签**。这会带来三个长期风险：

1. 语义混杂：`茶`、`红色`、`待审核`、`公众号封面`、`2026 春茶项目` 被放在同一棵树里，用户不知道应该从哪里找。
2. 标签膨胀：AI 或用户会产生 `清新`、`清爽`、`小清新`、`低饱和清新` 等近似词，搜索结果不稳定。
3. 维护成本高：分类改名、同义词、人工确认、AI 来源、低频标签和导出兼容没有清晰的治理边界。

### 最终建议

采用 **“固定分面 + 轻量层级 + 受控词表 + 少量自由标签 + AI 建议审核”** 的混合模型：

- 保留现有父子标签树，作为底层兼容和管理方式；
- 在产品界面上按分面展示，不把全部标签混成一棵导航树；
- 用户可见层级控制在 2 层，极少数场景允许 3 层；
- 推荐首版使用 9 个内容分面，另设系统筛选字段；
- AI 产生的是“候选标签”，不能直接成为事实；
- 搜索采用“关键词搜索 + 分面筛选 + 任意/全部标签逻辑”；
- 为规范标签增加别名、规范化名称、来源、置信度和人工确认状态；
- 先治理搜索和打标体验，再考虑复杂本体、知识图谱或自动合并。

## 2. 调研方法与证据等级

### 2.1 调研对象

本次参考了以下类型的实践：

| 类型 | 参考对象 | 关注点 |
|---|---|---|
| 摄影管理 | Adobe Lightroom Classic、digiKam、Photo Mechanic、Capture One 等 | 关键词层级、同义词、批量打标、元数据兼容 |
| 素材管理 | Eagle、PhotoPrism、Ente 等 | 标签/文件夹边界、快速筛选、视觉搜索 |
| DAM | IPTC Photo Metadata、XMP/IPTC 词汇、DAM taxonomy/facet 实践 | 受控词表、分面、标准字段、跨软件交换 |
| 社区与源码 | GitHub 开源项目、V2EX 公开 API、可访问的公开讨论 | 真实痛点、层级标签实现方式、用户治理成本 |

### 2.2 证据等级

- **A：** 官方文档或标准规范明确写出的能力/约束；
- **B：** 开源项目源码、官方仓库示例、可复现实现；
- **C：** 社区讨论中的经验和抱怨，只作为体验信号，不作为规范；
- **D：** 根据当前项目代码和上述资料推导出的设计建议。

由于部分厂商帮助中心存在地区限制、路径迁移或反爬，本报告不会把无法稳定打开的页面内容当作独立证据；来源清单中会保留官方入口，且把“官方能力”和“本项目推导”分开。

## 3. 行业实践提炼

### 3.1 Lightroom 类摄影软件：层级关键词解决规模问题，但需要规范词表

摄影软件普遍把关键词分成三种用途：

- **层级关键词：** 例如 `主体/饮品/茶/绿茶`，用于从宽到窄浏览；
- **同义词或导出词：** 用户输入“奶茶”时可以命中规范词“茶饮”，导出时可使用外部需要的词；
- **智能集合/筛选条件：** 将关键词与评分、日期、相机、位置等字段组合，不要求所有信息都成为标签。

可借鉴的核心不是照搬 Lightroom 的复杂面板，而是三条原则：

1. 标签要有“规范名称”，用户常用说法应通过别名命中；
2. 层级只解决语义从属关系，不承担项目、状态、时间等所有筛选条件；
3. 关键词录入必须能批量复用，否则用户会放弃维护。

### 3.2 digiKam：标签树适合管理，元数据设置决定可迁移性

digiKam 的文档把标签管理、元数据和设置分开，说明成熟工具通常不会把“内部分类树”和“文件元数据交换”混为一谈。对本项目有两个直接启示：

- 内部标签可以服务于快速检索，不必强制每次都写回原文件；
- 如果未来支持 XMP/IPTC 导入导出，应定义哪些标签可同步、哪些是本地工作流字段。

### 3.3 IPTC/XMP：主题词只是元数据的一部分，不等于所有业务字段

IPTC Photo Metadata Standard 和 User Guide 将照片元数据拆成描述、位置、人物、版权、状态等字段，并提供词汇表机制。可借鉴的设计边界：

- **内容描述**适合关键词/主题词；
- **版权、作者、来源、使用限制**应是独立字段；
- **拍摄时间、GPS、格式、尺寸、设备**应优先使用结构化字段；
- **受控词汇**需要稳定 ID、定义和别名，而不是只保存显示字符串。

### 3.4 Eagle/PhotoPrism 类工具：快速使用优先，分类不应成为学习门槛

素材库工具通常提供文件夹、标签、收藏、评分、搜索或语义搜索的并行入口。其共同经验是：

- 用户第一次导入素材时，不应被迫先建立完整分类体系；
- 搜索框、最近使用标签、批量操作比“完美树结构”更能决定日常效率；
- 文件夹更接近物理/项目归档，标签更接近跨文件的内容属性；
- 标签树应支持折叠、计数、搜索和多选，不能只靠手动逐层展开。

### 3.5 开源实现：层级标签通常采用路径或 parent_id，但搜索需要额外规范化

公开源码中常见两种实现：

- `parent_id` 关系表，适合重命名、移动、统计后代数量；
- `subject/child` 或 `project/team` 路径字符串，适合快速输入和导入导出。

当前项目采用 `parent_id`，从长期维护看更稳妥。需要补充的是规范化层：

- 标签显示名不应直接承担唯一检索语义；
- 需要规范名、别名、搜索 token 和可选的外部映射；
- 仅把标签名拼成 `tag_names` 再做 FTS，无法表达分面、同义词、排除条件和来源权重。

## 4. 用户痛点与失败模式

以下痛点在摄影/DAM 社区和多个产品的设计演化中反复出现，也与当前项目的代码结构直接相关：

| 痛点 | 用户表现 | 设计对策 |
|---|---|---|
| 标签太多 | 标签列表像词典，找不到常用项 | 只展示常用/最近使用，支持分面和搜索 |
| 同义词泛滥 | `清新`、`清爽`、`小清新`各自有结果 | 规范标签 + 别名 + 合并建议 |
| 分类边界不清 | “风景”到底是主体、场景还是用途 | 给每个分面写定义和示例，避免一词多义 |
| 层级太深 | 用户必须记住路径 | 可见深度 2 层，搜索结果显示完整路径 |
| AI 标签不可信 | 置信度未知，错误标签一旦写入就难清理 | AI 建议与正式标签分离，支持逐条确认/拒绝 |
| 文件夹和标签重复 | 同一素材被复制到多个项目目录 | 文件夹负责归档，标签负责跨目录属性 |
| 搜索结果过宽 | 搜“茶”命中大量无关内容 | 规范化 token、分面过滤、任意/全部逻辑 |
| 批量操作风险 | 一次误加标签影响大量素材 | 预览变更数、撤销批次、显示来源 |
| 新用户无从下手 | 第一次使用就要设计词表 | 提供默认分面和推荐标签，允许稍后治理 |

## 5. 当前项目的现状评估

### 5.1 已有优点

代码层面已经有几个非常值得保留的设计：

1. `tags.parent_id` + `UNIQUE(parent_id, name)`：允许树形组织，并防止同一父节点下重复命名。
2. `asset_tags` 多对多：素材可以同时属于多个主体、场景和用途。
3. `asset_tags.source`：已经能区分 `manual`、`ai_cloud`、`ai_local`，这是后续治理的关键字段。
4. `tag_ops`：已有打标流水和撤销入口，适合扩展批量操作回滚。
5. AI 建议单独存储：`ai_suggestions` 在确认之前不写正式关联，方向正确。
6. 搜索已有 CJK bigram、FTS5、LIKE 回退和 `any/all` 模式，说明搜索底层不是从零开始。

### 5.2 当前结构的主要限制

根据 `src-tauri/src/db/migrations.rs`、`tags.rs`、`search.rs`、`asset_tags.rs`、`ai.rs` 和设置页代码：

- `tags` 只有名称、父级、预置标记和排序，没有分类类型、规范名、别名、定义、状态；
- FTS 的 `tag_names` 是所有关联标签名称的拼接，无法区分“主体茶”和“状态待审核”；
- AI 确认时按 AI 返回的分类创建根标签和子标签，容易把模型输出直接扩大成词表；
- 用户可配置分类，但分类不是稳定 ID；分类改名时，历史标签的语义关联需要额外处理；
- `source` 是关联级别字段，尚未保存模型、提示词版本、置信度、人工确认时间等审计信息；
- 父标签统计包含后代素材，这是好的浏览体验，但搜索语义必须明确“点击父标签是否包含后代”。

### 5.3 关键设计判断

**不建议**现在把所有标签全部迁移成新的字段体系，也不建议立刻引入完整知识图谱。原因是当前项目是本地桌面应用，用户规模和数据量尚未证明需要复杂本体；同时直接改动现有树和 FTS 会增加迁移风险。

**建议**先在现有表上增加“类型/规范化/别名/AI 审核”的轻量能力，并在 UI 上以分面呈现。这样可以兼容旧数据，逐步治理。

## 6. 推荐的目标模型

### 6.1 三层概念

```text
结构化字段：文件格式、尺寸、拍摄时间、导入时间、评分、状态
        |
固定分面标签：主体、场景、风格、色彩、构图、光线、人物、用途、技术
        |
自由标签：用户临时项目词、客户名、灵感词、个人笔记词
```

三层边界如下：

- **结构化字段**适合精确比较、排序和范围筛选；
- **固定分面标签**适合跨素材复用和组合搜索；
- **自由标签**适合不值得进入公共词表的临时概念。

### 6.2 标签与文件夹的边界

| 对象 | 适合表达 | 示例 | 是否允许一项多处出现 |
|---|---|---|---|
| 文件夹/分库 | 物理位置、项目归档、备份边界 | `2026/春茶宣传/初稿` | 通常不建议复制 |
| 标签 | 内容属性、视觉属性、跨项目复用 | `主体/茶`、`场景/茶室` | 是 |
| 收藏/智能集合 | 临时工作集、保存的查询 | `本周待选` | 是 |
| 结构化字段 | 可排序、可范围过滤的信息 | 尺寸、日期、评分、状态 | 一个值或有限多值 |

规则：如果用户会问“这个素材是什么/有什么特征”，优先标签；如果会问“这个素材属于哪个工作流/什么时候/多大”，优先字段或集合。

## 7. 推荐分面和分类树

建议首版固定 **9 个分面**。分面是 UI 层概念，底层可以继续映射到现有父子标签。

### 7.1 主体/对象

```text
主体
  饮品
    茶
    咖啡
    果汁
  食物
    点心
    水果
  器物
    茶具
    杯子
    包装
  植物
  人物
  动物
  建筑
```

用途：回答“画面里有什么”。允许多选。AI 可建议，但应由人工确认。

### 7.2 场景/地点

```text
场景
  室内
    茶室
    厨房
    棚拍
  室外
    公园
    街道
    海边

    门店
    展会

    山林
    草地
```

用途：回答“在哪里”。建议允许多个场景词，但 AI 默认最多 2 个。

### 7.3 用途/项目

```text
用途
  电商
  社交媒体
  公众号
  海报
  包装设计
  教程/说明
  品牌资产
```

这里需要特别注意：如果项目名、客户名或阶段经常变化，优先建成独立字段或项目集合，而不是永久标签。分面只保留稳定的用途类型。

### 7.4 风格/情绪

```text
风格

  复古
  国风
  日系
  商业棚拍
  生活方式

  清新
  宁静
  温暖
  热烈
  治愈
  高级
```

“风格”和“情绪”是否合并取决于素材量。当前项目可先合并成“风格氛围”，当数据超过约 5,000 个标签实例后再拆分。

### 7.5 色彩

```text

```

颜色适合做可视化色块和多选筛选。不要让 AI 为同一画面同时生成大量近似词。

### 7.6 构图/视角

```text
构图
  景别
    特写
    半身
    中景
    全景
  视角
    平视

```

这是当前 AI 默认分类中最有价值的部分之一，但“构图视角”不应设置为严格单选，因为一张图可能同时是俯拍、特写和留白。

### 7.7 光线/时间

```text
光线

  人工光
  柔光
  硬光
```

“黄昏”既可能是拍摄时间也可能是色调风格。规范定义中应说明：时间分面只描述可观察的时间线索，不能把“黄昏金调”当作时间事实。

### 7.8 人物/主体属性

```text
人物
  无人物
  单人
  多人
  儿童
  成人
  动作
    手持
    品饮
    行走
```

如果没有人脸识别或姿态模型，首版只保留粗粒度词，避免制造虚假的精确性。

### 7.9 技术/格式

建议首选结构化字段；只有无法从文件可靠推导的视觉技术属性才做标签：

```text
技术
  透明背景
  可裁切
  可循环
  高分辨率
  竖版构图
```

文件类型、像素尺寸、视频时长、编码格式、拍摄设备不建议作为普通标签。

## 8. 哪些内容不应做标签

以下字段应保持结构化或状态化：

- 文件名、扩展名、MIME、尺寸、时长、编码；
- 创建时间、修改时间、拍摄时间、导入时间；
- 评分、收藏、选中、拒绝、待审核；
- AI 任务状态、批次、模型、置信度；
- 版权、作者、来源、许可、使用期限；
- 文件夹、分库、项目阶段；
- “已导出”“已交付”“需修图”等工作流状态。

把这些信息做成字段的好处是可排序、可统计、可校验，也不会污染内容标签搜索。

## 9. 搜索和筛选设计

### 9.1 搜索入口

搜索框支持三种输入：

1. 普通关键词：匹配文件名、规范标签、别名和备注；
2. 标签路径：如 `主体/饮品/茶`；
3. 简单操作符：如 `tag:茶`、`facet:场景=茶室`、`-tag:待审核`。

首版不必实现复杂布尔语言，但应预留解析器，不要把操作符当普通字符串传给 FTS。

### 9.2 分面筛选

右侧或顶部显示已命中的分面：

```text
关键词：茶
主体：茶（全部）
场景：茶室（全部）
色彩：绿色（任意）
状态：未确认（排除）
```

建议逻辑：

- 同一分面内默认 OR，例如主体“茶”或“咖啡”；
- 不同分面之间默认 AND，例如主体=茶 且 场景=茶室；
- 用户可切换“同一分面全部满足”；
- 父标签点击默认包含后代，提供“仅此标签”选项。

### 9.3 任意标签与全部标签

当前项目已经有 `any/all` 方向，建议在 UI 中明确命名：

- **任意匹配：** 包含所选标签中的至少一个；
- **全部匹配：** 同时包含所选标签；
- **排除：** 不包含所选标签。

避免使用只对开发者友好的 `any/all` 文案。

### 9.4 搜索排序

建议排序优先级：

1. 最近使用或最近导入；
2. 规范标签完全命中；
3. 别名命中；
4. 文件名命中；
5. 模糊/分词命中。

当前 FTS + LIKE 可以保留，但标签路径、别名和分面筛选应走结构化 SQL 条件，不应全部塞进 FTS 字符串。

### 9.5 空状态和引导

搜索无结果时显示：

- 是否搜索了别名；
- 是否切换为“任意匹配”；
- 是否清除某个分面；
- 是否包含未确认 AI 建议；
- 可一键查看“未分类素材”。

不要只显示“没有结果”，否则用户无法判断是没有素材还是标签词不一致。

## 10. 标签录入与日常使用流程

### 10.1 新用户首次使用

默认显示少量常用分面和推荐词，不要求先配置完整词表：

1. 导入素材；
2. 看到 AI 推荐或“常用标签”；
3. 一键确认/批量套用；
4. 在搜索中点击标签反向浏览；
5. 只有出现重复词或新项目需求时才进入标签治理。

### 10.2 手动打标

输入框应支持：

- 直接输入搜索已有标签；
- 显示完整路径和所属分面；
- 最近使用标签；
- 创建新标签时要求选择分面；
- 显示同义词提示，例如“清爽”已映射到“清新”；
- 批量素材上显示“新增 N 个，已有 M 个”。

### 10.3 批量打标

批量对话框建议显示预览：

```text
将对 128 个素材执行：
新增：主体/饮品/茶、场景/室内/茶室
跳过：已有标签 76 个
风险：其中 14 个素材已有“场景/室外”
```

提交后生成一个可撤销批次，沿用现有 `tag_ops` 思路。

### 10.4 标签治理

标签管理页应提供四类视图：

- 高频标签；
- 低频/孤立标签；
- 近似或重复标签；
- 未确认 AI 标签。

治理操作包括重命名、合并、移动、设置别名、停用和批量替换。删除应尽量改为“停用”而不是立即物理删除，以保留历史搜索和撤销能力。

## 11. AI 标签设计建议

### 11.1 AI 输出分为四个阶段

```text
模型输出 -> 规范化候选 -> 人工确认 -> 正式标签
```

每一步都应可追溯。不要将模型原文直接当成标签主数据。

### 11.2 建议保存的信息

现有 `ai_suggestions` 可逐步增加：

- `category_id` 或稳定分类 key；
- 原始标签文本；
- 规范标签 ID；
- 置信度；
- 来源模式：cloud/local/manual；
- 模型名和模型版本；
- 提示词版本；
- 人工操作：confirmed/rejected/modified；
- 确认人和确认时间。

如果不想立即改表，可先把这些信息放入 JSON 扩展字段，但应固定字段名和版本号。

### 11.3 AI 词表约束

给每个分面定义：

- 描述；
- 可用词表；
- 是否单选；
- 最大标签数；
- 置信度门槛；
- 允许的自由词比例。

例如：

| 分面 | 单选 | 最大数 | 默认置信度门槛 | 备注 |
|---|---:|---:|---:|---|
| 主体 | 否 | 5 | 0.70 | 可多主体 |
| 场景 | 否 | 2 | 0.75 | 地点不确定时不猜 |
| 主色 | 否 | 3 | 0.80 | 颜色词应受控 |
| 构图 | 否 | 4 | 0.70 | 只输出可观察属性 |
| 光线 | 否 | 3 | 0.75 | 不把风格词当光线 |
| 用途 | 否 | 2 | 不建议 AI 默认推断 | 通常由人工指定 |
| 工作流状态 | 是 | 1 | 禁止 AI 自动写入 | 结构化状态 |

### 11.4 AI 确认 UX

建议支持三种操作：

- 单条确认：接受、修改、拒绝；
- 批量确认：只确认高置信度，低置信度保留待审；
- 批量套用：将某个素材的最终标签复制给相似素材。

确认后必须能看到“这是 AI 建议还是人工添加”，并可按来源筛选和撤销。

## 12. 同义词、别名和多语言

### 12.1 数据规则

每个规范标签建议有：

```text
label_id: stable id
display_name: 茶
path: 主体/饮品/茶
aliases: 茶叶, tea, tea leaf
locale: zh-CN / zh-TW / en
status: active / deprecated
```

### 12.2 搜索规则

- 用户搜索别名时，结果映射到规范标签；
- 展示结果优先显示用户语言的规范名；
- 新建标签时先提示已有规范标签和相似别名；
- 简繁体、大小写、全半角、空格和连字符统一规范化；
- 不要在数据库里为每个语言复制一棵完整树。

### 12.3 合并规则

合并前显示影响范围：素材数、AI 批次数、历史操作数。合并后保留旧名称为别名，而不是彻底丢失旧词。

## 13. 数据模型建议

### 13.1 最小增量方案

在现有 `tags` 上增加：

```sql
ALTER TABLE tags ADD COLUMN facet_key TEXT NOT NULL DEFAULT 'custom';
ALTER TABLE tags ADD COLUMN canonical_name TEXT;
ALTER TABLE tags ADD COLUMN description TEXT;
ALTER TABLE tags ADD COLUMN status TEXT NOT NULL DEFAULT 'active';
ALTER TABLE tags ADD COLUMN is_system INTEGER NOT NULL DEFAULT 0;
```

新增别名表：

```sql
CREATE TABLE tag_aliases (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  tag_id INTEGER NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
  alias TEXT NOT NULL,
  locale TEXT,
  UNIQUE(alias, locale)
);
```

新增分类表或稳定配置：

```sql
CREATE TABLE tag_facets (
  key TEXT PRIMARY KEY,
  display_name TEXT NOT NULL,
  description TEXT,
  selection_mode TEXT NOT NULL DEFAULT 'multi',
  max_items INTEGER,
  sort_order INTEGER NOT NULL DEFAULT 0,
  is_system INTEGER NOT NULL DEFAULT 0
);
```

### 13.2 不建议首版做的模型

- 不建议立即把标签改为多级闭包表；
- 不建议立即引入 RDF/OWL 知识图谱；
- 不建议把每个 AI 原始词都永久写入标签主表；
- 不建议把所有结构化字段复制成标签；
- 不建议用路径字符串替换现有 `parent_id` 关系。

### 13.3 FTS 改造方向

保留 `fts_content` 和 `assets_fts`，但增加可检索列或独立 join：

- `canonical_tag_names`：规范标签名；
- `alias_names`：别名搜索文本；
- `facet_keys`：可选，适合快速候选提示；
- 结构化分面条件通过 `EXISTS` 子查询完成；
- 文件名和备注继续进入 FTS。

不要把“标签是否 AI 确认”“状态”“日期范围”等逻辑编码到拼接文本里。

## 14. 兼容现有数据的迁移策略

### 阶段 A：零破坏识别

1. 为现有根标签建立 `facet_key` 映射；
2. 无法判断的标签标记为 `custom`；
3. 保留原 `parent_id`、标签 ID 和素材关联；
4. 给常见重复词建立别名，不立即删除旧标签。

### 阶段 B：AI 输出收敛

1. AI 输出先匹配规范标签；
2. 未匹配词进入“待治理候选”；
3. 人工确认后才创建新标签；
4. 为每个批次记录词表版本。

### 阶段 C：搜索升级

1. 先把别名并入搜索；
2. 再加分面筛选；
3. 最后增加排除、保存搜索和排序权重；
4. 每阶段都保留旧关键词搜索作为回退。

## 15. 分阶段落地计划

### P0：先改善用户可用性

- 明确标签与文件夹边界；
- 根标签显示分面名称和计数；
- 搜索支持点击标签、任意/全部/排除；
- 标签输入显示完整路径和最近使用；
- AI 建议展示置信度/来源，并保持确认后写入；
- 建立默认 9 分面及说明。

### P1：治理重复和搜索质量

- `facet_key`、规范名、别名表；
- 同义词和简繁体规范化；
- 低频标签、重复标签、未确认标签视图；
- 父标签搜索包含后代，并提供“仅此标签”；
- 批量操作预览和撤销。

### P2：结构化工作流

- 状态、用途、项目改为字段或智能集合；
- 保存搜索；
- XMP/IPTC 导入导出映射；
- AI 模型/提示词版本和统计；
- 词表导入导出和版本迁移。

### P3：可选增强

- 语义搜索和视觉相似度；
- 自动推荐标签，但不自动确认；
- 跨库同步规范词表；
- 基于用户搜索日志的标签排序。

## 16. 验收指标

上线标签改造后，建议用真实使用数据验证，而不是只看单元测试：

| 指标 | 建议目标 |
|---|---:|
| 新用户首次找到素材的时间 | 小于 30 秒 |
| 常用标签从输入到确认 | 不超过 2 次点击 |
| 搜索无结果后通过别名找到的比例 | 持续上升，作为词表治理信号 |
| AI 建议人工确认率 | 分面分别统计，不追求统一阈值 |
| 低频标签占比 | 控制在总标签实例的 20% 以下 |
| 重复/近似标签月增长 | 应逐月下降 |
| 批量误操作撤销成功率 | 100% 可撤销 |
| 分面筛选平均响应 | 本地库常规操作小于 200ms |

## 17. 不建议做的事情

1. 不要一开始建立几十个大类和数千个小类；
2. 不要把每个 AI 输出词都自动写进正式词表；
3. 不要用文件夹层级替代标签系统；
4. 不要把评分、日期、格式、状态做成普通标签；
5. 不要强制用户每张素材都填写完整标签；
6. 不要为了“语义完整”把标签树做成 4 层以上；
7. 不要删除旧标签后丢失别名、历史操作和撤销信息；
8. 不要把复杂查询语法作为普通用户的唯一搜索入口；
9. 不要将用途、项目阶段等高变化信息固化到永久内容词表；
10. 不要在没有真实数据量和搜索日志前过早引入知识图谱。

## 18. 最终推荐方案（一句话版本）

对当前项目，最合适的不是“再设计一棵更大的标签树”，而是：

> **保留现有父子树作为存储，增加稳定分面和规范词表；用结构化字段承载状态/时间/格式，用别名解决用户语言差异，用分面搜索组合多个条件，用 AI 建议审核流程避免词表污染。**

推荐首版分面为：

1. 主体/对象
2. 场景/地点
3. 用途/项目类型
4. 风格/情绪
5. 色彩
6. 构图/视角
7. 光线/时间氛围
8. 人物/主体属性
9. 技术/可用性

其中“项目名、流程状态、版权、格式、日期、尺寸、评分”优先做字段或智能集合，而不是永久标签。
