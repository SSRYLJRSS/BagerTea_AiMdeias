## 1. 总体目标

本轮目标是恢复以下完整用户流程：

```text
素材库选择素材
  -> 视频/图片悬浮预览位置正确且可播放
  -> 进入 AI 打标
  -> 视频开关可在设置页正常开启并保存
  -> AI 生成建议
  -> “全部确认”按钮持续可见并批量写入
  -> 工作台只显示用户需要的分面
  -> 色彩/光线/时间等标签按稳定 facet key 正确归类
  -> 历史批次撤销不误删后续人工标签
```

## 2. 非目标与禁止事项

本轮不要做以下事情：

1. 不重写整个素材库、AI 打标或设置页。
2. 不引入新的状态管理库、UI 框架或大型媒体播放器依赖。
3. 不删除旧字段或破坏现有设置迁移兼容性。
4. 不改变 `commands -> services -> db` 分层。
5. 不在页面组件中直接调用 Tauri `invoke`；必须走 `src/api/`。
6. 不在数据库锁内执行网络请求、视频抽帧、图像解码或大文件 IO。
7. 不因为“测试现在是绿的”而跳过新增回归测试。
8. 不直接修改历史迁移 SQL；新增数据库变化必须添加新版本迁移。
9. 不把未知 facet key 静默归为 `custom` 而不记录 warning。
10. 不把“卡片文本选择问题”直接列为必做项，除非先得到真实复现证据。

## 7. 阶段 B：批量确认与视频开关链路

### B-1 修复统计语义

修改：`src/pages/AiTaggingPage.tsx`。

必须定义以下纯函数或等价清晰逻辑：

```ts
const pendingSuggestions = suggestions.filter((s) => s.status === "pending");
const awaitingGeneration = pendingSuggestions.filter(
  (s) => Object.keys(s.suggestedTags).length === 0,
);
const awaitingConfirmation = pendingSuggestions.filter(
  (s) => Object.keys(s.suggestedTags).length > 0,
);
const confirmed = suggestions.filter((s) => s.status === "confirmed");
```

按钮规则：

```text
running = true                 隐藏“全部确认”
running = false 且 awaitingConfirmation > 0  显示“全部确认（N）”
awaitingConfirmation = 0       不显示
```

按钮不能使用 `stats.pending`，必须使用“待确认建议”数量。

统计文案建议：

| 数值 | 文案 |
| --- | --- |
| `awaitingGeneration` | 待生成 |
| `awaitingConfirmation` | 待确认 |
| `confirmed` | 已确认 |
| rejected | 失败/已拒绝 |

不要再使用“处理中”表示多个不同状态。若保留旧版统计，必须明确它的计算含义。

要求：

## 9. 阶段 D：批次撤销数据安全

这是本轮最需要谨慎实现的后端任务。不能只把原 SQL 改成加一个 `source_batch_id` 条件后就结束。

### D-1 当前数据模型边界

`asset_tags` 的主键是 `(asset_id, tag_id)`，一条素材与一个标签当前只有一条关联。因此同一个标签被多个 AI 批次确认时，后续批次可能因为 `INSERT OR IGNORE` 不产生新的关联记录。

这意味着当前模型存在“单归属”边界：

```text
批次 A 添加 X
批次 B 再确认 X（INSERT OR IGNORE，不新增关联）
撤销 A -> X 可能被删除
撤销 B -> 没有自己的关联可恢复
```

本轮不要求重构成多来源关联表，但必须把这个边界写进测试和 UI 语义，不能假装已经完美解决。

### D-2 手工覆盖必须清空批次来源

当前 `asset_tags::assign_inner` 的手工覆盖分支只更新 `source='manual'`，没有清空 `source_batch_id`。

必须改为：

```sql
UPDATE asset_tags
SET source='manual',
    source_batch_id=NULL,
    confidence=NULL,
    confirmation='confirmed',
    confirmed_at=?3,
    confirmed_by='manual'
WHERE asset_id=?1
  AND tag_id=?2
  AND source != 'manual'
```

这样可以保证：

```text
AI 批次 A 添加 X
用户手工确认 X
撤销 A
```

不会因为残留 `source_batch_id=A` 而删除手工确认后的 X。

### D-3 撤销删除条件

对 `add` 流水的撤销，至少使用：

```sql
DELETE FROM asset_tags
WHERE asset_id = ?1
  AND tag_id = ?2
  AND source_batch_id = ?3
  AND source != 'manual'
```

注意：

- `source_batch_id` 必须与当前批次一致。
- `source != 'manual'` 是第二道保护。
- 删除前后都要在同一个事务中完成。
- 不要通过读取 `tag_ops` 后在事务外逐条删除。

### D-4 批次状态与幂等

可直接复用 `ai_batches.status` 的 TEXT 字段增加 `undone`，不需要额外表：

```text
pending / processing / done / cancelled / interrupted / undone
```

规则：

1. 只有 `done` 或 `cancelled` 且存在可撤销写入的批次显示“撤销”。
2. 撤销成功后设置为 `undone`。
3. `undone` 批次不再显示可点击“撤销”。
4. 重复调用返回 0 或明确的幂等结果，不再修改数据。
5. 撤销不应把批次 `confirmed` 计数伪装成 0；UI 可以显示“已撤销”，统计保持历史事实。

### D-5 remove 流水处理

当前 `remove` 反向操作重插时没有 `source_batch_id`，这对当前“撤销恢复关联”的语义可以接受，因为恢复后的关联不应继续属于被撤销批次。

本轮不实现 redo；在代码注释和文档中明确“暂不支持重做”，避免未来误以为来源信息完整。

### D-6 必须补的后端测试

至少补充：

1. AI 批次添加标签，撤销后标签消失。
2. 同一批次重复撤销幂等。
3. AI 添加后手工确认，撤销 AI 批次不删除手工确认的标签。
4. AI 添加后手工删除再重新添加，撤销 AI 批次不删除重新添加的标签。
5. 批次 A 添加、批次 B 对同一素材同一标签确认，验证当前单归属边界，并明确测试名称中写出预期语义。
6. `remove` 流水撤销后重新插入的关联 `source_batch_id` 为 NULL。

## 10. 阶段 E：素材库选择交互

### E-1 普通点击

评审确认：`selectionStore.toggle` 已支持取消，缺陷主要在 `AssetGridView.handleSelect` 的守卫条件。

当前问题代码：

```ts
else if (!selected.has(asset.id)) {
  toggle(asset.id, index, true);
}
```

修改要求：普通点击已选素材时也调用 `toggle`，让 store 决定添加或删除。

明确交互契约：

| 操作 | 行为 |
| --- | --- |
| 普通点击未选中 | 选中该素材 |
| 普通点击已选中 | 取消该素材 |
| Ctrl/Command 点击 | 多选切换 |
| Shift 点击 | 范围选择 |
| 空白区点击 | 清空选择 |
| Esc | 清空选择 |

### E-2 Shift 范围选择

本轮采用明确、可测试的规则：

1. 从 `anchorIndex` 到当前 index 计算闭区间。
2. 如果范围内全部已选，则取消整个范围。
3. 如果范围内存在未选，则补选整个范围。
4. 操作完成后将 `anchorIndex` 更新为当前 index。
5. 不能把 `undefined` id 放入 Set。

如果产品最终决定完全复制 Windows Explorer 的“Shift 以锚点替换范围”语义，应在实现前更新本节和测试，不允许一边按追加、一边按切换。

### E-3 测试文件清理

外部评审发现 `AssetGrid.test.tsx` 存在标题与断言矛盾：

- 用例标题写“再击已选中卡片 → 取消选择”。
- 注释和断言却写“保持不变”。

实现时必须同步修正标题、注释和断言，避免留下相互矛盾的测试文档。

### E-4 关于文本选择问题

当前证据不足以确认 `AssetCard` 文件名一定会被浏览器选中，因为文件名在带 `select-none` 的卡片后代中，CSS `user-select: auto` 会继承父级的禁止选择效果。

处理规则：

- 本轮不把它列为必做修复。
- 可以补一个真实浏览器/组件测试作为待复现验证。
- 如果真实复现，再把 `select-none` 提升到 `HoverPreviewTrigger` 外层并补 `preventDefault`。
- 没有复现证据时不要为了理论风险扩大 diff。

## 11. 阶段 F：视频悬浮预览 UI 改造

### F-1 交互目标

用户要求：

- 鼠标停留在视频缩略图上时播放。
- 播放位置在原卡片显示框内。
- 可轻微放大，但不要变成大浮窗。
- 鼠标离开立即停止。
- 不影响单击选择和双击打开完整查看器。

### F-2 推荐组件结构

不要继续让视频默认使用“固定定位、卡片下方浮层”的策略。建议：

```text
AssetCard（relative）
├── Thumbnail
├── duration / format badge
├── selection indicator
└── VideoHoverOverlay（active 时渲染）
    └── video
```

图片预览可以继续使用现有 `MediaPreviewPopover`，视频单独使用卡片内 overlay，避免为了视频需求破坏图片预览。

### F-3 尺寸与定位

默认：

- 覆盖原卡片 `inset: 0`。
- 不使用固定 `420px`。
- `overflow: hidden`。
- 与卡片使用相同圆角。

可选轻微放大：

- `scale(1.15)` 至 `scale(1.3)`。
- `transform-origin: center`。
- 必须有较高 z-index，但不能遮挡整个页面。
- 在窄窗口自动退回 `scale(1)`。

### F-4 播放生命周期

要求：

1. hover 触发器的进入延迟维持 300ms，删除 `VideoPreviewContent` 内部额外 250ms 延迟，避免双重延迟。
2. `active = true` 时创建/播放视频。
3. `active = false` 时暂停、重置到 0，并释放组件。
4. 静音、`playsInline`、短播上限保留。
5. 播放失败显示封面和轻量错误文案，不抛出到页面级边界。
6. 不同时让多个卡片视频持续播放；组件卸载必须清理监听和定时器。

### F-5 事件冲突

视频 overlay 不能吞掉卡片的选择和双击语义：

- hover overlay 默认 `pointer-events: none`，只承担显示和播放；
- 如果需要播放控件，控件必须明确阻止 click 冒泡并单独测试；
- 单击和双击仍由卡片根节点处理；
- 不能让视频元素拖拽文件或触发浏览器原生文本选择。

### F-6 视频预览测试

- `mimeType = video/*` 且 `durationMs = null` 时渲染视频 overlay。
- hover active 后 `<video>` 出现并尝试播放。
- hover 离开后视频暂停/卸载。
- `error` 事件后显示封面和错误文案。
- 预览尺寸不超过设计上限，位置不再固定在卡片下方。

## 12. 设置页与打标页 UI 设计规范

### 12.1 设置页

在线打标设置区必须独立可用，不能被本地模型探测状态阻塞。视频开关放在在线打标区，并使用：

```text
视频 AI 打标
对视频抽帧后打标（耗时更长）
[开关]
```

开关附近要能看出保存状态：

- 未保存：`有未保存的更改`。
- 保存中：禁用保存按钮并显示 `保存中…`。
- 已保存：显示 `已保存`。
- 保存失败：显示具体错误和重试动作。

### 12.2 AI 打标页

批次统计顺序建议：

```text
总数 | 待生成 | 待确认 | 已确认 | 失败
```

“全部确认”是批次级主操作，应放在批次统计下方，不能隐藏在单张工作台操作区。

当没有可确认建议时，显示解释性文字，不显示禁用后无提示的按钮。

### 12.3 工作台

固定布局顺序：

```text
主图 -> 胶片条 -> EXIF/状态 -> 标签编辑区 -> 单张确认操作
```

标签分面：

- 分面名固定宽度。
- 标签内容自适应换行。
- 标签使用现有 `TagChip`。
- 已确认状态显示文字，不伪装成可点击按钮。
- 单张“确认写入”是唯一主 CTA。

### 12.4 视频悬浮层

不能使用大面积黑色浮窗覆盖页面。视频 overlay 只覆盖卡片，播放失败时使用低干扰提示。不要增加额外红色播放框、渐变遮罩或大号按钮。

## 13. 代码规范与提交要求

### 13.1 前端

- TypeScript 严格类型，禁止无理由 `any`。
- 页面只编排状态和组件，不写 invoke 细节。
- Store 异步错误写入状态，并在 UI 展示。
- 纯函数优先单测：统计、facet 归一化、选择范围、视频类型判断。
- 大列表继续使用 `@tanstack/react-virtual`。
- 新增组件优先放 `components/common`、`components/media`、`components/ai` 等已有目录。

### 13.2 Rust

- command 只做参数校验、锁和事件。
- service 负责业务流程。
- db 负责 SQL、事务和数据一致性。
- 统一 `AppResult<T>` 和 `AppError::msg(...)`。
- 不使用生产代码 `unwrap()`。
- 数据库变更必须版本化迁移且幂等。
- 网络/抽帧/解码不得持有 DB 锁。

### 13.3 文件和 diff

- 保持现有 Windows CRLF 行尾，避免整文件换行格式变化。
- 不做无关格式化。
- 不重命名大量文件。
- 每个阶段只提交与该阶段相关的文件。
- 修改 Rust 字段时同步 `src/types/` 和 API 类型。

### 13.4 文档

每个阶段完成后更新：

- `docs/PROGRESS.md`：完成项、测试结果、决策日志。
- 必要时更新 `docs/ARCHITECTURE.md`：数据契约、状态机、迁移变化。
- 若 UI 规范发生变化，更新 `docs/UI_DESIGN_SYSTEM.md`。

## 17. 结论

本轮开发最重要的顺序不是先做视觉优化，而是先恢复数据正确性和错误可见性：

```text
先让设置页不白屏
  -> 再让视频开关和批量确认可用
  -> 再统一 facet key 与 color 存量迁移
  -> 再修复撤销的数据安全边界
  -> 再修复素材选择
  -> 最后调整视频悬浮播放视觉表现
```

任何实现如果只改 UI、不修状态语义和数据库来源约束，都不能视为完成。任何实现如果只改默认配置、不处理存量库，也不能视为完成。任何实现如果跳过测试和真机验收，也不能视为完成。
