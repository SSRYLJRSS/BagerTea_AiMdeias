### 两个必须先讲清的判断

**判断一：标签系统能跑，但守不住。**
它靠「所有调用方都记得做同一件事」维持一致性，而不是靠数据库约束和单点收口。
我在真库副本上实测：能插入两个完全同名的根级标签（`UNIQUE(parent_id,name)`
在 NULL 时失效，而你 19 个标签全是根级）；能插入指向不存在分面的孤儿标签
（`facet_key` 是裸 TEXT 无外键）；**能让标签树成环，然后任何递归 CTE
都会死循环**（10 秒 timeout 被杀，5 处 CTE 受影响，连防环逻辑本身也是 CTE）。
数据库一律不拦，只有应用层部分路径拦。

这就是「未来更新费力」的根源：**每加一个功能，都要重新检查有没有漏掉某条路径。**
§3 是这部分的完整设计 —— 把能用 SQL 表达的规则交给数据库，
把散在各处的判断收口到单点。

**判断二：超级搜索不是检索系统，是高级筛选器。**
`QueryExpr` 只有 `And/Or/Not/Leaf` 四种**硬条件**节点；未匹配的概念降级为
FTS 硬条件（`super_search_ai.rs:558`）；`order_by` 七个分支全是字段排序，
**grep `bm25|rank` 零命中**。

所以「草地必须有，蓝天最好有」这句话在当前模型里只有两种表达，都是错的：
全 AND（把「最好有」当成必须）或全 OR（丢掉「必须」）。
**这不是 UI 问题，是查询模型缺一个维度。**
§4 是 `SearchPlanV3` 的完整设计（`filter` / `must_not` / `should` /
`minimum_should_match` / 相关度排序）。

### 一期的能力边界（你 2026-09-01 拍板）

**要做的**：AI 把中文自然语言转成**可见、可改、可解释**的条件公式。具体是四件事：

| 能力 | 例子 | 在哪 |
|---|---|---|
| **精确条件** | 「5–10MB 的 JPG」「2026 年 7 月拍的」「前三色含红」 | 已有 + C-1 |
| **必须 / 加分 / 排除三档** | 「草地必须有，蓝天最好有，排除夜景」 | S1 S3 |
| **模糊匹配五种模式** | 「人」→ 人物/单人/一个人；「森材」→ 森林；「海滨」→ 海边 | S5 |
| **归零归因** | 「0 项，因为「含蓝」这条单独命中 0 张」 | C-2 |

**不做的**：视觉语义搜索（以图搜图、理解画面内容）。
因此不建 `asset_embeddings` 表、不写 `Retriever::Vector`
—— 那会产出一条永不启用的死路径。未来要做是纯增量，`SearchPlanV3` 一行不用改。

### 2.2 P0 阻断级（六条：三个功能 + 三个地基）

#### P0-1 自建分面的 AI 标签仍落 `custom` —— W2-10 被上一层整体旁路

计划书把 W2-10 标为「阻断级 · 不修则自建分面功能不成立」。
`resolve_facet_key`（`db/tag_facets.rs:674`）本身**写对了**，三个调用点
（`db/ai.rs:39 / 249 / 465`）也都切过去了。但 AI 返回的 key **在到达它之前**
已被改写：

```rust
// src-tauri/src/services/ai_cloud.rs:186-193
let mapped = crate::db::tag_facets::key_for_legacy_name(trimmed); // 自建 key → "custom"
let target = if valid_keys.contains(&mapped) {   // valid_keys 含 "custom" → 命中！
    mapped.to_string()                            // 直接变成 "custom"
} else if valid_keys.contains(&trimmed) { ... }   // 原样分支永远轮不到
```

分支顺序反了：先判 `mapped`。而 `key_for_legacy_name` 的 `_ => "custom"` 兜底
意味着**任何自建 key 都会 `mapped == "custom"`**，`custom` 又是 active +
`ai_and_manual`（实测确认），必然在 `valid_keys` 里 → 第一分支命中。

后果：你建「人物服装颜色」，AI 正确返回 `{"clothing_color":["红色"]}`，
**在解析阶段就变成 `{"custom":["红色"]}`，且不产生任何 warning**。
之后 `resolve_facet_key("custom")` → custom。

同时违反不变量 15（`resolve_facet_key` 是唯一路由入口）和计划书对
`key_for_legacy_name`「降级为纯函数，不再作为路由入口」的要求。

**为什么测试没抓到**（两层假绿叠加）：
- `db_integration.rs:1749` 的 `user_created_facet_full_pipeline` 用
  `serde_json::from_str::<CategorizedTags>` 直接反序列化「模拟 AI 返回」，
  **跳过 `parse_categorized_checked_ex`**，正好绕开这个 bug；
- `ai_cloud.rs:1516` 那条单测的 `valid = ["subject","scene"]`（刻意不含 `custom`），
  与真实配置不符。

整个测试集里没有一条覆盖「valid_keys 含 custom + 自建 key」这个真实场景。

#### P0-4【地基】根级标签的唯一约束失效 —— 你的 19 个标签全是根级

`tags` 表唯一约束只有 `UNIQUE(parent_id, name)`。SQLite 里 NULL 互不相等，
所以 `parent_id IS NULL` 时这个约束**完全失效**。我在库副本上实测：

```sql
-- 两次插入完全同名的根级标签，都成功
INSERT INTO tags(name,normalized_name,facet_key,parent_id) VALUES('测试A','测试a','scene',NULL);
INSERT INTO tags(name,normalized_name,facet_key,parent_id) VALUES('测试A','测试a','scene',NULL);
-- → SELECT COUNT(*) = 2
-- 大小写不同也各建一条（normalized_name 都是 'beach'）
INSERT ... VALUES('Beach','beach','scene',NULL);  -- id 355
INSERT ... VALUES('beach','beach','scene',NULL);  -- id 356
-- 子级同名则被正确拦住
INSERT ... VALUES('子','子','scene',334); -- 第二次 → UNIQUE constraint failed ✓
```

**为什么这是地基问题而不是小 bug**：
- 你的 19 个标签**全部是根级**（实测 `parent_id` 全 NULL），所以约束对你
  **100% 无效**；
- 唯一的防线是 `find_or_create_canonical` 的应用层查重
  （`tags.rs:197`，按 `facet_key + normalized_name` 查）。但
  `create_in_facet`（`:148`）、`create_tag` 命令（`tags_cmd.rs:219`）、
  `find_or_create_facet_root`、`find_or_create_root` 都**不查重**；
- 一旦出现两个 `normalized_name` 相同的标签，`confirm_suggestion_inner` 的
  `final_pairs` 反查（`db/ai.rs:465`）用的是
  `ORDER BY id LIMIT 1` —— 会**随机命中其中一个**，另一个变成永远无法被
  AI 命中的僵尸标签。

**好消息**：实测你现有数据**零冲突**，可以直接加约束，不需要数据清洗。

#### P0-5【地基】`tags.facet_key` 是裸 TEXT 无外键 —— 孤儿标签会完全隐身

实测在库副本上：

```sql
INSERT INTO tags(name,normalized_name,facet_key,parent_id)
  VALUES('孤儿','孤儿','no_such_facet',NULL);   -- 成功，无任何报错
```

`tags` 表的外键只有 `parent_id → tags(id)`（我读了 `pragma_foreign_key_list`）。
`facet_key` 没有指向 `tag_facets(key)` 的约束。

**为什么危险**：侧栏 `TagTree.tsx:66-69` 是
`facets.map(facet => tree.filter(n => n.tag.facetKey === facet.key))`
—— 按**分面清单**分组渲染。孤儿标签的 `facet_key` 不在任何分面里
→ **在侧栏完全不可见**，但它仍然：
- 计入 `list_tree` 的返回（前端 `tree` 数组里有它）
- 能被全文搜到（V21 触发器的 `EXISTS (tag_facets active)` 会把它排除…
  等等，实际上会被排除 —— 见下面的联动矩阵）
- 出现在 `TagAssignDialog`（`:53` 未知 facet「排最后」而非隐藏）

**实测好消息**：你现在 0 个孤儿（`SELECT COUNT(*) FROM tags WHERE facet_key NOT IN
(SELECT key FROM tag_facets)` = 0），可安全加约束。

#### P0-6【地基】分面状态联动只做了 2/6 条读路径

V21 迁移给 FTS 触发器加了 `EXISTS (tag_facets active)`，`search_candidates`（W2-5）
也加了。但**其他四条读路径没加**，导致「停用一个分面」这件事在系统各处
表现不一致：

| 读路径 | 文件 | 过滤分面状态？ | 停用分面后的表现 |
|---|---|---|---|
| 全文搜索（FTS） | V21 触发器 | ✅ | 标签立即搜不到 |
| 标签候选（AI 解析用） | `tags.rs:447 search_candidates` | ✅ | AI 不会解析到它 |
| `list_tree`（侧栏/弹窗的数据源） | `tags.rs:84` | ❌ | 标签仍在 `tree` 数组里 |
| `list_by_facet` | `tags.rs:389` | ❌（复用 list_tree） | 同上 |
| `top_tags_per_facet`（提示词候选词） | `tags.rs:411` | ❌ | **停用分面的标签仍会喂给 AI 当候选词** |
| `governance`（治理页） | `tags.rs:292` | ✅ | — |
| 筛选编译（`facet_has_any`/`facet_missing`） | `query_expr.rs:358` | ❌（只校验存在，不校验 active） | 能筛停用分面 |
| 素材标签读取 | `asset_tags.rs:164` | ❌ | 素材详情仍显示 |

侧栏「看起来正常」纯属**偶然** —— 因为它遍历的是 `facets`（只含 active），
不是遍历 `tree`。这是「靠调用方记得做同一件事」的典型脆弱点：
下一个功能只要直接用 `tree`，停用语义就漏了。

`top_tags_per_facet` 那条是**实际有害的**：停用 `color` 分面后（你的库正是
这个状态，虽然 0 标签所以现在无影响），它下面的标签仍会作为「已有候选词」
进入 AI 提示词，引导 AI 继续产出停用分面的标签，然后被
`parse_categorized_checked_ex` 丢弃并 warning。一个自相矛盾的循环。

### 我顺着评审思路查出的额外问题（评审未提及）

#### P0-7 标签树可形成环，且会让应用死循环（比 P0-4 更严重）

实测在库副本上（已 drop FTS 触发器以隔离变量）：

```sql
-- X 是根，Y 是 X 的子
INSERT INTO tags(...) VALUES('X',...,NULL);        -- id 355
INSERT INTO tags(...) VALUES('Y',...,355);         -- id 356
-- 把 X 挂到 Y 下 → 环
UPDATE tags SET parent_id=356 WHERE id=355;        -- 成功，无任何阻拦
SELECT id,name,parent_id FROM tags WHERE id IN (355,356);
-- 355|X|356
-- 356|Y|355
```

然后跑任何递归 CTE：

```sql
WITH RECURSIVE sub(id) AS (
  SELECT 355 UNION ALL SELECT t.id FROM tags t JOIN sub s ON t.parent_id=s.id
) SELECT count(*) FROM sub;
-- → 10 秒 timeout 被杀（无限递归）
```

**这不是理论风险。项目里有 5 处递归 CTE 会被它挂死**：
- `tags.rs:56 descendant_ids`（`update` 的防环检查自己就用它 —— **防环逻辑会先死循环**）
- `tags.rs:70 total_count`（每次 `list_tree` 对每个标签调一次）
- `tags.rs:117` 的 path 拼接（同样每标签一次）
- `query_expr.rs:391 / 415` 的 `include_descendants` 标签筛选（两处）
- `assets.rs:433` 的 `build_where` facet 筛选

`tags::update`（`:226-232`）的应用层防环用的是
`descendant_ids(conn, id)?.contains(&new_parent)` —— 它只在**环还不存在时**有效。
一旦通过任何绕过路径（直接 SQL、未来某个新命令、数据导入）形成环，
**整个应用会在下一次 `list_tree` 时卡死**，而且没有任何日志能指出原因。

**你现在是安全的**（实测无环），但这是「地基没打好」最典型的样子 ——
一个不可能自愈的、无诊断信息的、能让应用完全卡死的状态，
而唯一的防线是「所有写 `parent_id` 的路径都记得调那个检查」。

修法在 §3.4 D-3c：**BEFORE UPDATE 触发器 + 所有递归 CTE 加深度上限**。
实测深度上限确实能防死循环（`WHERE s.d < 16` 时环返回 17 行而非挂死）。

## 3. 标签系统地基设计

> 本节按第三方评审意见 2/3/4/7/11 完整重写。
> 初版的 `candidate` 设计有自相矛盾，已废弃并重新设计。

### 3.1 诊断：四个结构性弱点

不是「有几个 bug」，是**架构上依赖了四件不可靠的事**。

#### 弱点 A：一致性靠「所有调用方都记得」，而非数据库约束

| 该守的规则 | 现在靠什么守 | 漏在哪 |
|---|---|---|
| 同分面内标签名不重复 | `find_or_create_canonical` 的应用层查重 | `create_in_facet` / `create_tag` 命令 / `find_or_create_facet_root` / `find_or_create_root` 都不查（P0-4） |
| 标签的 `facet_key` 必须指向真实分面 | 无 | 完全不守（P0-5，实测可插孤儿） |
| 标签不能跨分面挂父 | `merge_preserve_alias` 有检查 | `tags::update` 没有；**INSERT 路径完全没有**（实测可插）；UI 也能做到（P2-5） |
| **标签树不能有环** | `tags::update` 调 `descendant_ids` | **该检查自身就用递归 CTE → 环已存在时它先死循环**（P0-7） |
| 分面 key 格式 | `validate_key` | 只在 `create` 调；迁移种子、V20 回填不走它 |

**判断标准**：能被 SQL 表达的规则（唯一性、引用完整性、环检测）就该由数据库守。
现在的分布是反的 —— 能被 SQL 守的反而在应用层，而且只在部分路径上。

#### 弱点 B：分面状态的「联动」是逐点实现的，而且语义过度绑定

两个独立问题叠加：

**B1（联动缺失）**：六条读路径里只有 2 条过滤了分面状态（详见 P0-6）。
根因是没有统一的「可见标签」查询入口。

**B2（语义过度绑定，评审意见 7）**：一个 `status` 字段同时决定五件事：

| 能力 | 当前由谁决定 | 停用分面后 | 这合理吗 |
|---|---|---|---|
| 侧栏/导航可见 | `status='active'` | 消失 | ✅ 合理 |
| 工作台可手工赋值 | `status` + `input_mode` | 消失 | ✅ 合理 |
| 参与 AI 打标提示词 | `status` + `input_mode` | 移除 | ✅ 合理 |
| **全文搜索可命中** | `status`（V21 触发器） | 消失 | ⚠ **可疑** |
| **素材详情展示已有标签** | 未过滤（P0-6 的漏洞） | 仍显示 | ⚠ **不一致** |

问题在后两条：**停用一个分面 ≠ 让历史素材上已有的标签凭空消失。**
现实场景：你决定「用途」这个分面不再用 AI 打，停用它。
但已经打了 200 张的「商业用途」标签，你还是想能搜到它们。
现在的语义会让这 200 张的标签在全文搜索里消失，而在素材详情里还在
—— 既不合理，又不一致。

#### 弱点 C：没有词表治理，AI 每次打标都在污染

实测你 19 个标签里已有两组语义重复：
- `people`：「单人」「一个人」「一个」
- `subject`：「女孩」「少女」

`tag_aliases` 表设计得好（`alias_type` 区分 synonym / old_name / translation / typo，
有 `is_searchable`，FTS 触发器也消费别名），但：
- **没有任何路径会自动创建 synonym 别名** —— 只有 `update_preserve_alias`（改名）
  和 `merge_preserve_alias`（合并）会写，都要用户手动操作
- **别名唯一性不按分面区分**（评审意见 11）：`tags.rs:338` 的冲突检查是
  `normalized_alias + locale`，跨分面也冲突。所以 `people` 分面用了「一个人」
  作别名后，`subject` 分面再也不能用这个别名

AI 的行为是 `find_or_create_canonical` 查不到就建新的。提示词里的
「含义相同必须用已有词」是软约束，小模型不可靠 —— 你的三个「一个人」就是证据。

#### 弱点 D：AI 打标的产出没有溯源信息（评审意见 5/6）

`ai_batches` 实测只有 `status/mode/total/processed/confirmed/created_at`
（`migrations.rs:120`）。缺：模型 id、模型版本、提示词版本、配置哈希。

后果：
- 换模型后无法判断「哪些标签是旧模型打的、该不该重跑」
- 改提示词后无法做 A/B 对比（W5a 的完成条件「同一批 20 张图对比三指标」
  实际上无法在数据层验证 —— 因为不知道哪批是改造前的）
- confidence 走的是「JSON 套字符串」的隐式协议（P0-3 的止血方案），
  下游随时可能再断链

### 3.2 设计原则（先定原则，再定实现）

| 原则 | 含义 | 违反它的代价 |
|---|---|---|
| **P1 能用 SQL 守的规则不放应用层** | 唯一性、引用完整性、环检测、跨分面约束 → DB 约束/触发器 | 每加一个写入路径都要重新检查一遍 |
| **P2 同一语义只有一个声明处** | `VISIBLE_TAG_COND`、`ALL_METADATA_KEYS`、`ALL_SORT_KEYS` 各只声明一次 | W2-8 加 rating 时漏了 2/5 处白名单，导致 P1-4 |
| **P3 不同能力用不同开关** | 分面的可见/可赋值/可 AI/可搜索是四件事 | 停用 AI 打标却让历史标签从搜索消失 |
| **P4 跨层传递用强类型，不用字符串编码** | `TagProposal` 而非 `Vec<String>` 里塞 JSON | P0-3 的整条链路断裂 |
| **P5 系统不改写用户明确表达的语义** | 库统计只能产生 warning/建议，不能删条件 | 搜「有定位的照片」返回全库 |
| **P6 每条约束都要有「加不上怎么办」的预检** | 迁移前扫描冲突数据 + 可恢复的合并流程 | 只在「当前这一份库零冲突」上验证过 |

### 3.3 分面能力矩阵：配置值 vs 有效值

二轮设计有个致命缺陷：**停用分面会把能力列归零，恢复时无法知道原配置**。
「AI+手工」的分面和「仅手工」的分面停用后都变成全 0，恢复时只能猜。

**正解：配置值与有效值分离。** 数据库只存配置值，有效值由函数派生。

```sql
-- V22a：四个「配置值」列。它们记录用户的意图，生命周期状态**永不覆盖它们**。
ALTER TABLE tag_facets ADD COLUMN cfg_visible_in_navigation INTEGER NOT NULL DEFAULT 1;
ALTER TABLE tag_facets ADD COLUMN cfg_manual_assignable     INTEGER NOT NULL DEFAULT 1;
ALTER TABLE tag_facets ADD COLUMN cfg_ai_assignable         INTEGER NOT NULL DEFAULT 1;
ALTER TABLE tag_facets ADD COLUMN cfg_searchable            INTEGER NOT NULL DEFAULT 1;
```

**有效值的派生规则**（纯函数，单点声明，SQL 与 Rust 各一份且有交叉测试）：

| 配置值 | `status='active'` | `status='inactive'` | `status='deprecated'` |
|---|---|---|---|
| `cfg_visible_in_navigation` | 原样 | **强制 0** | **强制 0** |
| `cfg_manual_assignable` | 原样 | **强制 0** | **强制 0** |
| `cfg_ai_assignable` | 原样 | **强制 0** | **强制 0** |
| `cfg_searchable` | 原样 | **原样**（停用不影响可搜） | 原样 |

```sql
-- SQL 侧：单一声明处（db/tag_facets.rs 的常量）

const EFF_VISIBLE:  &str = "f.status = 'active' AND f.cfg_visible_in_navigation = 1";

const EFF_SEARCH:   &str = "f.cfg_searchable = 1";   -- 注意：不看 status
```

```rust

/// （对 status × 4 个 cfg 的 3×16 = 48 种组合断言两边一致）。
pub struct FacetEffective { pub visible: bool, pub manual: bool, pub ai: bool, pub searchable: bool }

impl TagFacet {

            visible:    alive && self.cfg_visible_in_navigation,

}
```

| `active` + `manual_only` | 1 | 1 | **0** | 1 | active |
| `inactive` + `ai_and_manual` | 1 | 1 | **1** ← 记住原配置 | 1 | **inactive** |
| `inactive` + `manual_only` | 1 | 1 | **0** | 1 | **inactive** |
| `deprecated` | 1 | 1 | 按 input_mode | 1 | deprecated |

**关键**：`inactive` 的分面配置值仍然是 1，只是 `status` 让有效值为 0。
**恢复分面时只改 `status`，配置值原样复活** —— 这就是评审要的能力。

实测你的库：`color` 是 `inactive` + `manual_only` → 回填后
`cfg_ai_assignable=0`（记住它原本就不参与 AI），恢复后仍是「仅手工」。
如果它原本是 `ai_and_manual`，恢复后就还是「AI+手工」。

**`input_mode` 的处置**：改为**只读派生值**（`cfg_ai_assignable ? "ai_and_manual" : "manual_only"`），
序列化时计算，**不再是可写字段**。设置页的两组列表和拖拽跨组改为写
`cfg_ai_assignable`。W4 的前端 UI 一行不用改（DTO 形状不变）。

**`status` 保留什么**：只做生命周期（`active` / `inactive` / `deprecated`），
用于设置页分组。**所有功能判断读 `effective()`，不再直接读 `status` 或 `input_mode`。**

**`show_existing_assignments` 仍然不加列**：素材详情**恒显示**该素材实际挂着的
标签（否则用户会困惑「明明打过标，详情怎么是空的」），停用分面的标签加
灰色「已停用」角标。这是 UI 层的事。

### 3.4 数据库约束层加固（V22）

#### D-1 标签身份：明确定为「分面内唯一」

评审要求「明确标签身份是分面内唯一还是父路径内唯一」。**我选分面内唯一**，理由：

| 方案 | 含义 | 取舍 |
|---|---|---|
| 父路径内唯一（现状） | `scene/户外/海边` 和 `scene/室内/海边` 可共存 | 层级表达力强，但**同一分面内会有两个「海边」**，AI 反查（`ai.rs:473` 的 `ORDER BY id LIMIT 1`）会随机命中一个 |
| **分面内唯一（选它）** | 一个分面里「海边」只能有一个 | AI 反查确定；标签合并语义清晰；**符合受控词表的「一词一义」原则**；层级仍可用（「海边」可以挂在「户外」下），只是不能同名 |

这个选择直接决定了唯一索引的形态。

#### D-2 `schema_features` 能力表

二轮设计有个致命漏洞：**「有冲突就跳过 V22b」但没定义 `user_version` 怎么处理**。
后果是 A 用户的 V22 有唯一约束、B 用户的 V22 没有，代码只看到 `user_version=22`

#### D-3 约束清单

```sql
-- ═══ V22a：无条件执行，不依赖数据干净 ═══

-- (a) 环检测：BEFORE UPDATE OF parent_id
CREATE TRIGGER IF NOT EXISTS trg_tags_no_cycle
  BEFORE UPDATE OF parent_id ON tags
  WHEN new.parent_id IS NOT NULL AND EXISTS (
    WITH RECURSIVE anc(id, d) AS (
      SELECT new.parent_id, 0
      UNION ALL
      SELECT t.parent_id, a.d + 1 FROM tags t JOIN anc a ON t.id = a.id
       WHERE t.parent_id IS NOT NULL AND a.d < 12
    ) SELECT 1 FROM anc WHERE id = new.id
  )
BEGIN SELECT RAISE(ABORT, '不能把标签挂到自己的子标签下（会形成循环）'); END;

-- (b)【三轮修订，评审 P0-4】深度检查必须算「新父深度 + 被移动子树高度」。
--     二轮只查新父深度 —— 一个已有 4 层子树的节点移到第 6 层，子孙会到第 10 层。
--     我实测验证：新父 b6 深度 6，被移动节点 a1 子树高 4，6 + 4 = 10 > 8，
--     而二轮的检查会放行（因为 6 < 8）。
CREATE TRIGGER IF NOT EXISTS trg_tags_max_depth_au
  BEFORE UPDATE OF parent_id ON tags
  WHEN new.parent_id IS NOT NULL
   AND (
     -- 新父节点的深度（根 = 1）
     (WITH RECURSIVE anc(id, d) AS (
        SELECT new.parent_id, 1
        UNION ALL SELECT t.parent_id, a.d + 1 FROM tags t JOIN anc a ON t.id = a.id
         WHERE t.parent_id IS NOT NULL AND a.d < 12
      ) SELECT MAX(d) FROM anc)
     +
     -- 被移动节点的子树高度（自身 = 0）
     (WITH RECURSIVE des(id, d) AS (
        SELECT new.id, 0
        UNION ALL SELECT t.id, s.d + 1 FROM tags t JOIN des s ON t.parent_id = s.id
         WHERE s.d < 12
      ) SELECT MAX(d) FROM des)
   ) > 8
BEGIN SELECT RAISE(ABORT, '移动后标签层级会超过 8 层（含其下所有子标签）'); END;

-- INSERT 版本：新节点无子树，只需查新父深度 + 1
CREATE TRIGGER IF NOT EXISTS trg_tags_max_depth_ai
  BEFORE INSERT ON tags
  WHEN new.parent_id IS NOT NULL
   AND (WITH RECURSIVE anc(id, d) AS (
          SELECT new.parent_id, 1
          UNION ALL SELECT t.parent_id, a.d + 1 FROM tags t JOIN anc a ON t.id = a.id
           WHERE t.parent_id IS NOT NULL AND a.d < 12
        ) SELECT MAX(d) FROM anc) >= 8
BEGIN SELECT RAISE(ABORT, '标签层级不能超过 8 层'); END;

-- (c) 父子同分面：INSERT + UPDATE 双向
CREATE TRIGGER IF NOT EXISTS trg_tags_parent_facet_ai
  BEFORE INSERT ON tags
  WHEN new.parent_id IS NOT NULL
   AND (SELECT facet_key FROM tags WHERE id = new.parent_id) != new.facet_key
BEGIN SELECT RAISE(ABORT, '子标签必须与父标签属于同一分面'); END;
-- UPDATE 版本必须同时监听 parent_id 与 facet_key 两列

-- ═══ V22b：预检通过才执行，成功后写 schema_features ═══
-- (d) 统一 term 唯一性 —— 见 D-3b
-- (e) facet_key 引用完整性（INSERT + UPDATE 各一个触发器）
-- (f) 分面删除 RESTRICT
```

#### D-3b `tag_terms` 统一词条表

二轮只把「别名 vs 别名」限制到分面内，仍然不阻止：
① 一个标签的别名 = 另一标签的规范名；② 新建规范名 = 其他标签的别名；
③ 直接 SQL 写入造成歧义。而 `find_or_create_canonical`（`tags.rs:203`）的
`ORDER BY id LIMIT 1` 会**随机命中**其中一个。

**正解：规范名和别名进同一张表，共享同一个唯一空间。**

```sql
-- V22b
CREATE TABLE tag_terms (
  tag_id          INTEGER NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
  facet_key       TEXT    NOT NULL,      -- 冗余自 tags，让唯一索引能覆盖分面
  normalized_term TEXT    NOT NULL,
  term            TEXT    NOT NULL,      -- 原始写法（展示用）
  locale          TEXT    NOT NULL DEFAULT '',
  term_kind       TEXT    NOT NULL,      -- canonical | synonym | old_name | translation | typo
  is_searchable   INTEGER NOT NULL DEFAULT 1,
  created_at      INTEGER NOT NULL,
  PRIMARY KEY (tag_id, normalized_term, locale),
  CHECK (term_kind IN ('canonical','synonym','old_name','translation','typo'))
);

-- 核心约束：分面内一个 term 只能指向一个标签（不分规范名/别名）
CREATE UNIQUE INDEX ux_terms ON tag_terms(facet_key, normalized_term, locale);
-- 每个标签恰好一个 canonical
CREATE UNIQUE INDEX ux_terms_canonical ON tag_terms(tag_id, term_kind)
  WHERE term_kind = 'canonical';
-- 按 term 反查标签
CREATE INDEX ix_terms_lookup ON tag_terms(normalized_term, locale, facet_key);
```

**我在真库副本上建表实测了六个场景**：

| 场景 | 期望 | 实测 |
|---|---|---|
| 别名 = 另一标签的规范名 | 拒绝 | ✅ `UNIQUE constraint failed: ux_terms` |
| 新规范名 = 另一标签的别名 | 拒绝 | ✅ 同上 |
| 跨分面同名（`people/单人` + `subject/单人`） | 允许 | ✅ 两条共存 |
| 一个标签两个 canonical | 拒绝 | ✅ `ux_terms_canonical` 拦住 |
| 合并时源标签 canonical 与目标新别名同名 | **需要顺序约束** | ⚠ 直接加会冲突 → **必须先删源 terms 再加目标别名** |
| 正确顺序的合并 | 成功 | ✅ 目标获得 canonical + 2 个 synonym |

**第 5 条是重要发现**：`merge_preserve_alias` 必须调整顺序 ——
先 `DELETE FROM tag_terms WHERE tag_id = src`，再给 dst 加 synonym。
这也顺带化解了 D-4 的旧 `UNIQUE(parent_id,name)` 问题（源标签 term 删掉后，
`tags.name` 改成 `原名 #<id>` 不再有语义负担）。

#### 合并语义：旧词永久归属目标标签

评审正确指出一个空洞：我一边说「删除源标签的 terms」，一边说「要能从
deprecated 标签的 old_name 跳转」—— 这两件事不能同时成立。

**明确选第一种方案：合并时把旧词永久写成目标标签的 `old_name`。**
不加 `redirect_tag_id` / `merged_into` 字段。

理由：加跳转字段意味着**每次查找都要判断「命中的是不是 deprecated，要不要跳」**，
而且跳转可以链式（A 合并到 B，B 又合并到 C）→ 需要防环、需要限深度。
把旧词直接挂到最终目标上，查找永远一步到位，`ux_terms` 也天然保证唯一。

**合并的完整顺序**（`merge_preserve_alias` 必须严格按此，实测验证过）：

```
① 读出源标签的全部 terms（canonical + 所有别名）
② DELETE FROM tag_terms WHERE tag_id = src        ← 释放唯一空间
③ 把 ① 读出的每个 term 以 old_name（源的 canonical）
   或原 term_kind（源的别名）写给 dst
   ⚠ 若某个 term 与 dst 已有的 term 撞了 → 跳过它（dst 已经有这个词了）
④ tags.name of src → '原名 #<id>'（D-4 的方案 C，避开旧 UNIQUE）
⑤ tags.status of src → 'deprecated'
```

**效果**：合并后源标签在 `tag_terms` 里**一行都没有**，
它的所有词都归属 dst。查「一个人」直接命中 dst（「单人」），
**不需要任何跳转逻辑**。deprecated 标签只是 `tags` 表里的一条历史记录
（保留它是为了 `tag_ops` 的外键与审计），不参与任何查找。

**所以 `tag_terms` 的迁移只灌 active 标签是正确的** ——
历史上合并产生的 deprecated 标签，它们的词早已（或将会）归属目标标签。
唯一要处理的是**存量**：V22b 迁移前如果已有 deprecated 标签且它的
`tag_aliases` 还挂在自己名下，预检（D-2b）会把它列为「孤儿别名」，
建议迁移到它的合并目标 —— 但**你的库现在 0 个 deprecated 标签**（实测），
所以这条对你是空操作。

**测试**：`merge_moves_all_terms_to_target` /
`merge_skips_conflicting_term`（源和目标都有「海边」时不报错，跳过）/
`deprecated_tag_has_no_terms` / `search_old_name_hits_merge_target`。

**迁移路径**（V22b 内，单事务）：

```sql
-- ① 从 tags 灌 canonical（只灌 active —— deprecated 的词已归属目标标签）
INSERT INTO tag_terms (tag_id, facet_key, normalized_term, term, locale, term_kind, is_searchable, created_at)
SELECT id, facet_key, normalized_name, COALESCE(canonical_name, name), '', 'canonical', 1, :now
  FROM tags WHERE status = 'active';
-- ② 从 tag_aliases 灌别名（alias_type 直接映射 term_kind）
INSERT INTO tag_terms (tag_id, facet_key, normalized_term, term, locale, term_kind, is_searchable, created_at)
SELECT ta.tag_id, t.facet_key, ta.normalized_alias, ta.alias, ta.locale,
       ta.alias_type, ta.is_searchable, ta.created_at
  FROM tag_aliases ta JOIN tags t ON t.id = ta.tag_id WHERE t.status = 'active';
-- ③ tag_aliases 保留（只读，供回滚与历史查询）；新代码只写 tag_terms
--    ⚠ 双写策略见 §3.4 D-6 —— 不允许两表同时可写
```

**`tags.normalized_name` / `canonical_name` 怎么办**：保留（`from_row` 依赖它们，
改动面太大），但**降级为 `tag_terms` 的 canonical 行的镜像**。
`create_in_facet` / `update` 写 `tags` 时同事务写 `tag_terms`，
加测试守护两者一致（`tags_normalized_name_mirrors_canonical_term`）。

**查找逻辑统一**（消灭 `ORDER BY id LIMIT 1`）：

```rust

/// 这是所有「按名字找标签」的唯一入口：find_or_create_canonical /
/// AI 输出解析 / final_pairs 反查 / search_candidates 全部走它。
pub fn find_by_term(conn: &Connection, facet_key: &str, normalized: &str)
    -> AppResult<Option<TermHit>> { /* 返回 tag_id + term_kind + 该标签 status */ }
```

`ai.rs:473` 的 `final_pairs` 反查也改走它（评审指出它还写死 `status='active'`），
**注意**：不需要任何「跳转」逻辑 —— 合并时旧词已经**永久归属目标标签**
（见上文「合并语义」），所以查「一个人」直接命中「单人」。
deprecated 标签在 `tag_terms` 里一行都没有，不参与查找。

#### D-3c `tag_terms.facet_key` 的一致性保障

评审正确指出：`tag_terms` 同时存 `tag_id` 和 `facet_key`，而 `facet_key` 是
**从 `tags` 冗余过来的**（为了让 `ux_terms` 能覆盖分面维度）。
如果只靠应用层事务同步，直接 SQL、迁移脚本或遗漏的更新路径都会让两者漂移。

**三道防线，全部实测验证过**：

```sql
-- ① tags.facet_key 改动时自动同步 tag_terms（AFTER UPDATE）
CREATE TRIGGER IF NOT EXISTS trg_terms_sync_facet
  AFTER UPDATE OF facet_key ON tags
BEGIN
  UPDATE tag_terms SET facet_key = new.facet_key WHERE tag_id = new.id;
END;

-- ② 插入 tag_terms 时校验与 tags 一致（BEFORE INSERT）
CREATE TRIGGER IF NOT EXISTS trg_terms_facet_match_ai
  BEFORE INSERT ON tag_terms
  WHEN new.facet_key != (SELECT facet_key FROM tags WHERE id = new.tag_id)
BEGIN
  SELECT RAISE(ABORT, 'tag_terms.facet_key 必须与 tags.facet_key 一致');
END;

-- ③ 直接改 tag_terms.facet_key 时同样校验（BEFORE UPDATE）
--    防「绕过 ① 直接改 tag_terms」这条路径
CREATE TRIGGER IF NOT EXISTS trg_terms_facet_match_au
  BEFORE UPDATE OF facet_key ON tag_terms
  WHEN new.facet_key != (SELECT facet_key FROM tags WHERE id = new.tag_id)
BEGIN
  SELECT RAISE(ABORT, 'tag_terms.facet_key 必须与 tags.facet_key 一致');
END;
```

**实测结果**（我建了最小表跑过）：

| 场景 | 期望 | 实测 |
|---|---|---|
| 插入 `facet_key` 与 `tags` 不一致的 term | 拒绝 | ✅ `RAISE(ABORT)` 生效 |
| `UPDATE tags SET facet_key='subject'` | `tag_terms` 自动跟着变 | ✅ 同步为 `subject` |
| 直接 `UPDATE tag_terms SET facet_key='people'`（制造不一致） | 拒绝 | ✅ `RAISE(ABORT)` 生效 |

**⚠ 触发器 ① 与 ③ 的交互**：① 是 `AFTER UPDATE ON tags`，
它执行的 `UPDATE tag_terms` 会触发 ③ 的 `BEFORE UPDATE`。
此时 `tags.facet_key` 已经是新值，所以 ③ 的校验通过 —— **顺序是安全的**。
但这是个微妙点，**必须在建表 SQL 上写注释说明**，否则日后有人调整触发器顺序会踩坑。

**第四道防线：一致性检查 + 启用门槛**


#### D-6 `tag_aliases` → `tag_terms` 的切换与 feature gate

评审正确指出：止损线允许「`tag_terms` 建表但不建索引，应用继续走旧路径」，
但 S4 的 `TagAlias` 检索器依赖 `tag_terms` —— **部分路径读旧表、部分读新表
而没有 feature gate**，两表内容会逐渐漂移。

**明确规则：`schema_features.tag_unique_terms` 是唯一的开关，且不双写。**

| `tag_unique_terms` | 事实源 | 写入 | `TagAlias` 检索器 | `find_by_term` |
|---|---|---|---|---|
| `enabled = 1` | **`tag_terms`** | 只写 `tag_terms`；`tag_aliases` **冻结为只读** | ✅ 启用 | 查 `tag_terms`（唯一索引保证单行） |
| `enabled = 0` | **`tag_aliases`** | 只写 `tag_aliases`；`tag_terms` 表存在但**不读不写** | **❌ 禁用**（`Retriever::TagAlias` 直接返回空 + warning「别名扩展未启用」） | 回退旧逻辑：查 `tags` + `tag_aliases`，**保留 `ORDER BY id LIMIT 1` 兜底** |

**三条硬规则**：

1. **绝不双写。** 双写必然漂移（一处失败、事务边界不同、迁移中途崩溃）。
   要么全走新表，要么全走旧表。
2. **`enabled=0` 时 `tag_terms` 完全不参与**（连读都不读）。
   它只是个空表在那里等着 `apply_tag_constraints`。
3. **切换是单向的**：`0 → 1` 由 `apply_tag_constraints` 完成
   （重新执行迁移 SQL + 建索引 + 置 `enabled=1`）。
   **`1 → 0` 只在紧急回滚时手工做**，且必须清空 `tag_terms`
   （否则下次切回来会有陈旧数据）。

**代码形态**（把分支收在一个地方，不散落）：

```rust
/// 按名字查标签。schema_features 决定走哪条路径 —— 这是唯一的分支点。
/// 上层（AI 解析 / final_pairs 反查 / search_candidates / TagAlias 检索器）
/// 全部调它，不自己判断 feature。
pub fn find_by_term(conn: &Connection, feats: &SchemaFeatures,
                    facet_key: &str, normalized: &str, mode: TermMatch)
    -> AppResult<TermLookup>
{
    if feats.tag_unique_terms {
        find_by_term_new(conn, facet_key, normalized, mode)      // 查 tag_terms
    } else {
        // 旧路径：只支持 Exact / Alias 两种模式；Prefix/Contains/Fuzzy 返回
        // 空 + warning「需要先在设置页启用标签约束」
        find_by_term_legacy(conn, facet_key, normalized, mode)
    }
}
```

**注意这条的连带影响**：`enabled=0` 时 §4.2b 的 `Prefix`/`Contains`/`Fuzzy`
三种模式**都不可用**（旧表没有统一的 term 空间，做前缀扩展会漏掉规范名或别名）。
设置页的「数据完整性」区块要写清：
「启用标签约束后才能使用前缀、包含、纠错匹配」。

**测试**：`find_by_term_respects_feature_gate`（两种 feature 状态各断言一次）/
`alias_retriever_disabled_without_terms`（返回空 + warning）/
`prefix_mode_unavailable_without_terms`。

### 3.6 词表治理

初版的 `candidate` 设计被评审正确地判为自相矛盾。**重新设计如下。**

#### 核心改变：候选词不是标签的一种状态，而是「建议」的一种状态

初版错误地想用 `tags.status='candidate'`，导致三方矛盾（唯一索引不管它 →
可无限重复；可见条件不认它 → 建了也搜不到；`ai.rs:473` 反查写死 active →
确认不了）。

**正确做法**：候选词不进 `tags` 表，而是留在 `ai_suggestion_items` 里
—— **这张表本来就是为此设计的**（有 `facet_key` / `raw_name` /
`normalized_name` / `tag_id`（可空！）/ `confidence` / `decision` /
`decision_reason`）。

| 阶段 | 数据位置 | 状态 |
|---|---|---|
| AI 输出「一个人」，词表里没有 | `ai_suggestion_items`，`tag_id = NULL`，`decision='pending'` | **不进 `tags` 表** |
| 系统发现它疑似与「单人」重复 | 同上，`decision_reason = '疑似与「单人」重复'` | 待用户决定 |
| 用户选「合并到单人」 | `tag_id` 指向「单人」的 id，`decision='modified'`；同时给「单人」加 `synonym` 别名「一个人」 | 词表不新增条目 |
| 用户选「采纳为新词」 | 走 `find_or_create_canonical` 真正建标签，`decision='accepted'` | 词表新增 |
| 用户选「拒绝」 | `decision='rejected'` | 词表不动 |

**好处**：
- `tags` 表永远只有正式词 → 唯一索引、可见条件、AI 反查全部一致，无矛盾
- 完全复用现有表和 `ai_decide_suggestion_item` 命令（已注册）
- confirm 流程不变（现在就是「确认才写 `asset_tags`」，不变量 22）
- 打标不被阻塞：pending 的 item 在工作台正常显示，用户可直接确认

#### 近似匹配：只提示，不自动改写

在 `set_suggestion_tags`（`db/ai.rs:238`）写 item 时，`tag_id` 查不到精确匹配时
**多做一次近似查找**，命中则写进 `decision_reason`：

```rust
/// 近似匹配（只产生建议，绝不自动合并 —— 「女孩」vs「女人」编辑距离 1 但不同概念）。
/// 三级，按可信度降序：
///   ① 别名精确命中 → 直接给 tag_id（这已经是现有行为）
///   ② 一方是另一方的子串且长度差 ≤ 2 → decision_reason 记「疑似与 X 重复」
///   ③ 编辑距离 ≤ 1（中文按 char）→ 同上，但标注「拼写相近」
/// 阈值待调研验证（§6.4 第 6 项），当前值是保守猜测。
fn find_similar_tag(conn, facet_key, normalized) -> Option<(i64, String, SimilarReason)>
```

⚠ **阈值我没有业界依据**（调研被网络阻断）。所以设计成「只提示」而非
「自动合并」—— 即使阈值不准，代价只是多几条无用提示，不会污染词表。

#### 别名契约修正（评审意见 11）

`add_alias`（`tags.rs:338`）的冲突检查改为**按分面 + locale**：

```sql
-- 现在（错）：跨分面也冲突
WHERE normalized_alias = ?1 AND locale = ?2 AND tag_id != ?3

-- 改为：只在同分面内冲突
WHERE ta.normalized_alias = ?1 AND ta.locale = ?2 AND ta.tag_id != ?3
  AND EXISTS (SELECT 1 FROM tags t1 JOIN tags t2
               WHERE t1.id = ta.tag_id AND t2.id = ?3 AND t1.facet_key = t2.facet_key)
```

理由：分面是独立的语义空间。`people` 分面的「一个人」和 `subject` 分面
（假如有）的「一个人」是不同概念，不应互相排斥。

同时明确 `alias_type` 与 SKOS 的对应（**注意：SKOS 语义我未能验证**，
见 §6.4 第 5 项；下表是我的理解，施工前请确认）：

| `alias_type` | 我的理解对应 SKOS | 用途 | `is_searchable` |
|---|---|---|---|
| `synonym` | `altLabel` | 同义词（「一个人」→「单人」） | 1 |
| `old_name` | `altLabel`（历史） | 改名前的旧名 | 1 |
| `translation` | `altLabel`（带 locale） | 多语言 | 1 |

**现在的问题**：`merge_preserve_alias`（`:566`）和候选词合并都写 `old_name`。

- 排查「为什么这张图打出这个标」→ `raw_response` 有模型原话，
  `request_config_json` 有当时的完整输入 → **可完整复现**

**存储成本**：`raw_response` 约 200–500 字节/条；`request_config_json` 约 2–4 KB/批次
（不是每条）。410 张全打标 ≈ 200 KB。可接受。

#### D-8c 重跑策略与状态转移

**二轮的判定条件是错的。** 我用你的真库验证：

```sql
SELECT COUNT(*) FROM asset_tags WHERE source != 'manual' AND source_batch_id IS NOT NULL;
-- → 72（你全部已确认的标签）
SELECT COUNT(*) FROM asset_tags WHERE source != 'manual' AND source_batch_id IS NOT NULL
  AND confirmation = 'confirmed';
-- → 72
```

**你审核确认过的 72 条标签会被 `ReplaceAiOnly` 全部删除。** 评审说得对。

根因：`confirmation` 列的默认值就是 `'confirmed'`（schema），而
`assign_inner`（`asset_tags.rs:86`）无论 AI 还是手工路径都写 `'confirmed'`
—— **这个字段现在完全不区分「AI 未审核」和「用户已确认」**。
实测真库：`confirmation` 只有一个取值 `confirmed`，`source` 只有 `ai_local`。

**正解：新增明确的确认来源字段，定义完整状态机。**

```sql
-- V22a
ALTER TABLE asset_tags ADD COLUMN review_state TEXT NOT NULL DEFAULT 'ai_unreviewed';
-- 取值：ai_unreviewed | ai_reviewed | manual
CREATE INDEX ix_at_review ON asset_tags(review_state, tag_id, asset_id);
```

**回填规则**（V22a，保守 —— 宁可把已确认的当已确认）：

| 现有行 | `review_state` | 理由 |
|---|---|---|
| `source = 'manual'` | `manual` | 明确 |
| `source != 'manual'` 且存在对应的 `ai_suggestion_items.decision IN ('accepted','modified')` | **`ai_reviewed`** | 用户确认过 |
| `source != 'manual'` 且无对应 accepted item | `ai_unreviewed` | 未审核 |

实测你的库：72 条 `asset_tags` 对应 72 条 `decision='accepted'` 的 item
→ **全部回填为 `ai_reviewed`，不会被误删**。

**完整状态机**（这是评审要求的「写出完整状态转移和测试」）：

```
                    ai_unreviewed
                    ├── 用户在工作台点「确认」 ──────► ai_reviewed
                    ├── 用户手工改标签 ─────────────► manual
                    ├── 用户点「拒绝」 ─────────────► （删除该行）
                    └── ReplaceAiOnly 重跑 ─────────► （删除该行）✅ 允许

                    ai_reviewed
                    ├── 用户手工改标签 ─────────────► manual
                    ├── 用户手工移除 ───────────────► （删除该行）
                    ├── ReplaceAiOnly 重跑 ─────────► **不动** ✅ 评审要求
                    └── undo_batch 撤销该批次 ───────► （删除该行，D-3 语义不变）

                    manual
                    ├── AI 再次打出同标签 ──────────► **保持 manual**（不变量 9）
                    ├── ReplaceAiOnly 重跑 ─────────► **不动**
                    └── undo_batch ─────────────────► **不动**（D-2：source != 'manual' 守卫）
```

```rust
/// 重跑模式。**永不删除 review_state IN ('ai_reviewed','manual') 的行**。
pub enum RetagMode {
```

#### D-8d 置信度只用于排序与提示，不用于自动接收

评审正确指出：**LLM 自报的 confidence 通常没有校准意义**，
尤其不能据此自动创建新词。

**改为按「词是否已在词表」而非「confidence 高低」决定自动化程度**：

| AI 输出的词 | 处理 | 依据 |
|---|---|---|
| **精确命中** `tag_terms` 的 canonical 或 synonym | **可自动接收**（写 `asset_tags`，`review_state='ai_unreviewed'`） | 词表已认可这个词，风险只在「这张图是否真有这个特征」 |
| 近似命中（编辑距离/子串） | **只进 `ai_suggestion_items`，`decision='pending'`** + `decision_reason='疑似与 X 重复'` | 可能是近义词也可能是不同概念，必须人判 |
| 完全新词 | **只进 pending** | **绝不自动建词** |
| 任意情况下 confidence `< min_suggest`（默认 0.30） | 不入库（连 pending 都不进） | 明显是模型瞎猜 |

```
ai.confidence.min_suggest        默认 0.30  —— 低于此值直接丢弃
ai.auto_accept_exact_terms       默认 true  —— 精确命中词表的词自动接收
ai.auto_adopt_new_terms          默认 **false** —— 显式开关，默认关闭
```

**`auto_adopt_new_terms` 的措辞必须写清风险**：
「开启后 AI 可以直接向词表添加新标签。这会加快打标，但可能引入近义词
（如已有『海边』时新增『海滨』）。建议保持关闭，在『新词待确认』里逐个采纳。」

**confidence 仍然有两个正当用途**（不涉及自动决策）：
① 审核界面 `< 0.5` 标红（让用户优先看不确定的）；
② pending 列表按 confidence 降序（高置信的先审，效率高）。

## 4. 超级搜索地基：从「高级筛选器」到「检索」

> 本节按第三方评审意见 1（P0）完整新增。这是**本次修订最大的改动**。
> 评审的判断我认同：现有计划做完颜色、命中数、能力注入之后，
> 它仍然是个高级筛选器，不是检索系统。

### 4.1 诊断：为什么现在表达不了「草地必须有，蓝天最好有」

三个层面的缺失，逐层验证：

| 层 | 现状 | 证据 |
|---|---|---|
| **查询模型** | 只有 `And / Or / Not / Leaf` 四种节点，**全部是硬条件** | `query_expr.rs:92 QueryExpr` |
| **未匹配概念的处理** | 降级为 `LeafCond::Search`（FTS/LIKE）—— **仍然是硬条件** | `super_search_ai.rs:558-565`：`ConceptOutcome::Content(term)` → `leaves.push(Leaf{Search})`，然后 `pack_and` |
| **排序** | 七个分支全是字段排序（created_at / taken_at / size / resolution / name / rating / modified_at），**无相关度** | `assets.rs:509 order_by`；grep `bm25\|rank` = **0 命中** |

所以「草地必须有，蓝天最好有，整体接近清新人像，排除夜景」这句话
在当前模型里只有两种表达，都是错的：
- 全 AND → 没有蓝天的草地照片被排除（把「最好有」当成「必须有」）
- 全 OR → 只有蓝天没草地的也进来（丢掉了「必须」）

**这不是 UI 问题，是查询模型缺一个维度。**

### 4.2 设计：`SearchPlanV3`

评审指出二轮的 `SearchPlanV3` **没有 `retrievers` 字段**，S4 只是个孤立的接口外壳。
本轮把它接进主结构，并且只保留**两路真实可用**的检索器（见 §4.4 的范围决策）。

```rust
/// 检索计划（V3）。三段：硬性过滤 + 加权可选 + 多路召回 + 排序。
/// 与 Elasticsearch bool query 的 filter/must_not/should/minimum_should_match 同构。
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct SearchPlanV3 {
    /// 【四轮新增，评审 P6】三个版本号。保存搜索条件、日志排查、
    /// 未来改 AST 时的重放/迁移全靠它们。缺省值 = 当前版本（兼容旧 JSON）。
    ///
    /// - plan_schema_version：结构版本。加/删字段时 +1
    /// - normalization_version：normalize_expr 的规则版本。
    ///   改了归一化规则（如「空组删除」「单子节点折叠」）时 +1
    /// - compiler_version：compile_expr / compile_leaf 的 SQL 生成版本。
    ///   改了 SQL 形态（如 should 的求值方式）时 +1
    #[serde(default = "default_plan_schema_version")]
    pub plan_schema_version: u32,
    #[serde(default = "default_normalization_version")]
    pub normalization_version: u32,
    #[serde(default = "default_compiler_version")]
    pub compiler_version: u32,

    /// 硬性必须满足。沿用现有 QueryExpr（零改动复用全部编译逻辑）
    pub filter: Option<QueryExpr>,

    /// 硬性排除
    pub must_not: Option<QueryExpr>,

    /// 加权可选条件（SQL 可判定的）：满足则加分，不满足不淘汰
    pub should: Vec<ShouldClause>,

    /// 至少命中几条 should 才进结果。
    /// filter 为空且 should 非空时**强制 ≥ 1**（否则返回全库）
    pub minimum_should_match: u32,

    /// 多路召回：不能用 SQL 布尔表达的相关度来源（FTS bm25 排名、别名扩展）。
    /// 空 = 纯 SQL 路径。未来若加视觉语义，只需在 Retriever enum 加一个变体。
    pub retrievers: RetrieverPlan,

    /// 排序
    pub ranking: Ranking,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ShouldClause {
    pub cond: LeafCond,     // 与 filter 完全同一套叶子条件
    pub weight: f32,        // 默认 1.0
    pub label: String,      // 给用户看（「蓝天（加分项）」）
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum Ranking {
    /// 按字段（现有七个白名单之一）。用户显式选择时用
    Field { key: String, dir: String },
    /// 按相关度（should 加权 + retrievers 融合得分）
    Relevance,
}
```

#### 三个版本号的用法

评审指出：`SearchPlanV3` 有「版本」的名字但结构里没有版本字段。
未来保存搜索条件或调整 AST 时，**同一个 JSON 在新版本里可能被解释成不同含义**。

```rust
// 单一声明处（db/query_expr.rs）
pub const PLAN_SCHEMA_VERSION: u32 = 3;      // 与 SearchPlanV3 的 3 对应
pub const NORMALIZATION_VERSION: u32 = 1;    // normalize_expr 的规则版本
pub const COMPILER_VERSION: u32 = 1;         // compile_expr 的 SQL 生成版本
```

**三个版本各自管什么**（分开是因为它们的兼容性影响不同）：

| 版本号 | 什么时候 +1 | 旧值的处理 |
|---|---|---|
| `plan_schema_version` | 结构变了（加/删/改字段语义） | **必须写迁移函数** `migrate_plan_v3_to_v4`。读到旧版本先迁移再执行 |
| `normalization_version` | 归一化规则变了 | 读到旧值时**重新归一化一次**，然后按新规则执行。这不改变用户意图，只改变内部表示 |
| `compiler_version` | SQL 生成方式变了 | **无需处理** —— 编译是每次现算的，不持久化。这个版本号只用于**日志与 bug 排查**（「这条查询是用哪版编译器跑的」） |

**用在哪三处**：

1. **保存的搜索条件**（`superSearchStore` 的 `persist`，W5f-f6 已有）：
   `partialize` 现在存 `expr + query`，S1 之后改存整个 `SearchPlanV3`（含三个版本号）。
   hydrate 时若 `plan_schema_version < 当前` → 走迁移函数；
   若 `> 当前`（用户降级了应用）→ **丢弃并 warning**「保存的搜索条件来自更新版本，已重置」。
2. **AI 解析结果的日志**：`request_config_json`（§3.8 D-8b）里带上三个版本号，
   排查「为什么这条查询以前能用现在不行」时能一眼看出是哪一层变了。
3. **未来的「保存的搜索」功能**（计划书已拍板不做，但结构留好了）：
   存 `SearchPlanV3` 的 JSON + 三个版本号，重放时按上表处理。

**测试**：`plan_missing_version_defaults_to_current`（旧 JSON 无版本字段 → 补当前值）/
`plan_future_schema_version_is_rejected`（版本高于当前 → 丢弃 + warning）/
`normalization_version_bump_renormalizes`。

### 4.2b 匹配模式契约（精确 + 模糊）

评审正确指出：§3.6 的近似匹配只服务**AI 打标时的疑似重复发现**，
不等于**用户搜索时的模糊匹配**。「海」搜不搜到「海边」、「海滨」搜不搜到「海边」、
错别字怎么办 —— 之前没有正式契约。**这一节定义它。**

#### 五种匹配模式

```rust
/// 标签匹配模式。用户在 UI 上选，AI 也可以在 SearchIntentV3 里指定。
/// 每种模式的索引利用、扩展上限、排序影响、warning 都是确定的（见下表）。
#[derive(Debug, Clone, Copy, PartialEq, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub enum TermMatch {
    /// 规范名精确命中（normalized 后完全相等）
    Exact,
    /// 规范名或任意别名精确命中。**默认模式**
    Alias,
    /// 前缀命中（「青」→「青少年」）
    Prefix,
    /// 包含命中（「人」→「人物」「单人」「一个人」）
    Contains,
    /// 编辑距离 ≤ 1（「森材」→「森林」，容错别字）
    Fuzzy,
}

impl Default for TermMatch { fn default() -> Self { Self::Alias } }
```

`LeafCond::Tag` 增加一个字段（**向后兼容**，缺省 = `Alias`）：

```rust
Tag {
    facet_key: String,
    tag_ids: Vec<i64>,          // 显式选中的标签（UI 勾选路径）
    #[serde(default)]
    term_query: Option<String>, // 【新】按词查（AI/搜索框路径）
    #[serde(default)]
    term_match: TermMatch,      // 【新】词查的匹配模式
    mode: Option<String>,       // any | all
    include_descendants: bool,
}
```

**`tag_ids` 与 `term_query` 的关系**：二者可同时存在。
`term_query` 先按 `term_match` 扩展成一组 tag_id，与 `tag_ids` 求并集，
再走现有的 `compile_tag_leaf`。**编译层零改动** —— 只是多了一步扩展。

#### 五种模式的完整规格（每格都是确定的，不留解释空间）

| 模式 | SQL 形态 | 索引 | 扩展上限 | 影响排序 | warning |
|---|---|---|---|---|---|
| `Exact` | `normalized_term = ?` AND `term_kind='canonical'` | ✅ `ux_terms` 主键级 | 1 | 否 | 未命中时「没有叫「X」的标签」 |
| `Alias`（默认） | `normalized_term = ?`（不限 term_kind） | ✅ `ux_terms` | 1 | 否 | 命中别名时「「海滨」已归入「海边」」（**告知，不是警告**） |
| `Prefix` | `normalized_term >= :lo AND normalized_term < :hi`，`:hi = next_prefix(:lo)` | ✅ **必须用范围查询**（见下） | **10** | ✅ 按名字长度升序（短的更可能是用户想要的） | 命中 >1 时「「青」匹配到 N 个标签：青少年、…」；超上限时「只用了前 10 个」 |
| `Contains` | `normalized_term LIKE '%'\|\|?\|\|'%'` | ❌ 全表扫（见下） | **10** | ✅ 同上 | 同上 + 「包含匹配可能带来无关结果」 |
| `Fuzzy` | Rust 侧对候选集算编辑距离 | ❌（先用 Prefix 缩候选，再算距离） | **5** | ✅ 按距离升序，同距离按长度 | 「「森材」按相近词匹配到：森林」 |

**关于索引的实测结论**（我在 5 万行 `tag_terms` 上验证过）：

```
LIKE 'term123%'  → SCAN tt                                    ← 不走索引！
LIKE '%term123%' → SCAN tt                                    ← 预期
>= 'term123' AND < 'term124' → SEARCH tt USING INDEX ix       ← 走索引 ✅
GLOB 'term123*'  → SEARCH tt USING INDEX ix                   ← 也走索引 ✅
```

**`LIKE 'x%'` 不走索引**（因为默认 `LIKE` 是大小写不敏感的，SQLite 的
前缀优化要求列有 `COLLATE NOCASE` 或开 `case_sensitive_like`）。
**所以 `Prefix` 必须编译成范围查询而不是 `LIKE`**。
我们的 `normalized_term` 已经是 lowercase（`normalize_name` 保证），
所以范围查询语义正确。

耗时（5 万行）：范围查询 46ms、全表扫 52ms —— 当前规模差别不大，
但索引在 50 万行时是数量级差异，值得从一开始就写对。

#### `next_prefix`：上界必须算出来，不能拼 `U+FFFF`

评审指出「固定拼接 `prefix + U+FFFF` 对 emoji 或其他补充字符不一定正确」。
**我写了个最小 crate 实测，评审说对了 —— 这是个真实的漏检 bug。**

反例（Rust `str` 与 SQLite BINARY 排序都验证过）：

```
下界 "a"，旧上界 "a\u{FFFF}"
候选 "a😀"（确实以 "a" 开头）
  是否落在 [下界, 旧上界)？  → false   ← 被漏掉了！
  是否落在 [下界, next_prefix("a")="b")？ → true
```

原因：UTF-8 编码下 `U+FFFF` 是 `EF BF BF`，而 `U+1F600`（😀）是
`F0 9F 98 80` —— **字节序更大**。SQLite 的 BINARY 排序按字节比，
所以 `"a😀" > "a￿"`。我用 SQLite 直接验证：

```sql
SELECT ('a'||char(0x1F600)) < ('a'||char(0xFFFF));  -- → 0（即 a😀 更大）
-- 用 next_prefix 的上界 'b' 则三条全覆盖：
SELECT quote(x) FROM t WHERE x >= 'a' AND x < 'b';  -- → 'a', 'a￿', 'a😀'
```

**正确实现**（纯函数，好测）：

```rust
/// 计算字典序的「下一个前缀」，作为范围查询的开区间上界。
/// 不变式：所有以 prefix 开头的字符串 s 都满足 prefix <= s < next_prefix(prefix)。
///
/// 做法：把最后一个字符替换成它的下一个 Unicode 标量值（跳过 surrogate 区间
/// 0xD800..=0xDFFF —— char::from_u32 会拒绝它们）。
/// 若最后一个字符已是 char::MAX，则去掉它再对前一个字符递归（退化到更短的前缀）。
/// 全部字符都到顶时返回 None，调用方退化为「只用下界」（>= prefix，扫到表尾）。
pub fn next_prefix(prefix: &str) -> Option<String> {
    let mut chars: Vec<char> = prefix.chars().collect();
    while let Some(last) = chars.pop() {
        let mut cp = last as u32 + 1;
        while cp <= 0x10FFFF {
            if let Some(c) = char::from_u32(cp) {   // 自动跳过 surrogate
                let mut out: String = chars.iter().collect();
                out.push(c);
                return Some(out);
            }
            cp += 1;
        }
        // 该字符已到顶 → 丢掉它，对前一个字符继续
    }
    None   // 空串或全是 char::MAX
}
```

**实测的十一个用例（全部通过不变式检查）**：

| 输入 | `next_prefix` | 说明 |
|---|---|---|
| `"term123"` | `"term124"` | ASCII 递增 |
| `"青"` | `"靓"` | 中文（U+9752 → U+9753） |
| `"海边"` | `"海辺"` | 多字符只改最后一个 |
| `"😀"` | `"😁"` | **emoji（BMP 外）正确递增** |
| `"a😀"` | `"a😁"` | ASCII + emoji |
| `"\u{FFFF}"` | `"𐀀"`（U+10000） | **跨越 BMP 边界** —— 旧方案在这里彻底失效 |
| `"a\u{FFFF}"` | `"a𐀀"` | 同上 |
| `"\u{10FFFF}"` | `None` | char::MAX → 无上界，退化为只用下界 |
| `"a\u{10FFFF}"` | `"b"` | 末字符到顶 → 退化到前一个字符递增 |
| `"\u{D7FF}"` | `"\u{E000}"` | **正确跳过 surrogate 区间** |
| `""` | `None` | 空串 → 无约束 |

**SQLite 侧的前提**：`normalized_term` 列必须是默认的 **BINARY** 排序
（不能加 `COLLATE NOCASE`）—— Rust 的 `str` 比较是按 UTF-8 字节序，
只有 BINARY 排序与它一致。`tag_terms` 建表时不声明 COLLATE 即为 BINARY，
**这一点要在建表 SQL 上写注释锁死**，否则日后有人加了 COLLATE
就会让 `next_prefix` 的不变式失效。

**测试**（`next_prefix_covers_all_children`）：对上表十一个输入，
每个构造五个「以它开头」的探针字符串（`x`、`x` + 长中文、`x` + 两个 emoji、
`x` + char::MAX 等），断言全部落在 `[prefix, next_prefix)` 区间内；
再断言一个字典序更大的兄弟串落在区间外。
外加一条 SQL 层测试 `prefix_range_matches_rust_ordering` ——
往 `tag_terms` 插入含 emoji 的词，断言 SQL 范围查询与 Rust 判断结果一致。

### 4.3 SQL 实现（实测可行）

我用真实 rusqlite + bundled SQLite 验证了两点：

**① FTS5 `bm25()` 可用**（实测）：
```
bm25 可用: [(2, -1.06e-6), (1, -8.95e-7)]    ← 负值，越小越相关
bm25 带权重: -1.27e-6                        ← bm25(t, 2.0) 形式也支持
```

**② 加权 should + `minimum_should_match` 的 SQL 形态**（实测两种写法都通）。

**评审 P1-8 指出「should 的分数和命中计算存在重复执行」** —— 二轮的写法里
每个 should 的 SQL 片段出现两次（一次算 score、一次算 hits）。**改为一次求值**：

```sql
-- 三轮：每个 should 只求值一次，score 与 hits 从同一个 CASE 派生
SELECT id, score, hits FROM (
  SELECT a.id,
         -- 每个 should 一个 0/1 标记，只求值一次
         (CASE WHEN <should_1_sql> THEN 1 ELSE 0 END) AS m1,
         (CASE WHEN <should_2_sql> THEN 1 ELSE 0 END) AS m2,
         (CASE WHEN <should_3_sql> THEN 1 ELSE 0 END) AS m3
    FROM assets a
   WHERE <filter_sql> AND NOT (<must_not_sql>) AND a.deleted_at IS NULL
) AS marked
CROSS JOIN (SELECT 0) AS _   -- 占位，实际用外层再包一次派生列
-- 实际形态（两层派生表，SQLite 支持引用上一层的别名）：
SELECT id, score, hits FROM (
  SELECT id, m1, m2, m3,
         m1 * 1.0 + m2 * 1.5 + m3 * 0.8 AS score,
         m1 + m2 + m3                   AS hits
    FROM ( /* 上面那层 */ )
) WHERE hits >= :min_should
ORDER BY score DESC, id DESC      -- 尾缀 id DESC 保持分页稳定（不变量 28）
```

实测输出（4 行测试数据，权重 2.0 / 1.0）：`[(1, 3.0, 2), (2, 2.0, 1), (3, 1.0, 1)]`
—— 按 score 降序，`hits >= 1` 过滤生效。

**关键性质**：
- `should` 的 SQL 片段与 `filter` **完全相同**（都走 `compile_leaf`）→ 零新编译逻辑
- 白名单/参数绑定的安全性**自动继承**（不变量 26 不受影响）
- `filter` 为空时强制 `minimum_should_match >= 1`，否则 `hits >= 0` 返回全库

**性能**：每个 should 是一次相关子查询（`EXISTS`）。410 行无所谓；
3 万素材需探针（R2-5）。慢的话优化路径是「filter 先落临时表，再算 score」。

### 4.4 检索器：只做两路真实的，不为向量写空壳

**范围决策（你 2026-09-01 拍板）**：不做视觉语义搜索。
你要的是「AI 根据自然语言帮我把条件公式写出来」，不是「以图搜图」。

所以二轮/三轮设计的 `asset_embeddings` 表和 `Retriever::Vector` **全部砍掉**。
理由不只是省 0.5 天：

| 方案 | 问题 |
|---|---|
| 建表 + `unimplemented!()` | **死代码**。没有 embedding 时永远返回空，测试只能用合成向量测一个永不启用的路径 |
| 建表 + 完整暴力扫描实现 | 代码是真的，但**没有数据喂它** → 仍然是死路径，只是死得更长 |
| **不建表、不写 Vector 分支（选它）** | 零死代码。未来要做时是**纯增量**：加一个 enum 变体 + 一张表 + 一个回填命令，`SearchPlanV3` 结构一行不用改 |

**但 `RetrieverPlan` 仍然进 `SearchPlanV3`** —— 因为它承载的两路检索器是**真实且有价值**的，
不是为将来预留的空壳：

```rust
#[derive(Debug, Clone, Serialize, Deserialize, Default)]
pub struct RetrieverPlan {
    pub retrievers: Vec<WeightedRetriever>,
    pub fusion: Fusion,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum Retriever {
    /// FTS5 + bm25 相关度。已有能力（db/search.rs），本轮只是把得分暴露出来。
    /// 用途：「整体接近清新人像」里无法映射成标签的部分，按文字相关度排序而非硬筛。
    Fts { query: String, scope: SearchScope },
    /// 标签别名扩展：搜「海滨」→ 经 tag_terms 命中「海边」的 tag_id 再查。
    /// 已有能力（F3 的 find_by_term + tag_terms），本轮只是包装成检索器。
    TagAlias { text: String, facet_key: Option<String> },
    // 未来若要视觉语义：在这里加 Vector { query_vec, model_id, top_k }
    // + asset_embeddings 表 + 一个 embedding 回填命令。融合层与 SearchPlanV3 不用改。
}

#[derive(Debug, Clone, Copy, Serialize, Deserialize, Default)]
pub enum Fusion {
    /// 默认：RRF（Reciprocal Rank Fusion）—— 只用排名不用原始分数。
    /// score = Σ weight_i / (60 + rank_i)
    #[default]
    Rrf,
    /// 线性加权：各路得分 min-max 归一到 [0,1] 后加权求和。可选项
    Linear,
}
```

**为什么默认 RRF**：这解决了二轮遗留的量纲问题 —— bm25 返回负值、
should 加分是任意正数、别名命中是 0/1，三者的**排名**是可比的，**分数**不可比。
RRF 只用排名，不需要知道任何一路的分数范围或分布。

**必须的测试**（三条，都是真实路径）：
`rrf_fusion_is_scale_invariant`（某一路得分全乘 100，排序不变）/
`fts_retriever_exposes_bm25_rank` /
`alias_retriever_expands_via_tag_terms`（搜「海滨」命中「海边」的素材）。

#### 一期搜索能力的准确定位

**能做到的**：
- 标签、元数据、颜色、文件属性的精确筛选（`filter` / `must_not`）
- 「最好有 X」的加权可选（`should`）→ 影响排序而非淘汰
- 已有标签和 AI 一句话描述的文字相关度（FTS bm25）
- 标签别名扩展（搜「海滨」命中「海边」）
- **AI 把中文自然语言转成上面这些条件，并且条件在界面上可见、可改、可解释**

**做不到的**：理解图片视觉内容。「整体接近清新人像」如果这张图既没有「清新」标签
也没有相关描述文字，一期搜不到它。

**措辞边界**（文档和 UI 都要遵守）：
- ✅ 「AI 帮你把一句话转成搜索条件」/「按标签、属性、颜色和描述搜索」
- ❌ 不能说「视觉语义搜索」「以图搜图」「理解画面内容」

#### 守卫改为「结构-原句一致性校验」（评审 P1-10）

评审正确指出：依赖固定词表（「最好、优先、偏、倾向、接近」）会误判
「有蓝天更好」「蓝天可有可无」「尽量有蓝天」。**改为验证结构与原句是否冲突。**

```rust
/// preferred 守卫（三轮重写）。不再匹配固定词表，而是三级校验：
///
/// ① evidence 必须是原句的**真子串**（trim + 全角半角归一后比较）。
///    模型编造 evidence → 降级为 required + warning。
///    这一条最强 —— 它要求模型把判断依据落回原文，无法靠猜。
///
/// ② evidence 必须**包含该 concept 的 text 或其近邻**（±8 字窗口内）。
///    防止模型摘一段无关的话当依据（如 concept="蓝天" 但 evidence="最好是横图"）。
///
/// ③ 兜底信号（不作为唯一依据，只在 ①② 都通过后用于**提高**置信）：
///    原句是否含任一偏好词。含 → 正常；不含 → 保留为 preferred 但记 info 级 warning
///    「原文未见明显的偏好表述，已按加分项处理（可在下方改为必须）」。
///
/// 关键取舍：①② 失败才降级；③ 只提示不降级。
/// 理由：中文偏好表达太多（「有…更好」「…也行」「不强求…」「尽量…」），
/// 穷举必然漏；但「evidence 是原文子串且靠近 concept」这个结构约束
/// 对任何表达方式都成立。
fn guard_preferred(input: &str, group: &mut SearchGroupV3) -> Vec<String> { /* ... */ }
```

**实际效果对比**：

| 原句 | concept | evidence | 二轮（词表） | 三轮（一致性） |
|---|---|---|---|---|
| 「最好有蓝天」 | 蓝天 | 「最好有蓝天」 | ✅ 通过 | ✅ 通过 |
| **「有蓝天更好」** | 蓝天 | 「有蓝天更好」 | **❌ 误降级** | ✅ 通过 |
| **「蓝天可有可无」** | 蓝天 | 「蓝天可有可无」 | **❌ 误降级** | ✅ 通过（③ 记 info） |
| **「尽量有蓝天」** | 蓝天 | 「尽量有蓝天」 | **❌ 误降级** | ✅ 通过 |
| 「必须有蓝天」 | 蓝天 | （模型编造「最好有蓝天」） | ✅ 误通过 | **❌ 正确降级**（① 不是子串） |

### 4.8 色板可检索（关系表）

初版设计的 `LIKE '%,红,%'` 被评审正确地指出无法用索引。**我实测确认**：

```
LIKE 方案：  EXPLAIN QUERY PLAN → SCAN a2                （全表扫）
关系表方案： EXPLAIN QUERY PLAN → SEARCH USING COVERING INDEX ix_apc
```

**但要诚实说明性能数字**：在 30 万行规模上，两者实测都是 50–70ms
（LIKE 全表扫 30 万行 = 72ms；关系表覆盖索引 = 49ms）。
**索引的性能优势要更大规模才明显。**

**所以采用关系表的真正理由是表达力，不是性能**：

```sql
-- V23
CREATE TABLE asset_palette_colors (
  asset_id     INTEGER NOT NULL REFERENCES assets(id) ON DELETE CASCADE,
  rank         INTEGER NOT NULL,        -- 0 = 主色，按 ratio 降序
  color_bucket INTEGER NOT NULL,        -- 色名分桶（0..12，与 colorNameZh 分段一一对应）
  ratio        REAL    NOT NULL,        -- 该色占比 0..1
  PRIMARY KEY (asset_id, rank)
);
CREATE INDEX ix_apc_bucket ON asset_palette_colors(color_bucket, rank, asset_id);
```

**四种查询自然表达**（实测查询计划全部走覆盖索引）：

| 需求 | SQL |
|---|---|
| 主色是红 | `bucket=红 AND rank=0` |
| **前三色含红** | `bucket=红 AND rank<3` |
| 画面中有红 | `bucket=红`（不限 rank） |
| **红占比 >20%** | `bucket=红 AND ratio>0.2` ← 字符串方案完全无法表达 |
| 同时含红和蓝（前三色） | 两个子查询 `INTERSECT` |

**这就是关系表的价值**：`ratio` 和 `rank` 是字符串方案表达不了的维度。
「前三色含红」和「红占 30% 以上」是两个不同的问题，用户会两个都要。

**新 metadata key**（三个，对应三种 rank 范围）：
`palette_dominant`（rank=0）/ `palette_top3`（rank<3）/ `palette_any`（不限）。
值域是色名（走 enum，`in` 支持多选）。

⚠ **我仍不确定该做几个维度**（调研被网络阻断，§6.4 第 1 项）。
**但关系表的好处是：三个 key 的实现成本几乎为零**（只差 `rank` 的谓词），
所以「先做一个还是三个」变成纯 UI 决策，不影响数据层。
建议：数据层三个都通，UI 先只暴露 `palette_top3`（你的原始需求）。

**色名分桶必须与前端一致**：`color_bucket` 的 0..12 编号要与
`src/utils/colorName.ts` 的 `HUE_NAMES` + 灰阶分级严格对应。
**先写交叉测试再写实现**（同一组 RGB，Rust 的 bucket 和 TS 的色名必须对应）。

**回填**：`rescan_palette_colors` 命令 —— 读 `palette_json`，
Rust 侧算 bucket，批量插 `asset_palette_colors`。不解码图片，410 行毫秒级。

### 4.9 命中数诊断（AST 感知）

初版的 `cumulative` 顺序累加只对扁平 AND 有意义。**改为四个指标**：

```rust
/// 单个条件（AST 叶子）的诊断。path 是从根到该叶子的索引路径。
pub struct LeafDiagnostic {
    pub path: Vec<usize>,
    pub label: String,
    /// ① 该条件单独执行的命中数
    pub self_count: i64,
    /// ② 完整表达式的命中数（所有叶子共享同一个值）
    pub result_count: i64,
    /// ③ 把该叶子从 AST 中移除后的命中数
    pub count_without_leaf: i64,
    /// ④ delta = count_without_leaf - result_count
    ///    AND 下为正（该条件砍掉了多少）；OR 下为负或 0（该条件贡献了多少）；
    ///    NOT 下语义反转。这是唯一在三种节点下都有意义的量。
    pub delta: i64,
}
```

**为什么 `delta` 在三种节点下都成立**：

| 场景 | `self_count` | `result_count` | `count_without_leaf` | `delta` | 解读 |
|---|---|---|---|---|---|
| `A AND B`，看 B | B 单独 50 | 10 | 只有 A = 100 | **+90** | B 砍掉了 90 |
| `A AND B`，B 砍空 | B 单独 0 | **0** | 只有 A = 100 | **+100** | **B 是罪魁祸首** |
| `A OR B`，看 B | B 单独 50 | 120 | 只有 A = 100 | **−20** | B 多带来了 20 |
| `NOT B`（全局） | B 单独 50 | 360 | 无 NOT = 410 | **+50** | 排除了 50 |

**UI 规则**：
- `delta > 0` 且 `result_count == 0` → 标红「这个条件把结果砍到 0」
- `delta > 0` → 显示「−90」（灰色）
- `delta < 0` → 显示「+20」（表示它扩大了结果）
- `self_count == 0` → 额外标注「这个条件单独就没有匹配项」
  （区分「条件本身无效」和「与其他条件冲突」—— 这是很重要的区分）

**成本**：N 个叶子 = N（self）+ N（without）+ 1（result）= 2N+1 次 COUNT。
5 个条件 = 11 次。410 行微秒级；3 万素材需探针（R2-5）。
优化：`self_count` 和 `count_without_leaf` 可以并行发（同一个连接内串行，
但不阻塞主查询）。

**should 条件的诊断不同**：should 不淘汰结果，所以 `delta` 恒为 0 或负。
对 should 显示的是「命中该加分项的素材数 / 结果总数」（如「蓝天：12 / 106」）。

### 4.10 库能力注入：只告知，不改写

初版写「GPS 全空 → 让 AI 不要输出经纬度条件」。**这违反原则 P5，改掉。**

分两条清晰的边界：

| 用途 | 允许 | 例子 |
|---|---|---|
| **提示词里的事实告知** | ✅ | 「本库 0 张有 GPS 定位」—— 模型据此**自主决定**是否输出，不是被禁止 |
| **后端强制剔除条件** | ❌ **禁止** | 用户明确搜「有定位的照片」→ 必须返回 0 项 + 解释，不能删条件返回全库 |

| **建议放宽** | ✅ | 「移除定位条件后可得 205 项」+ 一个按钮 |

**实现**：库能力摘要仍然注入提示词（措辞改成陈述事实而非禁令），
但**后端不做任何基于库统计的条件剔除**。
零结果时的归因由 §4.9 的 `self_count` 自然给出 —— 不需要额外的库统计逻辑。


### 7.3 关键决策与理由

| 决策 | 理由 |
|---|---|
| **三段式（必须/加分/排除）而非一个大表达式** | 直接映射 `SearchPlanV3` 的 filter/should/must_not。用户的心理模型本来就是这三档（「一定要」「最好有」「不要」）。混在一个树里会让「加分」这个概念不可见 |
| **`minimum_should_match` 做成「至少满足 N 项」下拉** | 默认 0（纯排序影响）。放在加分项区域标题行，不是藏在设置里 |
| **加分项不支持嵌套** | 加分项之间天然是「各自独立加分」，OR/AND 对它无意义。这个限制让 UI 简单很多 |
| **只支持一层嵌套（在必须区）** | 后端支持 5 层，但摄影师需求是「A 且 B 且 (C 或 D)」这种一层。遇到更深的树**保留只读降级**，但改成**可展开的树形只读视图**而非一句话 |
| **字段选择器改可搜索 combobox** | 复用项目已有的 `ModelCombobox.tsx` 交互骨架（可输入 + ↑↓ + Enter + Esc + 点外关闭），**不引新依赖**。加「最近使用」置顶（localStorage 存 5 个） |
| **标签多选改 chip + 下拉勾选** | 弃用 `<select multiple>`。带搜索框的面板，按分面折叠分组（W3-3b 的 optgroup 逻辑可迁移），已选显示为可删 chip |
| **颜色改色块 + 三维度切换 + ratio 滑块** | ① 12 个 hue 色块 + 黑/灰/白（复用 `colorNameZh` 分段）；② 维度切换「主色 / 前三色 / 画面中有」（C-1 关系表的三个 key）；③ **ratio 阈值滑块**（「红色占 20% 以上」—— 这是关系表独有的表达力）；④ 高级折叠保留原始 hue/sat/lum |
| **数值输入加单位下拉** | `[5]–[10] [MB ▾]`（KB/MB/GB），后端始终收字节。消灭单位漏斗在手工路径上的可能 |
| **命中数显示 delta 而非累计** | C-2 的四指标。必须区显示 `−90`（砍掉多少），加分区显示 `+12/106`（命中多少）。`self_count==0` 时额外标注「这个条件单独就没有匹配项」—— 区分「条件本身无效」和「与其他条件冲突」 |
