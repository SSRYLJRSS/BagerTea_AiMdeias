## 1. BUG-A：FTS 路径下 ASCII 3+ 字符 token 内部子串搜索静默失败（P1）

### 1.1 根因确认

一句话：`db/search.rs::fts_search` 把查询整体包成 FTS5 双引号短语 `"..."`，短语要求「token 完整相等且相邻」，而 unicode61 把 `IMG_2024_001.jpg` 切成 `img / 2024 / 001 / jpg`、把 `photo001.jpg` 切成单 token `photo001`，`"202"≠2024`、`"photo"≠photo001`，token 内部子串永远不命中；≤2 字走 LIKE 子串语义，导致**同一素材搜索行为随字数不一致**。

涉及文件:函数：
- `src-tauri/src/db/search.rs:23-32` `fts_search`（短语化）
- `src-tauri/src/db/search.rs:11-21` `search_asset_ids`（>2 字路由到 FTS）
- `src-tauri/src/db/migrations.rs:60-66`（`assets_fts` tokenize=`unicode61`，分词边界选择面）

### 1.2 修复方案（查询侧，零迁移）

在 `search_asset_ids` 增加分支：查询长度 >2 且**包含非 CJK 字符**（ASCII 字母/数字/符号）时，改为「FTS 精确 ∪ LIKE 子串」**并集**返回。

为什么必须并集而非互斥：FTS 可能命中 LIKE 不命中的资产（例如查询跨标签边界、`tag_names` 展开串含空格但单个标签名不含该子串）；LIKE 可能命中 FTS 不命中的资产（token 内部子串）。两者取并集才是完整「子串语义」。

伪代码（最终形态，同时为 BUG-B/BUG-D 预留分支）：

```rust
pub fn search_asset_ids(conn: &Connection, raw: &str) -> AppResult<Vec<i64>> {
    let q = raw.trim().to_lowercase();
    if q.is_empty() { return Ok(Vec::new()); }
    let n = q.chars().count();
    if n <= 2 { return like_search(conn, &q); }            // 现状不动（≤2 字 LIKE）
    if q.chars().any(|c| !is_cjk(c)) {
        // BUG-A/B：混合查询（含 ASCII/符号）→ FTS ∪ LIKE，保证子串语义
        let fts_ids  = fts_search(conn, &q)?;              // 现状短语，作精确层
        let like_ids = like_search(conn, &q)?;             // 复用现有 LIKE（已转义 % _ \）
        return Ok(union_dedup(fts_ids, like_ids));
    }
    if n >= 4 { return fts_search_chunk_and(conn, &q); }   // BUG-D：纯 CJK 多字 → 2 字块 AND
    fts_search(conn, &q)                                   // 纯 CJK 3 字 → 现状短语（防误命中）
}

fn union_dedup(a: Vec<i64>, b: Vec<i64>) -> Vec<i64> {
    let mut seen = std::collections::HashSet::with_capacity(a.len() + b.len());
    let mut out = Vec::with_capacity(a.len() + b.len());
    for v in a.into_iter().chain(b) { if seen.insert(v) { out.push(v); } }
    out
}
```

要点：
- `is_cjk` 与 `bigram.rs` 是同一判断，建议把 `bigram.rs::is_cjk` 提升为 `pub` 复用，避免重复实现。
- 返回 id 顺序不影响后续：`assets::list` 拿到 id 后自行 `ORDER BY created_at DESC, id DESC`（`db/assets.rs:183`），`union_dedup` 只需去重无需保序。
- `like_search` 现有实现已正确处理 `% _ \` 转义与标签 `EXISTS` 子查询（`search.rs:34-48`），无需改动；代价是 ASCII 查询多一次全表 LIKE（见 1.3）。

**索引影响：无。** 不改写入侧、不改 tokenizer、不重建 FTS。

### 1.3 影响面与风险

| 风险点 | 说明 | 处置 |
|---|---|---|
| 纯 CJK 3 字查询 | 保持现状短语，`海边日` 不误命中 `上海公园湖边合影` 等既有通过用例 | 无回归 |
| ≤2 字 LIKE 路径 | 分支顺序在最前，完全不动 | 无回归 |
| ASCII 查询性能 | 混合分支多一次 LIKE 全表扫描；3 万素材约毫秒级，10 万素材约几十毫秒 | 可接受；后续结合 B17（IN 列表改造）与「FTS 命中时按候选集复核」优化 |
| 并集引入更多命中 | 子串语义本就是用户直觉（搜 `202` 命中 `12023.jpg` 属预期） | 符合 PRD 子串搜索预期 |
| FTS 短语对 `%` 等符号 | 保持现状加引号，`"100%"` 不崩溃但空；并集中 LIKE 兜底命中（顺带修复 BUG-B 症状） | 正向收益 |

### 1.4 验证方案

## 2. BUG-B：CJK 与 ASCII 相邻合并成单 token，跨边界子串搜索失败（P2）

### 2.1 根因确认

一句话：`utils/bigram.rs::cjk_bigram` 只在「CJK↔CJK」之间插空格，`度` 与 `100` 之间无分隔，unicode61 把 `度100` 合成**单 token**；查询侧切分出的 `100`/`度` 与索引 token `度100` 不等，FTS 短语不命中。

涉及文件:函数：
- `src-tauri/src/utils/bigram.rs:15-26` `cjk_bigram`（切分规则）
- `src-tauri/src/db/search.rs:23-32` `fts_search`（查询侧短语）
- `src-tauri/src/db/migrations.rs:86-117`（触发器调用 `cjk_bigram`，写入侧）

### 2.2 修复方案（分两层）

**第 1 层（查询侧，必须，零迁移）**：复用 BUG-A 的「混合查询 ∪ LIKE」。所有含 ASCII/符号的查询走并集，LIKE 子串直接命中 `进度100%.jpg`。此层单独即可让 `100` / `100%` / `度` / `进度10` 全部命中，**不需要任何索引迁移**。

**第 2 层（写入侧，推荐，需一次性重建）**：修改 `cjk_bigram`，在**所有「CJK↔非CJK」边界**（两个方向）插空格，使索引 token 语义正确：

```rust
pub fn cjk_bigram(s: &str) -> String {
    let mut out = String::with_capacity(s.len() * 2);
    let mut prev_cjk: Option<bool> = None;
    for ch in s.chars() {
        let cur_cjk = is_cjk(ch);
        if let Some(p) = prev_cjk {
            if p != cur_cjk { out.push(' '); }
        }
        prev_cjk = Some(cur_cjk);
        out.push(ch);
    }
    out
}
// 效果：
//   进度100%.jpg        → 进 度 100%.jpg
//   IMG_海边合照01.jpg  → IMG_ 海边合照 01.jpg
//   海边日落            → 海 边 日 落（不变）
```

写入/查询两侧共用同一函数（`bigram::register` 已注册进 SQLite，触发器与查询侧都调用它），天然保持一致；纯 CJK 切分不变，既有通过用例不受影响。

**V3 迁移（一次性重建，与 BUG-D 的 ORDER BY 合并）**：`migrations.rs` 新增 SCHEMA_V3，`user_version` 2→3：

**索引迁移结论（老板最关心）**：查询侧修复 = **零迁移**；写入侧根治 = **需要一次性全库重建**。成本 = 全库重算 fts_content + FTS rebuild，3 万素材约秒级、10 万素材约 10 秒内，发生在启动迁移（应用首次升级）时一次。建议接受该成本（一次性、低频、收益是索引语义完全正确）。

## 3. BUG-D：多标签搜索命中依赖 group_concat 分配顺序（P2）

### 3.1 根因确认

一句话：`migrations.rs` 三个 tag 触发器（`trg_at_ai` / `trg_at_ad` / `trg_tags_au`）中 `group_concat(t.name,' ')` 无 `ORDER BY`，tag_names 顺序 = 分配（插入）顺序；FTS 短语要求查询 token「相邻且同序」，`海边日落` 与 `日 落 海 边` 顺序不一致即空。

涉及文件:函数：
- `src-tauri/src/db/migrations.rs:97-117`（触发器 `group_concat` 无排序）
- `src-tauri/src/db/search.rs:23-32` `fts_search`（短语要求同序相邻）

### 3.2 修复方案（查询侧为主，写入侧加固）

**查询侧（解决顺序依赖，无需重建）**：`fts_search` 对**纯 CJK ≥4 字**查询改为「2 字块 AND」——查询按 2 个字符切块，每块作短语，块间 `AND`；最后单字余数独立成块。顺序无关：只要各 2 字块在索引中各自相邻出现（块间不要求相邻/同序）即命中。

```rust
fn fts_search_chunk_and(conn: &Connection, q: &str) -> AppResult<Vec<i64>> {
    let chars: Vec<char> = q.chars().collect();
    let mut chunks: Vec<String> = Vec::new();
    let mut i = 0;
    while i < chars.len() {
        if i + 1 < chars.len() {
            chunks.push(format!("{} {}", chars[i], chars[i + 1]));
            i += 2;
        } else {
            chunks.push(chars[i].to_string());
            i += 1;
        }
    }
    let query = chunks.iter()
        .map(|c| format!("\"{}\"", c))
        .collect::<Vec<_>>().join(" AND ");
    let mut stmt = conn.prepare("SELECT rowid FROM assets_fts WHERE assets_fts MATCH ?1")?;
    let ids = stmt.query_map([query], |r| r.get(0))?.collect::<Result<Vec<i64>, _>>()?;
    Ok(ids)
}
// 海边日落   → "海 边" AND "日 落"   （日 落 海 边 与 海 边 日 落 均命中 → BUG-D 修复）
// 上海公园  → "上 海" AND "公 园"   （命中 上海公园湖边合影；与既有用例一致）
// 上海湖(3字) → 仍走单短语，保持防误命中（上海湖 不得命中 上海公园湖边合影）
```

为什么 3 字仍走短语：既有通过用例 `fts_cjk_prefix_tokens_ok` 要求 `上海湖` 不命中 `上海公园湖边合影`（含 上/海/湖 但不相邻）；2 字块 AND 会让它命中，故 3 字必须保留短语。已知限制：3 字查询对「反序标签」（如 日/海边 顺序）仍不命中，QA 未要求，接受并记录。

**写入侧（加固，确定性）**：3 个触发器 `group_concat` 加 `ORDER BY t.sort_order, t.id`（子查询排序，与 `assets.rs fill_tags` 展示排序一致）：

```sql
CREATE TRIGGER trg_at_ai AFTER INSERT ON asset_tags BEGIN
  UPDATE fts_content SET tag_names = (
    SELECT cjk_bigram(COALESCE(group_concat(x.name, ' '), ''))
      FROM (SELECT t.name FROM asset_tags at JOIN tags t ON t.id = at.tag_id
             WHERE at.asset_id = new.asset_id
             ORDER BY t.sort_order, t.id) x
  ) WHERE asset_id = new.asset_id;
END;

CREATE TRIGGER trg_at_ad AFTER DELETE ON asset_tags BEGIN
  UPDATE fts_content SET tag_names = (
    SELECT cjk_bigram(COALESCE(group_concat(x.name, ' '), ''))
      FROM (SELECT t.name FROM asset_tags at JOIN tags t ON t.id = at.tag_id
             WHERE at.asset_id = old.asset_id
             ORDER BY t.sort_order, t.id) x
  ) WHERE asset_id = old.asset_id;
END;

CREATE TRIGGER trg_tags_au AFTER UPDATE OF name ON tags BEGIN
  UPDATE fts_content SET tag_names = (
    SELECT cjk_bigram(COALESCE(group_concat(x.name, ' '), ''))
      FROM (SELECT t.name FROM asset_tags at JOIN tags t ON t.id = at.tag_id
             WHERE at.asset_id = fts_content.asset_id
             ORDER BY t.sort_order, t.id) x
  ) WHERE asset_id IN (SELECT asset_id FROM asset_tags WHERE tag_id = new.id);
END;
```

SQLite 无 `ALTER TRIGGER`，V3 中 `DROP TRIGGER IF EXISTS` + 重建（与 BUG-B 合并为同一次迁移）。

**索引迁移结论**：**不需要专门重建**——查询侧 2 字块 AND 已与顺序无关；写入侧 ORDER BY 只影响新写入；若与 BUG-B 一起做 V3 重建，存量 tag_names 顺带统一为规范序（§2.2 的 V3 SQL 已含 ORDER BY）。

### 3.3 影响面与风险

| 风险点 | 说明 | 处置 |
|---|---|---|
| 3 字纯 CJK 防误命中 | 保持短语，`海边日`/`上海湖` 用例不变 | 无回归 |
| ≥4 字语义变化 | 由「整串连续短语」变为「2 字块 AND」：`海边日落` 现在命中同时含 海边+日落 的素材（可跨标签/跨文件名边界）——正是 BUG-D 预期 | 符合 QA 断言；文档记录语义 |
| 2 字块 AND 误命中 | 例：搜 `上海公园` 命中「上海+公园」两个独立标签的素材——属合理 AND 语义 | 接受 |
| 触发器重建 | `trg_tags_au` 重建后仍正确刷新改名后的 tag_names | 回归 `fts_consistency_tag_rename` |
| 与 BUG-A 混合分支关系 | 含 ASCII 查询走并集分支（`fts_search` 保持现状短语），不冲突 | 无 |

### 3.4 验证方案

- 复用回归标记：`fts_asset_tag_join_order_independent`（转绿）
- 新增断言：

## 4. BUG-E：fetchAllIds 全量拉取完整 Asset 对象（P2，前端）

### 4.1 根因确认

一句话：`src/stores/libraryStore.ts:85-96` `fetchAllIds` 调 `listAssets({limit: total})` 拉全量完整 Asset（23 字段 + tags 聚合）只取 id，浪费 IPC/JSON/内存；且 `commands/assets_cmd.rs:28-30` 对每个路径调 `allow_asset`，导致 asset 协议 scope 随全选无界增长。

涉及文件:函数：
- `src/stores/libraryStore.ts:85-96` `fetchAllIds`
- `src-tauri/src/commands/assets_cmd.rs:20-32` `list_assets`（含 `allow_asset` 副作用）
- `src-tauri/src/db/assets.rs:159-198` `list`（返回完整对象）

### 4.2 修复方案（纯新增，零迁移）

1. 后端 `db/assets.rs` 新增 `list_ids`（复用私有 `build_where` + 搜索逻辑，只 `SELECT a.id`）：
```rust
pub fn list_ids(conn: &Connection, filter: &AssetFilter) -> AppResult<Vec<i64>> {
    let search_ids = match &filter.search {
        Some(q) if !q.trim().is_empty() => Some(search::search_asset_ids(conn, q)?),
        _ => None,
    };
    let (cond, params) = build_where(filter, search_ids.as_deref());
    // 参数绑定方式与 list() 完全一致；仅 SELECT id，ORDER BY 同 list()
    let mut stmt = conn.prepare(&format!(
        "SELECT a.id FROM assets a WHERE {cond} ORDER BY a.created_at DESC, a.id DESC"
    ))?;
    // ...query_map 收集 Vec<i64>
}
```
2. `commands/assets_cmd.rs` 新增命令（**不调 allow_asset**，不暴露路径，天然解决 scope 增长）：
```rust
#[tauri::command]
pub fn list_asset_ids(state: State<AppState>, filter: AssetFilter) -> AppResult<Vec<i64>> {
    let conn = lock_db(&state)?;
    assets::list_ids(&conn, &filter)
}
```
3. `lib.rs` invoke_handler 注册 `list_asset_ids`。
4. 前端 `src/api/assets.ts` 新增 `listAssetIds(filter): Promise<number[]>`；`src/stores/libraryStore.ts` `fetchAllIds` 改调它并去掉 total/limit 依赖：
```ts
fetchAllIds: async () => {
  const { filter } = get();
  return listAssetIds({
    assetType: filter.assetType,
    untaggedOnly: filter.untaggedOnly,
    tagId: filter.tagId ?? undefined,
    search: filter.search || undefined,
  });
},
```

说明：`list_asset_ids` 全量返回 id 数组（10 万 id 约 1–2 MB IPC，可接受）；数量上限可作为后续 B19（limit 上限）一并处理，不在本 Bug 范围内。

**索引迁移：无。**

### 4.3 影响面与风险

| 风险点 | 说明 | 处置 |
|---|---|---|
| 后端新增命令 | 纯增量，不动既有命令 | 低 |
| 前端行为 | `fetchAllIds` 返回从 `Asset[]` 变 `number[]`，仅本函数调用方（全选/反选/批量操作）消费 id | 实施时同步检查调用方类型 |
| 权限 scope | 新命令不再触发 `allow_asset`，消除 scope 增长副作用 | 正向收益 |
| 空库 | 不依赖 total 计算 limit，空库返回 `[]` | 无 |

### 4.4 验证方案

- 新增 `list_ids_matches_list_filter`（qa_edge_tests.rs，db 层）：插入 3 素材、部分打标，断言 `assets::list_ids` 在 untagged_only / type / search 筛选下与 `assets::list` 的 items id 集合一致、且不返回 tags
- 前端：`npm run typecheck` + 手工 Ctrl+A（DevTools 观察 IPC payload 明显变小）

## 5. 下一批建议修复的非 Bug 隐患（Top 3，供老板排期）

从架构师报告「三、风险与改进建议（非 Bug 的隐患）」中，按「用户可感知影响 × 修复成本 × 风险」排序：

| 优先级 | 隐患 | 对应条目 | 推荐理由 |
|---|---|---|---|
| 1 | **导入管线拆锁** | B01（P1） | 唯一可复现「导入即全库假死」的路径；导入是核心高频操作，体验影响最大；架构师已给出成熟方案（锁外托管复制/元数据提取 → 短锁批量写库），实施路径清晰 |
| 2 | **delete_assets 异步化 + 删除失败收集** | B02 + B03（P1） | 3 万素材删除时主线程同步文件 IO → UI 白屏；磁盘删除失败被 `let _ =` 吞掉造成「库删了文件还在」假删除。修复成本低（`spawn_blocking` + 返回失败列表），数据可靠性收益明确 |
| 3 | **导出 move 同步库记录** | B04（P1） | move 后库记录指向不存在文件，预览/缩略图/AI 打标全链路失败且无提示；修复极小（move 成功后 `UPDATE assets SET file_path`），属数据完整性缺陷 |
| 备选 | 前端选中/总数一致性 | B09（P1） | 切筛选后 selected 残留，批量打标/删除会作用到不可见素材，有误操作风险；改动集中在前端两个 store，建议与上 3 项同批或紧随 |

> 说明：B18（fetchAllIds ids-only）已在本批 BUG-E 修复；B05（LRU 清理接入）与 B08（asset 协议 scope 收敛）建议列入第三批（成本低但非用户高频路径）。
