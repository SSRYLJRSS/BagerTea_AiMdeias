## §0 一页速览

### 0.1 结论

**三区方向成立**：它同时提升表达清晰度（用户易读易加）与 AI 可解释性（计划可逐条回显、可逐条改判）。后端 `SearchPlanV3 { filter, should, must_not }` 与三区 1:1，不需要改名、不需要改结构。

**但三区不会自动提升 AI 的语义正确率**——它提升的是可控性。所以必须保留：AI 解析结果预览、evidence 解释、用户把条件从「优先」改回「必须」的能力、以及每次执行都显示被忽略/降级/剔除的条件。

**开工前提**：① 先按 §0.4 重置软件；② 再冻结执行契约（§4）。跳过 ② 会在三处引入正确性问题（warning 语义反转、全选与列表不同源、诊断分母错集）。

### 0.3 顺序硬约束

1. **重置在一切之前** —— 见 §0.4。不重置就得写迁移，那是被明确取消的范围。
2. **Phase 1 在 Phase 2 之前** —— 契约不冻结就接线，等于把 §2 的 B1/B2/B3 直接做进产品。
3. **Phase 2 在 Phase 3 之前** —— 否则出现「三个框只有两个生效」，正是现在这版的病。
4. **Phase 4 在 Phase 6/7 之前** —— 数值分面复用 domain 驱动的输入控件，否则数值输入要写两遍。
5. **Phase 0 的 A4 设置修复最先做** —— 设置被整份覆写会让后续所有 AI 验收结果不可信。
6. **Phase 7 必须等 Phase 6 的红测试全部通过** —— 协议未冻结不进实现。

### 0.4 开工前置：软件重置（**仅限测试环境**）

> **⚠ 适用范围声明（v3.1 补）**
>
> 本节的「清空素材 / 标签 / 批次」**只适用于测试环境**。当前场景已确认：这台机器上的库就是开发测试库（410 张样片 + 19 个标签），不是生产数据。
>
> | 环境 | 做法 |
> |---|---|
> | **测试环境（本轮适用）** | 按下表直接重置。更稳一点的做法：先把 `%APPDATA%/bagertea_ai_media_v2/library.db` 复制一份留底，再重置原库 |
> | **真实用户库** | **不允许用重置代替迁移。** 要么保留旧数据迁移方案（v2 的 `normalization_version` 1→2 + `expr`→`plan` 摄入转换），要么本版本明确只支持「新建数据库」并在发布说明里写清 |
>
> 验收文档里凡出现「真库」二字，本轮一律指**这台机器上的测试库**，不是生产库。

范围决策：**测试环境不做任何旧数据迁移。** 开工前把库清空，只保留 AI 配置与在线接口。

现成设施已存在：设置页「数据与缓存 → 重置数据」→ `reset_app_data` 命令 → `db/reset.rs`，分类勾选、单事务、缓存文件事务提交后删。

| `ResetSelection` 字段 | 勾选 | 清掉什么 |
|---|---|---|
| `assets` | ✅ **勾** | `assets` + `export_tasks` + `video_proxies`，FK 级联 `asset_tags`/`ai_suggestions`，触发器同步清 `fts_content` + `assets_fts` |
| `tags` | ✅ **勾** | `tags` + `tag_facets` + `tag_ops`。**会自动 `seed_system_facets` 重建系统分面并把 `color` 置 inactive** —— 这一步不可省，否则 AI 提示词没有分面上下文，模型输出会全部归到 `custom`（`reset.rs:69-82` 记着这次线上事故） |
| `aiTasks` | ✅ **勾** | `ai_batches` / `ai_suggestions` / `ai_suggestion_items` |
| `aiConnections` | ❌ **不勾** | （不勾 = 保留 `ai_connections` + `ai_usage_bindings` + 系统凭据里的 API Key） |
| `preferences` | ❌ **不勾** | （不勾 = 保留 `settings` 表，**`settings.ai.profiles` / `activeProfile` 就在里面**） |
| `caches` | ✅ **勾** | `thumbnails/` `previews/` `proxies/` 目录 + 回写 `placeholder_path`/`hd_thumbnail_path` 为 NULL |

**三条必须知道的事：**

1. **原始照片文件不会被删。** `reset.rs:2` 的原则是「绝不触碰素材原文件」——它只清库记录与派生缓存。要真的删掉硬盘上的照片，得自己在资源管理器里删，或者重置后不再导入那个目录。
2. **`localStorage` 不在数据库里，重置清不掉。** 客户端只有两个持久化键：
   - `super-search-conditions`（`superSearchStore.ts:365`）—— **存着旧 `expr`，里面就是 epoch 格式的日期**。不清它，日期 P0 修完后这条陈旧条件仍会 hydrate 出来并报错。
   - `qb:recent-fields`（`QueryBuilder.tsx:58`）—— 无害，可留可清。

   → **Phase 0 要加一步：重置时同步清 `super-search-conditions`。** 建议做进 `reset_app_data` 的前端调用方（重置成功后 `localStorage.removeItem`），而不是让用户手动开 DevTools。
3. **API Key 在系统凭据里，不在库里。** `ai_connections.api_key_ref` 指向 keyring（`services/credentials.rs`）。不勾 `aiConnections` 就不会调 `delete_api_key`，密钥安全。

**验收**：重置后 `SELECT COUNT(*) FROM assets` = 0、`FROM tags` = 0、`FROM ai_batches` = 0；`FROM tag_facets` = 10（系统分面已重建，`color` 为 inactive）；`FROM ai_connections` > 0（保留）；设置页 AI 配置仍在且能连通。

### 1.5 启用约束前必须先修的两个潜伏 bug

`tag_unique_terms` 从 0 翻到 1 的那一刻：

1. **新别名永远进不了 FTS** —— FTS 触发器词源是 `tags.name UNION tag_aliases.alias`（`migrations.rs:1211-1220`），而 gate 开后 `add_alias` 只写 `tag_terms`（`tags.rs:501`）。合并保留的旧词同理。`deactivated_facet_tags_still_searchable` 之所以绿，是因为跑在 gate 关的状态下。
2. **`Tag.aliases` 恒空** —— `tags::aliases()`（`tags.rs:594`）只读 `tag_aliases`。

正解不是双写（铁律 9），而是让这两处也走同一个 gate 读 `tag_terms`。真库 `tag_aliases` 现有 0 行、19 个标签，现在修最便宜。

| `query_expr.rs:388` | `compile_metadata` 返回 `None` | `1=1` |
| `query_expr.rs:332` | `term_query` 明确但零命中 | `1=0` |

在 `filter` 里 `1=1` 的语义是「忽略这条」，是对的。但一旦同一套编译器被用在另外两个位置：

| 位置 | 折叠成 `1=1` | 折叠成 `1=0` |
|---|---|---|
| **`must_not`** | `NOT (1=1)` → **全库被排除，结果恒 0** | `NOT (1=0)` → **排除条件静默消失** |
| **`should`** | `CASE WHEN (1=1) THEN 1 ELSE 0` → **每张素材都加分**，score 失去意义；配合 `minimum_should_match ≥ 1` 还会让全库通过 | 该项恒不命中（无害） |
| **`minimum_should_match`** | 分子被污染 → 结果集异常收缩或膨胀 | — |

**v1 只写了「把 `compile_expr` 换成 `compile_expr_with`」——那只解决 warning 可见性，不解决语义。** 必须在 AST 层做**上下文相关的结构性删除**，见 [§4.2](#42-warning-的上下文相关剔除规则)。

#### B2 · 换源后全选 / 反选 / 批量操作会和结果列表不同源

列表将走 plan，但全选链路仍走 `expr`：

```
superSearchStore.ts:354  fetchAllIds() → listSuperAssetIds(query, expr)
src/api/superSearch.ts:45 listSuperAssetIds → listAssetIds(queryToFilter(…, expr))
```

v1 只规划了 `list_assets_by_plan`，**没有 `list_asset_ids_by_plan`，也没说 `fetchAllIds` 怎么改**。

后果：界面显示的是三区筛选后的结果，但 Ctrl+A / 反选 / 批量打标 / 导出 / 删除会按旧 `expr` 选中**另一批素材**。**这是用户数据操作风险，优先级与列表执行同级。**

同源清单（缺一不可）：列表页、总数、全选 ID、分页 offset、排序、warning。

#### B3 · 加分项诊断的分子与分母不在同一结果集

`search_plan.rs:534-541`：

```rust
let mut solo = SearchPlanV3::default();
solo.filter = Some(QueryExpr::Leaf { cond: sc.cond.clone() });   // ← 只有这条叶子
let hit = count_plan(conn, &solo)?;                              // ← 全库命中数
should_diag.push(ShouldDiagnostic { hit_count: hit, total_count: result_count });
                                                  // ↑ 分母却是当前 plan 的结果数
```

于是会出现 **「命中 500 / 106」**。用户要的是「当前结果集里有多少张命中了这个加分项」，即 `current_plan_result ∩ should_condition`。

正解：`solo.filter = AND(plan.filter, leaf)`，同时带上 `plan.must_not`，`should` 置空、`minimum_should_match = 0`。

#### B4 · `validate_search_plan` 校验不完整

`search_plan.rs:180-202` 现在只查四项：`should.len() ≤ 12`、`should` 空但 `min > 0`、`filter`/`must_not` 走 `validate_expr`、`Ranking::Field.key ∈ ALL_SORT_KEYS`。

**缺**：

| 缺的校验 | 现在的后果 |
|---|---|
| `weight ∈ {0.5, 1.0, 2.0}` | 任意浮点（含 NaN / 负数 / 1e9）直接进 `fmt_weight` 拼进 SQL 算式 |
| `minimum_should_match ≤ should.len()` | 可要求「至少满足 5 项」但只有 2 项 → 结果恒 0，无任何提示 |
| `Ranking::Field.dir ∈ {asc, desc}` | `compile_search_plan:298` 对非 `asc` 一律当 `DESC` → 拼错方向静默生效 |
| retriever `weight` 有效性 | RRF 权重可为 0 / 负数 / NaN |
| 三个版本号 | `planSchemaVersion: 99` 照常执行（`migrate_plan` 对 `v > current` 直接 no-op，`diagnose_search_plan_cmd` 也不调它） |

**不能只依赖 UI 下拉** —— persist 的 localStorage、直接 IPC 调用、旧版本数据都能绕过 UI。

#### B5 · 日期从 epoch 改 ISO —— **v3：迁移部分已由重置消解，只留 UI 修复**

方向是对的（后端 `compile_date` 本来就按 `YYYY-MM-DD` 字符串编译，见 P0）。v2 担心的是旧数据：

- `QueryBuilder.tsx:831 dateToEpoch` 产出数字
- `utils/dateShortcuts.ts` 的 `shortcutStartMs`/`shortcutEndMs` 也是数字
- `superSearchStore` 的 `partialize` 持久化了整棵 `expr`（`:367-372`）

**v3 裁决**：不写迁移。§0.4 的重置会清库，`super-search-conditions` 这个 localStorage 键也在 Phase 0 一并清掉。所以：

| v2 计划的工作 | v3 处置 |
|---|---|
| P0 的 UI 修复（`DateValue` / `dateToEpoch` / 两个 shortcut 改 ISO 字符串） | ✅ **保留**，Phase 0-2 |
| `normalization_version` 1→2 的日期数据迁移函数 | ❌ **取消**，`NORMALIZATION_VERSION` 保持 1 |

#### B6 · 「只有优先满足、没有必须满足」时 `minimum_should_match=0` 语义自相矛盾

UI 允许「至少满足 0 项」并声明「不满足也保留」，但 `search_plan.rs:229-233` 在 `filter` 为空且 `should` 非空时**强制 `.max(1)`**。用户想「全库展示、只按偏好排序」时，完全不命中的素材会被丢掉。

两条出路，必须选一条并让 UI 与后端说同一句话：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 允许真正的「全库软排序」：`filter` 为空 + `should` 非空 + `min=0` 时不强制，改为在 UI 明示「将显示全部 N 张，仅调整顺序」 | 需确认 30k 素材上 `CASE WHEN` 全表扫的耗时（走 R2-5 探针） |
| B | 明确禁止：`filter` 为空时「至少满足」下拉最小值锁 1，并在 UI 说明「优先满足需要至少一条必须条件，或至少命中 1 项」 | 表达力受限，但零性能风险 |

#### B7 · 执行层 warning 不能复用现有的 AI warnings 字段

`superSearchStore.warnings`（`:110`）现在**只喂 AI 解析警告**，来源单一：`applyAiSearch` 写入（`:258`）、`setAiInput` / `clearAiResult` / `setQuery` / `setExpr` 清空（`:179` `:195` `:215` `:220`）。

如果把执行层 warning 也塞进同一个数组，三处会互相覆盖：

| 场景 | 后果 |
|---|---|
| 刷新列表（`refresh`） | 执行 warning 写入 → 但 `setExpr` 已经把数组清空过，AI 的解释性 warning 丢了 |
| 重新输入 AI 文本（`setAiInput`） | 清空数组 → 上一次执行的「优先条件『蓝天』已忽略」也被清掉，用户以为问题消失了 |
| 清除 AI 结果（`clearAiResult`） | 同上 |

**修法：拆成两条通道，并给 warning 加来源与区标识。**

```ts
export type PlanWarningSource = "ai" | "plan";
export interface SearchWarning {
  source: PlanWarningSource;
  zone?: "filter" | "should" | "mustNot";   // source="plan" 时尽量给出
  message: string;
}

// store
aiWarnings: SearchWarning[];        // 生命周期跟 AI 解析（原 warnings 改名）
executionWarnings: SearchWarning[]; // 生命周期跟每次 refresh：请求开始清空，响应写入
```

渲染时两条通道合并显示在同一条黄字栏里，但按来源分组，且 `source="plan"` 的带区名前缀（「优先满足：…」）。**两者永不互相清空。**

#### B8 · `list_asset_ids_by_plan` 的返回协议不完整

v2 要求它「超 100000 记 warning」，但现有全选 API 是纯 `number[]`（`api/superSearch.ts:45` → `listAssetIds`），warning 无处可去。

**必须明确改成结构体：**

```ts
// 后端命令返回（Rust: PlanIdsResult）
export interface PlanIdsResult {
  ids: number[];
  total: number;           // 匹配总数（未截断前）
  truncated: boolean;      // 是否触到 100000 上限
  warnings: SearchWarning[];
}
// store 对外的类型 —— 与上面同形，不再伪装成 number[]
export type FetchAllIdsResult = PlanIdsResult;
```

**`fetchAllIds` 的返回类型必须是 `FetchAllIdsResult`，不能对外伪装成 `number[]`**（v3.1 曾在三处写成三种形态，已统一）。理由：一旦 store 只返回 `ids`，`warnings` 与 `truncated` 就在那一层丢掉了，§4.6 的策略表无从落地。消费方是 `AssetGridView`（决定菜单禁用与二次确认）与 `selectionStore`（记 `truncated` 供工具栏显示 `已选 N / total`）。

同理 `list_assets_by_plan` 返回的 `AssetPage.warnings` 也升级成 `SearchWarning[]` 而不是 `Vec<String>`——**后端 `prune_invalid` 本来就知道自己删的是哪个区**，把这个信息丢掉再让前端猜是浪费。

#### B9 · 优先条件与用户手动排序的语义冲突

文案说「满足越多越靠前」，但一旦用户把排序切成「拍摄时间」或「评分」：

`compile_search_plan:291-300` 的 `Ranking::Field { key, dir }` 分支只产出 `ORDER BY sortv {dir}, id DESC` —— `score` 虽然在中层算出来了，**但完全不进 ORDER BY**。而 `run_search_plan:337` 只在 `Ranking::Relevance` 且 retrievers 非空时才走融合。结果：**字段排序下优先条件对顺序零影响**，只通过 `hits >= min_should` 起过滤作用。

三种候选规则：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 字段排序为**主键**，`score DESC` 作**次级**：`ORDER BY sortv {dir}, score DESC, id DESC`；同时优先区标题旁显示「当前按拍摄时间排序，优先条件仅用于同值时的先后」 | 用户的显式指令仍然优先（不违反不变量 11），偏好不被静默丢弃，且尾缀仍是 `id DESC` → 分页稳定性（不变量 28）不变 |
| B | 只在 UI 提示「优先条件暂不参与排序」，后端不动 | 诚实但白丢了信息 |
| C | 只要有优先条件就强制 `Relevance` | ❌ **否决** —— 覆盖用户显式选择，违反不变量 11「系统不改写用户明确表达的语义」 |

**必须加验收测试**，不能留在实现者的理解里：

```
field_ranking_uses_should_score_as_tiebreak   同 taken_at 的两张，命中优先项的排前面
field_ranking_primary_key_wins_over_score     不同 taken_at 时，字段顺序不被 score 打乱
relevance_ranking_unaffected_by_this_change   Relevance 路径回归
```

#### B10 · `Ranking::Relevance` 的 retrievers 是双源

```rust

SearchPlanV3.retrievers: RetrieverPlan             // :143 —— run_search_plan 只读这个
```

#### B11 · 排除条件双重否定 ★★ **本轮唯一的正确性 P0**（v4 新增）

`ExcludeTag` 自己编译成 `NOT EXISTS(...)`（`query_expr.rs:366-378`），而 `plan.must_not` 又统一包一层 `NOT (...)`（`search_plan.rs:247-252`）。结果：

```
单条：NOT( NOT EXISTS(夜景) ) = EXISTS(夜景)  → 【只显示夜景】，与意图完全相反
多条：NOT( NOT EXISTS(A) OR NOT EXISTS(B) ) = EXISTS(A) AND EXISTS(B)
      → 【必须同时命中两个被排除的标签】
```

裁决与完整极性白名单见 **[§4.1b](#41b-must_not-的极性契约p0排除条件双重否定)**。一句话：**`must_not` 只放正向条件，`ExcludeTag` / `QueryExpr::Not` 禁止进入**，与 AI 侧 `build_plan_from_v3` 现有语义合流。Phase 1 新增 4 条红测试，Phase 2-0b 最先做。

#### B12 · AI「追加模式」在换源后没有定义（v4 新增）

`applyAiSearch` 的 append 分支现在合并 `expr` 然后**把 `plan` 置 `null`**（`superSearchStore.ts:243-249`）。plan 成为唯一事实源后这条路径直接失效 —— 「把 AI 条件追加到当前三区」无从执行。

逐字段合并规则见 **[§4.8](#48-ai追加模式的-plan-合并规则p1v4-补)**。要点：`filter` AND 合并保留内部 OR、`mustNot` OR 合并、`should` 拼接去重限 12、`minimumShouldMatch` 不改用户已设值、`ranking` append 恒不动。附带发现：`ShouldClause` 缺 `evidence` 字段，原文被 `build_plan_from_v3:970` 拼进 `label` 后丢失，§3.5 要求的「evidence 原文回显」目前无法实现。

### P0 · 手工日期条件根本无法编译

**现象**：条件构建器里手工加「拍摄时间 / 入库时间 / 修改时间」，后端报错，不是筛选。

| 侧 | 产出 / 期望 | 位置 |

## §3 前端设计

### 3.1 整体结构：自然语言入口 + 三区条件编辑器

后端字段一律不改名，前端只负责把它们显示成用户能理解的三个区域。

```
┌────────────────────────────────────────────────────────────┐
│ 🔍 跟人有关，最好是户外，排除夜景                    [搜索] │
│    AI 已理解 · 部分理解 · 按关键词搜索（三态，现有实现）      │
└────────────────────────────────────────────────────────────┘

必须满足 · 全部满足才显示                        结果 106 张
┌────────────────────────────────────────────────────────────┐
│ [标签 ▾] [人物]                            − 12    ⋯   × │
│ ＋ 添加条件                                                │
└────────────────────────────────────────────────────────────┘

优先满足 · 满足越多越靠前                        命中 12/106
┌────────────────────────────────────────────────────────────┐
│ [标签 ▾] [户外]        [一般偏好 ▾]        + 8/106  ⋯   × │
│ ＋ 添加优先条件                              〔高级设置〕  │
└────────────────────────────────────────────────────────────┘

排除 · 命中任一条就不显示                        排除了 4 张
┌────────────────────────────────────────────────────────────┐
│ [标签 ▾] [夜景]                            − 4     ⋯   × │
│ ＋ 添加排除条件                                            │
└────────────────────────────────────────────────────────────┘
```

映射：

```
必须满足 → plan.filter
优先满足 → plan.should（+ minimum_should_match）
排除     → plan.mustNot
```

用户永远看不到 `must` / `should` / `must_not` 这三个词。

### 3.2 命名与文案（终版）

```
必须满足 · 全部满足才显示
优先满足 · 满足越多越靠前
排除     · 命中任一条就不显示
```

三条被否决的备选，记录理由以免反复：

| 备选 | 为什么不用 |
|---|---|
| 必须写 / 非 | 「必须写」会被理解成「这个框必须填」，而不是「结果必须满足」 |
| 一定要有 / 最好有 / 不要有 | 只适合标签；「文件大小 ≥ 5MB 一定要有」「拍摄时间介于某日期不要有」读不通 |
| 必须条件 / 加分条件 / 排除条件 | 「加分条件」偏系统视角；「优先满足」直接说了用户想要的行为 |

### 3.3 条件行语法（三区共用）

每一行固定是：

```
[字段 ▾] [运算符 ▾] [值]                              [⋯] [×]
```

实例：

```
[文件大小 ▾] [介于 ▾] [5] 至 [10] [MB ▾]             ⋯  ×
[拍摄时间 ▾] [晚于 ▾] [2026-07-01]                   ⋯  ×
[标签 ▾]     [是 ▾]   〔人物 ×〕〔女孩 ×〕 ＋         ⋯  ×
```

| 元素 | 规则 |
|---|---|
| 字段选择器 | 可搜索 combobox（复用现有 `FieldSelect`，172 行原样可用），按「标签 / 时间 / 文件 / 图像 / 视频 / 位置 / 颜色」分组，最近使用 5 个置顶 |
| 运算符 | **按字段类型自动限制**，事实源是后端 `allowed_ops`（经 `NumericDomain` 下发，见 §5.3）。绝不出现「文件夹 大于」这种组合 |
| 数值值 | 显示单位、值域、常用预设（`[5]–[10] [MB ▾]`、`f/[2.8]`、`16:9` chip）。`between` 两侧**共用一个单位** |
| 标签值 | 可删除 chip + 搜索面板勾选，**不用逗号文本框** |
| `[⋯]` 更多 | 匹配方式（精确 / 别名 / 前缀 / 包含 / 纠错，默认别名）、包含子标签开关、复制此条到其他区 |
| `[×]` 删除 | **只保留这一个否定/移除入口**。不再有行内「是/不是」下拉 |

匹配方式放进 `[⋯]` 而不是行内：它是低频高级项，放行内会与「运算符」抢注意力，而且三区都需要它，行内空间不够。

### 3.4 三区各自的行为

#### 必须满足

```
必须满足以下 [全部 ▾] 条件        ← 默认「全部」，可切「任一」
```

**只允许一层条件组**：

```
必须有：
  人物
并且满足任一：
  室内
  户外
```

第一版不让用户自由组合无限层级的 AND / OR / NOT。业界经验支持这个取舍——[ux.stackexchange 的结论](https://ux.stackexchange.com/questions/68115/ui-for-and-or-and-not-query-combinations)是「我们最后决定不让用户混合条件，因为 UI 对他们太复杂了」。后端支持 5 层，但摄影师的真实需求是「A 且 B 且 (C 或 D)」。

遇到超过一层的树（AI 产出或旧数据）→ 保留现有的**可展开只读树形视图**（U-4 已实现），并允许「以 AND 追加新条件」。

#### 优先满足

```
优先满足：
[标签 ▾] [蓝天]     [一般偏好 ▾]        + 12/106     ⋯  ×
```

权重**只给三档**，不暴露浮点：

| UI 文案 | 后端 weight |
|---|---|
| 轻微偏好 | 0.5 |
| 一般偏好 | 1.0 |
| 强烈偏好 | 2.0 |

**「至少满足 N 项」移入〔高级设置〕折叠区**，不放标题行。理由：很多用户会把它误解成「满足几项就加多少分」，而它实际是「不满足 N 项就不显示」——一个会**缩小结果集**的开关放在「不满足也保留」的标题旁边，是自相矛盾的信号。折叠区内的文案要写全：

```
至少满足 [0 ▾] 项才显示
  0 = 不限（全部保留，只调整顺序）
  N = 至少命中 N 条优先条件的素材才会出现
```

并按 [B6](#b6--只有优先满足没有必须满足时-minimum_should_match0-语义自相矛盾) 的裁决处理「没有必须条件」的情形。

#### 排除

```
排除：
[标签 ▾]     [夜景]                     − 4      ⋯  ×
[文件类型 ▾] [视频]                     − 28     ⋯  ×
```

默认就是**命中任一条即排除**（对应 `mustNot = OR(rows)`，与 `build_plan_from_v3` 语义一致）。区内不提供行内「不是」下拉——否则用户同时看到「排除区」和「不是」，两种表达重复且能造出双重否定。

**排除区支持的条件类型与必须区完全一致**（标签 / 元数据 / 关键词 / 分面有无 / 素材类型 / 颜色），因为编译走的是同一套 `LeafCond`。唯一差别是不支持嵌套组（排除天然是 OR 平铺）。

### 3.5 AI 与手工共用同一套界面

AI 解析后**不只显示一句解释**，而是把结果直接填进三区：

```
AI 已识别（可直接修改）：
  必须满足    人物
  优先满足    户外          「最好是户外」   ← evidence 原文回显
  排除        夜景
```

用户可以直接：改字段、改运算符和值、**把条件在三区之间移动**（`[⋯]` → 移到「优先满足」/「必须满足」/「排除」）、删除。

这比「AI 返回一堆 chips、用户再重新手工输入」可靠得多，也是三区真正的价值所在——**AI 的判断变成可逐条改判的草稿，而不是一次性的黑盒结果**。

必须保留的四条护栏（指导书不变量 11 / §16）：

1. AI 解析结果预览 + `evidence` 原文回显（`guard_preferred` 已产出，UI 要显示）
2. 用户可把条件从「优先满足」提升为「必须满足」，**反向降级只能由用户操作**
3. AI 不得偷偷弱化用户明确写出的硬条件（`guard_preferred` 只做 preferred→required 降级，不做反向升级）
4. 每次执行都显示被忽略 / 降级 / 剔除的条件（[§4.2](#42-warning-的上下文相关剔除规则) 的 warning 通道）

### 3.6 每区的结果反馈

```
必须满足    结果 106 张
优先满足    命中 12/106
排除        排除了 4 张
```

单条归零时标红：

```
[前三色包含红 ▾] [包含 ▾] [🟥红]         − 106  ⚠   ⋯  ×
  ⚠ 这个条件把结果砍到 0（它单独命中 0 张）
```

三条硬要求：

- 加分项的命中数必须是**当前结果集内的交集**（修 [B3](#b3--加分项诊断的分子与分母不在同一结果集)），不能是全库命中数
- 排除项不能重复计算（修 [§4.1](#41-单一事实源) 的排除双算）
- 无效条件在 `must_not` / `should` 中不能简单折叠成 `1=1`（修 [B1](#b1--warning-的剔除语义在三区中会反转)）

**统计必须与结果列表共用同一套执行逻辑** —— 即诊断命令内部调用的编译器与列表命令完全一致，不允许出现「诊断用一套、列表用另一套」。

### 3.7 状态协议（v1 缺失，必须先定）

这是三区从「UI 改动」变成「需要新契约」的部分。

#### 单一事实源

```
plan.filter   ←→  必须满足区
plan.should   ←→  优先满足区（+ minimumShouldMatch）
plan.mustNot  ←→  排除区
plan.ranking  ←→  排序 chip
```

`expr` **降级为 `plan.filter` 的派生只读视图**，仅供旧代码路径（`FilterChips` 扁平渲染、`syncQueryFromExpr`）过渡使用，**不再是第二事实源**。AI 返回的 `expr` 在摄入时即丢弃（改用 `plan`），只保留 `plan`。

#### store API（对称三组，v1 只有 `setPlanShould`）

| 现有 | 需要新增 |
|---|---|
| `setPlanShould(should, min)` | `setPlanFilter(expr \| undefined)` |
| `removePlanShould(index)` | `setPlanMustNot(expr \| undefined)` |
| `setExpr`（保留但内部改写 `plan.filter`） | `removePlanFilterAt(path)` / `removePlanMustNotAt(path)` |
| — | `moveConditionBetweenZones(from, to, path)` |
| — | `clearZone('filter' \| 'should' \| 'mustNot')` |

#### 九条不变式

1. **手工改必须区不清空 AI 的优先项。** `setPlanFilter` 只动 `plan.filter`，`should` / `mustNot` 原样保留。（现状 `setQuery` / `replaceQuery` 会 `plan: null`，必须改。）
2. **排除条件只存在于 `plan.mustNot`。** AI 摄入时把 exclusions 从 `expr` 里剥掉（复用 `without_tag_leaves` 的同类逻辑），否则执行 plan 会双算。
3. **清空某一区 ≠ 清空 plan。** 三区全空时 `plan` 才置 `null`。
4. **`minimumShouldMatch` 随 `should` 长度自动收敛**：`min = clamp(min, 0, should.len())`，`should` 清空时 `min = 0`。
5. **持久化只存 `plan` + `query.sortBy/sortDir`**，不再存 `expr`。hydrate 时按三个版本号处理，未来版本丢弃 + 提示（见 §4.4）。
6. **`FilterChips` 的删除路径必须带区标识**：`{ zone: 'filter'|'should'|'mustNot', path: number[] | index }`。现在的 `removeExprAtPath(path)` 无法区分区，必须扩签名。
7. **两条 warning 通道互不清空**（B7）：`aiWarnings` 的生命周期跟 AI 解析，`executionWarnings` 的生命周期跟每次 `refresh`（请求开始清空、响应写入）。渲染时合并显示、按来源分组、`source="plan"` 带区名前缀。
8. **排序与优先条件的关系是「主次」不是「二选一」**（B9）：`plan.ranking` 是 `Field` 时字段为主键、`score DESC` 为次级；优先区标题旁显示「当前按 X 排序，优先条件仅用于同值时的先后」。绝不因为存在优先条件就替换用户选的排序字段。
9. **诊断结果必须自带区标识与代次**（v3.1 补）。现状 `LeafDiagnostic` 只有 `path: number[]`（`types/superSearch.ts:112`），而「必须区第 0 条」和「排除区第 0 条」的 `path` 都是 `[0]` —— 仅凭路径无法知道该删哪一条。`ShouldDiagnostic` 更是只有 `label`，连索引都没有：

```ts
export interface LeafDiagnostic {
  zone: "filter" | "mustNot";     // 【新】
  path: number[];
  planRevision: number;           // 【新】发起诊断时的 plan 代次
  label: string;
  selfCount: number; resultCount: number; countWithoutLeaf: number; delta: number;
}
export interface ShouldDiagnostic {
  index: number;                  // 【新】对应 plan.should 的下标
  planRevision: number;           // 【新】
  label: string; hitCount: number; totalCount: number;
}
```

`planRevision` 是 store 里的单调计数器，每次 plan 变更 +1。诊断是异步的（`diagnoseSearchPlan` 在 `useEffect` 里发起），**返回时若 `planRevision !== 当前值就整批丢弃** —— 否则旧诊断会指着新条件的位置，点「移除」删错东西。现有代码只用 `alive` 标志防竞态（`QueryBuilder.tsx:204-209`），那只能防「组件卸载」，防不了「plan 已经变了但组件还在」。

**受影响的两处归零操作都要改**，v3 只写了 `FilterChips`：

| 位置 | 现状 | 改成 |
|---|---|---|
| `SuperSearchPage.tsx:236` | `onRemove: () => removeExprAtPath(z.path)` | `removeAtZonePath(z.zone, z.path)`，并在 `planRevision` 过期时不渲染该按钮 |
| `FilterChips.tsx:96` | `removeExprAtPath(m.path)` | 同上，chip 模型带 zone |
| `QueryBuilder.tsx:300 rowDiagFor` | 按 `path.length` 匹配 | 先按 `zone` 过滤再匹配 path |

### 3.9 「三区常驻」与现有折叠头部的关系（v3.1 补）

冲突是真的：`SuperSearchPage.tsx:205-219` 用 `grid-template-rows: 0fr↔1fr` 折叠整个 `QueryBuilder`，折叠时还加 `pointerEvents: "none"`（`:213`）。滚动结果区会自动折叠（`useScrollDirection`，非对称阈值 24/12）。所以「三区常驻」指的是**展开态下三个区都在**，不是「永不折叠」。

折叠态必须保留的四样（放进摘要条，即现在 `FilterChips` 那一行）：

| 保留项 | 形态 | 理由 |
|---|---|---|
| **三区摘要 + 条数** | `必须 3 · 优先 2 · 排除 1` 三个小徽标，点任一个展开并滚到对应区 | 用户滚着看结果时至少知道「现在生效的是什么形状」 |
| **warning** | 黄字栏**不随折叠隐藏**（`executionWarnings` + `aiWarnings` 都算） | 「有 3 个条件被忽略」是必须一直可见的，否则用户会把「结果不对」归因错 |
| **当前排序说明** | `按拍摄时间 ↓（优先条件仅决定同值先后）` | B9 的说明文字如果只在展开态出现，等于没说 |
| **快速添加** | 一个 `＋` 按钮，点开直接展开并聚焦到「必须满足」区的新行 | 现有折叠态完全不能加条件（`pointerEvents: none`），这是「方便添加」的直接对立面 |

折叠态**不保留**：条件行本身、字段/运算符下拉、诊断数字（那些需要空间，且展开一次即可）。

实现上只改 `SuperSearchPage` 的 header 区结构（摘要条本来就在滚动容器外、恒可见），`QueryBuilder` 本体不动 —— 现有 FB2-06「折叠只改 header 高度、不改滚动容器 scrollHeight」的架构决定要保住，那是当年闪烁 bug 的根因修复。

## §4 执行契约（必须先冻结）

**这一章是 Phase 1 的交付物**：先写成契约 + 红测试，再动实现。v1 缺这一章，是它「不能直接开工」的主因。

### 4.1 单一事实源

一次搜索的下列六项，必须由**同一个 `SearchPlanV3` 经同一套编译器**产出：

| 项 | 命令 | 返回 | 现状 |
|---|---|---|---|
| 结果列表（分页） | `list_assets_by_plan(plan, offset, limit)` | `AssetPage { items, total, hasMore, warnings }` | **待建** |
| 总数 | 同上的 `total`（`count_plan` 改 `pub`） | — | **待建** |
| **全选 / 反选 ID** | `list_asset_ids_by_plan(plan)` | **`PlanIdsResult { ids, total, truncated, warnings }`** | **待建（B2 + B8）** |
| 排序 | `plan.ranking` | — | 已有，未接 |
| warning | 两个命令都返回 `SearchWarning[]`（含 `source` / `zone`） | — | 后端有通道但类型是 `Vec<String>`，plan 路径未用 |
| 逐条件诊断 | `diagnose_search_plan_cmd(plan)` | `(LeafDiagnostic[], ShouldDiagnostic[])` | 已有，但分母错集（B3） |

补充约定：

- **warning 类型统一为 `SearchWarning { source, zone?, message }`**（B7/B8）。`prune_invalid` 本来就知道自己删的是哪个区，把这个信息丢成裸字符串再让前端猜是浪费。`AssetPage.warnings` 的类型一并从 `Vec<String>` 升级。
- **全选返回必须是结构体，一路到底不降级**（B8）：`PlanIdsResult { ids, total, truncated, warnings }`，上限沿用 `list_ids` 的 100000（`assets.rs:663`）。`fetchAllIds` 的返回类型 **`FetchAllIdsResult` = `PlanIdsResult`**，不许中途退化成 `number[]`（否则 `warnings` 与 `truncated` 在 store 那层丢失）。`warnings` 并进 `executionWarnings`。
- 两个 plan 命令都必须先 `validate_search_plan` → 再 `prune_invalid`。**校验在剔除之前**：否则一个非法 `weight` 会先被剔除逻辑碰到，报错信息变得难懂。
- 排序在两条路上必须一致：`run_search_plan` 已把 `ORDER BY` 内置在 SQL 里，ID 版**必须复用 `compile_search_plan`** 而不是自己拼。
- `Ranking::Relevance` 走 `run_relevance_fused` 时是**内存 RRF + 分页**，ID 版必须走同一函数，否则全选顺序与列表不一致。
- `Ranking::Field` 的 `ORDER BY` 按 B9 的方案 A 改为 `sortv {dir}, score DESC, id DESC`（尾缀仍是唯一列 → 分页稳定性不变）。
- **`retrievers` 只有一个来源**：`SearchPlanV3.retrievers`。`Ranking::Relevance` 变成无载荷变体（B10）。

#### 4.1a `ResolvedSearchQuery → SearchPlanV3` 转换规则（v3.1 补：最大的契约缺口）

v3 只说「命令只收 plan」，没说现有那六个扁平条件字段怎么进 plan。它们今天由 `queryToFilter`（`api/superSearch.ts:8-34`）与 `expr` **并行**发给后端。新命令只收 plan，不定义转换就会**静默丢条件**。

好消息：转换函数**已经存在** —— `resolvedQueryToExpr`（`utils/queryExprUtils.ts:49-70`）已覆盖全部六个字段。坏消息：它把排除放进了 AND 里，也不管排序，而且现在只在 `applyAiSearch` 的 append 分支被调用过一次（`superSearchStore.ts:245`）。

**新增 `resolvedQueryToPlan(q: ResolvedSearchQuery): SearchPlanV3`**，逐字段规则：

| `ResolvedSearchQuery` 字段 | 去向 | 产出的 `LeafCond` | 备注 |
|---|---|---|---|
| `search` | `plan.filter` | `{ type: "search", value }` | 空串跳过 |
| `assetType` | `plan.filter` | `{ type: "assetType", value }` | `"all"` 跳过 |
| `untaggedOnly` | `plan.filter` | `{ type: "untagged" }` | `false` 跳过 |
| `facetFilters[]` | `plan.filter` | `{ type: "tag", facetKey, tagIds, mode, includeDescendants }` | **`mode: "any" \| "all"` 与 `includeDescendants` 必须原样带过去**；`tagIds` 空的项跳过 |
| **`excludeTagIds[]`** | **`plan.mustNot`** ← 与 `resolvedQueryToExpr` 不同 | **`{ type: "tag", facetKey: "", tagIds: [id], mode: "any", includeDescendants: true }`** ← **正向 Tag，不是 `excludeTag`** | 多个 id → `mustNot = OR(Tag a, Tag b, …)`。**必须是正向叶子，见 §4.1b 的 P0** |
| `metadataFilters[]` | `plan.filter` | `{ type: "metadata", filter }` | 原样 |
| `sortBy` / `sortDir` | `plan.ranking` | `Ranking::Field { key, dir }` | 有 `should` 时是否切 `Relevance` 由 B9 方案 A 决定（字段为主键 + score 次级） |

`plan.filter` 的组合方式：多个叶子 → `AND`，单个 → 直接是那个叶子，零个 → `None`（与 `resolvedQueryToExpr:68-69` 一致）。

**Phase 2 之后的终态**：超级搜索的 `ResolvedSearchQuery` 退化为**只剩 `sortBy` / `sortDir`** 两个字段作为 UI 状态；六个条件字段全部搬进 `plan`，`queryToFilter` 在超搜路径不再使用。

**范围限制（限制爆炸半径的关键）**：本轮**只有超级搜索页换 plan 执行链**。素材库页（`libraryStore` → `list_assets(AssetFilter)`）继续走扁平 `AssetFilter` 路径，一行不改。`list_assets` / `list_asset_ids` 两个旧命令保留。

**测试**：`resolved_query_to_plan_covers_all_flat_fields`（六个字段各造一个值，断言 plan 里逐个出现）/ `exclude_tag_ids_become_positive_tag_in_must_not`（断言 `mustNot` 里是 `tag` 不是 `excludeTag`，且不在 filter 里）/ `facet_filter_mode_and_descendants_survive`（`mode="all"` + `includeDescendants=false` 往返不丢）。

#### 4.1b `must_not` 的极性契约（**P0：排除条件双重否定**）

**这是 v3.1 里唯一的正确性 P0，必须在 Phase 2 之前修。**

两处代码叠加产生双重否定：

| 处 | 代码 | 产出 |
|---|---|---|
| `query_expr.rs:366-378` | `LeafCond::ExcludeTag` | `NOT EXISTS (SELECT 1 FROM asset_tags … )` —— **叶子自己已经是负向** |
| `search_plan.rs:247-252` | `plan.must_not` 分支 | `parts.push(format!("NOT ({})", …))` —— **计划层再包一层 NOT** |

后果（逐条推演）：

```
① 单条：must_not = ExcludeTag{夜景}
   → NOT ( NOT EXISTS(夜景) )
   = EXISTS(夜景)
   = 【只显示夜景】—— 与用户意图完全相反

② 多条：must_not = OR([ExcludeTag{A}, ExcludeTag{B}])
   → NOT ( NOT EXISTS(A) OR NOT EXISTS(B) )
   = EXISTS(A) AND EXISTS(B)
   = 【必须同时命中两个被排除的标签】—— 比 ① 更离谱
```

**裁决：采用方案一 —— `must_not` 里只放正向条件，由计划层统一负责那一层 `NOT`。**

理由：这正是 AI 侧现有的语义。`build_plan_from_v3`（`super_search_ai.rs:914-926`）对 `intent.exclusions` 压入的是 **`LeafCond::Tag`（正向）**，不是 `ExcludeTag`。所以 AI 路径本来就是对的，是 v3.1 的 §4.1a 转换规则写错了。方案一让手工路径与 AI 路径合流，零新语义。

**等价性可证**（所以转换是安全的，不是近似）：

```
ExcludeTag{tag_ids:[a,b]}                 ≡ NOT EXISTS(a) AND NOT EXISTS(b)
must_not = Or([Tag{a,desc}, Tag{b,desc}]) ≡ NOT( EXISTS(a) OR EXISTS(b) )
                                          ≡ NOT EXISTS(a) AND NOT EXISTS(b)   ← 德摩根
```
两侧都走同一个递归 CTE 取后代（`ExcludeTag` 在 `:372`，`Tag{include_descendants:true}` 在 `compile_tag_leaf`），所以后代语义也等价。

**极性白名单**（写进 `validate_search_plan`）：

| `LeafCond` | 编译形态 | 进 `must_not` |
|---|---|---|
| `Tag` / `AssetType` / `Metadata` / `Search` / `FacetHasAny` | 正向谓词 | ✅ **允许** |
| `Untagged` | `NOT EXISTS(任何标签)` | ✅ 允许 —— 它是**素材的一个特征**（「没有任何标签」），`NOT(特征)` = 「排除未打标的」，语义正确 |
| `FacetMissing` | `NOT EXISTS(该分面标签)` | ✅ 同上 —— 「排除某分面没标签的」 |
| **`ExcludeTag`** | `NOT EXISTS(…)` | ❌ **拒绝** —— 它不是特征，它本身就是「排除」这个**动作**。放进 `must_not` = 排除一个排除 |
| **`QueryExpr::Not`** | `NOT (…)` | ❌ **拒绝** —— 三重否定不可读，且 UI 不产生（已删「是/不是」下拉）。防 IPC / persist 手造 |

`ExcludeTag` 在 **`filter` 里仍然完全合法**（素材库路径与旧 expr 都还在用），只是不许进 `must_not`。

**Phase 1 必须新增的红测试（4 条）**：

```
must_not_single_exclusion_excludes_not_includes    must_not=Tag{夜景} → 结果里没有夜景（而不是只有夜景）
must_not_multiple_exclusions_are_or_semantics      must_not=Or([A,B]) → A 或 B 命中任一即被排除
validate_rejects_exclude_tag_in_must_not           ExcludeTag 进 must_not → Err
validate_rejects_not_node_in_must_not              QueryExpr::Not 进 must_not → Err
```

**受影响的另一处文档表述**：§3.4「排除区」的 `mustNot = OR(rows)` 成立，但 rows 编译出的**必须是正向叶子** —— 排除区的字段选择器**不提供「排除标签」这个字段**（它已在 §3.8 被删），用户选「标签」，语义由所在的区决定。这正是三区设计比「行内是/不是」更干净的地方：**否定只在区一级表达一次。**


### 4.2 warning 的上下文相关剔除规则

**核心原则：无效条件在 AST 层被结构性删除，不在 SQL 层折叠成常量。**

编译前先跑一遍 `prune_invalid(plan) -> (SearchPlanV3, Vec<SearchWarning>)`（**类型是 `SearchWarning` 不是 `String`**，与 §4.1 的 B7/B8 保持一致）：

| 位置 | 无效叶子的处置 | 理由 |
|---|---|---|
| `filter` | **删除该叶子**；父节点若因此变空则一并删除；整棵 `filter` 变空 → `filter = None` | 与今天 `1=1` 的语义等价，但不污染 SQL |
| `must_not` | **删除该排除项**；整棵变空 → `must_not = None` | 折叠成 `1=1` 会 `NOT(1=1)` 清空全库；折叠成 `1=0` 会让排除静默消失。两者都错 |
| `should` | **删除整条 `ShouldClause`**，并把 `minimum_should_match` 收敛到新长度 | 折叠成 `1=1` 会让每张素材都加分 |

每删一条产出一句用户可读的 warning（沿用现有文案，如「分面「X」已停用或不存在，已忽略该条件。」），并标注它在哪个区：

```
优先满足：「蓝天」已忽略 —— 该标签不存在（已从优先条件中移除）
```

`1=0` 保留但只在 `filter` / `should` 内合法（`term_query` 明确零命中 = 用户搜了个不存在的词，应当 0 结果）；在 `must_not` 里出现 `1=0` 必须转成「删除该排除项 + warning」。

**必测**（这三条 v1 完全没有）：

```
must_not_invalid_leaf_is_removed_not_negated     无效排除项 → 结果集不变，且有 warning
should_invalid_clause_is_removed_not_always_true 无效加分项 → 不影响任何素材的 score
min_should_converges_after_should_pruned         3 项 min=3，删 1 项后 min 自动变 2
prune_reports_zone_in_warning                    warning 文案带区名
```

### 4.5 诊断必须与列表走同一条「剔除后执行」链（v3.1 补）

现状：`diagnose_search_plan`（`search_plan.rs:515`）直接对**原始 plan** 反复调 `count_plan`，既不校验也不剔除。如果只按 v3 的 Phase 2-9 修交集，会出现「列表已经忽略了『蓝天』这条，但诊断还在给它统计命中数」的不一致。

**四条硬约束：**

1. **同一次 prune**：诊断命令入口先跑 `validate_search_plan(plan)?` → `let (plan, warnings) = prune_invalid(plan)`，**用剔除后的 plan 做全部诊断**。
2. **同一批 warning**：诊断的返回值也带 `warnings: Vec<SearchWarning>`，与列表命令返回的是同一批（同一个 `prune_invalid` 的产物）。前端可以只信一处，不必对两处结果做差集。
3. **被剔除的条件不再诊断**：它已经不在 plan 里了，自然不出现在 `LeafDiagnostic` / `ShouldDiagnostic` 列表中。UI 通过 warning 得知「这条被忽略了」，而不是通过一条 `selfCount=0` 的诊断（两者语义完全不同：一个是「条件无效」，一个是「条件有效但没匹配项」）。
4. **同一套编译器**：`count_plan` 内部已复用 `compile_search_plan`（`:550`），保持不变即可。不允许为诊断另写 SQL。

诊断命令签名随之变为：

```rust
pub fn diagnose_search_plan_cmd(plan: Option<SearchPlanV3>)
    -> AppResult<PlanDiagnostics>;

pub struct PlanDiagnostics {
    pub leaves: Vec<LeafDiagnostic>,     // 带 zone（见 §3.7）
    pub should: Vec<ShouldDiagnostic>,   // 带 index
    pub warnings: Vec<SearchWarning>,    // 与列表命令同批
}
```

### 4.6 全选截断与批量操作的安全策略（v3.1 补）

`PlanIdsResult.truncated` 光提示不够。现状是 `fetchAllIds()` 的结果**两处**被直接喂给 `setAll` / `invert`（`AssetGridView.tsx` 的 Ctrl+A/Ctrl+I 键盘分支与右键菜单的「全选」「反选」），随后删除 / 导出 / 批量打标都对这个集合执行。上限 100000 一旦触顶，「全选」实际是「选前十万项」。

**策略表（必须写进契约，不留给实现者理解）：**

### 4.8 AI「追加模式」的 plan 合并规则（P1，v4 补）

现状：`applyAiSearch` 的 append 分支合并的是 `expr`，然后**把 `plan` 直接置 `null`**（`superSearchStore.ts:243-249`）。换源后这条路径没有定义 —— 「把 AI 条件追加到当前三区」无从执行。

| 字段 | 合并规则 | 理由 |
|---|---|---|
| `filter` | **AND 合并，保留内部 OR**：复用 `mergeQueryExpr`（`queryExprUtils.ts:73-81`，它已经只拍平顶层 AND，不动内部 OR）。合并后按序列化形式**去重相同叶子** | 追加是收窄，AND 是唯一符合直觉的连接 |
| `mustNot` | **OR 合并**（`Or([old_children…, new_children…])`，同样去重） | 排除区的区内语义就是 OR「命中任一即排除」，追加排除项 = 往这个 OR 里加 |
| `should` | **拼接**（`[...old, ...new]`），按 `serialize(cond)` 去重；超过 `MAX_SHOULD_CLAUSES = 12` 时**按权重降序保留前 12 条**，丢弃的记 warning「加分项超过 12 条，已保留权重较高的 12 条」 | 加分项彼此独立，拼接无歧义；上限是后端硬约束（`search_plan.rs:148`） |
| `minimumShouldMatch` | `if old.should.is_empty() { new_min } else { old_min }`，最后 `clamp(0, merged.should.len())` | **追加不改用户已设的阈值**（不变量 11）。原本没有加分项时才采纳 AI 的建议值。AI 的 `min` 与保留值不同 → 记 info 级 warning |
| `ranking` | **append 恒保留用户当前的 `ranking`**；AI 建议了不同排序 → warning「AI 建议按拍摄时间排序，当前保持你选的排序（可在排序处切换）」。**replace 才采纳 AI 的 `ranking`** | 排序是用户的显式选择，追加条件不该改动它 |
| `retrievers` | append 时 `Or` 语义无意义 → **保留旧的**；replace 采纳新的 | RRF 的多路召回是整体策略，不是可叠加项 |
| 三个版本号 | 取**当前应用的常量值**（不是两侧的 max） | 合并产物是本版本新造的 plan |
| `aiWarnings` | **替换为本次解析的 warning + 合并产生的 warning**（不累积历史） | 它们描述的是「这一次解析」；累积会让用户看到早已解决的旧提示 |
| `executionWarnings` | 不参与合并（生命周期跟每次 `refresh`，见 §3.7 不变式 7） | — |
| `resolvedTags` | 按 `tagId` 合并去重（现有 `mergeResolvedTags` 已正确） | 名称映射是纯查找表，越全越好 |
| `evidence` | 随各自的 `ShouldClause` 走 —— **`ShouldClause` 需要新增 `evidence: Option<String>` 字段**。现在 `build_plan_from_v3:970` 只把它拼进 `label`（`"{text}（加分项）"`），原文丢了，§3.5 要求的「evidence 原文回显」无从实现 | 每条加分项的依据属于那条，不属于整个 plan |

**replace 与 append 的差别只有两处**：`ranking` 与 `retrievers`（replace 采纳 AI 的，append 保留用户的）。其余字段两种模式用同一套规则 —— replace 相当于「旧 plan 为空时的 append」。

`planRevision` 在合并成功后 +1（§3.7 不变式 9），使在途的旧诊断整批失效。

**测试（4 条，已计入 §4.7）**：`append_and_merges_filter_keeps_inner_or`（旧 filter 含 `Or([A,B])`，追加 C 后仍是 `And([Or([A,B]), C])` 而不是拍平）/ `append_or_merges_must_not` / `append_concats_should_and_caps_at_12`（造 8+7 条，断言留 12 条且是权重最高的 12 条 + 有 warning）/ `append_never_changes_user_ranking`（用户选了 `taken_at asc`，AI 返回 `Relevance`，断言 ranking 未变且有 warning）。

## §5 数值范围设计

### 5.1 哪些属性是数值范围（精确表）

事实源：`search_query.rs:118 key_spec` / `:180 allowed_ops` / `:203 value_expr`。`ValueKind` 只有 `String | Number | Date | Folder` 四个变体。

#### 数值型 15 个 —— 支持 `= 属于任一 > ≥ < ≤ 介于`

| key | SQL 表达式 | 存储 | 真实值域 | 现在 UI | 问题 |
|---|---|---|---|---|---|
| `file_size` | `a.file_size` | INTEGER 字节 | 本库 5.98–36.2 MB | KB/MB/GB 下拉 | ✅ 机制对，但单位会重置 / `between` 两侧独立 / 亚 KB 归零 |
| `duration_ms` | `a.duration_ms` | INTEGER 毫秒 | — | ×1000 +「秒」 | ✅ |
| `resolution` | `(a.width * a.height)` | 派生 INTEGER **总像素** | 2–45 MP | ×1e6 +「MP」 | ✅ 这个后缀正是防「填 1920」 |
| `width` / `height` | `a.width` / `a.height` | INTEGER | 640–12000 | 裸数字 `step=any` | 无边界提示 |
| `aspect_ratio` | `CAST(a.width AS REAL)/a.height` | 派生 REAL | 0.4–2.5 | 裸数字 | **无 16:9 / 4:3 预设**，要用户自己算 1.7778 |
| `iso` | `a.iso` | INTEGER | 50–102400（对数档） | 裸数字 | 步进 1 跨 5 个数量级 |
| `aperture` | `a.aperture` | REAL | f/1.0–f/22 | 裸数字 | **步进 1 跳过所有真实档**，无 `f/` |
| `focal` | `a.focal` | REAL | 8–800 | 裸数字 | 缺 `mm` 后缀（机制已有未用） |
| `dominant_hue` | `a.dominant_hue` | INTEGER 0–359 **环形** | 0–359 | 裸数字 | 跨 0° 语义只写在字段标签文字里，无 clamp |
| `dominant_sat` / `dominant_lum` | 同名列 | INTEGER | 0–100 | 裸数字 | 该是 0–100 滑块，无 clamp |
| `latitude` | `a.latitude` | REAL 带符号 | −90…90 | 裸数字 | **无 clamp** |
| `longitude` | `a.longitude` | REAL 带符号 | −180…180 | 裸数字 | 同上 |
| `rating` | `a.rating` | INTEGER NOT NULL DEFAULT 0 | 0–5（0=未评级，**故意无 null guard**） | **UI 里没有** | 后端全套可用，前端不可达 |

#### 日期型 3 个 —— 只 `≥ ≤ 介于`

`taken_at` / `created_at` / `modified_at`，INTEGER epoch ms，编译**左闭右开**。UI 有快捷但**线上格式是 P0**。

#### 枚举 / 字符串型 13 个 —— 不能比大小

| key | 运算符 | 备注 |
|---|---|---|
| `file_ext` `mime_type` | eq / in | |
| `camera` `lens` `video_codec` `audio_codec` | eq / in / contains | |
| **`shutter`** | eq / in / contains | **TEXT `"1/125"`，无法比大小**。「快门快于 1/500」表达不出来（真实缺口，§9 记录） |
| `has_location` `favorite` | eq / in，值域 `yes`/`no` | `has_location` 现在是自由文本框；`favorite` UI 没有 |
| `folder` | eq / in | 编译成 `file_path LIKE 'dir/%'`；UI 没有 |
| `palette_dominant` / `palette_top3` / `palette_any` | eq / in（+`min` 作占比阈值） | 按规格只暴露 `top3` |

### 5.2 八个特殊编译情形（改动时不能踩坏）

1. **`dominant_hue` 跨 0°**（`:628`）：`lo > hi` 时编译成 `(expr >= ?1 OR expr <= ?2)` 而非报错。**唯一允许区间倒置的 key。**
2. **`palette_*` 绕过 kind 分派**（`:453`）：先调 `compile_palette_meta`，所以 palette key 永远到不了 `compile_string`。
3. **`palette_*` + `min` = 占比阈值**（`:364-377`）：`eq` + 数值 `min` → `color_bucket = ?1 AND ratio >= ?2`。把 `min` **挪用成比例，不是区间下界**。守卫：恰好一色、`0.0..=1.0`、`in`+`min` 拒绝。
4. **日期 `between` 半开**（`:705`）：`max` 取次日 0 点；`lte` 同样，所以「不晚于 D」含 D 全天。
5. **`resolution` / `aspect_ratio` 额外守卫**（`:242`）：两操作数非空 + `height != 0`。
6. **数值绑定按整数/浮点分流**（`:580-587`）：`fract()==0` → `Integer`，否则 `Real`，避免对整数列做浮点比较。
7. **数值 key 也接受数值字符串**（`:563`）：副作用是 `"1920"` 与 `1920` 并存。
8. **占位符重编号**（`:809`）：本地 `?1..?n` 编译后由 `offset_placeholders` 平移。新增编译分支必须走同一条路。

`in` 上限 100 个值（`:653`）；量纲警告（`:402`）对 `value`/`min`/`max` 各自独立生效。

### 5.3 `NumericDomain` 单一事实源

值域现在在**四处各写一遍**：TS 的 `FIELD_OPTIONS[].kind`、Rust 的 `allowed_ops`、AI schema 里只给 `file_size` 的 `minimum: 1024`、`dimension_warnings` 的三条阈值。这正是 S0 给 key **名**治好的病，在 key 的**值域**上又长了一次。

```rust
pub struct NumericDomain {
    pub key: String,            // 内置 key 或 "facet:people_count"
    pub unit: Unit,             // Raw | Bytes | Millis | Pixels | Degrees | Percent | Stars | Custom(String)
    pub min: Option<f64>,       // 输入 clamp + AI schema minimum
    pub max: Option<f64>,       // 同上 + maximum
    pub step: f64,
    pub decimals: u8,
    pub presets: Vec<(String, f64)>,  // ("16:9", 1.7778) ("f/2.8", 2.8)
    pub circular: bool,               // dominant_hue：min > max 合法
    pub suspicious_below: Option<f64>,// R2-2 量纲提示阈值
    pub allowed_ops: Vec<String>,     // 与 search_query::allowed_ops 同源
}
```

一处定义，五处消费：① UI 的 `min/max/step/后缀/预设` ② `allowed_ops` ③ AI schema 的 `minimum`/`maximum` ④ 量纲警告 ⑤ **数值分面的 domain 动态生成**（§6 的关键）。

命令 `get_numeric_domains() -> Vec<NumericDomain>`，前端进 store（照 `metadataStore` 写法）。数值分面的 domain 由 `tag_facets` 的 `num_*` 列即时生成，与内置 key 混在同一个列表里返回 —— **这样 §6 不需要另写一套输入 UI**。

**测试**：`numeric_domain_single_source`（双向断言：每个 `ValueKind::Number` 的 key 都有 domain；每个 domain 的 `allowed_ops` 与 `search_query::allowed_ops` 逐字相等）。

### 5.4 控件选型：范围一律成对 min/max，不用滑块

- Maersk 设计系统 2026-03 的[结论](https://designsystem.maersk.com/updates/articles/2026-03-19-sliders/)：「做范围过滤时，成对的 min/max 数字输入更快、更精确、更可访问、跨设备更可靠」
- NN/g [《Sliders, Knobs, and Matrices》](https://www.nngroup.com/articles/sliders-knobs/)：连续控件用于**探索**，精确取值要离散输入
- Zillow [实测](https://www.zillow.com/news/utilizing-both-explicit-implicit-signals/)：最常用的过滤器就是 price 的 min/max 与卧室数
- [UXmatters](http://www.uxmatters.com/mt/archives/2010/02/numeric-filters-issues-and-best-practices.php)：数值过滤器是最容易让用户困惑的一类

**唯一用滑块的是探索性 0–100 量**：色板占比阈值（U-3 已如此，保留）、`dominant_sat`、`dominant_lum`。

| unit | 控件 | 例 |
|---|---|---|
| Bytes | 数字 + 单位下拉，`between` **共用一个单位** | `[5]–[10] [MB ▾]` |
| Millis | 数字 + 「秒」后缀 | `[30] 秒` |
| Pixels | 数字 + 「MP」+ 预设 | `2MP · 8MP · 24MP · 45MP` |
| Raw（比例） | **预设 chip 优先** + 数值覆盖 | `1:1 · 4:3 · 3:2 · 16:9 · 9:16` |
| Raw（光圈） | 档位下拉 / `step=1/3` + `f/` 前缀 | `f/[2.8]` |
| Raw（ISO） | 档位下拉 | `ISO [800]` |
| Degrees(circular) | 色相条 + 双游标；倒置时提示「跨 0° 区间」 | — |
| Percent | 0–100 滑块 | — |
| Stars | 0–5 星选择器 | `★★★☆☆` |
| Custom("人") | 数字 + 自定义后缀 | `[5] 人` |

### 5.5 候选值带命中数（最省力的易用性改进）

分面搜索的经典做法：[Azure AI Search](https://learn.microsoft.com/en-us/azure/search/search-faceted-navigation) —「facets 帮你找到想找的，同时确保你不会得到零结果」；[IRSG](https://archive-irsg.bcs.org/informer/?p=1737) —「显示的分面值应收敛到当前有结果的那些」。

## §6 数值化打标

**v1 这一章是设计草案，缺三样东西：数值分面的配置没有落库位置、AI 载荷无法承载数字、分面生命周期与数值的关系未定义。v2 补齐。**

### 6.1 现状：预留了洞，门没开

**类型选择器的主战场是创建对话框**（业界惯例：类型在创建时定），而它现在连单选/多选都不给。

### 6.2 三条硬障碍

**① 用户自定义分面永远进不了 `metadata` 白名单。** `ALL_METADATA_KEYS` 是编译期 `&[&'static str]`（`search_query.rs:46`），`key_spec` 对不在其中的 key 一律 `None`（`:121`）。运行期产生的 `people_count` 不可能走 metadata 路径 → **必须新增 `LeafCond` 变体。**

**② `key_spec`/`value_expr`/`allowed_ops` 全是对字面量 `match` 并映射到 `a.<column>`。** 比较「按素材连接的值」需要 EXISTS 子查询 → **现成模板是 `compile_palette_meta`（`:295`）**，它已经在对卫星表做 `EXISTS (… WHERE apc.asset_id = a.id AND apc.ratio >= ?2)`。照抄这个形状。

**③ AI 的 `key` 枚举是静态的**（`:1902`），模型无法在 `metadata` 里点名用户分面 → 但**已有运行期枚举的先例**：`facetHint` 的 enum 就是从活的分面列表动态生成的（`:1851-1856`）。照这个写法。

### 6.3 完整数据模型（V24）

#### ① 分面的数值配置 —— 加在 `tag_facets`（追加列，铁律 2）

```sql
ALTER TABLE tag_facets ADD COLUMN num_min      REAL;      -- NULL = 不限
ALTER TABLE tag_facets ADD COLUMN num_max      REAL;      -- NULL = 不限
ALTER TABLE tag_facets ADD COLUMN num_unit     TEXT NOT NULL DEFAULT '';  -- 展示后缀「人」「mm」
ALTER TABLE tag_facets ADD COLUMN num_decimals INTEGER NOT NULL DEFAULT 0;
ALTER TABLE tag_facets ADD COLUMN num_step     REAL NOT NULL DEFAULT 1;
```

`FACET_COLS` 追加末尾 → 索引 16–20，`facet_from_row` 的 `r.get(N)` **逐个数一遍**（铁律 2：插中间会静默数据错位，编译和测试都不报错）。

`facet_kind` 同时加约束：`CHECK(facet_kind IN ('tag','number'))`（V24 里用重建表或 `PRAGMA` 检查，SQLite 不支持给已有列加 CHECK —— 若成本高则退化为应用层校验 + 一条测试）。

**`NumericDomain` 就从这五列生成**（`key = "facet:<facet_key>"`），这是 v1 说不通的那一环。

#### ② 数值载荷表

```sql
CREATE TABLE asset_facet_numbers (
  asset_id        INTEGER NOT NULL REFERENCES assets(id) ON DELETE CASCADE,
  facet_key       TEXT    NOT NULL,
  value           REAL    NOT NULL,
  source          TEXT    NOT NULL DEFAULT 'manual',
  review_state    TEXT    NOT NULL DEFAULT 'ai_unreviewed',
  source_batch_id INTEGER,
  created_at      INTEGER NOT NULL,
  PRIMARY KEY (asset_id, facet_key)      -- 每素材每分面恰好一个值
);
CREATE INDEX ix_afn_value ON asset_facet_numbers(facet_key, value, asset_id);
```

不做通用 EAV —— 业界评价一致：「EAV 暴露了它全部的老问题：查询性能差、失去数据控制、无法校验、难以维护」（[stackoverflow](https://stackoverflow.com/questions/19364140/best-pattern-for-modeling-sparse-attributes)、[dba.stackexchange](https://dba.stackexchange.com/questions/20759/is-there-a-name-for-this-database-schema-of-key-values/20763)）。这里是**单一 `REAL` 列的普通 1:N 表**，`WHERE facet_key=? AND value BETWEEN ? AND ?` 直接走覆盖索引。

`source` / `review_state` / `source_batch_id` 照抄 `asset_tags` → **A3 的重跑状态机与 undo 语义不用重新设计**。PK 顺带成为**第一个真正被 DB 保证的分面约束**（对比 `max_items` 至今无 CHECK 无触发器）。

**为什么不加 `asset_tags.value_num`**：那样每个数值分面得挂一个傀儡标签行，标签名会进 FTS 聚合（`migrations.rs:1212` 拼 `t.name`），标签树里出现假节点。这也符合 [Cloudinary](https://cloudinary.com/documentation/custom_metadata) 把 structured metadata 与 tags 分成两类的做法。

#### ③ 建议项载荷 —— `ai_suggestion_items` 扩两列

```sql
ALTER TABLE ai_suggestion_items ADD COLUMN item_kind TEXT NOT NULL DEFAULT 'tag';  -- tag | number
ALTER TABLE ai_suggestion_items ADD COLUMN num_value REAL;                          -- item_kind='number' 时有值
```

现有 CHECK 保持不变（`decision IN ('pending','accepted','modified','rejected')`、`confidence` 0..1）。`tag_id` 对数值项恒 NULL（列本来就可空）。

#### ④ 强类型协议扩展

```rust

// AnalysisResult 加一个平行字段（不改 CategorizedTags 的形状，避免波及全部调用方）

```

选择「平行字段」而不是把 `CategorizedTags` 的值类型改成枚举：后者会波及 `ai_cloud.rs` + `db/ai.rs` 的十几个调用点，而前者只在 `parse_categorized` 的输出端分流。

### 6.4 全链路：AI 填数 → 确认 → 撤销 → 重跑

这是 v1 完全没有的部分。六个环节逐一定义：

| 环节 | 数值分面的行为 | 复用/新增 |
|---|---|---|
| **提示词** | 数值分面**不发词表**，发「这是数值分面，输出一个 0–50 的整数，单位：人」。`FacetPromptContext` 加 `facet_kind`/`num_min`/`num_max`/`num_unit` | 改 `build_prompt_context`（`tag_facets.rs:769`）+ `ai_cloud.rs:158-179` 的规则渲染 |
| **schema** | 该分面的 `minimum`/`maximum` 从配置生成；key 枚举运行期生成（照 `facetHint`） | 改 `intent_schema` / 打标侧 schema |
| **解析** | **只接受无歧义单值**，见下方「数值解析的严格规则」。有歧义（范围 / 约数 / 多个数字）或越界 → **不落值，进 `pending` + `decision_reason`**（不变量 11：不改写模型/用户的明确表达，宁可少给） | 新 `parse_number_proposal` |

#### 数值解析的严格规则（v3 收严）

**AI 自动落建议的路径必须严格；转换预览的路径可以宽松但不得自动裁决。** 两者用同一个解析函数，返回三态而不是一个数：

```rust
pub enum NumberParse {
    Value(f64),                 // 无歧义单值 → 可落建议
    Ambiguous { reason: String },// 有歧义 → 进 pending / 进转换预览的「待确认」桶
    None,                       // 完全没有数字
}
```

| 输入 | 结果 | 说明 |
|---|---|---|
| `"5"` `"5.0"` `"05"` | `Value(5.0)` | `"5"` 与 `"5.0"` **归一为同一个值** |
| `"5人"` `"5 人"` `"人数5"` | `Value(5.0)` | 恰好一个数字 token + 纯标签性文字，允许 |
| `"-3"` | `Value(-3.0)` | 负数本身合法；是否越界由 `num_min` 判 |
| **`"5~6"` `"5-6"` `"5 到 6"` `"5至6"`** | **`Ambiguous("范围")`** | ❌ 不再取首个数字。把范围静默变单值违反不变量 11 |
| **`"约5"` `"大约 5"` `"5左右"`** | **`Ambiguous("约数")`** | 限定词表：`约` `大约` `左右` `上下` `approximately` |
| **`"不少于5"` `"超过5"` `"5以上"` `"至少5"`** | **`Ambiguous("比较式")`** | 限定词表：`不少于` `不多于` `超过` `以上` `以下` `至少` `最多` |
| **`"3或4"` `"3、4"`** | **`Ambiguous("多值")`** | 出现两个以上数字 token |
| `"很多"` `"一群人"` | `None` | 无数字 |
| `NaN` / `Infinity` / 越界 | `Ambiguous("超出范围 0–50")` | **绝不裁到边界** |

两条路径对三态的处置：

| 路径 | `Value` | `Ambiguous` | `None` |
|---|---|---|---|
| **AI 落建议** | 写 `ai_suggestion_items`（`item_kind='number'`, `num_value`, `decision='pending'`） | 同样写 item 但 `num_value = NULL` + `decision_reason = "范围/约数，需人工确认：原文「5~6」"` | 丢弃 + warning |
| **`tag→number` 转换预览** | 进 `parsed` 桶 | 进 `ambiguous` 桶，**列出原文让用户逐条填数**，不猜 | 进 `unparseable` 桶 |

**测试**：`number_parse_accepts_unambiguous_single_value` / `number_parse_rejects_range_forms` / `number_parse_rejects_approximation_words` / `number_parse_rejects_comparison_words` / `number_parse_rejects_multiple_numbers` / `number_parse_rejects_nan_inf_and_out_of_range` / `ai_ambiguous_number_goes_to_pending_not_value` / `five_and_five_point_zero_normalize_equal`。

### 6.6 `tag → number` 转换的完整规则（v1 只写了一句）

`convert_facet_kind(key, target, dry_run) -> ConversionReport`

#### 解析与归一

解析统一走 §6.5 的 `NumberParse` 三态。转换预览侧的桶分配：

| 输入标签名 | 桶 | 说明 |
|---|---|---|
| `"5"` | `parsed` | |
| `"5人"` | `parsed` | 恰好一个数字 token |
| `"5.0"` | `parsed` | 与 `"5"` **归一为同一个值** |
| `"约 5"` / `"5~6"` / `"不少于5"` / `"3或4"` | **`ambiguous`** | **v3 收严：不取首个数字。** 列出原文，让用户逐条填数 |
| `"很多"` | `unparseable` | 无数字 → 列进「会丢失」清单 |

#### 十条规则

1. **多个标签映射到同一数值** → 合法（不同素材可以是同一个数）。
2. **同一素材通过多个标签映射到不同数值** → **冲突**。PK 只允许一个值，必须在 dry-run 里逐条列出让用户选，**不自动裁决**。
3. **冲突的优先级参考**（仅作为预选，仍需用户确认）：`review_state` 优先级 `manual > ai_reviewed > ai_unreviewed`；同级不自动选，标红等用户处理。
4. **父子层级** → 数值分面不支持层级。转换前若该分面存在非根标签，预览里报「N 个标签有父子关系，转换后层级会丢失」。
5. **别名** → 别名不产生值，转换时丢弃，列进预览。
6. **原标签** → 转换后置 `status='deprecated'`（**不物理删**，保证 undo 与历史可查），并从 `asset_tags` 移除关联；每步写 `tag_ops` 以便撤销。
7. **FTS** → 移除 `asset_tags` 关联时触发器自动更新（铁律 6 的顺序天然满足）。
8. **AI 建议** → 该分面下 `decision='pending'` 的 item 全部置 `rejected`，`decision_reason='分面已转为数值型'`。
9. **`number → tag` 直接禁止** —— 会把连续值退化成离散标签，不可逆。Airtable 的教训：改类型「数值会保留，非数值的值会丢失」（[社区](https://community.airtable.com/other-questions-13/change-populated-field-type-21141)），且 text→number 有[已知的精度篡改 bug](https://community.airtable.com/t5/other-questions/serious-bug-with-field-type-changes/m-p/159826)。
10. **必须先 dry-run**：

```rust
pub struct ConversionReport {
    pub parsed:      Vec<(i64, String, f64)>,        // tag_id, name, value
    pub ambiguous:   Vec<(i64, String, String)>,     // tag_id, name, 歧义原因（v3 新增桶）
    pub unparseable: Vec<(i64, String, i64)>,        // tag_id, name, asset_count
    pub conflicts:   Vec<(i64, Vec<(i64, f64, String)>)>, // asset_id, [(tag_id, value, review_state)]
    pub hierarchy_loss: usize,
    pub alias_loss:     usize,
    pub pending_rejected: usize,
}
```

UI 全部展示，用户逐项确认（`ambiguous` 桶要能就地填数）后才执行。整个转换在**单事务**内，`dry_run = true` 时一行不写。

**测试**：`convert_parses_number_from_tag_name` / `convert_normalizes_5_and_5point0` / `convert_reports_unparseable` / `convert_reports_per_asset_conflicts` / `convert_reports_hierarchy_and_alias_loss` / `convert_rejects_pending_suggestions` / `convert_number_to_tag_rejected` / `convert_dry_run_writes_nothing` / `convert_is_atomic`。

### 6.7 为什么它必须独立立项

改动面：**8 个后端文件 + 8 个前端文件**，贯穿迁移 / 查询编译 / AI 提示词 / AI 解析 / 建议项 / 确认 / 撤销 / 重跑 / 删除级联 / 类型转换十个环节。它不是「加一列 + 加一个下拉」，而是与 F 波次同量级的一次地基扩展。所以 v2 把它拆成**协议设计（Phase 6）+ 实现（Phase 7）**，且排在超级搜索可用之后。

| **[UXmatters](http://www.uxmatters.com/mt/archives/2010/02/numeric-filters-issues-and-best-practices.php)** | 「带数值的过滤器仍是最令人困惑的一类」 | ✅ 单位 / 预设 / 命中数都在补这个 |
| **[Azure AI Search](https://learn.microsoft.com/en-us/azure/search/search-faceted-navigation)** / **[IRSG](https://archive-irsg.bcs.org/informer/?p=1737)** / **[Facet Search 指南](https://www.hybrismart.com/2019/02/13/facet-search-the-most-comprehensible-guide-best-practices-design-patterns/)** | 候选值带命中数；收敛到当前有结果的值，「确保你不会得到零结果」 | ✅ §5.5。C-2 的 delta 是**事后**归因，这是**事前**预防，两者互补 |

## §12 施工铁律

违反任何一条都要返工，每次提交前对照。前 6 条继承地基指导书，后 8 条是本轮新增。

| # | 铁律 | 为什么 |
|---|---|---|
| 1 | **`COLUMNS` / `FACET_COLS` 是位置映射，新列只能追加末尾**，改完逐个数 `r.get(N)` | 插中间会静默数据错位，编译和测试都不报警（Phase 7 要给 `tag_facets` 加 5 列） |
| 2 | **改 FTS 触发器必须：复制现有 SQL 再改 → 立即 `rebuild` → 先在内存库跑通全部 FTS 测试** | 地基指导书铁律 3；Phase 0-4 要动 |
| 3 | **DB 写操作短暂持锁；网络/解码放锁外** | 长持锁会饿死列表和打标 |
| 4 | **永不覆盖人工确认的标签/数值**：`review_state IN ('ai_reviewed','manual')` 的行任何重跑都不动 | Phase 7 的数值确认路径同样适用 |
| 5 | **系统不改写用户明确表达的语义**：库统计、Fuzzy 结果、AI 的排序建议都只能建议，要用户点了才改条件 | 本轮三处依赖它：B9 排序主次、§4.8 append 不改 ranking、§6.5 数值歧义进 pending |
| 6 | **绝不双写 `tag_aliases` 与 `tag_terms`**，`schema_features` 是唯一开关 | Phase 0-4 的正解是让 FTS 与 `aliases()` 也走这个 gate，不是双写 |
| 7 | **`must_not` 里只放正向条件。** `ExcludeTag` / `QueryExpr::Not` 禁止进入 | §4.1b 的 P0：双重否定会把「排除夜景」变成「只要夜景」 |
| 8 | **否定只在区一级表达一次。** 行内不再有「是/不是」，字段表不再有「排除标签」 | 三种写法并存必然产生自相矛盾的条件 |
| 9 | **无效条件在 AST 层结构性删除，不在 SQL 层折叠成 `1=1`/`1=0`** | §4.2：同一个折叠在 `filter` 里无害、在 `must_not` 里清空全库、在 `should` 里给全库加分 |
| 10 | **列表 / 总数 / 全选 ID / 排序 / warning / 诊断，六项共用同一个 plan 与同一套编译器** | §4.1 + §4.5：任何一项另开一条路，就会出现「界面说 106、诊断说 500」 |
| 11 | **协议类型一路到底不降级。** `PlanIdsResult` 不许在 store 层退化成 `number[]`，`SearchWarning` 不许退化成 `String` | 降级的那一层就是 warning 与 `truncated` 丢失的地方 |
| 12 | **异步诊断必须带 `planRevision`，过期整批丢弃** | 只用 `alive` 标志防不了「plan 变了组件还在」，会点到错的条件上 |
| 13 | **每个任务必须带测试，断言真实值。** 不许只断 `is_ok()`；不许留松弛区间；不许绕过被测代码路径 | 地基指导书本轮有 3 处假绿，其中 `effective_value_sql_matches_rust` 是同义反复 |
| 14 | **重置只在测试库/备份副本上做。** 真实用户库不允许用重置代替迁移 | §0.4 的适用范围声明 |

| 2 | **Phase 2 改完 store 后前端测试挂超过 20 条** | 先判断是「测试断言了旧的 `expr` 事实源」（改测试）还是「换源丢了条件」（修实现）。**绝不为了让测试过而保留 `expr` 双源** |

| 4 | **B6 方案 A（全库软排序）在 3 万素材上单次超 800ms** | 走地基指导书止损线 6：改「filter 先落临时表再算 score」，或退到方案 B（锁最小值 1） |
| 5 | **诊断的 2N+1 次 COUNT 在 3 万素材上超 500ms** | 降级为「只算 `result_count` + 当前编辑那条的 self/without」（地基止损线 11） |
