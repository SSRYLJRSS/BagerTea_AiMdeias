## 1. 执行摘要

两份专家方案的总体方向正确，以下原则应直接保留：

1. 手动超级筛选和 AI 智能搜索共用一套查询模型。
2. AI 只生成受控结构化条件，不生成和执行 SQL。
3. AI 解析结果回填为可编辑的条件芯片。
4. 标签通过稳定 facet_key、规范名称和别名解析。
5. 无 AI 配置时，手动超级筛选仍然完整可用。

但原方案还不能直接进入开发，必须先修正四个核心问题：

- 当前元数据筛选只有精确集合匹配，无法表达“大于 5MB”“时长超过 10 秒”“2025 年拍摄”等条件。
- 数据库标签分面已经使用稳定 facet_key，但 AI 打标仍主要依赖设置中的可变分类名称，两个事实来源需要合并。
- 当前 FTS 会先把全部命中 ID 拉回 Rust，再拼接到素材查询中，不适合复杂组合和大召回的超级搜索。
- 一期 AI 搜索只能解析已有标签、文本和元数据，不能假装理解所有未打标图片。真正的画面语义搜索需要独立的 embedding/CLIP 索引。

建议将本期拆成四个阶段，预计 7～10 个开发日：

| 阶段 | 内容 | 建议周期 |
|---|---|---:|
| P0 | 查询协议、标签语义和产品边界定稿 | 0.5～1 天 |
| P1 | 元数据查询底座和搜索性能改造 | 2～3 天 |
| P2 | 超级筛选页面与通用素材网格 | 2～3 天 |
| P3 | AI 智能搜索和结构化输出降级链 | 2～3 天 |

保存筛选、智能文件夹、评分和视觉语义搜索不纳入一期。

## 2. 两份专家方案评审

### 2.1 可以直接采用的部分

- 一个统一查询模型，两条输入路径：手动筛选和 AI 解析。
- AI 不接触 SQL，后端按字段和操作符白名单编译查询。
- 所有查询值使用参数绑定。
- 标签名称先经过分面、规范名和别名解析，再转换为内部 ID。
- 同一分面内支持 any/all，不同分面之间默认 AND。
- 标签排除默认包含后代标签。
- 复用现有分页、缩略图、虚拟滚动和批量操作。
- AI 解析后可自动执行，但全部条件必须可见、可删、可修改。
- 保存筛选和智能文件夹放到二期。

### 2.2 需要修订的部分

第一份方案的部分代码盘点已经过时。当前项目中：

- Rust AssetFilter 已有 metadata_filters。
- list_metadata_facets command 已实现并注册。
- 前端已有 MetadataPanel、SelectedFilterTags 和 metadataStore。
- 数据库已进入 V8，具备 tag_facets、tag_aliases 和 AI 候选记录。

因此，真正的 P0 不是补齐这些半成品，而是升级元数据协议、统一标签事实来源并调整搜索执行链路。

第二份方案提出的“API 级结构化输出优先 + 三级降级”应采用，但必须补充：

- 服务商能力探测结果需要缓存，避免每次搜索重复付费探测。
- 所有结构化输出仍要经过 Rust 白名单校验。
- AI 输出和最终数据库查询要分成两个对象，不能让 AI 直接生成 tagId。
- 相对日期必须携带当前日期、时区和地区信息。

## 3. 当前系统能力

### 3.1 已有基础

当前项目已具备：

- SQLite 素材数据库和分页查询。
- FTS5 中文搜索、短语搜索和 LIKE 回退。
- 图片、视频、未打标和回收站筛选。
- 标签父子层级、分面、规范名和别名。
- 标签重命名、合并、停用和 AI 候选基础。
- EXIF：相机、镜头、ISO、光圈、快门、焦距。
- 文件属性：格式、大小、宽高、视频时长和编码。
- 拍摄时间、入库时间、修改时间。
- 虚拟滚动素材网格和批量操作。
- 多 AI 档案以及 OpenAI 兼容、Anthropic 双协议。

### 3.2 当前缺口

#### 查询协议没有真正统一

前端 LibraryFilter、Rust AssetFilter 和未来 AI 查询之间尚无独立、稳定、可版本化的 SearchQuery。

#### 元数据只能做集合匹配

当前 MetadataFilter 本质上是：

~~~text
{ key, values[] }
~~~

只能选择“某个相机”“某个格式”“某个固定区间”，不能表达任意数值或日期范围。

#### 标签分类存在两个事实来源

数据库使用稳定 facet_key，但 AI 打标设置仍使用：

~~~text
TagCategory { name, hint, single, max }
~~~

name 可以被用户修改，不能继续作为机器协议。

#### FTS 执行链路不适合超级搜索

当前流程是：

~~~text
关键词
  -> FTS/LIKE 得到全部 asset id
  -> Rust 拼接 IN (...)
  -> 再执行素材筛选
~~~

超级搜索应将全文召回留在数据库内部，通过受控子查询、CTE 或 JOIN 与其他条件组合。

#### 素材网格与 libraryStore 强耦合

当前 AssetGrid 直接订阅 useLibraryStore。超级搜索如果复用该 Store，会覆盖普通素材库筛选，并产生退出恢复、分页和异步竞态问题。

## 4. 最终产品目标

### 4.1 入口

- 单击底部“素材库”：进入普通素材库。
- 双击底部“素材库”：进入超级搜索。
- 双击必须取消待执行的单击导航，不能先闪到普通素材库。
- 支持 Esc 返回。
- 建议支持 Ctrl+Shift+F，解决双击入口不易发现的问题。
- 超级搜索页面中底栏“素材库”继续保持高亮。

### 4.2 超级筛选

一期至少支持：

- 全部、图片、视频。
- 未打标。
- 关键词。
- 标签分面。
- 同分面 any/all。
- 父标签包含后代或仅自身。
- 排除标签。
- 文件夹。
- 文件格式和 MIME 类型。
- 宽度、高度、分辨率和宽高比。
- 文件大小。
- 拍摄时间、入库时间、修改时间。
- 相机、镜头、ISO、光圈、快门、焦距。
- 视频时长、视频编码、音频编码。
- 排序字段和方向。

建议增加两个非常实用的治理条件：

- 缺少指定分面标签，例如“没有风格标签”。
- 缺少关键元数据，例如“没有拍摄时间”。

### 4.3 AI 智能搜索

AI 将自然语言转换为已有查询条件，例如：

~~~text
2025 年拍的横构图海边素材，大小 5MB 以上，不要夜景
去年夏天用 Sony 拍的视频，时长 10 秒以上
暖色调、清新风格的人像，按分辨率从高到低
~~~

一期明确边界：

- 可以理解标签、文件名、格式、时间、设备、大小、尺寸、时长和排序。
- 只能搜索已经进入数据库的文字、标签和元数据。
- 对没有标签、描述或 embedding 的图片，不承诺直接理解画面。
- AI 搜索只生成查询，不创建标签、不修改素材数据。

## 5. 统一查询模型

### 5.1 两层查询对象

不要让 AI 直接生成最终数据库查询，建议拆成：

~~~text
SearchIntent
  AI 生成
  包含标签文字、分面提示、元数据条件和排序意图

ResolvedSearchQuery
  后端生成
  包含已解析 tagId、合法字段、合法操作符和规范单位
~~~

这样能避免 AI 幻觉标签 ID，也能清楚展示“模型理解了什么、系统最终执行了什么”。

### 5.2 AI 输出示例

~~~json
{
  "assetType": "image",
  "tags": [
    {
      "facetKey": "scene",
      "text": "海边",
      "includeDescendants": true
    }
  ],
  "excludeTags": [
    {
      "facetKey": "lighting",
      "text": "夜景"
    }
  ],
  "metadata": [
    {
      "key": "file_size",
      "op": "gte",
      "value": 5242880
    },
    {
      "key": "taken_at",
      "op": "between",
      "min": "2025-01-01",
      "max": "2025-12-31"
    }
  ],
  "sortBy": "resolution",
  "sortDir": "desc"
}
~~~

AI 不得输出：

- SQL 或 SQL 片段。
- 数据库列名。
- assetId 或 tagId。
- limit 或 offset。
- schema 之外的字段。
- 自动创建标签的命令。

### 5.3 后端最终查询

ResolvedSearchQuery 建议包含：

- search。
- assetType。
- untaggedOnly。
- facetFilters。
- excludeTagIds。
- missingFacetKeys。
- metadataFilters。
- sortBy 和 sortDir。

trashOnly 不允许由 AI 控制，超级搜索默认不查询回收站。分页字段单独管理。

## 6. 元数据筛选改造

### 6.1 新协议

将当前 MetadataFilter 升级为：

~~~ts
type MetadataOp =
  | "eq"
  | "neq"
  | "in"
  | "contains"
  | "prefix"
  | "gt"
  | "gte"
  | "lt"
  | "lte"
  | "between";

interface MetadataFilter {
  key: MetadataFilterKey;
  op: MetadataOp;
  value?: string | number;
  values?: Array<string | number>;
  min?: string | number;
  max?: string | number;
}
~~~

该协议当前不落库，应一次性升级，不建议长期兼容新旧两种形态，否则二期 saved_filters 会继承两套语义。

### 6.2 字段白名单

| key | 类型 | 支持操作 |
|---|---|---|
| file_ext | 字符串 | eq、in、prefix |
| mime_type | 字符串 | eq、in、prefix |
| width | 数值 | eq、gt、gte、lt、lte、between |
| height | 数值 | eq、gt、gte、lt、lte、between |
| resolution | 数值 | eq、gt、gte、lt、lte、between |
| aspect_ratio | 数值 | eq、gt、gte、lt、lte、between |
| file_size | 字节数 | eq、gt、gte、lt、lte、between |
| duration_ms | 毫秒 | eq、gt、gte、lt、lte、between |
| taken_at | 日期/时间 | gte、lte、between |
| created_at | 日期/时间 | gte、lte、between |
| modified_at | 日期/时间 | gte、lte、between |
| camera | 字符串 | eq、in、contains |
| lens | 字符串 | eq、in、contains |
| iso | 数值 | eq、in、gte、lte、between |
| aperture | 数值 | eq、gte、lte、between |
| shutter | 字符串 | eq、in、contains |
| focal | 数值 | eq、gte、lte、between |
| video_codec | 字符串 | eq、in、contains |
| audio_codec | 字符串 | eq、in、contains |
| folder | 路径 | eq、prefix |

规范单位：

- 文件大小统一为字节。
- 视频时长统一为毫秒。
- 日期最终统一为时间戳或明确的闭开区间。
- resolution 统一为 width × height 的像素面积。
- 宽高比由 width / height 派生。

数值和日期字段为 NULL 时，默认不命中比较条件。

### 6.3 UI 快速选项

现有“1～10MB”“10～60 秒”“拍摄月份”等可以保留为快捷预设，但点击后应转换为统一的比较条件，而不是继续形成特殊底层协议。

例如：

~~~text
大于 5 MB
  -> { key: file_size, op: gte, value: 5242880 }

2025 年
  -> { key: taken_at, op: between, min: 2025-01-01, max: 2026-01-01 }
~~~

### 6.4 SQL 编译

Rust 必须按 key 和 op 双重白名单编译：

~~~text
file_size + gte -> a.file_size >= ?
camera + contains -> a.camera LIKE ? ESCAPE '\'
taken_at + between -> a.taken_at >= ? AND a.taken_at < ?
~~~

禁止将 AI 返回的字段名或操作符直接拼入 SQL。

### 6.5 Facet API

现有 list_metadata_facets 应扩展为同时返回：

- 离散项目 items。
- 数值范围 stats。
- 常用 presets。
- 支持的操作符。
- 单位和展示格式。

范围型字段不应返回几十个精确值供用户逐项勾选。

## 7. 标签系统适配

### 7.1 稳定分面

建议最终使用：

| 显示名称 | 稳定 key | 示例 |
|---|---|---|
| 场景/地点 | scene | 海边、室内、街道 |
| 主体/物体 | subject | 人、茶杯、汽车、建筑 |
| 人物属性 | people | 人数、年龄、动作、关系 |
| 风格 | style | 清新、复古、胶片、极简 |
| 色彩 | color | 暖色、冷色、低饱和 |
| 氛围情绪 | mood | 宁静、热烈、治愈 |
| 构图视角 | composition | 横图、竖图、特写、俯拍 |
| 光线/时间 | lighting | 逆光、柔光、黄昏、夜景 |
| 用途 | purpose | 广告、封面、头像 |
| 技术语义 | technical | 慢动作、延时等非纯 EXIF 技术概念 |
| 自定义 | custom | 用户自建标签 |

“横图”“竖图”可以作为构图语义标签，但宽高比仍需提供独立的结构化筛选，二者不能互相替代。

### 7.2 标签和元数据的边界

标签表达视觉和业务语义：

- 主体。
- 场景。
- 风格。
- 色彩。
- 氛围。
- 构图。
- 光线。
- 用途。

元数据表达可精确比较的技术事实：

- 格式。
- 大小。
- 尺寸。
- 时间。
- 相机和镜头。
- ISO、光圈、快门、焦距。
- 视频时长和编码。

禁止为了搜索方便把技术元数据批量复制成标签，否则标签树会迅速膨胀并产生双重事实来源。

### 7.3 标签解析顺序

AI 输出标签文字后，后端按以下顺序解析：

1. 用 facetKey 限定分面。
2. normalized_name 精确匹配。
3. tag_aliases.normalized_alias 精确匹配。
4. 搜索候选并计算相似度。
5. 只有一个明显高置信度候选时允许自动采用。
6. 多候选或低置信度时返回 warning。
7. 无法解析时不让该条件悄悄生效，也不创建新标签。

返回示例：

~~~json
{
  "warnings": [
    "未识别标签：清透",
    "标签存在歧义：暖色，可选 color/lighting"
  ]
}
~~~

### 7.4 标签治理规则

- 重命名自动保留旧名称别名。
- 合并自动保留源名称和源别名。
- 跨分面合并默认拒绝。
- 删除默认改为停用。
- 停用标签保留历史关联，但不进入新建候选。
- 新标签必须选择分面。
- 同一别名不能指向多个有效规范标签。
- AI 搜索中的未知词只形成 warning，不进入正式标签树。
- 标签查询和分配应按分面懒加载，不长期依赖完整标签树。

### 7.5 设置页调整

tag_facets 应成为标签分类的唯一事实来源。

设置页中的 tagCategories 改为按 facet_key 保存的 AI 配置，例如：

~~~text
facetKey
hint
enabledForAi
single
maxItems
~~~

规则：

- facet_key 不可修改。
- 显示名称可以本地化。
- 用户修改显示名不影响搜索协议。
- 旧中文分类通过映射迁移到稳定 key。
- 无法映射的分类进入 custom，不丢配置。
- AI 打标和 AI 搜索都读取同一套 facet 配置。

### 8.4 交互原则

- AI 条件和手动条件始终使用同一种芯片。
- 芯片显示字段、操作符、值和单位，不能只显示裸值。
- AI 解析默认替换当前条件。
- 若用户选择追加，必须明确显示“追加到当前筛选”。
- 数值、时间和滑块使用提交或防抖，避免每个像素变化都查询。
- 无结果时提示可能导致无结果的条件，并支持一键移除。
- 筛选变化沿用当前安全策略：清空选中，避免批量操作不可见素材。
- AI warning 是正常产品状态，不应以致命错误弹窗表现。

## 9. AI 智能搜索后端

### 9.1 模块划分

~~~text
commands/super_search_cmd.rs
services/super_search_ai.rs
services/ai_cloud.rs
db/assets.rs
db/search.rs
db/tags.rs
~~~

职责：

- super_search_cmd：参数校验、配置读取、异步调度。
- super_search_ai：schema、提示词、解析、校验、标签解析和 warning。
- ai_cloud：通用文本 JSON 请求和协议降级。
- assets：查询白名单编译和分页。
- search：全文召回和相关度。
- tags：规范标签、路径和别名候选。

### 9.2 请求流程

~~~text
用户输入
  -> 校验长度
  -> 短锁读取 AI 档案、分面和标签候选
  -> 释放数据库锁
  -> 组装 schema、当前日期、时区、当前筛选
  -> 调用模型
  -> 解析 SearchIntent
  -> 白名单校验
  -> 标签文字解析为 tagId
  -> 返回 ResolvedSearchQuery、explanation、warnings
  -> 前端回填并执行查询
~~~

网络请求期间不能持有数据库锁。

### 9.3 三级降级

第一级：API 级结构化输出

- Anthropic 使用强制 tool use。
- OpenAI 兼容端点优先 json_schema。
- schema 禁止额外字段。

第二级：JSON Object

- 使用 json_object。
- 在 system prompt 中重复字段白名单和示例。

第三级：普通文本 JSON

- 完整解析失败后截取对象。
- 仍失败时将错误原因带入重试一次。
- 本地模型复用现有退化检测和卸载重载逻辑。

服务商不支持某种模式后，应缓存该档案的能力，后续请求直接走可用等级。

### 9.4 提示词规则

- 当前日期和时区必须进入提示词。
- 时间表达转换为绝对区间或受控相对时间。
- “不要、排除、不含”生成排除条件。
- 不确定的概念进入普通 search 或 warning，不编造结构化值。
- 标签只输出文字和分面提示。
- 不输出 SQL、ID、分页或数据库列名。
- 不创建标签。
- 最大标签条件、元数据条件和输入长度要有限制。

## 10. 数据库与性能

### 10.1 FTS 改造

必须避免将全部 FTS 命中 ID拉回 Rust 后再构造大型 IN 列表。

建议将全文召回编译为数据库内的受控子查询或临时结果关系，并为相关度排序预留 rank。

普通排序继续支持：

- created_at。
- taken_at。
- modified_at。
- name。
- size。
- resolution。

存在 search 且用户未明确指定排序时，建议默认采用“相关度优先，时间次序”，而不是仍按入库时间排序。

### 10.2 标签和分面统计

现有标签计数和元数据分面计数主要是全库统计。超级搜索建议逐步支持上下文计数：

- 统计应应用其他筛选条件。
- 计算某个分面时忽略该分面自身的当前选择。
- 用户可以看到继续选择后大约还剩多少结果。

一期如果工期紧，可以先使用全局计数，但 UI 不应暗示它是当前结果计数。

### 10.3 索引

建议 V9 初始评估：

~~~sql
CREATE INDEX idx_assets_taken_at ON assets(taken_at);
CREATE INDEX idx_assets_camera ON assets(camera);
CREATE INDEX idx_assets_file_size ON assets(file_size);
CREATE INDEX idx_assets_width_height ON assets(width, height);
~~~

是否增加 lens、duration_ms、file_ext 和表达式索引，应以真实 3 万素材数据库的 EXPLAIN QUERY PLAN 和基准结果决定。

### 10.4 查询限制

后端应限制：

- 输入文字长度。
- 单次标签条件数量。
- 单次元数据条件数量。
- 每个标签分面的 tagId 数量。
- 分页上限。
- AI 返回内容长度。
- 递归标签深度异常。

## 12. 测试与验收

### 12.1 查询测试

- 每一种字段和合法操作符。
- 非法字段和非法操作符。
- 同分面 any/all。
- 不同分面 AND。
- 父标签包含后代和仅自身。
- 排除标签及后代。
- 关键词、标签、元数据和排序组合。
- NULL 不误命中。
- 日期边界正确。
- MB、GB、秒、分钟单位转换正确。
- resolution 按像素面积比较。
- 快速切换筛选时旧响应不能覆盖新结果。

### 12.2 AI 测试

至少通过：

~~~text
2025 年拍的横图海边素材，大于 5MB，不要夜景
去年夏天拍的竖版人像，风格清新
Sony 拍的视频，时长 10 秒以上，按分辨率排序
~~~

同时覆盖：

- AI 返回非法字段。
- AI 返回标签 ID。
- 未知标签。
- 同名标签歧义。
- 相对日期。
- Anthropic、json_schema、json_object 和普通 JSON。
- 本地模型退化。
- 无 AI 配置。
- AI 搜索不产生任何标签写入。

### 12.3 标签治理测试

- 重命名保留旧名称搜索。
- 合并保留源名称和别名。
- 跨分面合并被拒绝。
- 停用标签不进入新候选。
- 别名不能指向多个有效标签。
- 显示名称修改不影响 facet_key。
- 旧分类映射失败时进入 custom。

### 12.4 前端验收

- 从任意页面双击素材库进入超级搜索。
- 双击不先触发普通导航。
- 条件芯片可单独删除。
- 清除全部恢复默认查询。
- AI 条件可替换或追加。
- 无结果提示可移除相关条件。
- 1366px 和 1920px 布局稳定。
- 亮色、暗色均使用主题变量。
- 网格保持虚拟滚动和批量操作能力。

### 12.5 性能指标

- 3 万素材下普通结构化筛选首屏目标不超过 500ms。
- 大规模 FTS 命中不产生超长 IN SQL。
- AI 请求约 60 秒超时，期间不持数据库锁。
- 素材网格滚动无明显掉帧。
- 查询和分面统计不阻塞 Tauri 主线程。

## 14. 最终决策

### 必须采用

- SearchIntent 与 ResolvedSearchQuery 分层。
- AI 不生成 SQL 和 ID。
- 后端字段、操作符白名单。
- 稳定 facet_key。
- 规范标签和别名解析。
- 元数据比较操作。
- 独立 superSearchStore。
- 通用 AssetGridView。
- FTS 数据库内组合查询。
- API 结构化输出优先和三级降级。
- AI 搜索零数据写入。

### 暂缓

- 保存筛选。
- 智能文件夹。
- 评分。
- CLIP/embedding 视觉搜索。
- 搜索专用模型档案。
- XMP/IPTC 双向写回。

### 最终结论

超级搜索一期的核心不是增加一个 AI 搜索框，而是先把标签、元数据和全文搜索统一成一套可解释、可组合、可修改、可测试的查询系统。

AI 只是这套系统的自然语言入口。只有在查询协议、标签分面和后端白名单稳定后，后续的保存筛选、智能文件夹和视觉语义搜索才有可靠基础。
