`cargo test --test ai_service_integration -- --test-threads=1` 连续运行时，出现过：

## 三、高优先级问题

### P1-01 素材筛选存在异步响应覆盖竞态

位置：[libraryStore.ts](../../src/stores/libraryStore.ts#L86)

`refresh()` 获取当前筛选条件后发起异步请求，响应返回时无 request id 或筛选快照校验，直接写入 `items` 和 `total`。快速切换搜索词、标签、类型或排序时，旧请求可能比新请求更晚返回并覆盖新结果。

`loadMore()` 也存在同类问题：它捕获旧的 `items` 和 `filter`，请求返回后直接追加数据。

影响：

- 页面展示与当前筛选条件不一致；
- 图片、视频或回收站素材可能混在一起；
- 用户可能对错误素材执行删除、移动或打标。

推荐解决方法：

1. 为每次查询生成递增 `requestId` 或 AbortController；
2. 响应写入前核对请求 ID 和当前筛选快照；
3. 筛选变化时废弃正在执行的分页请求；
4. 增加“旧请求慢返回、新请求快返回”的自动化测试。

> **🔍 灵犀复核（2026-08-23）**：**属实，同意 P1。** 已对照 `libraryStore.ts` 源码确认：`refresh()` 捕获 `filter` 后 await，响应写入前无任何校验；`loadMore()` 同样捕获旧 `items` 和 `filter` 直接追加。补充两个报告未提及的细节：① `setFilter()` 的 no-op 优化只能避免相同筛选重复触发，救不了竞态本身；② `loadMore()` 里有 `known` Set 去重，防的是跨页重复而非覆盖。修复方案上给个更轻的替代：响应回来后拿 `get().filter` 与捕获的 `f` 做深比较，不一致直接丢弃，不需要 requestId 计数器。另外 **`loadMore` 的后果比 `refresh` 更严重**——它用旧 `items.length` 做 offset，竞态时 offset 错位会漏整页数据，建议优先修。

### P1-02 AI 批次快速切换可能显示错误建议

位置：[aiStore.ts](../../src/stores/aiStore.ts#L94)

`openBatch()` 设置 `currentBatchId` 后异步加载建议，但请求返回后无条件写入 `suggestions`。快速切换批次 A、B 时，A 的慢响应可能覆盖 B 的内容。

影响：

- 页面标题显示批次 B，但工作台显示批次 A；
- 用户可能确认、拒绝或编辑错误批次的建议。

推荐解决方法：

- 使用请求令牌；
- 写入前验证 `currentBatchId === requestedBatchId`；
- 增加 A 慢/B 快和 A 快/B 慢两种测试场景。

> **🔍 灵犀复核（2026-08-23）**：**属实，同意 P1，且竞态面比报告描述的更大。** 已确认 `openBatch()` 无条件写入 `suggestions`。报告漏了一点：`confirm()`/`reject()` 完成后也会回调 `openBatch(get().currentBatchId)`——如果用户在确认请求飞行途中切换了批次，确认结果回写同样会错批次。修复成本极低：写入前一行 `if (get().currentBatchId !== batchId) return;` 即可，连测试都可以后补，这应该是四个 P1 里最便宜的修复。

### P1-03 CSV 导出会覆盖已有文件

位置：[export_local.rs](../../src-tauri/src/services/export_local.rs#L251)

清单始终写入固定文件名 `导出清单.csv`，调用 `fs::write()` 会直接覆盖目标目录中的同名文件。

影响：可能无提示损坏用户之前保存的清单。

推荐解决方法：

- 使用与素材导出相同的唯一文件名策略，例如 `导出清单(1).csv`；
- 或在 UI 中提示用户并二次确认覆盖；
- 推荐先写临时文件，再原子重命名。

> **🔍 灵犀复核（2026-08-23）**：**属实，但定级可商榷。** 已确认 `write_csv_manifest()` 固定写 `导出清单.csv` 且 `fs::write` 直接覆盖。有点讽刺的是——`unique_dest()`（含 B06b 的 999 上限防覆盖回退）就在同一个文件里，素材导出用了它，清单导出却没用，属于“工具就在手边却没接”的典型，修复只需 `unique_dest(&dest, "导出清单.csv")` 一行。定级方面提个不同意见：被覆盖的是**可再生的派生数据**（清单随时可重新导出），不是原始素材，用户损失有限，严格说是 P1 尾 / P2 头。原子写建议本身认可，对崩溃时序有意义。

### P1-04 “移动”操作可能虚假报告成功

位置：[export_local.rs](../../src-tauri/src/services/export_local.rs#L187)

跨盘移动采用“复制后删除源文件”。如果复制成功但源文件删除失败，代码只记录日志并返回成功，随后数据库更新为新路径。

结果：

- UI 显示移动成功；
- 原位置仍残留文件；
- 用户无法知道移动并未完整完成。

如果文件已经移动但数据库更新失败，也可能形成“文件在新位置、数据库仍指向旧位置”的不一致状态。

推荐解决方法：

- 删除源文件失败时返回部分失败状态，不报告完整成功；
- 数据库更新失败时尝试回滚文件移动；
- 为任务增加 `partial_failed` 状态和逐文件结果；
- 增加文件占用、只读源文件、数据库更新失败等测试。

> **🔍 灵犀复核（2026-08-23）**：**部分属实，报告有一处明显误判，建议 P1 降为 P2。** 逐条对照源码后的结论：
> - **误判**：报告称“如果文件已经移动但数据库更新失败，也可能形成不一致状态”——代码里 DB 更新失败**并非静默**：错误被捕获后任务标记 `failed`，错误消息明确写着“文件已移动但库记录未更新，请重新入库”，用户是知情的。
> - **属实**：`move_file()` 中 `remove_file` 失败仅 `tracing::warn` 后返回 `Ok`，UI 显示成功而源文件残留——但注释 B04 表明这是**有意的取舍**（文件已在新位置、DB 指向新位置，仅旧位置多一份副本，数据无损）。
> - 结论：真正的问题只剩“用户不知道有残留副本”。`partial_failed` 状态方向正确，但对单人桌面应用，整套逐文件结果框架偏重——**建议降级为软提示**：任务完成时附带“N 个源文件未能清理”的 warning 即可。三项测试建议（文件占用/只读源/DB 失败）倒是值得做，其中 DB 失败路径已有部分处理。

## 四、中优先级问题

### P2-01 AI 取消最多可能等待约 300 秒

位置：[ai_cloud.rs](../../src-tauri/src/services/ai_cloud.rs#L446)

HTTP 客户端的单请求超时为 300 秒。取消标志只在素材之间检查，无法中断当前正在执行的网络请求。

推荐解决方法：

- 使用可取消的异步 HTTP 请求；
- 或使用取消令牌配合较短分段超时；
- UI 明确区分“已请求取消”和“当前请求已结束”。

> **🔍 灵犀复核（2026-08-23）**：**属实，但报告建议未考虑设计上下文，直接采纳会引入回归。** 已确认 300s 总超时且取消只在素材间检查。但源码注释写明了 300s 的理由：本地 7B 纯 CPU 模型单张响应可能远超 60s，短超时会误杀慢速打标——报告建议的“较短分段超时”会重新引入这个已知问题。另外用的是 `reqwest::blocking`，取消令牌方案在阻塞客户端上不可用。我的意见：**不动超时，主攻第 3 条建议**——UI 明示“取消已受理，当前图片完成后停止”，把语义诚实化，成本最低且不碰稳定性。若一定要可中断，需换 async 客户端，改动面大，建议单独立项。

### P2-02 Tauri 事件订阅失败产生未处理 Promise

位置：[hooks.ts](../../src/hooks/hooks.ts#L16)、[taskStore.ts](../../src/stores/taskStore.ts#L48)

`subscribe().then(...)` 没有 `catch`。全局任务监听在 `Promise.all()` 成功前就把 `subscribed` 设置为 `true`，失败后不会自动重试。

实际测试中已经观察到：

```text
TypeError: Cannot read properties of undefined (reading 'transformCallback')
```

这也是前端测试进程退出码为 1 的直接原因之一。

推荐解决方法：

- 捕获订阅失败；
- 失败时恢复 `subscribed = false`；
- 释放已成功建立的部分监听；
- 为 Tauri API 增加完整测试 mock。

> **🔍 灵犀复核（2026-08-23）**：**属实，同意修复方向，另指出一个报告未点破的实现细节坑。** 已确认 `useTauriEvent` 的 `subscribe().then(...)` 无 `catch`（但 cleanup 已用 `cancelled` 标志处理了“订阅在卸载后才 resolve”的情况，说明作者考虑过时序，唯独漏了 reject 分支）。修复“释放已成功建立的部分监听”时要小心：`Promise.all` 一旦 reject，先前已 resolve 的 unlisten 函数拿不到——**必须改用 `Promise.allSettled` 再逐个回收**，直接按报告写法改会泄漏监听。taskStore 部分与 P2-11 重复，意见见 P2-11。

### P2-03 设置加载失败后页面永久显示加载状态

位置：[SettingsPage.tsx](../../src/pages/SettingsPage.tsx#L75)、[settingsStore.ts](../../src/stores/settingsStore.ts#L31)

Store 保存了 `loadError`，但设置页没有读取。加载失败时 `draft` 为空，页面只显示“加载设置中”，用户无法重试或理解原因。

推荐解决方法：

- 显示错误信息和重试按钮；
- 设置加载失败时禁用保存；
- 区分首次加载、加载失败和空配置三种状态。

> **🔍 灵犀复核（2026-08-23）**：**属实，同意 P2，典型的“后端修了、前端没接”断链。** 已确认：`settingsStore` 明确存了 `loadError`（B28 注释表明是有意暴露的错误状态），但 `SettingsPage` 只判 `!draft` 就渲染“加载设置中…”。修复就是补一个 `loadError` 分支加重试按钮，成本极低。同意“加载失败时禁用保存”的子建议——这对应用 B28 想防的“用户在默认设置上保存覆盖真实配置”事故，其实比显示错误本身更关键。

### P2-04 API Key 明文存储

位置：[settings.rs](../../src-tauri/src/db/settings.rs#L248)

API Key 作为设置 JSON 明文保存到 SQLite。项目文档已经披露该限制，但真实用户场景仍存在本地泄露风险。

推荐解决方法：

- 使用 Windows Credential Manager、系统钥匙串或 Tauri Stronghold；
- 数据库只保存引用 ID；
- 导出设置时默认剔除密钥。

> **🔍 灵犀复核（2026-08-23）**：**属实，同意 P2，但对推荐工具提出替换意见。** 已确认 `save_settings()` 将整个 Settings JSON 序列化进 SQLite，`api_key` 明文在内。单机单人桌面应用风险确实低于服务端，但 Windows 下 SQLite 文件可能被同步盘/备份带出机器，值得修。工具选型上：**推荐 `keyring` crate（Windows Credential Manager 后端）而非 Stronghold**——Stronghold 要引入一整套依赖和密码恢复流程，对这个体量的项目过重；`keyring` 几百行接入就能解决。第 3 条“导出设置剔除密钥”建议成本低、优先做。

### P2-05 预览命令仍可能读取任意本地媒体

位置：[thumbnail_cmd.rs](../../src-tauri/src/commands/thumbnail_cmd.rs#L35)

`get_preview()` 目前只检查绝对路径和扩展名，没有验证路径是否来自当前入库清单或授权目录。受损前端或开发者工具可以请求任意支持格式的本地文件。

推荐解决方法：

- 后端验证路径属于已入库资产或明确授权目录；
- 更稳妥的方式是使用一次性预览 token，而不是直接接受任意路径。

> **🔍 灵犀复核（2026-08-23）**：**属实，但建议 P2 降为 P3，且推荐方案存在场景矛盾。** 已确认现状仅校验绝对路径+扩展名白名单。两点保留意见：① B24 注释表明这是对更早任意读取问题的**有意修复**，项目文档已披露，属于已知接受的纵深防御缺口；本地应用的受损前端是极端威胁模型，实际风险低。② 报告推荐的“一次性 token”方案**不适用于本场景**——`get_preview` 服务的是“待入库预览”，文件尚未入库、没有 asset id，token 无从颁发。务实做法：前端把本次导入会话的文件清单登记给后端（短 TTL），预览仅允许读清单内路径。结论：方向认可，方案需重写，优先级可后置。

### P2-06 清理缩略图缓存期间持有数据库锁

位置：[thumbnail_cmd.rs](../../src-tauri/src/commands/thumbnail_cmd.rs#L62)

缓存文件删除操作在数据库锁作用域内执行。缓存较大或磁盘较慢时，素材查询、保存设置、标签操作都会等待。

推荐解决方法：先读取需要清理的路径，释放数据库锁，再执行文件清理，最后短事务清理数据库字段。

> **🔍 灵犀复核（2026-08-23）**：**属实，同意 P2，修复方案正确。** 已确认 `clear_thumbnail_cache` 在 `db.lock()` 作用域内执行 `thumbs.clear()` 的批量文件删除。补一个实施提醒：B27 的“回写 placeholder/hd 路径为 NULL”逻辑和文件删除耦合在同一个锁块里，拆锁时必须整体迁移到最后的短事务，不能只搬删除、把回写落下，否则会回到 B27 修过的“DB 指向已删文件”破图问题。

### P2-07 AI 批量上限会静默截断用户选择

超过 `batch_limit` 时直接 `take()` 前 N 项，没有返回被截断数量。用户可能认为全部素材已经进入 AI 批次。

推荐解决方法：

- 超限时拒绝并提示；
- 或返回 `acceptedCount`、`ignoredCount`，让用户明确确认。

> **🔍 灵犀复核（2026-08-23）**：**属实，同意 P2，推荐两道防线并行。** 已确认 `ai_create_batch` 里 `.take(limit.max(1))` 静默截断。补充一个更前置的方案：`batch_limit` 本来就在 settings 里，前端提交前就知道上限，**在提交入口拦截提示比后端返回 acceptedCount 体验更顺**；后端 take 保留作兜底防线。两个都做成本也不高。

### P2-08 React 重复 key 警告

前端测试多次报告素材网格出现重复 key。需要确认是测试 fixture 重复 ID，还是分页竞态造成真实重复数据。

> **🔍 灵犀复核（2026-08-23）**：**属实，报告“需确认根因”的态度正确，补充定位线索。** 已确认卡片 `key={asset.id}`，重复警告必然是 `items` 数组内重复 id。排查方向：① `loadMore` 已有 `known` Set 去重防跨页重复，但 **`refresh()` 没有去重**；② 单次响应内重复只能来自后端 offset 分页在数据变动时的经典重复问题；③ 测试 fixture 重复 id。顺手修复建议：把去重下沉到 store 层统一做（refresh 也过滤），一行 Set 的事，无论根因是哪个都能先止血。同意 P2 定级。

## 五、其他观察

### P2-09 CSV 公式注入风险

位置：[export_local.rs](../../src-tauri/src/services/export_local.rs#L256)

CSV 字段虽然处理了逗号、引号和换行，但没有防护以 `=`, `+`, `-`, `@` 开头的值。恶意文件名或标签在 Excel 中打开时可能被当作公式执行。

推荐解决方法：对危险前缀字段增加单引号或其他安全转义，并在测试中覆盖恶意文件名和标签。

> **🔍 灵犀复核（2026-08-23）**：**属实，且有一个报告没点到的加重因素。** 已确认 `csv_escape` 只处理逗号/引号/换行。报告设想的攻击面是“恶意文件名”，但更现实的入口是：**标签可能来自 AI 建议（LLM 输出），属于不可信数据**——AI 生成的标签以 `=` 开头并杂凑成公式形态的概率远高于用户遇到恶意文件名。修复一行前缀转义，性价比高，同意 P2。

### P2-10 AI 页面设置保存错误未被处理

位置：[AiTaggingPage.tsx](../../src/pages/AiTaggingPage.tsx#L108)

切换配置档案或模型时调用 `void save(...)`，没有捕获失败。设置保存失败时用户可能以为已切换，但后端仍使用旧配置。

推荐解决方法：显示保存中状态、成功状态和错误提示；失败时恢复 UI 选择。

> **🔍 灵犀复核（2026-08-23）**：**属实，同意 P2。** 已确认 `AiTaggingPage.tsx` L77/L84 两处 `void save(...)`（`settingsStore.save` 失败会 throw，被 void 吞掉），切档/切模型时 UI 与后端配置错位风险成立。行号小偏差：实际在 L77/L84 而非 L108，不影响结论。最低成本修法：先把 `void` 换成带 toast 报错的调用，保存中状态可以后补。

### P2-11 全局任务监听失败后无法恢复

位置：[taskStore.ts](../../src/stores/taskStore.ts#L45)

`subscribed` 在订阅动作完成前就设为 `true`。如果任意一个事件监听失败，之后不会再尝试建立监听。

推荐解决方法：只有所有监听成功后才标记已订阅；部分成功时逐个回收并允许重试。

> **🔍 灵犀复核（2026-08-23）**：**属实，但本条与 P2-02 的 taskStore 部分是同一份代码拆成两处报，属于报告自身的一致性缺陷，建议合并为一项。** 技术上补充：`subscribed = true` 放在 `await` 前是防并发重入（App 挂载时可能被调多次），意图有合理性，正确写法是 try/finally：失败时置回 false 并回收已成功的监听（需 `Promise.allSettled`，理由见 P2-02 意见）。另外报告未提供重试机制的具体形态——建议直接在下次任意命令调用时惰性重订阅，避免引入定时器。
