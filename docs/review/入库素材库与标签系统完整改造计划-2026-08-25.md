# 入库、素材库与标签系统完整改造计划

> 日期：2026-08-25  
> 范围：入库页面、任务进度、媒体预览、RAW 浏览、视频播放、批量打标、标签体系、超级搜索  
> 文档性质：问题诊断与实施计划  
> 当前状态：仅完成代码审阅与资料调研，尚未修改业务代码

## 1. 执行摘要

本次反馈表面上涉及多个页面和交互问题，但从代码结构看，问题主要集中在三条共享契约没有闭环：

1. **任务状态契约不统一**：页面局部状态和全局任务状态分别维护，造成反馈延迟、重复进度条和阶段语义不稳定。
2. **媒体预览契约不统一**：待入库预览、素材库缩略图、RAW 高清图、视频封面和视频播放由不同路径处理，缺少统一的加载层级、缓存策略和错误状态。
3. **标签分面契约迁移未完成**：后端已经迁移到稳定 `facetKey` 和 `tag_facets`，部分前端仍读取已废弃的 `tagCategories`，导致基础分类消失，并继续影响 AI 打标、标签设置和超级搜索。

因此，不建议把本次工作拆成若干互不相关的界面小修。正确方向是先统一上述三条契约，再完成各页面体验改造。

## 2. 用户反馈归纳

### 2.1 入库选择流程中断

用户选完第一组文件后，待入库清单取代了空状态区域，页面不再提供继续选择文件或文件夹的可见入口。虽然当前代码支持追加合并，但功能不可发现，导致用户误认为只能选择一次。

目标体验：

- 清单非空时仍能继续选择文件；
- 支持继续选择文件夹并递归扫描；
- 新选择内容追加到当前清单；
- 自动按规范化路径去重；
- 拖拽追加与文件选择器追加使用同一逻辑；
- 正在正式入库时才禁止修改清单。

### 2.2 点击入库后缺少即时反馈

点击“开始入库”后，界面仍然可以滚动，但进度条可能十几秒后才出现。用户无法判断应用是在扫描、计算哈希、读取元数据，还是已经卡死。

这属于典型的**首个反馈延迟**问题，而不是单纯的主线程冻结问题。

目标体验：

- 点击后 300ms 内出现任务状态；
- 在无法计算准确百分比时显示确定的阶段文案和不确定进度；
- 后续切换为准确的整体进度；
- 当前文件、成功数、重复数、失败数实时更新；
- 取消操作和取消结果可理解。

### 2.3 进度条重复且位置不合理

当前入库页内容区有一条局部进度条，底栏左侧又有一条全局任务进度条。两者来源相同，但布局、信息密度和生命周期不同，形成重复反馈。

目标体验：

- 全应用只保留一套任务展示；
- 任务条放在“入库 / 素材库 / 打标”底栏上方；
- 不挤压底栏主导航；
- 用户切换页面后仍可查看任务进度；
- 支持取消、完成停留、失败查看和重试入口。

### 2.4 缺少悬浮大图和视频预览

待入库清单和素材库都只能查看小缩略图。快速浏览时必须打开查看器，操作成本较高。

目标体验：

- 鼠标停留约 300ms 后出现大图预览；
- 图片展示较高分辨率缓存图；
- 视频展示自动静音的 3 秒或 5 秒预览；
- 鼠标快速扫过卡片时不触发；
- 预览不改变选中状态，不阻塞滚动；
- 浮层自动避让窗口边缘。

### 2.5 RAW 浏览速度慢

用户期望素材库先显示 RAW 内嵌的 JPEG 预览，再在后台生成高清 RAW 解析结果。当前项目虽然已经建立双层缩略图和 RAW 真解码能力，但需要验证实际运行是否始终遵守“内嵌预览优先、真解码延后”的原则。

目标体验：

```text
进入素材库
  -> 立即显示占位图或 RAW 内嵌 JPEG
  -> 可见区素材进入高清任务队列
  -> 后台完成 RAW 解析
  -> 高清结果平滑替换已有预览
```

### 2.6 视频不能稳定播放

查看器已经使用 HTML `<video>`，但“存在标签”不等于本地媒体链路可用。播放还依赖以下条件：

- Tauri asset protocol 已放行原始文件路径；
- MIME 类型正确；
- WebView 支持该视频和音频编码；
- 大文件读取支持 Range 请求；
- 加载、解码和资源错误被前端识别；
- 本地协议在目标操作系统上支持媒体随机访问。

目标体验：

- 播放、暂停；
- 可拖动时间轴；
- 前进和后退 5 秒；
- 0.5x、1x、1.5x、2x 倍速；
- 音量和静音；
- 显示当前时间和总时长；
- 编码不支持时给出明确原因和可行操作。

### 2.7 批量打标数量过少

当前实现存在配置上限，并在前后端对超出部分进行截取。虽然代码默认值已经不是 100，而是 500，但用户体验仍然表现为“选了很多，只处理前一部分”。

目标体验：

- 用户选择的全部素材进入同一个逻辑任务；
- 不静默丢弃超出上限的素材；
- 内部按照小分块执行 AI 请求；
- 总任务量可以是数千张；
- 失败只影响单张或单个子批次；
- 批次能够暂停、取消、续跑和重试失败项。

### 2.8 基础标签和打标入口消失

打标界面显示标签总数为 0，基础标签分类没有固定出现，用户无法进行手动打标。随后 AI 打标可能显示“当前没有待打标的建议”，造成整个打标流程不可用。

目标体验：

- 无论 AI 是否已生成建议，系统基础分面始终显示；
- 手动模式进入后立即可以录入标签；
- AI 建议为空时，基础分面和已有规范词表仍然存在；
- “没有 AI 建议”不能等同于“不能打标”。

### 2.9 标签设置和超级搜索受到连锁影响

标签、AI 打标和超级搜索共享同一语义体系。如果分类定义分别来自旧设置、数据库分面、标签树和 AI 输出，任何一个入口发生漂移，搜索和打标都会出现不一致。

目标是建立唯一数据流：

```text
tag_facets
  -> 标签目录与规范词表
  -> 手动打标
  -> AI 提示词与候选解析
  -> 标签设置与治理
  -> 普通筛选与超级搜索
```

## 3. 代码现状与直接证据

### 3.1 入库逻辑支持追加，但入口被隐藏

`ImportPage.stage()` 已经实现追加和路径去重：

- 读取新扫描结果；
- 使用已有路径构建 `Set`；
- 过滤重复路径；
- 追加到原有 `plan.items`。

代码位置：`src/pages/ImportPage.tsx` 第 57 行附近。

但“选择文件”按钮只在 `plan` 为空时显示。清单出现后，右侧只渲染 `PendingList`，因此用户失去了继续选择入口。

结论：这是**功能已存在但交互入口条件错误**，不需要重写追加算法。

### 3.2 入库进度存在两套订阅与展示

局部进度：

- `ImportPage` 订阅 `import://progress`；
- 页面内容顶部渲染 `ProgressBar`、文件名和取消按钮。

全局进度：

- `App` 启动 `startGlobalTaskWatch()`；
- `taskStore` 再次订阅 `import://progress`；
- `BottomBar` 左侧渲染全局任务条。

结论：同一事件被两个 UI 独立消费，生命周期和展示规则无法保证一致。

### 3.3 哈希阶段没有进度事件

后端入库流程先对全部文件执行 SHA-256 哈希，再进入复制和元数据提取阶段。当前第一批进度事件发生在后续的并行处理循环中。

大文件、视频、机械硬盘或网络磁盘会显著拉长哈希阶段。前端已经设置 `running=true`，但由于没有任务阶段事件，用户只能看到按钮消失或页面状态变化，无法确认工作仍在进行。

结论：需要把任务创建事件前移到命令开始处，并为哈希阶段提供独立阶段反馈。

### 3.4 不同阶段重复使用局部 current/total

复制与元数据阶段使用文件总数作为 `total`，缩略图阶段又把 `total` 改为待生成缩略图数量，并将 `current` 从 1 重新开始。

这会产生以下问题：

- 全局进度可能倒退；
- 进度条从接近完成突然跳回低比例；
- `done >= total` 可能被误判为整个任务完成；
- 完成停留计时可能在中间阶段提前触发。

结论：需要区分 `phaseCurrent/phaseTotal` 与 `overallCurrent/overallTotal`。

### 3.5 RAW 已有内嵌预览和真解码，但缺少真实链路验收

当前 `imaging.rs` 的核心策略为：

1. 提取 TIFF、CR3 或标记扫描得到的内嵌 JPEG；
2. 内嵌图尺寸足够时直接使用；
3. 尝试 `image::open()`；
4. 高清尺寸下才调用 RAW 或 HEIC 特殊解码。

这一总体方向正确，但仍存在风险：

- RAW 内嵌预览提取失败后可能执行不必要的通用解码尝试；
- 标记扫描会将文件整体读入内存；
- RAW 文件较大时整文件扫描代价明显；
- 网格可见区会主动请求 512px 高清图，可能快速占满 4 个解码许可；
- 查看器直接请求 1280px，可能与网格缩略图竞争；
- 文档中的性能结论尚未全部经过用户真实样本验收。

### 3.6 视频播放缺少完整诊断和流式服务保证

当前查看器对视频直接执行：

```tsx
<video src={convertFileSrc(current.filePath)} controls autoPlay />
```

后端查询素材时会动态放行文件路径，CSP 也允许 `asset:` 媒体资源。但当前代码没有：

- 播放错误状态展示；
- `canPlayType()` 预检；
- `loadedmetadata`、`stalled`、`waiting` 等状态处理；
- Range 请求能力验证；
- 不兼容编码的转码或代理预览；
- 大文件和不同操作系统的回归测试。

结论：视频问题不能只通过增加几个前端按钮解决，必须先验证资源服务链路。

### 3.7 批量上限会截断用户选择

当前设置默认 `batchLimit=500`。创建批次时：

- 前端发现超限后只提交前 N 个 ID；
- 后端再次执行 `.take(limit)`；
- 其余素材不会进入批次。

这种实现把“控制单次成本”和“限制整个用户任务”混为一谈。

正确模型应为：

```text
用户逻辑批次：2000 张
  -> 子任务 1：1-50
  -> 子任务 2：51-100
  -> ...
  -> 子任务 40：1951-2000
```

### 3.8 标签迁移存在明确的数据源错误

后端已经建立 `tag_facets`，并初始化以下系统分面：

- `subject`
- `scene`
- `purpose`
- `style`
- `color`
- `composition`
- `lighting`
- `people`
- `technical`
- `custom`

设置结构也已经声明 `tagCategories` 为弃用字段，业务应该切换到 `aiFacetConfigs` 和数据库分面。

但 `AiTaggingPage` 仍向 `Workbench` 传入：

```tsx
categories={settings?.tagCategories ?? []}
```

旧分类在迁移后会被清空，因此工作台的 `panelCategories` 也可能为空。只有 AI 返回了分类标签时，额外分类才会临时出现。

结论：这是基础标签为 0 的直接代码根因之一。

## 4. 总体设计原则

### 4.1 单一事实源

- 任务状态由统一任务中心维护；
- 媒体预览由统一媒体服务维护；
- 标签分面由 `tag_facets` 维护；
- AI 设置只能覆盖提示和启用状态，不能重新定义分面结构；
- 超级搜索只消费已经解析和验证的稳定协议。

### 4.2 快速反馈优先

- 所有耗时操作先立即反馈，再执行重任务；
- 首屏先显示已有低成本结果；
- 高质量结果在后台替换；
- 失败不能让界面变成永久骨架或无提示空白。

### 4.3 逻辑批次与执行分块分离

用户选择数量决定逻辑批次大小，性能和 API 成本由内部执行分块、并发和限流控制。不能通过截断用户选择规避性能问题。

### 4.4 真实素材验收优先

合成测试只能验证边界和不崩溃，不能证明真实 RAW、视频编码和大文件体验符合要求。必须建立受控的真实样本测试集。

## 5. 详细改造方案

## 5.1 入库清单与继续添加

### UI 调整

在 `PendingList` 固定头部增加：

- “添加文件”图标按钮；
- “添加文件夹”图标按钮；
- 列表/网格切换；
- 清空清单；
- 当前素材数量和总大小。

左侧底部继续保留“开始入库”，但不把“继续添加”放在左侧，避免用户在清单浏览和添加文件之间来回寻找。

### 交互规则

- 新文件追加到当前清单末尾；
- 重复路径不重复加入；
- 扫描期间显示“正在扫描新选择”；
- 扫描失败不清除原有清单；
- 扫描结果为 0 时只提示本次未发现支持文件；
- 正式入库开始后禁用清单编辑；
- 入库完成后根据结果决定是否保留失败项。

### API 调整建议

`inspect_import` 返回结果增加：

```text
accepted
ignoredUnsupported
ignoredDuplicatePath
scanErrors
```

便于前端说明“本次新增多少、忽略多少”，而不是只显示笼统错误。

## 5.2 统一任务中心

### 任务模型

建议引入统一 `TaskSnapshot`：

```ts
interface TaskSnapshot {
  taskId: string;
  kind: "import" | "export" | "ai" | "thumbnail";
  status: "queued" | "running" | "cancelling" | "done" | "failed" | "cancelled";
  phase: string;
  phaseLabel: string;
  phaseCurrent: number;
  phaseTotal: number | null;
  overallCurrent: number;
  overallTotal: number | null;
  currentItem?: string;
  succeeded: number;
  skipped: number;
  failed: number;
  cancellable: boolean;
  message?: string;
}
```

### 入库任务阶段

```text
queued       已创建任务
scanning     扫描文件
hashing      计算指纹
processing   复制文件并提取元数据
committing   写入素材库
previewing   生成快速预览
done         完成
```

### UI 布局

在底栏上方增加独立任务层：

- 与底栏左右边距对齐；
- 默认显示一行摘要；
- 多任务时允许展开任务列表；
- 进度条在导航栏上方，而不是嵌入左下角；
- 当前页面不再重复显示同一任务进度；
- 页面可以显示结果摘要，但不再绘制第二条进度条。

### 完成和失败语义

- 100% 后停留约 1.5 秒；
- 有失败项时不自动消失，显示“查看详情”；
- 取消后显示部分完成结果；
- 阶段之间不重置整体进度；
- 无法准确计算总量时使用不确定进度，不伪造百分比。

## 5.3 统一悬浮预览

### 组件结构

建议新增：

```text
HoverPreviewTrigger
MediaPreviewPopover
ImagePreviewContent
VideoPreviewContent
useHoverIntent
previewRequestCache
```

### Hover Intent

- 鼠标进入立即显示轻微可交互反馈；
- 停留 300ms 后启动预览；
- 鼠标仍在移动时不启动重任务；
- 离开触发卡片和预览浮层超过 400ms 后关闭；
- 同一时刻只允许一个预览浮层；
- 快速移动到相邻卡片时取消上一请求。

### 图片预览

- 优先复用已有高清缩略图；
- 未生成时请求 1024px 左右的预览缓存；
- 请求期间先展示现有 placeholder；
- RAW 不在 hover 主线程路径执行无界真解码；
- 预览最大尺寸受窗口可用区域约束。

### 视频预览

两级策略：

1. 优先使用原视频进行静音短预览；
2. 原视频编码不兼容或读取过重时，使用后台生成的代理预览。

代理预览建议：

- 3 至 5 秒；
- 480p 或 720p；
- H.264/AAC MP4 或目标 WebView 明确支持的格式；
- 静音版本可省略音轨；
- 按素材 hash 缓存；
- 只在首次明确 hover 后生成。

## 5.4 RAW 渐进式加载

### 快速层

RAW 快速层只允许：

- TIFF IFD 内嵌 JPEG；
- Panasonic `JpgFromRaw`；
- CR3 容器内嵌预览；
- 有明确文件读取上限的 JPEG 标记扫描；
- 通用类型占位图。

快速层不允许：

- 全尺寸 RAW 去马赛克；
- 读取整个超大文件到内存；
- 无上限地占用所有 CPU；
- 阻塞素材库首屏数据返回。

### 高清层

高清层执行：

- RAW 真解码；
- 目标尺寸缩放；
- 色彩转换；
- 缓存写入；
- 完成事件通知前端替换图片。

任务优先级建议：

```text
当前查看器素材
  > hover 预览素材
  > 当前可见网格素材
  > 即将进入视口的素材
  > 空闲预热素材
```

### 缓存键

缓存键至少包含：

- 素材 ID 或内容 hash；
- 文件修改时间；
- 目标尺寸；
- 解码器版本；
- 色彩管线版本。

### 可观测性

增加结构化性能日志：

```text
assetId
format
source=embedded|generic|raw_decode
embeddedScanMs
decodeMs
resizeMs
writeMs
cacheHit
resultDimensions
```

## 5.5 视频播放与基础控制

### 第一阶段：诊断现有播放链路

对目标 Windows 环境验证：

- MP4 H.264/AAC；
- MOV H.264；
- MP4 H.265/HEVC；
- MKV H.264；
- WebM VP9；
- 大于 1GB 的长视频；
- 高码率短视频。

记录：

- `canPlayType()`；
- `video.error.code`；
- `networkState`；
- `readyState`；
- 是否收到 Range 请求；
- 是否返回 `206 Partial Content`；
- 首帧时间；
- 拖动后的恢复时间。

### 第二阶段：播放资源服务

若 asset protocol 无法稳定满足随机访问，增加专用媒体协议或本地 HTTP 服务：

- 仅绑定 `127.0.0.1`；
- 路径通过素材 ID 映射，不直接接收任意文件路径；
- 支持单 Range 请求；
- 返回正确 `Content-Type`；
- 返回 `Accept-Ranges: bytes`；
- 合法 Range 返回 `206` 和 `Content-Range`；
- 越界返回 `416`；
- 防止路径穿越和越权读取。

### 播放控制

基于 `HTMLMediaElement`：

- `play()` / `pause()`；
- `currentTime -= 5`；
- `currentTime += 5`；
- `playbackRate = 0.5 | 1 | 1.5 | 2`；
- 时间轴与 `timeupdate`；
- `duration` 和已缓冲区；
- 全屏；
- 音量与静音。

不依赖负数 `playbackRate` 实现倒放，因为浏览器兼容性不足。用户提出的“后退”应实现为跳回固定秒数。

## 5.6 大批量打标

### 数据模型

保留一个用户可理解的逻辑批次，并增加内部分块状态。

建议字段：

```text
ai_batches
  total
  queued
  processing
  succeeded
  failed
  cancelled

ai_batch_chunks
  batch_id
  chunk_index
  status
  retry_count
  started_at
  finished_at
```

也可以首版不新增分块表，只通过建议记录状态进行调度，但必须保证应用重启后能够恢复未完成任务。

### 执行策略

- 逻辑批次允许数千张；
- 云端模型默认每个子批 20 至 50 张；
- 本地模型可按硬件性能调整；
- 并发默认为 1 至 3；
- 视频任务成本更高，应单独计权；
- 服务商限流时指数退避；
- 单张失败落库并继续下一张；
- 取消只停止尚未开始的请求；
- 已生成建议保留，可续跑剩余任务。

### UI 性能

以下区域必须虚拟化：

- 胶片条；
- 批次素材列表；
- 失败项列表；
- 大批量标签应用预览。

素材对象按页加载，不允许一次性把数千个完整 `Asset` 和全部标签载入前端。

### 设置文案

删除或重命名“批量上限”：

- 用户总批次不设低上限；
- 设置项改为“执行分块大小”；
- 高级设置中提供并发数量；
- 默认值由本地/云端模式决定；
- 不应把系统内部保护暴露成用户任务限制。

## 5.7 标签系统修复

### 唯一事实源

`tag_facets` 负责：

- 稳定 key；
- 默认显示名称；
- 描述；
- 单选或多选；
- 最大数量；
- 排序；
- 系统分面状态。

`aiFacetConfigs` 只负责：

- AI 是否使用该分面；
- AI 提示词 hint；
- 可选本地化显示名。

`tagCategories` 仅在读取旧数据并迁移时使用，不能继续出现在业务渲染路径。

### 打标工作台

进入页面后加载系统分面，不依赖当前建议内容：

```text
list_tag_facets
  + aiFacetConfigs 显示名覆盖
  + 当前素材已有标签
  + 当前 AI 建议
  -> WorkbenchPanel[]
```

每个分面应显示：

- 分面名称；
- 当前标签；
- 搜索已有标签入口；
- 最近使用标签；
- AI 建议来源和置信度；
- 新建标签入口；
- 单选/数量上限反馈。

即使当前素材没有任何标签，基础分面仍必须存在。

### 标签录入

- 输入时搜索规范名和别名；
- 结果显示完整路径；
- 相同名称不同分面必须区分；
- 创建前检查近似词和别名；
- 未命中时允许创建到当前分面；
- 手动创建直接为正式标签；
- AI 新词先作为候选，不自动污染正式词表。

### 标签设置页面

设置页应拆成两个职责明确的区域：

1. **系统分面配置**：显示名、AI 开关、提示语，只允许有限编辑；
2. **标签管理与治理**：新增、重命名、移动、合并、别名、停用、重复词治理。

不应在一行中同时放置机器 key、显示名、提示词和开关而缺少清晰层级。

## 5.8 超级搜索一致性

超级搜索应继续遵守现有两层协议：

```text
SearchIntent
  -> 后端解析和校验
ResolvedSearchQuery
  -> 数据库执行
```

改造要求：

- AI 只输出标签文字和 `facetKey`；
- AI 不输出 tag ID、SQL 或数据库列名；
- 文字通过规范名和 alias 解析为 tag ID；
- 未解析标签作为 warning 返回；
- warning 不清空当前查询；
- 用户删除某个条件时不重新调用 AI；
- 标签设置、手动打标和搜索使用同一份分面显示名；
- 父标签包含后代的行为保持一致；
- 排除条件默认包含后代；
- 迁移后不再使用旧中文分类名作为机器协议。

## 9. 风险与约束

### 9.1 RAW 许可与格式覆盖

当前 RAW/HEIC 解码依赖涉及 LGPL/GPL 许可。内部使用问题较小，但对外分发前仍需完成许可确认。真实相机格式覆盖不能只依赖扩展名白名单。

### 9.2 Tauri 本地视频协议差异

不同操作系统 WebView 对自定义协议播放大视频的能力可能不同。Windows 可用不代表 macOS 和 Linux 同样稳定。若产品目标仅为 Windows，应明确冻结平台范围；若需要跨平台，应优先采用可控的 Range 媒体服务。

### 9.3 AI 成本与性能

允许数千张进入任务不代表同时请求数千张。必须通过分块、并发、限流和预算提示控制资源消耗，同时保留完整用户任务。

### 9.4 标签迁移兼容性

旧标签 ID 和 `asset_tags` 关联必须保留。迁移应增加分面和别名，不应重建整棵标签树或删除旧标签后重新创建。

### 9.5 当前工作区存在未提交改动

后续实施前应先确认现有未提交改动的归属和基线。改造过程中不能覆盖或回退用户已有代码，需要按模块逐步集成并持续回归。

## 11. 最终建议

本次改造应按以下顺序推进：

1. 先恢复入库连续选择、即时反馈和基础标签入口；
2. 统一任务状态、媒体预览和标签分面三个共享契约；
3. 再处理 RAW、视频和大批量任务的性能问题；
4. 最后完成标签治理与超级搜索的全局一致性回归。

最关键的产品原则是：

> 用户选择的内容必须完整进入任务；耗时操作必须立即给出反馈；低成本预览必须先显示；系统基础标签必须永远可用；同一个概念在入库、打标、设置和搜索中只能有一个事实来源。
