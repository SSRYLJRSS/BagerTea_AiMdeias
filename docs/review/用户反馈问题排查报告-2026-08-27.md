# 用户反馈问题排查报告（2026-08-27）

## 0. 结论先行

本次仅做代码阅读、构建/测试和外部资料调研，没有修改业务代码。

当前反馈不是一个孤立的样式问题，而是四条链路同时存在：

1. **启动白屏**：Tauri/WebView2 自身存在首屏渲染白闪风险；项目还在 Rust 窗口创建前同步初始化数据库，并在前端首屏同时触发设置加载、素材库刷新、全局任务监听。生产构建产物还使用了 `/assets/...` 绝对路径，必须优先验证，这可能导致桌面包加载资源失败。
2. **素材库滑动抽搐**：素材卡片仍然挂载 `useHoverIntent`，并在 hover 后创建视频 overlay 或固定大图 popover；这与“素材库禁止大图预览”的要求直接冲突，也是滚动时布局/图层抖动的高概率根因。
3. **主图预览串层**：`ViewerPage` 被作为 `LibraryPage` 的兄弟节点渲染，库页的 `GridToolbar + SideBar + AssetGrid` 并没有卸载或隐藏，因此查看器不是“新页面”，而是被追加到原页面布局之后，必然出现左侧筛选/回收站/标签与查看器内容同时存在、空间挤压和错位。
4. **AI 设置和标签设置难读**：AI 设置里使用了“用途绑定”“连接档案”等偏实现的术语，并把同一套连接管理重复嵌入超级搜索/打标页面；标签页又同时显示分面结构、AI 行为配置和标签管理入口，造成同一概念多处编辑、重复保存和信息架构冲突。

建议优先级：

- **P0**：确认并修复 Tauri 生产资源路径；查看器切换为真正的页面级替换；彻底移除素材库 hover 媒体预览。
- **P1**：把启动重任务移出首屏关键路径，增加可解释的局部加载态；重做 AI 连接配置的信息架构和文案；合并分面结构与 AI 行为配置。
- **P2**：补充性能埋点、真实大库滚动测试、视频编码样本和设置页可用性验收。

## 2. 问题一：启动白屏时间长

### 2.1 代码证据

#### 前端首屏同时启动多个异步链路

`src/App.tsx`：

- 第 45–48 行：挂载后启动全局任务监听 `startGlobalTaskWatch()`。
- 第 50–55 行：挂载后读取设置并应用主题。

`src/pages/LibraryPage.tsx`：

- 第 27–29 行：页面挂载后立即执行 `useLibraryStore.refresh()`。

因此首屏至少会同时产生：设置 IPC、素材列表 IPC、三类任务事件监听；`React.StrictMode` 在开发环境还会让 effect 进行额外的挂载/清理探测，导致开发环境可能出现重复请求或重复初始化观感。

#### Rust 在窗口可见前做同步工作

`src-tauri/src/lib.rs`：

- 第 19–29 行：`run()` 中同步创建数据目录、打开 SQLite、执行数据库迁移；失败直接 `panic!`。
- 第 31–33 行：同步清理旧预置标签。
- 第 44–113 行的 `setup`：读取设置、读取缓存策略、执行一次缩略图 LRU 清理、查询回收站策略、标记中断 AI 批次。
- 第 78–81 行：`ThumbnailService::cleanup_lru(max_mb)` 在 setup 中同步执行。数据量大或磁盘慢时可能直接延长窗口可见前的等待。

回收站清理本身已经放到线程中（第 93–101 行），这是正确方向；但缩略图 LRU 清理和若干数据库操作仍在 setup 主路径内。

#### 生产构建资源路径风险

当前 `vite.config.ts` 没有设置 `base: './'`。实际生成的 `dist/index.html` 包含：

```html
<script type="module" crossorigin src="/assets/index-Bw1oFxv5.js"></script>
<link rel="stylesheet" crossorigin href="/assets/index-CRLUiB7o.css">
```

Tauri 桌面资源通过自定义协议/本地资源加载，绝对根路径 `/assets/...` 在生产包中需要重点验证；如果 WebView2 将其解析成错误根路径，表现可能是长时间白屏或永远无法进入 React。该问题不能仅靠增加 spinner 掩盖。

### 2.2 为什么会白屏

需要区分两个阶段：

1. **React 尚未绘制前的白闪**：属于 WebView2/Tauri 首次创建和加载文档的已知现象，和窗口背景色、窗口可见时机有关。
2. **React 已开始但内容迟迟不完整**：由数据库迁移、setup 同步清理、资源路径错误或首屏多个 IPC 请求叠加导致。

当前项目把这两个阶段混在一起观察，所以必须用时间戳拆分：窗口创建、HTML loaded、React root render、设置 ready、素材列表 ready、首个缩略图 ready。

### 2.3 推荐方案

**第一优先：先验证生产资源路径。**

- 将 Vite 生产资源改为相对路径策略（建议验证 `base: './'`），重新打包 Tauri，打开 WebView2 控制台确认 JS/CSS 是否 404。
- 若项目后续引入路由，使用 hash 路由或确保深链接不会被本地协议当成文件路径。
- 这一步是启动正确性的门禁，不应先用动画掩盖。

**第二优先：缩短关键路径。**

- `db::init` 和必要迁移保留在后端启动，但把缩略图 LRU 清理、非关键标签整理、历史任务标记移到后台任务；只把“应用可运行所必需”的初始化留在关键路径。
- 前端先绘制 TitleBar、页面骨架和素材库 skeleton，再异步刷新设置/素材。设置加载不应阻塞主布局绘制。
- 对设置、素材列表、任务监听做一次性启动协调器，避免多个页面 effect 独立发起重复初始化。
- 生产环境去掉不必要的 `StrictMode` 双调用影响（开发环境可保留，但应在性能测量时使用 production build）。

**第三优先：优雅过渡。**

- 若 WebView2 白闪无法完全消除，采用“主窗口 `visible: false`，前端 ready 后 `show()`”或独立 splash window。
- 更推荐轻量主窗口 skeleton：深色/浅色背景与主题变量一致，显示 logo + “正在准备素材库…” + 不定进度条；设置/素材数据继续后台加载。
- 不建议无条件延迟 1–3 秒再显示窗口；应以 `DOMContentLoaded + React 首帧` 为最低条件，并设置超时兜底，避免后台任务卡死导致永不显示。

### 2.4 验收指标

- 生产包从进程启动到 React 首帧、到素材列表 ready 分别有日志时间戳。
- 无 `/assets/...` 404；JS/CSS 首次加载成功。
- 冷启动白屏（纯白背景）不可见或小于 100 ms；若设备无法达到，至少显示主题一致的 skeleton，而不是白屏。
- 窗口显示后 300 ms 内出现 TitleBar 和页面骨架；素材列表随后渐进出现。
- 数据库/缓存清理不会阻塞首帧，也不会阻塞窗口拖拽与关闭。

## 3. 问题二：素材库滚动抽搐，且仍存在被禁止的大图/视频预览

### 3.1 代码证据

`src/components/library/AssetCard.tsx`：

- 第 1–3 行注释明确写着卡片“含 300ms 悬浮预览”。
- 第 8–11 行导入 `MediaPreviewPopover`、`ImagePreviewContent`、`VideoHoverOverlay`、`getImageHoverPreview`。
- 第 61–62 行每一张卡片都调用 `useHoverIntent`。
- 第 109–116 行视频 hover 后挂载 `VideoHoverOverlay`，覆盖原卡片并创建 `<video>`。
- 第 119–123 行图片 hover 后挂载固定定位的 `MediaPreviewPopover`。
- 第 129–143 行图片 hover 会再请求 1024px 高清预览。

相关实现：

- `VideoHoverOverlay.tsx` 在挂载后尝试自动播放，并设置 5 秒播放上限；卸载时暂停并把 currentTime 归零。
- `MediaPreviewPopover.tsx` 使用 `position: fixed; z-index: 40`，并通过 `getBoundingClientRect()` 计算位置。
- `mediaPreview.ts` 维护 1024px hover 缓存；`getVideoProxyPreview` 虽返回 null，但卡片内仍直接播放原视频。

### 3.2 抽搐/错位的成因

1. **滚动期间 hover 状态频繁切换**：虚拟列表会不断挂载/卸载行和卡片，300 ms 进入、350 ms 离开定时器会与滚动事件交错。
2. **媒体元素改变合成层**：视频 overlay 是绝对定位覆盖层，创建和销毁 `<video>` 会触发解码、纹理上传和合成层变化。
3. **固定大图浮层脱离网格坐标系**：popover 用 fixed 坐标计算，滚动/重排时触发重新测量；它可能短暂出现在旧卡片位置，形成“图层错位”。
4. **高清预览 IPC 与虚拟化竞态**：一个卡片刚触发 1024px 请求就被滚出视口，Promise 完成后仍可能让旧浮层渲染；虽然图片内容有局部取消，但卡片/浮层层级本身仍在变化。
5. **产品要求与实现相反**：用户已经明确不允许素材库大图预览，但当前代码仍保留图片 popover 和视频短播 overlay，说明“禁止预览”的约束没有落实到组件边界。

### 3.3 推荐方案

**立即处理（P0）：素材库卡片只保留缩略图和轻量角标。**

- `AssetCard` 删除 hover intent、`MediaPreviewPopover`、`ImageHoverContent`、`VideoHoverOverlay` 及 `getImageHoverPreview` 依赖。
- 素材库内不创建 `<video>`，不请求 1024px hover 图；只使用 `Thumbnail` 的占位图 + 视口内高清缩略图。
- 保留文件名渐变层、选中态、视频时长/格式角标；双击才进入 Viewer。
- `src/components/media/*Hover*` 和 `src/api/mediaPreview.ts` 如果没有其他消费者，应在后续代码清理阶段删除；若暂不删除，至少确保没有任何素材库入口调用。

**保留并强化已有的正确机制。**

- `Thumbnail.tsx` 已有 IntersectionObserver、模块级缓存和 generation 保护，这套机制适合网格缩略图；不要把高清尺寸扩大到 hover 大图。
- 继续使用 `AssetGridView` 的行级虚拟化，先通过运行时复现确认是否还有其他串图，再考虑调整 overscan 或估算高度。
- 所有异步缩略图请求继续使用 assetId + generation，禁止通过“整行动态 key”强制 remount 来掩盖问题。

### 3.4 验收指标

- 快速滚动时 DOM 中不存在素材库 `<video>` 和 fixed 大图 popover。
- 连续滚动 30 秒，卡片尺寸、网格行位置、滚动条位置无跳动；无旧图闪入新卡片。
- 只有进入 Viewer 后才加载高清主图/视频源。
- 通过浏览器元素检查或自动化测试确认 `MediaPreviewPopover`、`VideoHoverOverlay` 不在素材库渲染树中。

## 4. 问题三：进入主图预览后左侧素材库筛选、回收站等内容仍然出现并错位

### 4.1 代码证据

`src/pages/LibraryPage.tsx`：

- 第 56–62 行始终渲染 `GridToolbar`、`SideBar`、`AssetGrid`。
- 第 75 行在同一个父级中追加 `{preview && <ViewerPage ... />}`。

这意味着 Viewer 打开后，素材库并没有被替换；它只是成为 `LibraryPage` 的另一个子节点。

`ViewerShell.tsx`：

- 第 20–30 行自身使用 `h-full min-h-0 flex flex-col`，内部再放工具条、左属性栏、媒体舞台和胶片条。

当它被放在已经包含库页工具栏和侧栏的父级中时，会同时争抢高度。Viewer 内部的 280px 左栏也会和库页的 224px 左侧栏并列/串接，形成用户看到的“全部标签、回收站、分辨率方向旋转等撞在一起”。

### 4.2 推荐方案

查看器必须是**页面级模式切换**，不是库页内容追加。推荐两种等价实现：

```text
App
 ├─ TitleBar（始终保留）
 └─ main
     ├─ LibraryPage（preview = null 时）
     └─ ViewerPage（preview != null 时，替换 LibraryPage 内容）
```

或在 `LibraryPage` 内部：

```text
return preview
  ? <ViewerPage asset={preview} onClose={...} />
  : <LibraryContent ... />
```

必须满足：

- Viewer 打开时卸载 `GridToolbar`、`SideBar`、`AssetGrid` 和库页上下文操作条。
- TitleBar 是否保留：建议保留，符合当前 Viewer 注释“标题栏始终可见”的设计。
- 底部全局 `BottomBar`：建议在 Viewer 模式隐藏，避免与 ViewerFilmstrip 双重导航；若产品必须保留，则明确只保留返回库页，不显示库页高亮和双击搜索行为。
- Viewer 自己负责 `ViewerToolbar + ViewerInfoSidebar + MediaViewport + ViewerFilmstrip`，左栏只显示当前素材属性/标签，不显示素材库筛选项。
- 关闭 Viewer 后恢复库页筛选、滚动位置和选中态；不要重新挂载导致用户上下文丢失。

### 4.3 验收指标

- 双击卡片进入 Viewer 后，页面中不存在“素材筛选、全部、回收站、标签树”等库页元素。
- Viewer 左栏只包含当前素材详情；媒体舞台和胶片条占据剩余空间，不被库页侧栏挤压。
- Esc/关闭按钮返回库页，原筛选条件、滚动位置和选中状态可恢复。
- 窄窗口下不出现双滚动条、内容叠层或胶片条被底栏遮挡。

## 5. 问题四：AI 设置说明文字出现横线穿过/不在框内

### 5.1 代码证据与直接原因

`src/pages/SettingsPage.tsx` 的 `AiPurposePanel`：

- 第 565 行开始由 `Group` 生成带边框容器。
- 第 580–582 行在线服务说明使用 `className="-mt-2 px-4 ..."`。
- 第 632–634 行本地服务说明同样使用 `-mt-2`。

`Group` 在第 648–655 行对 children 外层使用 rounded border。说明文字的 `-mt-2` 会把段落向上拉，视觉上覆盖到 Group 的上边框，因此用户看到横线穿过文字或文字像“不在框里”。这不是字体问题，而是负外边距和边框层叠造成的布局错误。

此外，通用 `Field`（第 659–667 行）采用左右两列且右侧 `shrink-0`。在窗口较窄或说明文本较长时，左侧会被压缩，进一步增加换行和边框碰撞概率。

### 5.2 推荐方案

- 说明文字改成 Group 内部的普通说明区：`px-4 py-3 bg-surface`，不要使用负 margin。
- 说明区与字段列表之间用明确的 border-bottom 或间距分隔，说明文本不参与字段行的 flex 对齐。
- `Field` 在窄窗口下改为响应式：宽屏左右两列，窄屏上下两行；控件允许 `min-width: 0`。
- 文字改为用户语言，例如“用于理解素材内容的在线服务”“仅在本机处理，不会上传素材”，把协议、keyring 等技术细节折叠到“高级信息”。

### 5.3 验收指标

- 1366×768、960×640（项目最小窗口）下说明文字不压线、不溢出、不被控件遮挡。
- 在线/本地切换时说明区高度平滑变化，不造成整个设置页跳动。
- 所有表单行在缩窄窗口下仍可读，按钮不被挤出可视区。

## 6. 问题五：AI 配置表达混乱，“用途绑定/连接档案”不符合用户心智

### 6.1 当前实现的问题

`AiPurposePanel`（第 538 行以后）对“超级搜索 AI”和“打标 AI”分别渲染一套配置。在线模式中又叠加：

1. “部署方式”单选；
2. “使用云端 API……连接档案统一管理”说明；
3. `UsageBindingLine` 的“用途绑定”下拉；
4. `AiConnectionManager` 的“连接档案”列表；
5. 连接列表中的协议、地址、模型、密钥和测试连接。

结果是同一套服务配置被拆成“用途绑定”和“连接档案”两个用户不熟悉的概念，并且每个 AI 子页重复出现连接列表。用户难以回答“我到底在哪里选择服务？模型在哪里改？搜索和打标是否共用？”

`AiConnectionManager.tsx` 还存在几个可用性风险：

- 第 149–154 行直接把“连接档案”作为主要标题和解释，术语偏实现。
- 第 264–265 行协议选项使用 `/chat/completions`、`/messages`，但没有解释“什么时候选哪一个”。
- 第 186–187 行把地址、模型、密钥状态全部压成一行，信息密度过高。
- `AiPurposePanel` 的 `deployment` 只是组件 state（第 560 行），没有看到与 Settings 持久化绑定的明确字段；重新进入页面可能回到默认推断状态。
- `AiConnectionManager` 只在在线模式分支中渲染；本地连接若也需要统一模型/端点管理，当前入口不一致。

### 6.2 外部产品可借鉴的结构

调研到的 CC Switch 采用“提供商配置是唯一实体，再选择同步到哪些应用”的结构；其高级选项才展开协议、完整 URL、模型映射等技术字段。Hermes/CC Switch 的 provider preset 也把名称、base URL、API key、API mode、模型列表集中在一个清晰的 provider 表单中。

适合本项目的简化结构：

```text
AI 设置
 ├─ 超级搜索
 │   ├─ 服务：跟随默认 / 选择一个服务
 │   ├─ 模型
 │   └─ 高级：协议、超时、失败降级
 ├─ 自动打标
 │   ├─ 服务：跟随默认 / 选择一个服务
 │   ├─ 模型
 │   └─ 打标策略：时机、视频、批次
 └─ 服务管理（唯一入口）
     ├─ 在线服务：名称、地址、模型、API 密钥、测试
     └─ 本地服务：引擎地址、模型、检测状态
```

面向用户的替换文案建议：

| 当前文案 | 建议文案 |
|---|---|
| 连接档案 | AI 服务 / 服务配置 |
| 用途绑定 | 此功能使用的服务 |
| 部署方式 | 服务位置：在线 / 本机 |
| 使用云端 API…… | 通过在线服务分析素材；素材是否上传取决于所选服务 |
| API 密钥保存到系统凭据 | API 密钥会安全保存在 Windows 凭据管理器中 |
| 接口协议 | API 格式（高级） |

### 6.3 推荐改法

- 服务配置只维护一份；超级搜索/自动打标只选择服务，不重复渲染服务列表。
- “此功能使用的服务”默认项为“跟随默认服务”，用户需要独立服务时再选择。
- 把服务管理移到 AI 设置顶部或独立“服务管理”页，支持新增、编辑、测试、删除。
- 默认折叠协议/完整 URL/模型映射；普通用户只看到服务名称、地址、模型、密钥状态和“测试连接”。
- 在线/本机切换必须持久化，并在切换时只显示相关字段；不要仅依赖组件 `useState` 推断。
- 每个功能页顶部显示当前实际生效配置摘要：“自动打标：本机 · Qwen2.5-VL · 已连接”。
- 删除危险操作前显示使用该服务的功能数量，而不是只显示“清除用途绑定”。

### 6.4 验收指标

- 新用户在 10 秒内能完成“添加服务 → 测试 → 选择给自动打标使用”。
- 搜索与打标可共用同一服务，也可独立选择；修改服务详情不会复制出第二份配置。
- 页面中不再出现用户无法理解的“连接档案/用途绑定”主标题；技术术语只在高级信息出现。
- API key 永不回显，错误信息可操作（地址错误、鉴权失败、模型不存在分别说明）。

## 7. 问题六：标签与分类、封面结构、AI 行为配置重复且职责不清

### 7.1 当前实现的重复入口

`SettingsPage.tsx` 的 `route === "tags"` 区域（第 324 行以后）同时渲染：

1. `FacetManagePanel`（第 327–329 行）：分面结构管理；
2. “AI 行为配置”说明（第 331–337 行）；
3. `draft.aiFacetConfigs` 的 details 列表（第 339–378 行）：提示词、显示名、AI 参与、工作台显示；
4. “分类词条”卡片和 `TagManageDialog` 入口（第 380–389 行）。

而 `FacetManagePanel.tsx` 文件头部又明确写着“AI 覆盖设置仍在 SettingsPage 的 aiFacetConfigs 单独维护，本组件不重复存结构”。这说明当前代码虽然注释声称要统一，但实际仍然是三套视觉入口：分面结构、AI 行为、标签词条。

### 7.2 为什么用户会看不懂

- “封面结构管理/分面结构管理”定义的是分类大类；“AI 行为配置”又重复列出同一个 facet key；用户不知道哪个是事实源。
- 提示词 hint、显示名覆盖、是否参与 AI 与分面本体规则（单选/多选、适用媒体）分散在不同层级。
- 标签词条通过对话框另开，用户无法在同一上下文看到“这个分面有哪些词条、哪些素材引用、AI 如何使用”。
- 保存按钮是页面底部统一保存，但分面 CRUD/标签治理/连接管理又各自即时写后端，保存语义不一致。

### 7.3 推荐的信息架构

设置页只保留一个“标签与分类”入口：

```text
标签与分类
 ├─ 分类列表（唯一事实源）
 │   ├─ 显示名、稳定 key、适用媒体、单选/多选、状态
 │   └─ 展开详情
 │       ├─ 基本规则：描述、选择模式、最大数量、适用范围
 │       ├─ AI 行为：是否参与 AI、给 AI 的说明、工作台显示
 │       └─ 分类词条：搜索、新建、重命名、别名、合并、停用
 └─ 统一保存/即时操作说明
```

规则：

- `tag_facets` 是分面结构唯一事实源；`tags` 是分面下词条唯一事实源。
- AI 行为只保存对 `facet_key` 的覆盖，不重复保存 selection mode/max/description。
- 创建、重命名、停用、合并、迁移都显示影响范围；有历史引用时默认软停用。
- 普通显示名可以修改，稳定 key 创建后锁定；历史查询和已有标签不受显示名修改影响。
- 如果保留标签管理对话框，它只能作为“分类词条”的二级编辑器，不再作为另一个顶层设置体系。
- 明确区分“即时治理操作”（创建/停用/合并）和“页面草稿保存”（AI 行为偏好），避免用户误以为所有操作都等到页面底部才生效。

### 7.4 验收指标

- 一个 facet 的结构和 AI 行为可以在同一个详情区域完成配置。
- 页面上同一 facet key 只出现一次主编辑入口。
- 修改显示名不会改变历史标签、搜索公式或 AI 结果。
- 停用/合并前显示标签数、素材数、历史查询数和 AI 配置数。

## 8. 需要一并检查的全局冲突

1. **旧注释/产品术语未同步**：`src-tauri/src/lib.rs` 顶部仍写着“AI/网盘命令注册”，但当前用户已经不需要网盘；应在正式实施阶段清理注释、README、导出类型和命令注册的残留描述。
2. **Viewer 与底栏职责冲突**：Viewer 自带胶片条，App 仍无条件渲染全局 BottomBar；需要明确 Viewer 模式下的导航策略。
3. **启动初始化职责分散**：App、LibraryPage、ImportPage、SettingsPage 都可能各自触发 settings load；应统一为 store 层 single-flight，避免多个页面重复加载。
4. **性能测量缺失**：当前单元测试通过不能证明滚动不卡顿；必须补浏览器 Performance/录屏数据和真实素材样本。
5. **异步资源状态需要统一**：缩略图已有缓存和代际保护，但 hover 预览又维护另一套缓存；删除 hover 预览后应确认没有遗留请求入口和无用缓存。
6. **生产包与开发环境差异**：Vite dev server 使用 `http://localhost:1420`，生产包使用 Tauri asset protocol；白屏问题必须在 `tauri build` 产物中复现，不能只看 `npm run dev`。
