## §0 给施工 AI 的十二条铁律

违反任何一条都要返工，请在每次提交前对照。

| # | 铁律 | 为什么 |
|---|---|---|
| 1 | **一个波次内，一个文件只能有一个 owner。** 见 §2 文件所有权表 | 上一轮交付就是因为多波次并行改同一文件产生了隐性冲突 |
| 2 | **`COLUMNS` 是位置映射，新列只能追加末尾。** 插中间会静默数据错位 —— 编译和测试都不报错，只在运行时数据错乱 | `assets.rs` / `tag_facets.rs` 的 `from_row` 按索引读 |
| 3 | **改 FTS 触发器必须：① 复制现有 SQL 再改 ② 改完立即 `INSERT INTO assets_fts(assets_fts) VALUES('rebuild')` ③ 先在内存库跑通全部 FTS 测试再上真库** | V21 的注释里记着两个实测坑 |
| 4 | **DB 写操作短暂持锁；网络/解码放锁外** | 长持锁会饿死列表和打标 |
| 5 | **`PRAGMA foreign_keys=ON` 是全部 CASCADE 的前提**（`db/mod.rs:31`），不许关 | — |
| 6 | **删除标签关联必须先删 `asset_tags` 再删 `tags`** | 让 FTS 触发器有机会跑 |
| 7 | **手工覆盖必须清 `source_batch_id`** | 否则撤销 AI 批次会误删手工标签 |
| 8 | **数据库约束不因功能报错而回退。** 约束报错说明有路径在写非法数据 → 修那条路径 | 见 §14 止损线 3 |
| 9 | **绝不双写 `tag_aliases` 与 `tag_terms`。** `schema_features` 是唯一开关 | 双写必然漂移 |
| 10 | **永不覆盖人工确认的标签。** `review_state IN ('ai_reviewed','manual')` 的行任何重跑都不动 | — |
| 11 | **系统不改写用户明确表达的语义。** 库统计和 Fuzzy 结果只能建议，要用户点了才改条件 | — |
| 12 | **每个任务必须带测试。** 测试要断言**真实值**，不许只断言 `is_ok()` 或不 panic；不许留松弛区间（如上限 1500 却断言 ≤1600）；不许绕过要验证的代码路径 | 上一轮有 10 处假绿，其中 3 处直接掩盖了 P0 |

### 每个任务的完成标准（三条都要满足）

1. **代码改完**，且改动范围不超出任务卡片里列的文件
2. **测试写完并通过**，测试名与卡片一致（便于交叉检查）
3. **四关全绿**：`npm run typecheck` / `npm run test:unit` / `cd src-tauri && cargo test` / `npm run build`

### 遇到以下情况停下来问，不要硬推

- 卡片里的「现状」与你读到的代码不符（说明基线变了）
- 需要改卡片没列的文件
- 测试写不出来（通常说明设计有洞）
- 触发 §14 任何一条止损线

### R0-1 JPG 拍摄时间解析

| 项 | 内容 |

  BEFORE UPDATE OF parent_id ON tags
  WHEN new.parent_id IS NOT NULL AND EXISTS (

      UNION ALL

#### F3-b `next_prefix` 纯函数

```rust
/// 计算字典序的「下一个前缀」，作为范围查询的开区间上界。
/// 不变式：所有以 prefix 开头的字符串 s 都满足 prefix <= s < next_prefix(prefix)。
///
/// ⚠ 不能用 `prefix + '\u{FFFF}'` —— 实测 UTF-8 下 U+1F600（😀）字节序大于 U+FFFF，
///   那样会漏掉所有含 emoji 的标签。SQLite 侧验证：
///   SELECT ('a'||char(0x1F600)) < ('a'||char(0xFFFF));  → 0
pub fn next_prefix(prefix: &str) -> Option<String> {
    let mut chars: Vec<char> = prefix.chars().collect();
    while let Some(last) = chars.pop() {
        let mut cp = last as u32 + 1;
        while cp <= 0x10FFFF {
            if let Some(c) = char::from_u32(cp) {   // 自动跳过 surrogate
                let mut out: String = chars.iter().collect();
                out.push(c);
                return Some(out);
            }
            cp += 1;
        }
        // 该字符已到顶 → 丢掉它，对前一个字符继续
    }
    None   // 空串或全是 char::MAX → 无上界，调用方只用下界
}
```

**十一个必测边界**（我已实测全部通过）：

| 输入 | 期望 | 说明 |
|---|---|---|
| `"term123"` | `Some("term124")` | ASCII |
| `"青"` | `Some("靓")` | 中文 |
| `"海边"` | `Some("海辺")` | 只改最后一个字符 |
| `"😀"` | `Some("😁")` | emoji（BMP 外） |
| `"a😀"` | `Some("a😁")` | 混合 |
| `"\u{FFFF}"` | `Some("𐀀")` | **跨越 BMP 边界** |
| `"a\u{FFFF}"` | `Some("a𐀀")` | 同上 |
| `"\u{10FFFF}"` | `None` | char::MAX |
| `"a\u{10FFFF}"` | `Some("b")` | 末字符到顶 → 前一个递增 |
| `"\u{D7FF}"` | `Some("\u{E000}")` | **跳过 surrogate** |
| `""` | `None` | 空串 |

### S2 `Ranking::Relevance` + RRF 融合（0.75 天）

```rust
#[derive(Debug, Clone, Copy, Serialize, Deserialize, Default)]
pub enum Fusion {
    /// 默认：RRF（Reciprocal Rank Fusion）—— 只用排名不用原始分数。
    /// score = Σ weight_i / (60 + rank_i)，k=60 是业界常用值。
    /// 天然免疫「bm25 是负数、should 加分是任意正数」这个量纲问题。
    #[default]
    Rrf,
    /// 线性加权：各路得分 min-max 归一到 [0,1] 后加权求和。可选项
    Linear,
}
```

**为什么默认 RRF**：bm25 返回负值（越小越相关）、should 加分是任意正数、
别名命中是 0/1 —— 三者的**排名**可比，**分数**不可比。RRF 只用排名，
不需要知道任何一路的分数范围或分布。这是最稳的默认。

最终得分：`final_score = should_score 的 RRF + Σ retriever 的 RRF`
（should 的加权得分也转成排名参与 RRF，保证量纲统一）。

**FTS bm25 实测可用**（我验证过）：
```
bm25 可用: [(2, -1.06e-6), (1, -8.95e-7)]     ← 负值，越小越相关
bm25 带权重: -1.27e-6                          ← bm25(t, 2.0) 形式也支持
```

测试：**`rrf_fusion_is_scale_invariant`**（把某一路得分全乘 100，排序不变）/
`relevance_ranking_orders_by_should_score` /
`field_ranking_overrides_relevance`（用户显式选排序字段时不用相关度）

必须 vs 加分的判断：
- 「一定要有 / 只要 / 必须」→ concepts（必须）
- 「不要 / 排除 / 除了」→ exclusions（排除）

#### evidence 一致性守卫（三级校验）

**不匹配固定词表**（「有蓝天更好」「蓝天可有可无」「尽量有」都不含表内词），

### C-1 色板关系表（V23，1 天）

```sql
CREATE TABLE asset_palette_colors (
  asset_id     INTEGER NOT NULL REFERENCES assets(id) ON DELETE CASCADE,
  rank         INTEGER NOT NULL,        -- 0 = 主色，按 ratio 降序
  color_bucket INTEGER NOT NULL,        -- 色名分桶，与 colorNameZh 分段一一对应
  ratio        REAL    NOT NULL,        -- 该色占比 0..1
  PRIMARY KEY (asset_id, rank)
);
CREATE INDEX ix_apc_bucket ON asset_palette_colors(color_bucket, rank, asset_id);
```

**为什么关系表而不是字符串列**：`LIKE '%,红,%'` 的查询计划是 `SCAN`（实测）。
但更重要的是**表达力** —— `ratio` 和 `rank` 是字符串方案根本表达不了的维度。
实测 30 万行规模上 LIKE 全表扫 72ms、关系表覆盖索引 49ms，性能差别要更大规模才明显。

**四种查询自然表达**（实测查询计划全部走覆盖索引）：

| 需求 | SQL |
|---|---|
| 主色是红 | `bucket=红 AND rank=0` |
| **前三色含红** | `bucket=红 AND rank<3` |
| 画面中有红 | `bucket=红`（不限 rank） |
| **红占比 >20%** | `bucket=红 AND ratio>0.2` ← 字符串方案完全无法表达 |
| 同时含红和蓝（前三色） | 两个子查询 `INTERSECT` |

**三个新 metadata key**（对应三种 rank 范围）：
`palette_dominant`（rank=0）/ `palette_top3`（rank<3）/ `palette_any`（不限）。
值域是色名（走 enum，`in` 支持多选）。

### C-2 AST 感知命中诊断（0.5 天）

```rust
/// 单个条件（AST 叶子）的诊断。path 是从根到该叶子的索引路径。
pub struct LeafDiagnostic {
    pub path: Vec<usize>,
    pub label: String,
    /// ① 该条件单独执行的命中数
    pub self_count: i64,
    /// ② 完整表达式的命中数（所有叶子共享同一个值）
    pub result_count: i64,
    /// ③ 把该叶子从 AST 中移除后的命中数
    pub count_without_leaf: i64,
    /// ④ delta = count_without_leaf - result_count
    ///    AND 下为正（砍掉多少）；OR 下为负（贡献多少）；NOT 下反转。
    ///    这是唯一在三种节点下都有意义的量
    pub delta: i64,
}
```

**为什么 `delta` 在三种节点下都成立**：

| 场景 | `self_count` | `result_count` | `count_without_leaf` | `delta` | 解读 |
|---|---|---|---|---|---|
| `A AND B`，看 B | 50 | 10 | 100 | **+90** | B 砍掉了 90 |
| `A AND B`，B 砍空 | **0** | **0** | 100 | **+100** | **B 是罪魁祸首** |
| `A OR B`，看 B | 50 | 120 | 100 | **−20** | B 多带来 20 |
| `NOT B` | 50 | 360 | 410 | **+50** | 排除了 50 |

**UI 规则**：
- `delta > 0` 且 `result_count == 0` → 标红「这个条件把结果砍到 0」
- `delta > 0` → 显示「−90」（灰色）；`delta < 0` → 显示「+20」
- `self_count == 0` → 额外标注「这个条件单独就没有匹配项」
  （**区分「条件本身无效」和「与其他条件冲突」** —— 这是很重要的区分）

**should 的诊断不同**：should 不淘汰结果，`delta` 恒为 0 或负。
对 should 显示「命中该加分项的素材数 / 结果总数」（如「蓝天：12 / 106」）。

**成本**：N 个叶子 = N（self）+ N（without）+ 1（result）= 2N+1 次 COUNT。
5 个条件 = 11 次。410 行微秒级；3 万素材需探针（R2-5）。
debounce 300ms，与主查询并行（不阻塞结果渲染）。

测试：`diagnostic_delta_identifies_zeroing_leaf` /
`diagnostic_self_count_zero_is_distinguished` /
**`diagnostic_works_under_or_and_not`**（断言上表四行）/
`diagnostic_should_shows_hit_ratio`

## §17 给施工 AI 的最后叮嘱

**这份文档的每个数字都是实测出来的，不是估的。** 如果你读代码时发现与
「现状」描述不符，**先停下来问**，因为那意味着基线变了，后面的设计可能也要调。

几个最容易踩的坑，按被踩概率排序：

1. **`COLUMNS` / `FACET_COLS` 插中间** —— F1 要给 `tag_facets` 加五列，
   给 `assets` 加 `review_state`。**追加末尾，然后逐个数 `r.get(N)` 的索引**。
   这个错误编译和测试都不报警，只在运行时数据错乱。
2. **改 FTS 触发器忘了 `rebuild`** —— F4 要改 6 个触发器的聚合子查询。
   改完立即 `INSERT INTO assets_fts(assets_fts) VALUES('rebuild')`。
3. **`merge_preserve_alias` 的顺序** —— 必须先删源 terms 再给目标加别名。
   反了会 `UNIQUE constraint failed`，而且这个错误只在「源和目标有同名词」时出现，
   容易漏测。
4. **`Prefix` 用了 `LIKE 'x%'`** —— 实测不走索引。必须 `>= :lo AND < :hi`，
   `:hi` 由 `next_prefix` 算。测试 `term_match_prefix_uses_index` 会抓住这个。
5. **`next_prefix` 拼 `U+FFFF`** —— 会漏掉所有含 emoji 的标签。
   用文档里给的实现，别自己想。
6. **测试断言写弱了** —— 上一轮有 10 处假绿，其中 3 处直接掩盖了 P0。
   每写一条测试问自己：「如果我把被测代码删掉，这条测试会失败吗？」
7. **`review_state` 回填写错** —— 那 72 条是用户真实确认过的标签。
   回填逻辑必须按 `ai_suggestion_items.decision IN ('accepted','modified')` 判定，
   并且有 `v22_backfill_marks_existing_confirmed_as_reviewed` 守护。
