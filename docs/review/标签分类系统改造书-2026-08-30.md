## 2. 需求还原

把你的话逐条翻译成可验收的需求：

| 编号 | 你的原话（要点） | 需求 |
|---|---|---|

## 3. 根因诊断：为什么现在会复杂、会出 bug

### 3.1 双源是万恶之源（这是最关键的一条）

一个分面的属性**被劈成两半存在两个地方**：

```
tag_facets 表（SQLite）                  settings.app_settings JSON
├─ key            ← 机器协议            ├─ facetKey        ← 外键（字符串，无约束）
├─ display_name   ← 用户可改            ├─ displayName     ← 又一个显示名（覆盖上面那个）
├─ description    ← 给人看的说明        ├─ hint            ← 给 AI 看的说明
├─ selection_mode                       ├─ enabledForAi    ← 是否参与 AI
├─ max_items                            └─ visibleInWorkbench ← 是否显示在工作台
├─ applies_to
├─ sort_order / is_system / status
```

由此直接派生出的问题：

1. **两个保存通道**。`FacetManagePanel` 里「基本规则」点按钮即时写 DB，「AI 行为」进设置草稿等页面「保存设置」。用户改完一半切走 → 丢一半。代码里为此打了补丁（名称/说明失焦自动保存），但语义仍然分裂。
2. **两个显示名**。`build_prompt_context()` 里 `cfg.display_name` 覆盖 `dbf.display_name`。用户在两个地方都能改名，结果不一致时以谁为准要看代码。
3. **孤儿条目**。`aiFacetConfigs` 是 JSON 数组，`facetKey` 没有外键约束。删除/重命名分面时它不会跟着变。`build_prompt_context()` 靠「DB 里查不到就 skip」兜底，`FacetManagePanel` 靠「缺条目就补建」兜底 —— 两处兜底代码都是双源的税。
4. **缺条目 = 静默不参与 AI**。`build_prompt_context()` 只遍历 `ai_facet_configs`。历史库里某个分面没有对应条目，它就永远不进 AI 提示词，而 UI 上看不出异常。为此又加了 `seed_ai_config()`。

**结论：这四个 bug 类别全部会随「用户自建分面」放大。必须先合表，再谈其他。**

### 3.2 `description` / `hint` 的区分是伪需求

当前语义：`description` = 给人看的背景（「识别画面中可辨认的主体物件」），`hint` = 给 AI 的约束（「只写可观察到的主要物体，不写推测身份」）。

实际上这两句话是**同一件事的两种措辞**。让用户填两遍，结果就是：多数人只填一个，另一个空着；而 AI 提示词只读 `hint`，`description` 从来没进过提示词（已确认：`ai_cloud.rs build_prompt()` 只用 `c.hint`，`c.description` 字段在 `FacetPromptContext` 里但没被消费）。

你的判断是对的：合并。

### 3.3 `enabledForAi` + `visibleInWorkbench` 两个布尔表达不了「手工分类」

现状是两个独立开关，四种组合里有两种是无意义的：

| enabledForAi | visibleInWorkbench | 含义 | 有意义吗 |
|---|---|---|---|
| ✅ | ✅ | AI 打 + 人工可改 | 有 |
| ❌ | ✅ | 只手工填（用途/评分） | 有 |
| ✅ | ❌ | AI 打了但人看不到、改不了 | **无意义，且危险** |
| ❌ | ❌ | 存在但完全不可用 | 无意义（等于停用） |

用两个布尔表达一个三态选择，用户要理解笛卡尔积。改成单枚举后，UI 从两个 checkbox 变成一个分组归属，而且不可能落到无意义状态。

### 3.4 前端还有三处硬编码分面清单，直接和 R1 冲突

`src/stores/tagStore.ts`：

| 常量 | 内容 | 与 R1 的冲突 |
|---|---|---|
| `BASE_FACET_DEFAULTS` | 10 个系统分面的显示名/描述/single/max **副本** | 用户改了 DB 里的值，这份副本不会变；`buildWorkbenchFacets` 里 `f?.maxItems ?? base.maxItems` 会在 DB 值为 null 时回退到硬编码的 5 |
| `WORKBENCH_DEFAULT_KEYS` | 7 个 key 的白名单 | 用户新建分面走 `BASE_FACET_KEYS.includes(key) ? ... : true` 的 else 分支才默认显示 —— 逻辑正确但绕 |
| `keyForLegacyName` | 中文名 → key 的 map（26 条） | 用户建的中文分面名不在 map 里，`normalizeTagKeys` 会把它归 `custom`。**这是 R1 最直接的破坏点** |

`buildWorkbenchFacets` 还有一个更隐蔽的问题：它遍历的是 `BASE_FACET_KEYS`（前端常量），**不是**后端返回的 facets。所以后端删掉一个系统分面，前端照样渲染它（用硬编码默认值）。

### 3.5 只能停用不能删除 = 你担心的残留

`deactivate()` 只把 `status` 改成 `inactive`。残留物：

- `tags` 表里该分面下的标签还在（`facet_key` 指向一个 inactive 分面）
- `asset_tags` 关联还在 → FTS 里 `tag_names` 还在（因为触发器只看 `tags.status`，不看 `tag_facets.status`）→ **停用的分面下的标签仍然能被全文搜到**
- `settings.aiFacetConfigs` 里的条目还在
- `ai_suggestion_items.facet_key` 还指向它
- `tag_ops` 流水还在

对「暂时不想用」这是正确的（保留历史）。但对「建错了想删掉」，用户拿不到干净状态。

## 4. 目标架构：一张表、一段话、两个组

三条设计决定，其余全部从它们推导：

### 决定一：`tag_facets` 成为分面的唯一存储，`aiFacetConfigs` 彻底废弃

分面的**全部**属性都在 `tag_facets` 一张表里。`settings.app_settings` 里不再有任何分面相关字段。

好处：一个保存通道（后端事务）、一个显示名、不可能有孤儿条目、不可能有「缺条目静默不参与 AI」。

### 决定二：`description` 一个字段，同时给人和给 AI

`hint` 字段删除。`description` 既显示在设置页（label：**「这类标签是什么」**）、也整段进 AI 提示词。

UI 提示文案改为引导用户写「AI 能照着做」的说明：

> 例：「画面中可辨认的主要物体，只写看得见的实体，不写推测的品牌或身份」

### 决定三：`input_mode` 单枚举替代两个布尔

```
input_mode = 'ai_and_manual'   -- AI 自动打标（人工可复核修改）
           | 'manual_only'     -- 只手工填写（AI 完全不碰）
```

| 场景 | input_mode | AI 提示词 | 打标工作台 | 素材库侧栏 | 超级搜索 |
|---|---|---|---|---|---|
| 主体/场景/风格… | `ai_and_manual` | ✅ 进 | ✅ 显示（AI 组） | ✅ | ✅ |
| 用途/评分/客户/授权状态… | `manual_only` | ❌ 不进 | ✅ 显示（手工组） | ✅ | ✅ |

**关键：`manual_only` 只影响「AI 是否产出」，不影响「能不能筛、能不能搜、能不能手填」。** 这正是你要的语义。

### 4.1 最终 `tag_facets` 表结构

```sql
CREATE TABLE tag_facets (
  key            TEXT PRIMARY KEY,   -- 稳定机器 key，创建后永久锁定
  display_name   TEXT NOT NULL,      -- 「分类名称」，可随时改
  description    TEXT NOT NULL DEFAULT '',
                                     -- 「这类标签是什么」，同时给人和 AI（合并原 description + hint）
  input_mode     TEXT NOT NULL DEFAULT 'ai_and_manual',
                                     -- ai_and_manual | manual_only（替代 enabled_for_ai + visible_in_workbench）
  selection_mode TEXT NOT NULL DEFAULT 'multi',   -- single | multi
  max_items      INTEGER,            -- multi 时的上限；NULL = 不限；single 恒为 1
  applies_to     TEXT NOT NULL DEFAULT 'all',     -- all | image | video
  sort_order     INTEGER NOT NULL DEFAULT 0,
  is_system      INTEGER NOT NULL DEFAULT 0,      -- 系统分面不可物理删除
  status         TEXT NOT NULL DEFAULT 'active',  -- active | inactive
  created_at     INTEGER NOT NULL,
  updated_at     INTEGER NOT NULL,
  CHECK(input_mode IN ('ai_and_manual','manual_only')),
  CHECK(selection_mode IN ('single','multi')),
  CHECK(status IN ('active','inactive')),
  CHECK(applies_to IN ('all','image','video'))
);
```

变化：**新增 `input_mode`；删除 `hint`（原在 JSON 里）；删除 `enabled_for_ai` / `visible_in_workbench`（原在 JSON 里）**。

### 4.2 用户可编辑项：从 9 个压到 6 个

| 现在（分散在两处，9 项） | 改造后（一处，6 项） |
|---|---|
| 分类名称 | ① **分类名称**（必填） |
| 稳定 key（只读展示） | ② **英文标识**（创建时可改，之后只读） |
| 给人的说明 | ③ **这类标签是什么**（合并了原「给人的说明」+「给 AI 的识别规则」） |
| 给 AI 的识别规则 | ↑ |
| 参与 AI 打标与搜索（checkbox） | ④ **归类**：AI 自动打标 / 只手工填写（单选） |
| 在打标工作台显示（checkbox） | ↑ |
| 单选 / 多选 | ⑤ **可选几个**：只能选 1 个 / 可多选（上限 N，留空不限） |
| 数量上限 | ↑ |
| 适用媒体 | ⑥ **适用于**：全部 / 只图片 / 只视频（**折叠在「高级」里**，默认全部） |

## 5. 行业对照

> 说明：本轮受网络访问限制，未能抓取到一手文档页面。以下为基于既有知识的对照，标注了确定性。**实施前建议就 §5.2 的删除语义再查一次一手文档。**

### 5.1 稳定 key vs 显示名（确定）

三种主流做法：

| 做法 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| 不透明 id（`fld_xxx` / UUID） | Airtable、Notion 的 property id | 绝对稳定，改名零成本 | **AI 提示词里毫无语义** —— 模型看到 `fld_a1b2` 不知道该填什么 |
| 用户可见 slug（`people_clothing_color`） | GitHub label、Jira custom field key、Hugo/Jekyll taxonomy | AI 可读、可写文档、可调试 | 用户可能改名后 slug 语义过期 |
| 直接用显示名当 key | **我们的 v1（已废弃）** | 简单 | 改名即断裂（正是 v8→v10 迁移要解决的问题） |

**我们选第二种，理由是 AI 可读性。** 这是本项目区别于普通 CRUD 的地方 —— key 会进提示词，`subject` / `people_clothing_color` 能让模型正确归类，`fld_a1b2` 不能。当前 `validate_key()`（小写 snake_case、2–64、不以数字开头）已符合这个方向，保留。

CJK 转 slug 的处理：现有 `slugify()` 把非 `[a-z0-9_]` 全替换成 `_`，所以「人物服装颜色」会变成空串 → 用户必须手填英文。这是可接受的（比机器音译出 `renwufuzhuangyanse` 这种既不可读又易冲突的串要好），但**必须在 UI 上明确提示**：当自动生成结果为空时，输入框 placeholder 要写「请输入英文标识，如 clothing_color」而不是留空让用户困惑。

### 5.2 删除有数据的字段（部分确定）

已知的通用模式（Airtable / Notion / Jira 一类工具都采用其中之一）：

| 模式 | 行为 | 适用 |
|---|---|---|
| 软删（deprecate） | 标记不可用，历史值保留可查 | 「暂时不用」 |
| 硬删 + 级联 | 删字段连带删所有值，二次确认 + 展示影响范围 | 「建错了」 |
| 迁移后删 | 先把值搬到另一字段，再删 | 「重构分类体系」 |

我们**三种都要**，但优先级不同：软删（已有）→ 硬删（本次新增，R6）→ 迁移（本次不做，列入后续）。

Jira 的经验值得抄：删除 custom field 前展示「该字段被 N 个 issue 使用、被 M 个筛选器引用」。我们的 `get_tag_facet_impact()` 已经返回 `{tagCount, assetCount, aiConfigCount}`，方向一致 —— 但 `aiConfigCount` 在合表后失去意义，应换成「有多少条 AI 建议明细引用它」。

### 5.3 分面数量的经验上限（较确定）

faceted search 的通用经验：**同屏可见分面 5–9 个**（Miller 定律区间），超过就要分组或折叠。

我们当前 10 个系统分面 + 用户自建，很快会突破。设计上必须：
- 设置页按 AI/手工两组分开（这正是 R4 的收益）
- 素材库侧栏按 `sort_order` 排列并支持折叠（TagTree 已按分面分组，但没有分面级折叠）
- 超级搜索的分面下拉必须**分组**（optgroup 按分面），而不是把所有标签平铺

### 5.4 单选 vs 多选（确定）

通用规则：**互斥概念用单选，共存概念用多选**。

对照我们的分面：

| 分面 | 当前 | 应该 | 理由 |
|---|---|---|---|
| `scene` | multi(3) | **multi** ✅ | 你明确提到「有些照片不止一个场景」（R8）—— 一张图可以既是「海边」又是「日落」 |
| `composition` | multi(4) | multi | 一张图可以既「特写」又「对称」 |
| `people` | multi(4) | multi | 数量 + 年龄段 + 动作是三个维度 |
| 评分（用户自建） | — | **single** | 互斥 |
| 授权状态（用户自建） | — | **single** | 互斥 |

结论：默认 `multi` 是对的；`single` 主要给用户自建的状态类分面。

## 6. 数据库改造（v18 迁移）

### 6.1 迁移步骤（幂等可重入）

```rust
/// v18：分面单一事实源。
/// ① tag_facets 增 input_mode 列；
/// ② 从 settings.aiFacetConfigs 回填 input_mode 与 description（hint 并入 description）；
/// ③ 清空 settings.aiFacetConfigs（此后不再读写）。
fn migrate_v18(conn: &Connection) -> AppResult<()> {
    // ① 增列（有 CHECK 的列不能直接 ALTER ADD，先加无约束列，靠 Rust 层校验兜底）
    add_column_if_missing(conn, "tag_facets", "input_mode",
                          "TEXT NOT NULL DEFAULT 'ai_and_manual'")?;

    // ② 回填：读 settings JSON，把每条 aiFacetConfig 的语义搬进 tag_facets
    let mut s = settings::get_settings(conn)?;
    for cfg in &s.ai_facet_configs {
        // enabledForAi=false → manual_only（用户曾明确关掉 AI）
        let mode = if cfg.enabled_for_ai { "ai_and_manual" } else { "manual_only" };
        // hint 非空则并入 description（description 为空时直接用 hint；
        // 两者都非空时换行拼接，不丢用户已写的任何文字）
        conn.execute(
            "UPDATE tag_facets SET
                input_mode = ?2,
                description = CASE
                    WHEN ?3 = '' THEN description
                    WHEN trim(description) = '' THEN ?3
                    WHEN instr(description, ?3) > 0 THEN description   -- 已包含，不重复拼
                    ELSE description || char(10) || ?3
                END,
                display_name = COALESCE(NULLIF(?4, ''), display_name),
                updated_at = ?5
              WHERE key = ?1",
            params![cfg.facet_key, mode, cfg.hint.trim(),
                    cfg.display_name.as_deref().unwrap_or("").trim(),
                    now],
        )?;
    }

    // ②b visible_in_workbench=false 的分面：语义上是「AI 打但人看不到」，
    //     这是无意义状态（§3.3）。统一按「参与 AI」处理，不再隐藏。
    //     （测试阶段可接受；若有用户真依赖此状态，可在 UI 上停用该分面。）

    // ③ 清空 JSON 侧（Settings.ai_facet_configs 字段改 skip_serializing 后自然消失）
    s.ai_facet_configs.clear();
    settings::save_settings(conn, &s)?;

    // ④ 系统分面的默认 input_mode 修正：purpose / technical 天然是手工类
    conn.execute(
        "UPDATE tag_facets SET input_mode='manual_only', updated_at=?1
          WHERE key IN ('purpose','technical') AND is_system=1
            AND NOT EXISTS (SELECT 1 FROM tags WHERE facet_key = tag_facets.key)",
        params![now],
    )?;
    Ok(())
}
```

第 ④ 步的守卫（`NOT EXISTS ... tags`）：只改「还没有任何标签」的分面，避免覆盖用户已在用的配置。

### 6.4 FTS 触发器补一条：分面停用/删除也要刷新

现有触发器只看 `tags.status`，不看 `tag_facets.status`（§3.5 的残留问题之一）。补一条：

```sql
CREATE TRIGGER trg_facet_status_au AFTER UPDATE OF status ON tag_facets BEGIN
  UPDATE fts_content SET tag_names = (<同现有聚合子查询>)
   WHERE asset_id IN (
     SELECT at.asset_id FROM asset_tags at JOIN tags t ON t.id = at.tag_id
      WHERE t.facet_key = new.key
   );
END;
```

同时把聚合子查询的 WHERE 条件从 `t.status='active'` 改成：

```sql
WHERE at.asset_id = ? AND t.status = 'active'
  AND EXISTS (SELECT 1 FROM tag_facets f
               WHERE f.key = t.facet_key AND f.status = 'active')
```

效果：**停用分面 → 该分面下的标签立即从全文搜索消失；恢复分面 → 立即回来**。与「停用标签」的语义一致。

### 7.2 `delete_tag_facet`：真删除 + 级联（对应 R6）

```rust
/// 物理删除分面及其全部引用（R6：不留残留）。
/// 系统分面拒绝删除（只能停用）；删除前调用方必须已展示 get_tag_facet_impact。
pub fn delete_facet(conn: &Connection, key: &str) -> AppResult<FacetDeleteReport> {
    let f = get(conn, key)?;
    if f.is_system {
        return Err(AppError::msg("系统分类不能删除，只能停用"));
    }
    let tx = conn.unchecked_transaction()?;

    // ① 收集该分面下全部标签 id（含后代）
    let tag_ids: Vec<i64> = { /* SELECT id FROM tags WHERE facet_key = ?1 */ };

    // ② 删 asset_tags（触发 trg_at_ad → FTS tag_names 自动重算）
    //    注意必须先删关联再删标签，让 FTS 触发器有机会跑
    let unlinked = tx.execute(
        "DELETE FROM asset_tags WHERE tag_id IN (SELECT id FROM tags WHERE facet_key=?1)",
        params![key])?;

    // ③ 删 tag_ops 流水（否则 undo_batch 会拿到已删 tag_id → JOIN 失败静默丢行）
    let ops = tx.execute(
        "DELETE FROM tag_ops WHERE tag_id IN (SELECT id FROM tags WHERE facet_key=?1)",
        params![key])?;

    // ④ 删 ai_suggestion_items（facet_key 是 TEXT，无外键，必须显式清）
    let items = tx.execute(
        "DELETE FROM ai_suggestion_items WHERE facet_key = ?1", params![key])?;

    // ⑤ 删 tag_aliases（tags 有 ON DELETE CASCADE，但显式删更清楚且不依赖 pragma）
    tx.execute(
        "DELETE FROM tag_aliases WHERE tag_id IN (SELECT id FROM tags WHERE facet_key=?1)",
        params![key])?;

    // ⑥ 删标签本体
    let tags_deleted = tx.execute("DELETE FROM tags WHERE facet_key = ?1", params![key])?;

    // ⑦ 删分面
    tx.execute("DELETE FROM tag_facets WHERE key = ?1", params![key])?;

    tx.commit()?;
    Ok(FacetDeleteReport { tags_deleted, unlinked, ops, items })
}
```

**返回删除报告**，前端展示「已删除 N 个标签、解除 M 个素材关联」—— 让破坏性操作的结果可见。

前端二次确认必须用「输入分类名确认」而非简单 `window.confirm`（当前 `FacetManagePanel` 用的是 `window.confirm`，对不可逆操作太弱）。

## 8. 删除与级联规则总表

这是 R11 的交付物。每一行都要有对应测试。

### 8.1 删除分面（`delete_tag_facet`）

| 对象 | 动作 | 机制 |
|---|---|---|
| `tag_facets` 行 | 删 | 显式 DELETE |
| 该分面下 `tags` | 删 | 显式 DELETE |
| `asset_tags` 关联 | 删 | 显式 DELETE（**必须在删 tags 之前**，让 `trg_at_ad` 跑） |
| `fts_content.tag_names` | 重算 | `trg_at_ad` 自动 |
| `assets_fts` 索引 | 重算 | `trg_fc_au` 自动 |
| `tag_aliases` | 删 | 显式 DELETE（不依赖 CASCADE） |
| `tag_ops` 流水 | 删 | 显式 DELETE（防 `undo_batch` JOIN 到已删 tag） |
| `ai_suggestion_items` | 删 | 显式 DELETE（`facet_key` 是裸 TEXT，无外键） |
| `ai_suggestions.suggested_tags` JSON | **不动** | 历史 AI 原始返回，保留可追溯；确认时 `key_for_legacy_name` 会把已删 key 归 `custom` |
| `settings` | 无需动 | v18 后 JSON 里已无分面数据 |
| 前端 `tagStore` | 刷新 | 调用方 `await refresh()` |

### 8.2 停用分面（`deactivate_tag_facet`）

| 对象 | 动作 |
|---|---|
| `tag_facets.status` | → `inactive` |
| `tags` / `asset_tags` | **保留**（历史不丢） |
| FTS `tag_names` | **移除该分面标签**（新增 `trg_facet_status_au`，§6.4） |
| AI 提示词 | 不再包含（`build_prompt_context` 只取 active） |
| 工作台 / 侧栏 / 超级搜索下拉 | 不再显示（`list_tag_facets` 只返回 active） |
| 已保存的查询条件引用它 | 仍可执行（`tag_ids` 有效），但 UI 标「已停用」 |

### 8.3 删除标签（`delete_tag`，现有但前端未接线）

| 对象 | 动作 | 机制 |
|---|---|---|
| `tags` 行 + 后代 | 删 | `ON DELETE CASCADE`（`parent_id` 自引用外键） |
| `asset_tags` | 删 | CASCADE |
| `tag_aliases` | 删 | CASCADE |
| `tag_ops` | 删 | CASCADE |
| FTS | 重算 | `trg_at_ad` |
| `ai_suggestion_items.tag_id` | → NULL | `ON DELETE SET NULL` |

**前提：`PRAGMA foreign_keys=ON`**（`db/mod.rs:28` 已开）。**必须有测试守护这条**，因为 rusqlite 默认是关的，一旦哪次连接漏开就变成静默残留。

### 8.4 重命名标签 / 分面

| 操作 | 联动 |
|---|---|
| 重命名标签 | 旧名进 `tag_aliases`（`alias_type='old_name'`）→ `trg_tags_au` 刷 FTS → 旧名仍可搜到 |
| 重命名分面（改 display_name） | key 不变 → 所有引用自动跟上 → **零联动成本**（这就是稳定 key 的全部价值） |
| 改分面 `input_mode` | 下次 AI 打标生效；已有标签不动 |
| 改分面 `max_items` | 只约束**新增**；已超限的历史标签保留（UI 显示「已达上限」但不强制删） |

### 8.5 前端刷新责任表

| 后端写操作 | 必须刷新 |
|---|---|
| 任何分面 CRUD | `tagStore.refresh()`（facets + tree） |
| 删除分面 | `tagStore.refresh()` + `libraryStore.refresh()`（筛选条件可能引用已删标签） + 清 `selectionStore` |
| 确认 AI 建议 | `libraryStore.refresh()` + `tagStore.refresh()` + `loadRecent()` |
| 标签增删改 | `tagStore.refresh()` + `libraryStore.refresh()` |
| 入库完成 | `libraryStore.refresh()` + **`metadataStore.refresh()`**（修 P2-E：当前永不刷新） |

建议：给 `tagStore` 加一个 `invalidate()`，让所有写操作统一调它，而不是每个调用点自己记得调两三个 store。

| 通用外观 | 20 | 最臃肿。`colorStrip` 一个功能占 7 个控件（enabled + 3 个位置开关 + height + mode + count）→ 压成「显示色条 [开关]」+「▸ 色条细节」折叠 |

## 11. AI 打标提示词改造

对应 R8 + R10。

### 11.1 当前提示词的四个问题

以主分支 `ai_cloud.rs build_prompt()` 为准：

| 问题 | 表现 |
|---|---|
| **没给词表** | 提示词只有分面清单，没有「这个分面已经有哪些标签」。模型每次自由发明词 → 「海边/海滨/海岸/沙滩海边」四个标签指同一件事 → 标签体系膨胀（已确认：`collect_tag_dictionary()` 只在搜索侧用，打标侧没用） |
| **`description` 没进提示词** | `FacetPromptContext.description` 字段存在但 `build_prompt` 只用 `c.hint`。用户在设置页写的「给人的说明」对 AI 完全无效 |
| **多值语义弱** | 「（可多选，1-3 个）」没说清「可以同时有多个场景」。你明确提到这个问题（R8） |
| **没有反例约束** | 只有一句「不确定归属时留空」。缺「不要推测品牌/人名/地名」「不要写摄影评价」这类硬约束 |

### 11.2 目标提示词

```
你是素材库的标注器。看图，按下面的分类给出标签，只返回 JSON。

【输出格式】
{"description":"一句话描述","tags":{"分类key":["标签1","标签2"]}}

【description】
一句话说清画面里有什么，≤20 字。
例：「夜晚树下多人合影」「桌面上的陶瓷茶具特写」
不要写「这是一张…」，不要写画质/器材/拍摄建议，不要堆逗号标签。

【tags 规则】
1. 只用下面列出的分类 key 作为键，不要发明新的键。
2. 优先从「已有标签」里挑词。含义相同就用已有的词，不要造近义词
   （已有「海边」就不要写「海滨」「海岸」）。
3. 已有标签里没有合适的，才写新词。新词要短（2-6 字）、要具体。
4. 一个分类可以有多个标签。画面里同时存在多个就都写上
   —— 比如一张图既是「海边」又是「日落」，两个都要写进 scene。
5. 只写你在画面里直接看到的。不要推测品牌、人名、地名、品类、价格、
   拍摄意图。看不清就不写。
6. 每个标签只归一个分类。不确定归哪个分类，宁可不写。
7. 没有合适标签的分类，值给空数组 []。

【分类清单】
scene ── 场景/地点（可多选，最多 3 个）
  素材发生的环境或地点。一张图可以同时属于多个场景，都写上。
  只写看得见的环境，不要推测具体地名。
  已有标签：海边、室内、街道、公园、山地

subject ── 主体/对象（可多选，最多 5 个）
  画面中可辨认的主要物体。只写看得见的实体。
  已有标签：人、猫、茶具、汽车

people ── 人物属性（可多选，最多 4 个）
  人物数量、年龄段、可观察的动作。没有人物就给空数组。
  已有标签：单人、多人、成年、儿童、坐姿

（…按 sort_order 列出全部 input_mode=ai_and_manual 的分面…）

【示例输出】
{"description":"海边日落时的双人剪影",
 "tags":{"scene":["海边","日落"],"subject":["人"],"people":["多人","剪影"]}}
```

### 11.3 实现要点

```rust
fn build_prompt(facets: &[FacetPromptContext], dict: &FacetDict) -> String
```

复用搜索侧已有的 `collect_tag_dictionary()`，但打标侧的参数要更紧：

| 参数 | 搜索侧现值 | 打标侧建议 | 理由 |
|---|---|---|---|
| 每分面标签数 | 50 | **20** | 打标是每张图一次请求，token 成本 ×N 张 |
| 别名 | 每标签 5 个 | **0**（不给别名） | 打标要的是「用哪个词」，别名只会让模型困惑 |
| 总字符上限 | 6000 | **1500** | 同上 |
| 排序 | `sort_order, id` | **按 `asset_count` 降序** | 常用词优先，冷门词不占额度 |

按 `asset_count` 降序是关键改动 —— 让高频词进提示词，模型更可能复用它们，标签收敛更快。

### 11.4 解析侧同步收紧

最后一条是新增的：当前 `max_items` 只写在提示词里，模型不遵守时没有兜底（已确认：写入侧无任何 max 强制，只有解析时的 `take(5)` 硬上限）。

## 12. 超级搜索改造：不报错 + 强约束

对应 R9 + R10。核心思路：**用协议层收窄 + 三层降级，让「AI 输出不合规」变成「结果略差」而不是「报错」。**

### 12.1 现状：为什么会报错

主分支的搜索链路已经比 `agents/ai` 分支强很多（`SearchIntentV2` 分组协议 + 本地语义守卫 + concept 解析）。剩下的报错来源：

| 来源 | 位置 | 现状 |
|---|---|---|
| JSON 解析失败 | `parse_intent()` | 抛 `AppError("AI 未返回可解析的 JSON")` → 前端红字 |
| serde 反序列化失败 | `parse_intent()` | 抛 `AppError("AI JSON 校验失败：{e}")` |
| 结构校验失败 | `validate_intent()` | 抛错（非法 sortBy 等） |
| 元数据 key/op 非法 | `search_query::validate_metadata()` | 抛错 |
| 三级降级全失败 | `request_text_json()` | 抛「AI 请求降级仍失败」 |
| 未识别标签 | `resolve_*` | ✅ 已经是 warning（正确） |
| 连接/鉴权失败 | `should_fallback()` 短路 | 抛错（**这个应该保留** —— 配置问题必须让用户知道） |

前五条都应该改成「降级 + warning」。

### 12.2 强约束：JSON Schema 用 enum 从协议层收窄

当前 `intent_schema()` 里 `facetHint` 是自由 `string`。改成 enum：

```rust
fn intent_schema(facets: &[FacetPromptContext]) -> serde_json::Value {
    let facet_keys: Vec<&str> = facets.iter().map(|f| f.key.as_str()).collect();
    let metadata_keys: Vec<&str> = search_query::ALL_KEYS.to_vec();   // 白名单常量
    json!({
      // ...
      "facetHint": { "anyOf": [
          { "type": "string", "enum": facet_keys },   // ← 从协议层收窄
          { "type": "null" }
      ]},
      "metadata": { "type":"array", "items": {
          "properties": {
            "key": { "type":"string", "enum": metadata_keys },   // ← 同上
            "op":  { "type":"string", "enum": ["eq","in","contains","gt","gte","lt","lte","between"] },
          }
      }}
    })
}
```

签名从 `intent_schema()` 变成 `intent_schema(facets)`。收益：**支持 `json_schema` 的服务商（Tier::Structured）在服务端就拒绝非法 key**，根本到不了我们的校验层。这是「不报错」最有效的一层 —— 用户新建分面后 enum 自动包含它，零代码改动（R1）。

对不支持结构化输出的服务商（降到 Tier::JsonObject / Plain），仍靠 §12.3 的本地降级兜底。

### 12.3 三层降级：任何解析失败都退化成关键词搜索

```rust
pub fn parse_search(cfg, text, facets, dict) -> AiSearchParseResult {
    // 第 1 层：正常解析
    match try_parse_strict(cfg, text, facets, dict) {
        Ok(r) => return r,
        Err(e) if is_config_error(&e) => return Err(e),   // 鉴权/连不上 → 真报错
        Err(e) => warnings.push(format!("AI 未能完全理解这句话（{e}），已按关键词搜索")),
    }
    // 第 2 层：部分解析 —— JSON 能读出 groups 但某些字段非法 → 剔除非法项保留其余
    if let Some(partial) = try_parse_lenient(&raw) {
        return AiSearchParseResult { expr: partial.expr, warnings, .. };
    }
    // 第 3 层：纯关键词兜底 —— 把用户原句当关键词，永不失败
    AiSearchParseResult {
        expr: Some(text_search_expr(text)),
        explanation: format!("按关键词「{text}」搜索"),
        warnings,
        ..
    }
}
```

`text_search_expr(text)` = `QueryExpr::Leaf { cond: Search { value: text, scope: All } }`，走已有的 FTS 链路。

**这样「超级搜索报错」这个类别就彻底消失了** —— 最差情况是退化成普通关键词搜索，用户还能看到结果 + 一行黄字说明。

### 12.4 部分解析（第 2 层）的剔除规则

| 非法项 | 处理 |
|---|---|
`sortBy` 不在白名单 | 用默认 `created_at` + warning |
| `sortDir` 非法 | 用 `desc` |
| `assetType` 非法 | 用 `all` |
| 某个 `metadata` 条目 key/op 非法 | **剔除这一条**，保留其他条目 + warning |
| 某个 `concept` 的 `facetHint` 未知 | 降级为全分面搜索（不指定 facet）+ warning |
| 某个 `group` 全部条件都非法 | 剔除这个 group；若所有 group 都空 → 落到第 3 层 |
| `text_terms[].scope` 非法 | 用 `all` |

原则：**能救一条算一条**。当前是一条非法整个请求失败。

### 12.5 给 AI 的搜索提示词补强（R10）

搜索侧已有 `collect_tag_dictionary()`（每分面 50 词 + 别名），方向对。补两点：

**① 明确告诉 AI「分类清单是封闭的」**

```
【可用分类】（只能用这些 key，不要发明）
scene ── 场景/地点：素材发生的环境或地点
subject ── 主体/对象：画面中可辨认的主要物体
purpose ── 用途：稳定的发布或设计用途
（…）

【各分类已有的标签】（优先匹配这些）
scene: 海边 | aliases: 海滨, 海岸
scene: 室内
subject: 人
（…）
```

当前 prompt 里分面说明与词典是分开两段的，但没有「只能用这些 key」的显式约束句。加上。

**② 元数据字段也给清单**

用户搜「大于 5MB 的横图」，模型要知道 `file_size` 和 `aspect_ratio` 这两个 key 存在。当前 prompt 没有列元数据字段清单，模型只能靠猜。补一段：

```
【可用的文件属性】
file_size（字节，如 5MB 写 5242880）
duration_ms（毫秒）
aspect_ratio（宽/高，横图 > 1，竖图 < 1）
resolution（宽×高像素数）
taken_at / created_at（日期，YYYY-MM-DD）
camera / lens / file_ext / video_codec
iso / aperture / focal / width / height
```

这是「不报错」的第二个来源 —— 模型不猜字段名，非法 key 自然减少。

### 12.6 「标签范围要单独」的落地（你的原话）

理解为：搜索时希望能表达「某个分类内部的范围」，而不是只能挑具体标签。三个新能力：

| 能力 | UI 表达 | 编译 |
|---|---|---|
| 「场景 是 海边 或 山地」（同分面多选 OR） | 标签下拉改**多选** | `Tag{facet_key, tag_ids:[a,b], mode:"any"}`（协议已支持，UI 只让选一个） |
| 「场景 同时是 海边 和 日落」（同分面 AND） | 多选 + 「同时满足」勾选框 | `mode:"all"`（协议已支持，UI 无入口） |
| 「场景 有任意标签 / 没有标签」 | 新增两个字段（§10.3③） | `facet_has_any` / `facet_missing` |

前两个是**协议层已经支持、UI 层没做**（`QueryBuilder` 的 `cond.tagIds[0]` 只取第一个）。这是最低成本的收益：改 UI 即可，后端零改动。

### 16.3 需要你拍板的三件事

1. **`visible_in_workbench=false` 的分面怎么处理？** 我的建议是按「参与 AI」统一处理（§6.1 ②b），因为「AI 打了但人看不到」本身是无意义状态。如果你有分面真的靠这个隐藏，告诉我，我改成迁移成 `manual_only`。

2. **系统分面允许删除吗？** 我的建议是不允许（只能停用），因为 `subject`/`scene` 这些 key 在代码注释、文档、`key_for_legacy_name` 里都有引用。如果你想彻底删掉「色彩」这类已停用的系统分面，我可以加一个「强制删除」开关。

3. **「打标时机=自动」删掉还是实现？** 我的建议是本轮删掉（它现在是死配置），自动打标作为独立特性做 —— 因为它涉及入库管线、失败重试、批次归属等一整套问题，混进本次改造会拖长战线。
