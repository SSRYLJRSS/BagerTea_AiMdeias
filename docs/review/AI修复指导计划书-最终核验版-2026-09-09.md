### 1.2 对两份报告的勘误

两份报告的主体判断基本可靠，但后续 AI 必须按以下勘误执行：

1. “入口不可发现”不能推出新增第四个标签或顶栏入口。用户明确保留双击“素材库”的产品设计，本轮只加 500ms 提示。
2. “在 setPlanShould 一处重算权重即可全覆盖”不成立。applyAiSearch replace、appendPlanMerge、跨区移动直接 set、persist merge、migrate/onRehydrate 等路径可能绕过它。必须建立统一的 plan 归一化边界。
3. minimumShouldMatch 不是“随 should 数量 clamp”即可，而是新 UI 契约下无条件为 0。旧 clamp 逻辑和相关文案需要逐步收敛。
4. append 超过 12 条时不能再按旧 weight 排序后截断，否则它在归一化之前使用了不可信权重。应先按合并后的用户可见顺序去重并保留前 12 条，再统一生成位置权重。
5. C-18 不能笼统断言“第一条命中素材一定排前”。只有 relevance 排序，或字段主排序值相同的样本，才能隔离验证位置权重。
6. cargo fmt 不能在脏工作树里由 AI 擅自全量执行并提交。先记录基线，等 P0 独立完成后单独处理格式批次，且不创建 commit 除非用户要求。
7. “升级 testing-library 即可消除 React static flag 告警”只是猜测，不得作为确定修复。先固定最小复现和版本矩阵，再决定升级。
8. unwrap 的验收口径必须区分生产和测试，不能继续用全库 795 作为健康度结论。

## 4. P0-B：优先满足区排序交互

### 4.1 产品行为

- 每条优先条件有清晰、低干扰的拖拽手柄；整行不可拖，避免输入框选词时误触。
- 拖动时显示稳定落点，支持从任意位置移动到开头、相邻位置和末尾。
- 完成后立即写回 plan.should 顺序，序号 1..N 同步更新。
- 不出现权重、连接词、匹配模式或“至少满足 N 项”。
- 为键盘和自动化提供兜底：每行操作菜单加入“上移”“下移”，边界项禁用相应命令。不得只依赖 HTML5 drag-and-drop。
- 移动菜单继续保留“移到必须满足/排除”；区内排序与跨区移动是不同命令。

### 4.2 推荐实现

当前 GroupEditor 的 DragHandle/DropLine 和 dndId 使用 VNode id，直接把 should 索引伪装成 VNode 容易与 filter/mustNot 拖拽状态串扰。推荐增加专用、很小的 Should DnD 状态：dragShouldIndex 和 hoverShouldIndex，或者给现有状态加入明确 zone/类型判别。不要依赖数组索引作为 React key；新增条件应有稳定 UI key，若不改领域类型，可在组件本地维护与列表变更同步的 key 映射。

统一使用纯函数 reorderShould(list, from, to)：

1. 校验 from/to 均在合法范围；相同位置直接返回原数组。
2. 先 splice 取出源项，再按删除后的目标索引插入，明确 to 表示最终插入位置。
3. 返回新数组，绝不原地修改 store 中的 should。
4. 所有拖拽落点和上移/下移命令都调用同一函数，再调用 setPlanShould。

UI 应复用现有边框、surface、accent、圆角和 hover 变量。手柄使用项目已有符号或 lucide GripVertical（若当前文件已有 lucide 体系）；提供 aria-label “拖动优先条件 N”。落点不得改变整行高度导致页面跳动。

### 4.3 必测边界

- 3→1、1→3、2→2；移动后 label/evidence/cond 不丢失。
- 第一项“上移”和末项“下移”禁用；中间项两者可用。
- 删除、添加、跨区移动后仍可继续排序。
- 拖拽取消、dragEnd、组件卸载后状态清空，不遗留高亮落点。
- 排序后 planRevision 增加一次，只触发一次预期刷新；不得因 dragOver 连续刷新。
- 12 条上限下的首尾移动正确。

## 5. P0-C：统一位置权重与计划归一化

### 5.1 唯一契约

对于任何进入执行、持久化或 UI store 的 SearchPlanV3：

- should 最多 12 条，数组顺序就是用户优先级顺序。
- minimumShouldMatch 无条件为 0。
- UI 不接收也不编辑 weight；存入的外部/历史 weight 不能决定最终顺序。
- 最终 weight 只允许 2.0、1.0、0.5，并按当前位置自动生成。
- 推荐三分桶：索引小于 ceil(N/3) 为 2.0；小于 ceil(2N/3) 为 1.0；其余为 0.5。N=1 时为 2.0，N=2 时为 2.0/1.0，N=3 时为 2.0/1.0/0.5。

### 5.2 统一纯函数

在 src/utils/planUtils.ts 建立并导出 normalizeShouldByPosition 和 normalizeSearchPlan。不得在 QueryBuilder、store action、persist 各复制一份权重算法。

normalizeShouldByPosition 的职责：按输入顺序截取前 12 条，保留 cond/label/evidence，覆盖 weight。normalizeSearchPlan 的职责：调用前者并强制 minimumShouldMatch=0，同时保留 filter、mustNot、retrievers、ranking 和版本字段。

归一化是幂等的：normalize(normalize(plan)) 必须深度相等。不要修改调用者传入的对象或数组。

### 5.3 必须覆盖的写入边界

| 路径 | 当前风险 | 修复要求 |
|---|---|---|
| setPlanShould | 原样存 weight，min 只 clamp | 调用统一归一化，min 固定 0 |
| moveConditionBetweenZones | 新建 weight=1，直接 set nextPlan | 组装完成后归一化整个 plan |
| applyAiSearch replace | AI plan 直接进入 store | AI plan 先迁移/校验，再统一归一化 |
| applyAiSearch append | appendPlanMerge 使用旧 weight 排序截断 | 去重后按可见顺序保留前 12，再归一化；更新旧 warning 文案 |
| persist merge | persisted plan 原样塞入首帧状态 | merge 返回前归一化，防止首帧执行旧 min/weight |
| migrate/onRehydrate | 只改版本，不改 should 语义 | migratePlanV3 成功后归一化；未来版本仍按原规则拒绝 |
| 其他 plan 重建 | 后续代码可能直接 set plan | 搜索所有 plan: / nextPlan 写点，确保入口归一化或明确证明 should 为空 |

注意：store 内当前存在 migratePlanV3 与 utils 中同名函数的迹象。实施前先确认真实引用关系，收敛为一个公开实现，避免同名双逻辑。

### 5.4 单元测试矩阵

1. N=0、1、2、3、4、5、12、13 的权重与截断结果。
2. 输入 weight 为非法值、NaN 或旧顺序时被覆盖；原对象未改变。
3. label、evidence=null、evidence 文本、cond 引用内容完整保留。
4. minimumShouldMatch 输入为负数、1、大于 N，结果均为 0。
5. normalize 幂等。
6. AI replace/append、跨区移入/移出、删除、hydrate 后均满足相同不变式。
7. append 超过 12 条按 base 后 incoming 的去重后顺序保留，不再按传入 weight 排序。
8. 未来 plan 版本仍被拒绝，不因归一化意外“降级接受”。
