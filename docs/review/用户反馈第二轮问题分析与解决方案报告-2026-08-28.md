## FB2-01 Alt+滚轮控制素材框大小（入库 + 素材库）

### 现状

素材库网格的格子尺寸是**两个硬编码常量**，没有任何用户可调入口：

```tsx
// src/components/library/AssetGridView.tsx:35-36
const GAP = 8;
const MIN_CARD = 160;
```

列数与行高由宽度反推（`AssetGridView.tsx:91,98`）：

```tsx
const columns = Math.max(2, Math.floor((width + GAP) / (MIN_CARD + GAP)));
const virtualizer = useVirtualizer({
  count: rowCount,
  getScrollElement: () => scrollElementRef?.current ?? ref.current,
  estimateSize: () => (width - GAP * (columns - 1)) / columns + GAP,  // 正方形格子 + 间距
  overscan: 3,
});
```

入库页网格是纯 CSS Grid（无虚拟化），同样硬编码：

```tsx
// src/components/import/PendingList.tsx:381
<div className="grid grid-cols-[repeat(auto-fill,minmax(110px,1fr))] gap-2 p-2">
```

全仓库当前**只有一处** wheel 监听 —— `MediaViewport.tsx:147-160`（Viewer 里 Alt+滚轮缩放图片）。网格层完全没有 wheel/altKey/deltaY 处理。

缩略图请求尺寸也是常量：`Thumbnail.tsx:10` `const SIZE = 512`。

### 方案

**1) 档位化，不做连续缩放。** 定义等比档位（约 1.25×）：

```ts
export const CELL_STEPS = [96, 120, 150, 190, 240, 300, 380, 480] as const; // px
```

理由（性能）：连续缩放会让 `@tanstack/react-virtual` 每帧 `measure()` 重算全部行高，并让缩略图请求尺寸在任意值间漂移，缓存键 `${assetId}:${kind}:${size}`（`thumbnailCache.ts:24-26`）几乎必然全部 miss，等于每次滑动都重新生成一遍缩略图。档位化后缩略图尺寸只在 2~3 个固定值间切换，缓存命中率接近 100%。

**2) 缩略图尺寸随档位分级**（把 `Thumbnail.tsx:10` 的 SIZE 从常量改为入参）：

| 格子宽 | 请求尺寸 | 理由 |
|---|---|---|
| ≤ 190px | 512 | 覆盖 2× DPR（190×2=380 < 512） |
| 240–380px | 1024 | 512 在 380px 格子上 2× DPR 会糊 |
| ≥ 480px | 1024 | 再往上收益递减，1024 够用 |

**3) 事件实现**（沿用 `MediaViewport.tsx:147-160` 已验证的模式）：

- 原生 `addEventListener("wheel", fn, { passive: false })` —— React 的 `onWheel` 在 React 19 下是 passive，`preventDefault()` 无效，拦不住滚动。
- 命中条件 `e.altKey === true` → `preventDefault()` + 走档位；否则完全放行给正常滚动。
- 节流：`requestAnimationFrame` 合并 + 每档最小间隔 60ms。触摸板惯性滚动一次能产生几十个 wheel 事件，不节流会一口气从最小跳到最大。

**4) 缩放锚点保持。** 缩放前记录视口垂直中心对应的 item index，档位切换后 `virtualizer.scrollToIndex(anchorIndex, { align: "center" })`。否则行高一变，`scrollTop` 对应的内容位置完全漂移，用户会"缩放后不知道自己在哪"。

**5) 为什么用 Alt 而不是行业更常见的 Ctrl（回答"人家优秀案例"）：**

Eagle / Adobe Bridge / Finder / Explorer 都用 `Ctrl`（macOS `Cmd`）+ 滚轮，但它们是原生应用。本项目跑在 WebView2 里，**`Ctrl+滚轮` 被 WebView2 抢去做页面级缩放**，会把整个 UI（含侧栏、工具条、字号）一起放大，而且 Tauri 默认不禁用。Alt 在 WebView2 中无绑定，`preventDefault()` 即可完全接管。所以**采纳用户提的 Alt 方案是技术上更正确的选择**。

同时补两个可发现的入口（Alt+滚轮属于隐藏手势，新用户找不到）：
- `GridToolbar.tsx:88-108` 排序旁加一个 3 档的大小切换按钮组或滑块；
- 键盘 `Ctrl/Cmd + =` / `Ctrl/Cmd + -` 增减一档（与 `AssetGridView.tsx:127-142` 已有的 Ctrl+A/Ctrl+I 键盘处理放在一起）。

**6) 状态放哪。** 放 `Settings`（见 §9 的 `appearance.grid.cellStep`），落库持久化，跨会话记住。素材库与入库页各存一份档位（`libraryCellStep` / `importCellStep`），因为入库缩略图通常要更小更密。会话内即时生效不等保存 —— 与 `SettingsPage.tsx:357` 主题 `applyTheme` 的即时预览做法一致。

### 验收标准

- 素材库/入库两页，Alt+滚轮上下各能走完全部档位，边界处不抖动、不报错。
- 不按 Alt 时滚动行为与现在完全一致（无回归）。
- 缩放过程中滚动位置的"视觉锚点"不跳；连续快速滚动不掉帧（目标 ≥ 50fps，259 项样本）。
- 重启应用后档位保持。

## FB2-02 设置→外观：素材框比例与填充方式

### 现状

**素材库**：卡片比例被硬编码为正方形，缩略图硬编码裁切填充。

```tsx
// src/components/library/AssetCard.tsx:66
"group relative aspect-square cursor-pointer overflow-hidden rounded-md outline-none select-none",
```
```tsx
// src/components/library/Thumbnail.tsx:90 与 :108
className="absolute inset-0 h-full w-full object-cover"
```

**入库页**：这里藏着一个真实缺陷。`LazyThumb` 的 className 拼接产生了 Tailwind 定位类冲突：

```tsx
// src/components/import/PendingList.tsx:67
<div ref={ref} className={clsx("relative overflow-hidden bg-[var(--color-surface)]", className)}>
// 调用处 src/components/import/PendingList.tsx:216
<LazyThumb path={item.path} kind={item.kind} className="absolute inset-0" />
```

结果这个 div 同时带 `relative` 和 `absolute`。Tailwind v4 生成的样式表里 `relative` 排在 `absolute` 之后，**实际生效的是 `relative`**。于是：

- `LazyThumb` 不是绝对定位覆盖层，而是参与文档流的相对定位块；
- 卡片（`PendingList.tsx:209-214`）的其余子元素（视频层、角标、文件名、移除按钮）全是 `absolute`，唯一撑高度的就是 `LazyThumb` 里那个 `h-full w-full` 的 `<img>`；
- `h-full` 对 auto 高度的父级解析为 `auto` → **卡片高度 = 首张图片的固有比例**。

这正是截图 1 里 5 个卡片呈 16:9 扁条（视频封面比例）的原因。混排图片与视频时，行内每张卡片高度不同、行与行也不齐 —— 也就是用户说的"不好看"的机制性来源。

### 方案

**1) 容器统一比例 + 内容按填充方式适配。** 这是唯一能保证网格对齐的结构；当前入库页是反过来的（内容比例决定容器高度），必须纠正。

比例档位（用户明确"只允许设置同一比例"）：

| 值 | 说明 | 适用 |
|---|---|---|
| `1:1` | 正方形（当前行为） | 混排默认，最中性 |
| `4:3` | 传统相机 | 图片为主 |
| `3:2` | 135 画幅 | 单反/微单素材库 |
| `16:9` | 宽屏 | **视频为主的库，推荐默认** |
| `3:4` / `2:3` / `9:16` | 竖版 | 竖屏/手机素材 |
| `auto` | 瀑布流（各卡片按自身比例，列内堆叠） | 见下方取舍 |

**2) 填充方式**：

| 值 | CSS | 视觉 | 代价 |
|---|---|---|---|
| `cover`（裁切填满） | `object-fit: cover; object-position: center` | 网格最齐、最"满" | 裁掉画面边缘 |
| `contain`（完整显示） | `object-fit: contain` | 构图完整，比例不同的素材留边 | 出现空白边 |
| `smart`（智能） | 内容比例与容器比例差 < 阈值（建议 15%）用 cover，否则 contain | 兼顾 | 同一行内可能混两种观感 |

**3)「别太丑」的三个关键设计决定**（这是这条需求真正的难点）：

- **不要拉伸。** 明确不提供 `object-fit: fill`。拉伸变形是唯一"绝对丑"的选项，视频与图片比例本来就不同，拉伸后人脸会被压扁。用户说的"填充拉伸这些你设置好"按"填满/完整"两态实现，不做形变。
- **contain 的留边背景不用纯灰。** 默认 `--color-surface`；再提供一个 `matchDominantColor` 选项 —— 留边填该素材的主色（低饱和处理：Lab 里把 L 拉向背景、C 压到 30%）。这是 Apple Photos / Google Photos 的做法，留边不再是"缺口"而是画面的延伸。**这一项依赖 FB2-08 的算法色板**，也是建议把 FB2-02 与 FB2-08 排进相邻批次的原因。
- **统一圆角与内描边。** cover 模式下深色图片贴着深色背景会失去边界，卡片加 `ring-1 ring-inset ring-black/5`（浅色主题）/ `ring-white/5`（深色主题），比加外边框更干净。

**4) `auto`（瀑布流）的取舍。** 视觉上最漂亮，但与现有虚拟化不兼容：`AssetGridView.tsx:95-100` 的 `useVirtualizer` 是**等高行**模型（`estimateSize` 返回单一值），瀑布流需要 masonry / `lanes` 模式并逐项 `measureElement`。改造量约等于重写网格虚拟化层。**建议第一版不做 `auto`**，先交付 7 个固定比例；若确实需要，单独立项。

**5) 顺带修掉 `PendingList.tsx:67` 的类冲突** —— 把 `LazyThumb` 的基础类改为不含 `relative`，或让调用方通过独立 prop 传定位，避免 clsx 拼出互斥类。这个 bug 不修，入库页的比例设置不会生效。

### 设置项落点

`SettingsPage.tsx:350-368` 的「通用外观」Group 内新增一个"素材框"小节（字段结构见 §9）。改动即时预览、保存后持久化，与主题一致。

### 验收标准

- 切换比例后素材库与入库页行高完全一致，任意混排都不出现锯齿行。
- cover / contain / smart 三态视觉符合预期，无形变。
- 深色与浅色主题下卡片边界都清晰可辨。
- 入库页卡片高度不再随首图比例变化（类冲突已修）。

## FB2-03 悬停自动播放前几秒「失效」【P0，根因已定位】

### 根因（四重叠加，第 1 条是决定性的）

**① Tauri asset 协议白名单没放行入库清单的路径 —— 这是"完全播不出来"的直接原因。**

静态配置是空白名单：

```json
// src-tauri/tauri.conf.json
"assetProtocol": { "enable": true, "scope": [] }
```

运行期只放行三个内部目录：

```rust
// src-tauri/src/lib.rs:59-80
let thumbs_dir = scope_dir.join("thumbnails");
let previews_dir = scope_dir.join("previews");
let proxies_dir = scope_dir.join("proxies");
app.asset_protocol_scope().allow_directory(&thumbs_dir, true)   // 缩略图
app.asset_protocol_scope().allow_directory(&previews_dir, true) // 入库预览封面
app.asset_protocol_scope().allow_directory(&proxies_dir, true)  // 视频兼容代理
```

素材**原文件**是靠命令层逐路径放行的：

```rust
// src-tauri/src/commands/assets_cmd.rs:19-21
fn allow_asset(app: &tauri::AppHandle, path: &str) {
    let _ = app.asset_protocol_scope().allow_file(Path::new(path));
}
// :40-42 —— list_assets 对返回的每一项都放行
for a in &page.items { allow_asset(&app, &a.file_path); }
```

而入库清单走的是 `inspect_import`，**它没有调用 `allow_asset`**：

```rust
// src-tauri/src/commands/import_cmd.rs:55-60
#[tauri::command]
pub async fn inspect_import(paths: Vec<String>) -> AppResult<importer::ImportPlan> {
    tauri::async_runtime::spawn_blocking(move || Ok(importer::inspect_paths(&paths)))
        .await.map_err(|e| AppError::msg(format!("扫描线程异常: {e}")))?
}
```

于是前端这一行必然被拒：

```tsx
// src/components/import/PendingList.tsx:172-180
<video ref={videoRef} src={convertFileSrc(item.path)} muted playsInline preload="metadata" autoPlay ... />
```

`asset://localhost/<原文件路径>` 返回 403 → `<video>` 触发 `error` → `PendingList.tsx:133-135` `setVidError(true)` → 退回封面并显示「无法播放 · 双击打开」。封面能显示是因为它来自 `previews` 目录（在白名单内），所以现象正是"看起来只是不播，没有报错"。

> 交叉验证：Viewer 里播视频是通的（`ViewerPage.tsx:62,129` 同样用 `convertFileSrc(current.filePath)`），因为那些素材来自 `list_assets`，路径已被逐条放行。这个对比可以确认根因就是放行差异，而非编解码问题。

**② 入库页默认是列表视图，列表视图根本没有预览层。**

```tsx
// src/components/import/PendingList.tsx:288
const [view, setView] = useState<ViewMode>("list");
```

只有网格分支（`:380-395`）渲染 `PendingItem` → 才有 `PendingVideoLayer`。用户如果没手动点右上角网格图标，连代码路径都进不去。

**③「前几秒」这个语义从来没实现过。**

```tsx
// src/components/import/PendingList.tsx:136-141
const onLoaded = () => {
  v.currentTime = 0;
  void v.play().catch(() => { if (!released) setVidError(true); });
};
```

从 0 播到结尾，无 `loop`、无时长上限。一个 12 秒或 5 分钟的素材会一直放下去。

**④ 素材库网格是被主动删掉的，不是"坏了"。**

```tsx
// src/components/library/AssetCard.tsx:1-3
/** 网格卡片（指导书 §2.2/§6.1）：...
 *  素材库禁止大图/视频 hover 预览：不创建 <video>、不请求 1024px hover 图、
 *  不渲染 fixed 大图浮层；hover 只允许边框/文件名透明度变化（§3.3）。双击进入 Viewer。 */
```

对应 commit `8fa88be`「删除素材库大图/视频 hover 预览 + 缩略图滚动稳定」。所以在素材库里这不是修复，而是**以受控方式重新引入**。

### 方案

**Step 1 —— 后端一行修复（最小改动，立刻解决入库页）**

`inspect_import` 改为接收 `AppHandle`，对 `plan.items` 逐条 `allow_asset()`，与 `list_assets` 完全同一函数、同一安全模型。

安全评估：只放行**用户自己主动选择/拖入**的路径，且是读权限；与现有 `list_assets` 的放行范围性质相同，不扩大攻击面。**不要**改成 `allow_directory` 或放宽 `tauri.conf.json` 的 scope —— 那会把整个盘暴露给 webview，`lib.rs:56` 的注释已明确写了"不放行 data_dir 根（含 library.db）"的收敛意图，不能倒退。

**Step 2 —— 实现"前几秒"语义**

抽一个共用 hook `useHoverPreviewPlayback`：

- `previewSeconds`（默认 3，设置可调 2~10）；
- `startAt`：默认 `min(duration * 0.1, 2s)` —— 跳过片头黑场/淡入。截图 1 里第 2、3 张就是夜景，0 秒处几乎全黑，从 10% 开始体验明显更好；
- `timeupdate` 到 `startAt + previewSeconds` 时回跳 `startAt` 实现循环（比 `loop` 属性可控，且能限定只播这一段）；
- `muted` + `playsInline` + `preload="metadata"` 保持不变。

**Step 3 —— 素材库受控重新引入**

复用 `useHoverIntent`（`src/hooks/useHoverIntent.ts`，enter 300ms / leave 350ms，已验证）+ 把 `PendingList.tsx:88-102` 的模块级单实例注册表（`acquireVideo`）提取成共用模块。性能护栏（这些是当初删掉它的原因，必须一次补齐）：

- **全局同时最多 1 个 `<video>`**（复用 `acquireVideo`）；
- **滚动中不激活** —— 滚动事件打一个 150ms 的抑制窗，快速滑过整个库不创建任何媒体元素；
- `AssetCard` 不再挂 `fixed` 大图浮层（沿用 §3.3 的约束），只在卡片内 `absolute inset-0` 原位播放；
- 设置开关 `appearance.hoverPreview.enabled`（默认开）+ `previewSeconds`，用户机器吃不住可以直接关。

**Step 4 —— 失败兜底分场景**

| 场景 | 兜底 |
|---|---|
| 入库页（未入库） | 播放失败 → 只显示封面 + 「双击打开」。**不触发转码** —— 入库前就为预览转码是不可接受的成本 |

## FB2-04 + FB2-05 Viewer 空白与图片错位【P0，同一根因】

这两条用户分开提，但**是同一个 CSS 高度链缺陷的两个表现**。先讲根因，再分别给方案。

### 共同根因：Viewer 的高度约束链断了

```tsx
// src/components/viewer/ViewerShell.tsx:19-32
<div className="flex h-full min-h-0 flex-col bg-[var(--color-bg)]">
  {toolbar}
  <div className="flex min-h-0 flex-1">
    {sidebar && (
      <aside className="w-[280px] shrink-0 overflow-y-auto border-r border-[var(--color-border)] p-3">
        {sidebar}
      </aside>
    )}
    <div className="min-w-0 flex-1">{stage}</div>   {/* ← 问题在这一行 */}
  </div>
  {filmstrip}
</div>
```

`ViewerShell.tsx:28` 这个包裹层**只有 `min-w-0 flex-1`，没有 `flex`、没有 `flex-col`、没有 `min-h-0`**。它是块级容器，高度由内容决定。于是：

```tsx
// src/components/viewer/MediaViewport.tsx:283（图片分支）
"relative flex min-h-0 min-w-0 flex-1 select-none items-center justify-center overflow-hidden bg-[var(--color-bg)]"
```

`flex-1` 与 `min-h-0` **在非 flex 父级下双双失效**，舞台高度 = 内容高度。由此产生两个后果：

**后果 A（= FB2-04，下方大片空白）**
内容比行高矮时，舞台按内容高度顶对齐，下方留出一整段空白，横跨到胶片条之前。截图 2 里视频 + 控制条约 800px，可用行高约 980px → 约 180px 空白，且因为空白属于右列，视觉上从侧栏右边一直延伸到窗口右缘。**这不是设计留白，是布局塌陷的残留。**

**后果 B（= FB2-05，图片越界错位）**
两个分支的尺寸约束全是**百分比**：

```tsx
// MediaViewport.tsx:271（视频分支）
<div className="flex max-h-[82%] max-w-[92%] items-center justify-center"
     style={{ maxHeight: `${STAGE_HEIGHT_PCT}%`, maxWidth: `${STAGE_WIDTH_PCT}%` }}>
// MediaViewport.tsx:306（图片分支）
className="max-h-full max-w-full object-contain select-none"
```

按 CSS 规范，`max-height` 的百分比在父级高度为 `auto` 时**解析为 `none`**。所以纵向没有任何约束。图片只受 `max-w-full` 限制，被撑到舞台宽（约 1500px），3:2 的 RW2 → 高约 1000px，超过可用行高 → 压住/盖住底部胶片条。这就是截图 3 的"完全错位"。

**视频"看起来对"是运气，不是约束。** 16:9 在 92% 宽度下算出约 750px 高 + 45px 控制条，刚好塞得进去。换一个 4:3 或竖屏视频，同样会越界。所以用户说的"把视频浏览的那个区域设置搬过来"，如果字面照做（把 92%/82% 抄到图片分支）**仍然无效** —— 百分比在 auto 父级下依旧解析为 none。必须先修高度链。

### 方案：统一媒体舞台 + 底部标签区

**1) 修高度链（一行，但是全部的前提）**

`ViewerShell.tsx:28` 改为 `flex min-h-0 flex-1 flex-col`，右列变成纵向 flex 容器。此后 `flex-1` / `min-h-0` / 百分比高度全部生效。

**2) 右列改为三段结构**

```
┌─ ViewerToolbar（已有，固定）───────────────────────┐
├── aside 属性栏 ──┬── StageFrame（flex-1，图片/视频共用）──┤
│                  ├── ViewerTagBar（新增，固定高，可折叠）─┤
├─ ViewerFilmstrip（已有，固定）─────────────────────┤
```

标签区**放在右列内、舞台下方**，正好填掉后果 A 的空白 —— 这就是用户"把这下面空白的地方变成标签展示区"的直接落实。

**3) 用 padding 取代 92%/82% 魔数**

舞台 `relative flex min-h-0 flex-1 items-center justify-center overflow-hidden p-4`，媒体 `max-h-full max-w-full object-contain`。理由：
- 百分比在窄窗口会白白浪费 8%/18% 的空间，且 82% 这个数字与控制条实际高度毫无关系（控制条高度变了它不跟着变）；
- padding 无百分比解析陷阱，行为可预测；
- **图片与视频共用同一个 `StageFrame`**，这才真正做到用户要的"图片只允许在那个区域展示"，而且以后加任何媒体类型都自动一致。

**4) 缩放/平移覆盖到视频**

当前 zoom/pan 只在 `!isVideo` 时挂载（`MediaViewport.tsx:149`、`:163` 两处早退）。改为视频也支持：
- Alt+滚轮锚点缩放、双击 1x↔2x、放大后拖拽 —— 全部复用已有的 `zoomAt` / `onPointerDown` / `viewportMath.ts`；
- 事件优先级用现成机制：`VideoPlayer` 根节点有 `data-player-root`（`VideoPlayer.tsx:323`），控制条内的点击已 `stopPropagation`，不会和舞台拖拽冲突；
- 性能：`transform: scale()` 作用在 `<video>` 上是合成层变换，GPU 直接处理，**不会触发重解码**，代价可忽略。

**5) 补边界钳制（现有缺陷）**

`MediaViewport.tsx:196-207` 的 `onPointerMove` 只做 `offset = start + delta`，**没有任何钳制**。放大后可以把图片整个拖出视野，只剩黑屏。需在 `viewportMath.ts` 增加：

```ts
clampOffset(scale, offsetX, offsetY, stageRect, mediaNaturalSize) → { offsetX, offsetY }
```

规则：媒体缩放后若小于舞台则居中锁定；若大于舞台则限制平移量使媒体边缘不越过舞台边缘。

**6) 全屏（图片 + 视频都要）—— 这里有一个 ACL 阻塞点**

现状只有视频有全屏，且实现是：

```tsx
// src/components/media/VideoPlayer.tsx:189-195
const toggleFullscreen = useCallback(() => {
  if (document.fullscreenElement) void document.exitFullscreen();
  else void boxRef.current?.requestFullscreen();
}, []);
```

问题：**Fullscreen API 在 WebView2 里只让元素铺满 webview 视口，不会让操作系统窗口全屏。** 本应用 `decorations: false`（`tauri.conf.json`）+ 自绘标题栏，所以现在点全屏只是"播放器盒子撑满窗口内容区"，标题栏还在，不是真全屏。要真全屏需要同时调 Tauri 的窗口 API：

```ts
await getCurrentWindow().setFullscreen(true);
```

**但 capabilities 没给这个权限**：

```json
// src-tauri/capabilities/default.json
"core:window:allow-minimize",
"core:window:allow-toggle-maximize",
"core:window:allow-close",
"core:window:allow-start-dragging"
```

`core:default` 包含的 `core:window:default` 是只读类命令集合，**不含 `allow-set-fullscreen`**。必须在 capabilities 里补 `core:window:allow-set-fullscreen`，否则调用会被 ACL 直接拒绝。

方案：新增 `useMediaFullscreen(targetRef)`：
- 进入：`requestFullscreen()` + `setFullscreen(true)` 双管；退出反向，并监听 `fullscreenchange`（`VideoPlayer.tsx:285-289` 已有）与窗口侧事件对账；
- 图片与视频共用；
- 触发方式：`F` 键 + 工具栏按钮。**图片不用双击** —— 双击已被 1x↔2x 缩放占用（`MediaViewport.tsx:170-179`），冲突；
- 全屏态下隐藏侧栏与胶片条，只保留媒体 + 自动隐藏的极简控制条（鼠标静止 2s 后淡出）。

**7) ViewerTagBar 设计（FB2-04 的正解）**

- 高度 `h-24`（约两行 chip），可点标题折叠为 `h-8`；内容超出时内部纵向滚动，不挤压舞台；
- chips 复用 `TagChip`（`src/components/library/TagChip.tsx`），删除直连 `ViewerPage.tsx:85-92` 已有的 `removeTag`；

## FB2-06 超级搜索折叠闪烁 + 删除快速编辑条【P0，根因已定位】

### 根因：卸载 ↔ scrollHeight 的正反馈环

**闪烁的核心链条（4 步成环）：**

**① 详细条件面板是条件卸载，不是动画。**

```tsx
// src/pages/SuperSearchPage.tsx:134-140
{chrome === "expanded" && (
  <div className="px-4 pt-3">
    <div className="mx-auto max-w-5xl"><QueryBuilder /></div>
  </div>
)}
```

这与 hook 顶部注释的承诺直接矛盾 —— `useScrollDirection.ts:1-5` 写的是「只返回两态，由调用方决定动画（transform/opacity），本 hook 不触发布局重排」，而调用方实际做的是整块 DOM 卸载。

**② 面板与虚拟化网格共用同一个滚动容器。**

```tsx
// src/pages/SuperSearchPage.tsx:105-108
<div ref={bindScroll} data-testid="super-search-scroll" className="min-h-0 flex-1 overflow-y-auto" onFocusCapture={forceExpand}>
// :143-152 —— 网格把这个容器当外部滚动源
<AssetGridView ... scrollElementRef={scrollRef} {...actions} />
```

**③ 卸载面板 → `scrollHeight` 减少 H（QueryBuilder 约 120~200px）→ 浏览器把 `scrollTop` 向下钳制最多 H → 产生一次负 delta。**

**④ hook 把负 delta 判为"上滚"，累计 15px 后强制展开：**

```ts
// src/hooks/useScrollDirection.ts:36-47
const dir: "down" | "up" = delta < 0 ? "up" : "down";
if (dir !== lastDir.current) { lastDir.current = dir; moved.current = 0; }
moved.current += Math.abs(delta);
if (moved.current >= thresholdRef.current) {
  moved.current = 0;
  setState(dir === "down" ? "collapsed" : "expanded");
}
```

展开 → `scrollHeight` 增加 H → 下一次滚动又收起 → **无限振荡**。用户看到的"一直闪烁"就是这个环在跑。

**两个叠加触发源（会让环更容易起振）：**

**叠加源 1 —— 跨页滚动状态串味。** `AssetGridView` 挂载时会强行写 `scrollTop`：

```tsx
// src/components/library/AssetGridView.tsx:66-72
const saved = useLibraryStore.getState().gridScrollTop;
if (el && saved > 0) el.scrollTop = saved;
```

`gridScrollTop` 存在 `libraryStore.ts:195-196`，是**素材库页**的滚动量。超级搜索页复用了同一个字段和同一个网格组件 → 先在素材库滚到一半，再进超级搜索，网格一挂载就把共享滚动容器跳到别处，立刻触发方向判定。

**叠加源 2 —— 点结果卡片就强制展开。**

```tsx
// src/pages/SuperSearchPage.tsx:109
onFocusCapture={forceExpand}
```

`AssetCard` 是可聚焦的（`AssetCard.tsx:60` `tabIndex={0}`），点任意一张结果都会把 focus 冒泡到容器 → 强制 `expanded` → 内容增高 → 视图跳动。截图 4 里正好是刚点过卡片的状态。

**hook 本身还缺两个常规护栏：** 没有"顶部区域不收起"的最小 `scrollTop` 门槛（在 `scrollTop=20` 处收起摘要条毫无意义）；阈值上下对称（15/15），边界处天然抖动。

### 方案

**方案 A（推荐）—— 把可折叠区移出滚动容器，从根上断掉反馈环。**

结构改为：搜索摘要条 + 详细条件面板都放在**滚动容器之外**的固定 header 区；滚动容器只装虚拟化网格。这样折叠/展开只改 header 高度，**完全不改 `scrollHeight`**，浏览器不会钳制 `scrollTop`，环不成立。

代价：header 展开时会压缩网格可视高度（`flex-1` 自动处理），虚拟化的 `clientHeight` 变化由 `useVirtualizer` 正常处理，不产生递归。这是 Gmail / Notion / Linear 等应用处理"滚动收起顶栏"的标准做法 —— 收起的是壳，滚的是内容，两者不共用同一个滚动上下文。

**方案 B（备选，仅当必须保留现结构时）**：面板保留在 DOM，用 `grid-template-rows: 0fr → 1fr` 或 `max-height + overflow:hidden` 动画收起（避免 `display:none` 导致高度突变），**并且**切换时手动补偿 `scrollTop`（记录切换前后 `scrollHeight` 差值写回）。可行但脆 —— 任何后续在这个容器里加内容都可能重新起振。不推荐。

**方案 C（无论 A 还是 B 都必须做）—— hook 加固：**

```ts
useScrollDirection({
  collapseThreshold: 24,   // 收起要滚得更多
  expandThreshold: 12,     // 展开更灵敏（非对称滞回，消除边界抖动）
  minScrollTop: 48,        // 低于此值恒为 expanded
  suppressMs: 300,         // 程序化改变状态后 300ms 内忽略 scroll 事件
})
```

**方案 D —— 跨页滚动状态隔离。** `AssetGridView` 新增 `scrollRestoreKey?: string | null`：素材库传 `"library"`，超级搜索传 `"superSearch"`（或 `null` = 不恢复）。`libraryStore.gridScrollTop` 改为 `Record<string, number>`。这条即使不修闪烁也该修 —— 现在两个页面的滚动位置是互相污染的。

**方案 E —— focus 强制展开收窄范围。** 只在 `e.target.closest("[data-filter-zone]")` 命中（搜索框 / QueryBuilder 内控件）时才 `forceExpand`，点结果卡片不触发。

### 删除「快速编辑条件」（用户明确要求）

用户的原话是"我的是加一个展开详细对吧，那就不需要单独在下面再加一个快速编辑条件了"—— 判断是对的：同一个功能给了两个入口，而且底部那个还是浮在结果网格上的（截图 4 里它正压着缩略图）。

需要删除的位置：

| 位置 | 内容 |
|---|---|
| `SuperSearchPage.tsx:154-161` | `sticky bottom-2` 的「快速编辑条件」圆角按钮 |
| `SuperSearchPage.tsx:164-182` | QuickEdit 抽屉（含第二个 `<QueryBuilder />` 实例） |
| `SuperSearchPage.tsx:44` | `const [quickEdit, setQuickEdit] = useState(false)` |
| `SuperSearchPage.tsx:62-64` | `useEffect(() => { if (quickEdit) setChrome("expanded"); })` |
| `SuperSearchPage.test.tsx:109-113` | 用例「FB-06：底部快速编辑条打开抽屉」 |

**保留并强化唯一入口** —— `SuperSearchPage.tsx:120-129` 的「⤵ 展开详细条件」。建议改为**常驻双向开关**（收起时显示"展开详细条件 ⤵"，展开时显示"收起 ⤴"），而不是只在收起态出现。理由：滚动方向只应该是"建议"，用户必须能在任何时候手动锁定自己想要的状态；现在展开态下没有任何手动收起入口，只能靠往下滚，这也是闪烁体验被放大的原因之一。

### 验收标准

- 在 259 项结果上连续快速上下滚动 10 秒，条件面板**不出现任何往复闪烁**。
- 先在素材库滚到中段，再进超级搜索，进入时不发生跳动。
- 点击结果卡片不会导致条件面板展开/页面跳动。
- 底部再无浮动的「快速编辑条件」按钮与抽屉。
- 摘要条上的展开/收起按钮常驻可用，手动设定后短时间内不被滚动方向覆盖（`suppressMs` 生效）。

```ts
// src/types/settings.ts:26
videoTagging: boolean;
```

### 现有实现的四个问题

1. **成本 ×3。** 每个视频 3 次视觉 API 调用。云端 API 是 3 倍 token 与 3 倍时延；本地 Ollama 单帧就要数十秒，259 项里的视频批次实际不可用。
2. **第 0ms 帧质量差。** 相机视频开头常是黑场/自动曝光未稳定。截图 1 的夜景素材第 0 秒几乎全黑，等于白花一次 API 调用。
3. **没装 ffmpeg 就完全不能给视频打标。** `extract_keyframes` 找不到二进制直接返回空 vec（`video.rs:380-382` 的 `resolve_binary` 返回 None），然后：
   ```rust
   // ai_cloud.rs:729-734
   if frames.is_empty() {
       return Err(AppError::msg("视频抽帧失败：未安装 ffmpeg 或编码不支持（可在设置关闭视频打标）"));
   }
   ```
   但**封面（placeholder）在入库时就已经生成好了**，用它打标根本不需要 ffmpeg 在打标时可用。
4. **抽帧没走并发闸。** 项目里有 `imaging::acquire()`（`imaging.rs:26,41`，`MAX_PERMITS = 4`）限制并发解码，但 `extract_keyframes` 没用它。批量打标时可能同时拉起大量 ffmpeg 进程打满 CPU。（对比：`preview.rs:49-50` 是正确用了 `imaging::acquire()` 的。）

### 方案

**设置结构**（详见 §9）：

```ts
videoTagging: boolean;                          // 保留：总开关
videoTaggingMode: "cover" | "frames";           // 新增，默认 "cover"
videoFrameCount: number;                        // 新增，2~8，默认 3（仅 frames 模式）
```

**封面打标（`cover`，建议默认）**
- 直接复用 `asset.placeholderPath` 或 `hd` 缩略图，走**与图片打标完全相同的代码路径**；
- **零 ffmpeg 调用、零额外解码、1 次 API 调用**；
- 顺带解决问题 3（未装 ffmpeg 也能打标）；
- 适用场景：静态镜头、单场景素材、追求速度与成本 —— 这是绝大多数库的常态。

**抽帧打标（`frames`）**
- 帧位改为 `d * (i + 0.5) / n` —— n=3 → **16.7% / 50% / 83%**，避开首尾黑场（修问题 2）；
- 阈值随 n 自适应 `ceil(n / 2)`：n=2→1、n=3→2、n=4→2、n=6→3。当前的固定 2 在 n=6 时过松（1/3 的帧命中就通过），n=2 时又过严；
- 抽帧循环内加 `imaging::acquire()`（修问题 4）；
- **失败路径也要清临时目录** —— 现在 `ai_cloud.rs:717-748` 只在部分分支 `remove_dir_all`，中途 API 失败会把 webp 帧留在 `temp_dir/bagertea_kframes_*` 堆积。建议用 RAII guard（Drop 时删目录）而不是散落的清理调用；
- 适用场景：多场景/运镜大的素材、追求标签召回率。

**UI 落点**
- 打标页：`AiTaggingPage.tsx:246-266` 现有「打标模式」分段控件是 AI/手动，**视频子模式作为第二行分段控件**，仅当 `batchHasVideo` 为真时显示（`AiTaggingPage.tsx:131-134` 已有这个判断），避免纯图片批次出现无关选项；
- 设置页：作为默认值（`SettingsPage.tsx` AI 设置区）；
- **成本前置告知**：在「开始打标」按钮上方明示 `抽帧 3 帧 × 12 个视频 = 36 次请求`。让用户按下按钮前就知道代价，比事后看进度条卡住要好得多。`computeAiStats`（`src/utils/aiStats.ts`）已能统计批次内容，加一个视频计数即可。

### 验收标准

- `cover` 模式下：视频批次不产生任何 ffmpeg 进程，API 调用数 = 视频数，未装 ffmpeg 也能正常打标。
- `frames` 模式下：帧位不再取第 0ms；抽帧并发不超过 4；无论成功/失败/取消，`temp_dir` 都无残留。
- 两种模式切换后立即生效（无需重启），且设置落库往返一致（`settingsStore.ts:66-75` 已有保存后回读对账）。
- UI 上能看到本次批次的预估请求次数。

### 新增能力一：算法主色提取

#### 算法选型（这是用户要我"好好调查"的部分）

三类主流色彩量化算法的对比：

| 算法 | 代表实现 | 优点 | 缺点（对本场景） |
|---|---|---|---|
| **中位切分 MMCQ** | Color Thief（JS）、`color_thief` crate | 极快、零依赖、实现简单 | **不输出占比** —— 色条画不出宽窄；低饱和图容易返回"泥灰"色（社区已知问题） |
| **八叉树 Octree** | 多数 GIF 量化器 | 快、内存可控 | 量化格子固定，感知上接近的颜色会被硬切成两块 |
| **k-means（Lab 空间）** | `kmeans_colors` crate（okaneco） | **自带占比**、Lab 欧氏距离≈人眼感知距离、簇心就是真实代表色 | 需迭代，比 MMCQ 慢（但在缩略图尺度上无所谓，见下方性能） |

**结论：用 Lab 空间的 k-means。** 决定性理由是**色条必须有占比**才能画出宽窄不一的分段（这才是"调色师色卡"的信息量所在），而 MMCQ 结构上就不产出占比。Lab 空间聚类的结果也更符合"调色师看到的颜色" —— RGB 空间里欧氏距离与感知距离偏差很大，深蓝和深紫在 RGB 里很近但人眼分得很清。

推荐依赖：
- `kmeans_colors`（okaneco，MIT/Apache-2.0）—— 支持 Lloyd 与 Hamerly 两种算法，配合 `palette` 的 `Lab` / `Oklab` 类型；`Sort::sort_indexed_colors` 直接返回按频次排序的簇心 + `percentage`；
- `palette`（色空间转换：sRGB ↔ Lab ↔ LCh，用于排序与命名）。

> 实施时需 `cargo add` 确认当前版本与 `image 0.25` 的兼容性，并把版本 pin 住 —— 本项目已有对 API 不稳定 crate 锁精确版本的先例（`Cargo.toml:45` `rawler = "=0.7.2"`）。备选方案：若不愿引入新依赖，MMCQ 自己写约 150 行也能跑，但要额外补占比统计，不划算。

#### 提取流程

**在已经生成好的 512px 缩略图上做，不碰原图。**

1. `imaging::decode_thumb(thumb_path, 512)`（`imaging.rs:400` 已有）→ `DynamicImage`
2. 下采样到约 100×100（≈ 1 万像素）
3. 丢弃极端像素：纯黑 `L* < 4` 与纯白 `L* > 96` 且饱和度极低的点（避免整张图的主色被黑边/白底吃掉）
4. sRGB → Lab
5. k-means：`k = 6`，Hamerly，3 次不同随机种子取评分最优的一次（单次 k-means 对初值敏感，多次取优是该库文档建议的做法）
6. 合并 ΔE < 6 的相邻簇（避免色条上出现两块肉眼看不出差别的分段）
7. 输出按占比降序的 `hex + rgb + ratio`，最多 8 条

#### 性能

1 万个点、k=6、Hamerly、3 次 run × 约 20 轮迭代 —— **单张在亚毫秒到几毫秒量级**。259 张走 `rayon`（`Cargo.toml:39` 已有）并行 → **整库一秒级**。

对比 AI 打标：单张视觉 API 调用是**数秒到数十秒**。所以用户说的"色彩这玩意可以直接电脑程序算法直接识别"，量级差距是 3~4 个数量级 —— 这个判断完全站得住。

#### 触发时机（三条路径）

| 时机 | 挂点 | 说明 |
|---|---|---|
| 入库时 | `importer.rs` 生成缩略图之后 | 顺带算，几乎零额外成本（缩略图已在内存里，可省一次解码） |

| 单张重算 | `AssetInfoPanel.tsx:50-63` 的「重新读取」 | 已是现成入口 |

视频取封面帧（`placeholderPath` 已有）计算。v2 可选"取 3 帧平均"。

### 新增能力二：色条 UI（`ColorStrip` 组件）

参考图（Grace Kelly 泳池那张）的形态是**紧贴画面下沿的一条水平色带**，这是 Behance / Cinema Palettes / 调色参考站的通用做法。落地设计：

**形态**
- 一条无缝水平色带，各段按占比分宽；
- 高度分档：`thin` 6px（网格小图）/ `normal` 10px / `thick` 16px（大图浏览）；
- 紧贴媒体下沿，无间隙 —— 有间隙就变成"图表"，贴着才是"色卡"；
- hover 单段显示 `#1B2A3C · 31%`；点击 → 以该色为条件搜索（接 §FB2-08 的 `dominant_hue` 索引列）。

**两个容易做丑的地方**
- **按占比分段 vs 等宽分段。** 参考图是等宽 10 块，但等宽会让 1% 的高光色和 40% 的主色一样宽，信息量低。**建议默认按占比**，设置里给 `equal` 选项让用户选参考图那种观感。
- **深浅主题下的可读性。** 浅色主题下米白色块贴在浅背景上会"消失"。色带整体加 `ring-1 ring-inset`（浅色主题 `black/8`，深色主题 `white/8`），比给每段加边框干净得多。

**无障碍**：`role="img"` + `aria-label="主色：深蓝 31%、米白 22%、橙 14%…"`。

| `colorStrip.showInImportGrid` | boolean | `false` | 入库网格（入库前色板可能还没算） |
| `colorStrip.height` | `"thin"｜"normal"｜"thick"` | `"normal"` | |
| `colorStrip.mode` | `"ratio"｜"equal"` | `"ratio"` | 见上方取舍 |
| `colorStrip.count` | `4｜6｜8` | `6` | 显示前 N 色 |

## 12. 需要你确认的决策点

1. **网格比例默认值**：库以视频为主建议默认 `16:9`，混排建议 `1:1`（当前行为）。选哪个？
2. **`auto`（瀑布流）比例**：本轮不做（需重写虚拟化层），确认可以吗？
3. **色条分段方式**：默认「按占比」（信息量高）还是「等宽」（更接近你给的参考图）？
4. **未知/停用分面 key 的落地策略**：模型返回了已停用的 `color`，是 **丢弃** 还是 **归入 custom**？（现在是错误地落回 `color`）
5. **存量 AI 色彩标签**：保留可搜（推荐）还是提供一键清理并默认执行？
6. **视频打标默认模式**：默认 `cover`（省钱快）还是 `frames`（更准）？
7. **全屏行为**：进入全屏时是否需要真·操作系统窗口全屏（需补 capabilities 权限），还是只在窗口内铺满就够？
8. **`Ctrl/Cmd + =/-` 快捷键**：除 Alt+滚轮外是否也要加？（Alt+滚轮属隐藏手势，新用户发现不了）
