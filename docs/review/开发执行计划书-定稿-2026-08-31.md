## 1. 六个问题的裁决（含数据依据）

### Q1 `visible_in_workbench=false` 的分面怎么迁移？

**裁决：统一按 `enabledForAi` 映射，不做特殊处理。这个问题实际上不存在。**

我把你库里的 `aiFacetConfigs` 全部读出来了：

| facetKey | enabledForAi | visibleInWorkbench | 分面 status | 标签数 |
|---|---|---|---|---|
| scene | true | （未设置） | active | 4 |
| style | true | （未设置） | active | 1 |
| people | true | （未设置） | active | 6 |
| subject | true | **true** | active | 5 |
| composition | true | （未设置） | active | 1 |
| lighting | true | （未设置） | active | 2 |
| color | false | **false** | **inactive** | **0** |

**只有 `color` 一个分面用了 `visibleInWorkbench: false`，而它已经是 `inactive` 状态、0 个标签**（V16 迁移把它停用了，颜色改由算法主色呈现）。

所以 V20 回填时：6 个 `enabledForAi=true` → `ai_and_manual`；`color` → `manual_only`，但它 `status=inactive` 所以哪里都不显示。**零风险，零特殊处理。**

顺带一个发现：你库里 **`purpose` / `technical` / `custom` 三个分面完全没有 `aiFacetConfigs` 条目**。按当前 `build_prompt_context` 的逻辑（只遍历 `ai_facet_configs`），这三个分面**永远不进 AI 提示词** —— 而设置页上看不出任何异常。这正是③诊断的「缺条目 = 静默不参与 AI」，在你的库里是实际发生的。合表后自动消失。

### Q2 系统分面能否物理删除？

**裁决：不允许。但给 `color` 这类「已停用 + 0 标签」的系统分面一个更好的呈现。**

理由：`subject`/`scene` 这些 key 写在代码注释、`key_for_legacy_name` 映射表、迁移种子清单、文档里。物理删除会留下一堆指向不存在 key 的引用。

但你的 `color` 确实是个尴尬状态 —— 停用了、0 标签、还占着列表位置。设置页的处理：**已停用的系统分面折叠进「已停用」区**，只给「恢复」按钮，不给删除。视觉上不占权重，也不会让你觉得「有个删不掉的垃圾」。

用户自建的分面**可以物理删除**（W2-3 的 `delete_tag_facet`），这才是你真正需要的能力。

### Q3 「打标时机 = 自动」删掉还是实现？

**裁决：W0 删掉选项，但在 W5 末尾加一个更轻的替代品。**

数据依据：你库里 **410 张素材，只有 10 张打了标**（`asset_tags` 有 72 行，覆盖 10 个 asset）。也就是说 97.6% 的素材未打标。

「入库即自动打标」这个功能对你有真实价值。但直接实现它涉及：入库管线插钩子、失败重试归属、批次与导入任务的生命周期耦合、取消语义交叉 —— 是个独立特性。

**替代品（W5g，成本极低）**：素材库侧栏「未打标」筛选旁边加一个按钮「把这些送去打标」，一键把当前筛选结果全部塞进 `aiStore.pendingAssetIds` 并跳转打标页。你的实际操作路径从「手动框选 400 张」变成「点两下」。这解决了 90% 的痛点，零管线改动。

真正的「入库即打标」等你用一段时间后再决定要不要。

### Q4 地图视图要做吗？

**裁决：砍掉地图视图。保留定位筛选字段 + 信息面板 GPS 展示。**

这是被数据直接推翻的一条。三个依据：

1. **你的相机是 `DC-S5M2`（松下 S5II），410 张全部是它拍的。这款机身没有 GPS 模块。** 除非你用手机 App 回写坐标，EXIF 里不会有 GPS。
2. **你的库 `user_version=17`，`latitude`/`longitude` 列还不存在** —— V18 迁移都没跑过。
3. 即使跑了 V18 + `rescan_asset_geo_taken` 回填，**大概率是 410 个 NULL**。

做一个只能显示 0 个点的地图视图，是纯浪费。

**保留的部分**（成本极低，且是「已投入未释放」）：
- W3-3a：`QueryBuilder` 加 `latitude`/`longitude`/`has_location` 字段（后端白名单已就绪，纯接线）
- W5f-f5：`mediaMeta.ts` 加「定位」字段（信息面板显示经纬度）

**重新评估的时机**：等你实际入库一批带 GPS 的素材（手机照片 / 带 GPS 的机身 / 无人机素材）后单独立项。届时我建议直接做真地图（瓦片），而不是 SVG 散点 —— 因为那时候点数会多到需要聚合。

### Q5 设置页「通用外观」精简要做吗？

**裁决：做，但降级为 W4 的 optional，工期紧就砍。**

`colorStrip` 用 7 个控件（`enabled` + 3 个位置开关 + `height` + `mode` + `count`）表达一个「要不要显示色条」，是过度配置的典型。但它不影响任何功能，纯体验。

### Q6 工期与交付批次？

**裁决：分两批。**

| 批次 | 内容 | 工期 | 交付后你能做什么 |
|---|---|---|---|

## 3. 由数据触发的两项范围变更

### 3.1【新增，高优先】RAW 宽高缺失 —— 影响你 50% 的素材

**问题**：`importer.rs` 的 `extract_meta()` 对图片走 `image::image_dimensions(file)`。这个函数**不支持 RW2**（image crate 无 RAW 解码器）→ 返回 Err → `width`/`height` 保持 NULL。

我核实了它不会被任何回填补上：
- `update_media_metadata()` 是唯一的宽高回写函数，调用点只在 `media_refill.rs`
- `list_video_ids_needing_metadata()` 的 WHERE 是 `mime_type LIKE 'video/%' OR duration_ms IS NOT NULL` → **图片永远不入选**
- `exif_meta.rs` 不提取宽高（grep 确认）

**后果**（你已经能看到但可能没归因）：

| 影响 | 说明 |
|---|---|
| 「分辨率」分面 | `list_metadata_facets` 的 present 条件是 `width IS NOT NULL AND height IS NOT NULL` → **205 张 RAW 完全不出现在分辨率分面里** |
| `resolution` / `aspect_ratio` 搜索 | NULL 不命中 → 搜「横图」「大于 2000 万像素」对 RAW **永远 0 结果** |
| 信息面板 | RAW 的「分辨率」一栏空白 |
| `cellFit: "smart"` | 智能填充依赖宽高比，RAW 退化 |

**修法（W1-4）**：`rawler` 的 `decode_file()` 返回的 `RawImage` 有 `.width` / `.height` 字段（`raw_decode.rs:31` 在用）。两条路：

- **A（推荐）**：新增 `raw_decode::probe_dimensions(path) -> Option<(u32,u32)>`，只读 `rawler::decode_file()` 的 width/height 就返回，**不做 binning、不做色彩管线**。入库时 `image_dimensions` 失败且是 RAW 白名单扩展名 → 走这条。
- B：等生成高清缩略图时搭车回写（`imaging.rs:401 decode_thumb` 已有 `img.dimensions()`）。但那是懒加载，用户不滚到就永远没有。

选 A。同时提供 `rescan_image_dimensions` 回填命令处理你已入库的 205 张（照抄 `rescan_asset_palette` 模式）。

**为什么这项比地图视图重要**：它影响你 50% 的素材、4 个已交付功能，且是「用户会遇到但不知道为什么」的类型。地图视图影响 0 张素材。

### 3.2【新增，必做】同源文件组（RAW+JPG）—— 205 组

**现状**：你的 205 组 `_1091396.JPG` + `_1091396.RW2` 被当成 **410 个完全独立的素材**。

| 场景 | 当前行为 |
|---|---|
| AI 打标 | **发 410 次请求，其中 205 次是重复内容** |
| 标签 | 给 JPG 打的标签，RAW 没有 |
| 精确去重 | 查不出（hash 不同，实测重复组 = 0） |
| 浏览 | 网格里每张照片出现两次 |
| 导出 | 选「全部」导出双份 |
| 删除 | 删了 JPG，RAW 还在 |

**你的定案（2026-08-31）**：「不用独立管理，算同一张照片。因为它们是同样的内容，所以打标时可以省点力。但素材库里还是要独立显示，加一个开关让用户自己选是否合并显示。」

据此分三层，**每层的默认值不同**：

| 层 | 语义 | 默认 | 收益 |
|---|---|---|---|
| **数据层** | 两条 `assets` 记录**永远独立** | — | 不动现有任何查询/计数语义 |
| **打标层** | 视为同一张照片：AI 只打一次，标签自动同步 | **开** | **请求量 410 → 205，成本与时间直接减半** |
| **浏览层** | 素材库默认独立显示 410 项；开关可切合并（205 项 + 「+RAW」角标） | **关** | 你要的「还是独立显示」 |

判定方式：**同目录 + 同主干名 + 一个 RAW 一个非 RAW**。零解码、零新列、不建表 —— 从现有 `file_path` 派生（实测你的 205 组主干名完全配对，无一例外）。

详细设计与边界见 [W5h](#w5h-同源文件组rawjpg本文档新增必做)。**排期从「最后 optional」提到「W5 第二位、必做」**，因为 W5d（phash）依赖它的判定函数，且 W5a（提示词）的验收基准会被批次去重影响。

### 3.3 顺带调整：视频相关项全部降级

你库里 **0 个视频**。以下项从「必做」降为「保持现状不动」：

| 项 | 原计划 | 调整 |
|---|---|---|

| `duration_ms` 分面 | W0-2 修高亮 | **仍然修**（成本 1 行，且以后会用到） |
| 视频代理转码 | 已有 | 不动 |
| `media_kind` 不可空化 | ② 提到「更稳妥」 | **不做**。前端 `isVideoAsset` 有三层兜底，408 个 NULL 无实际影响 |

## 6. 迁移设计（V19 / V20 / V21）

### 6.0 W1-0：先让 V18 落地

你的库 `user_version=17`，代码已写到 v18。**W1 第一步是用当前 main 分支代码启动一次应用**，让 `migrate_v18`（GPS 经纬度列）跑完，确认 `user_version=18`。

### 6.1 V19：数据列

### 6.2 为什么分三段而不合成一个 V19

② 主张「单一 V19 承载全部变更」。我拆成三段，**核心理由是失败粒度**：

| 段 | 操作 | 风险 |
|---|---|---|
| V19 | 纯 `ALTER ADD COLUMN` + `CREATE INDEX` | 极低 |
| V20 | 读写 `settings` JSON 回填 | 中 |
| V21 | 重建 FTS 触发器（体系经 V1→V3→V8→V17 演进，注释记录两个实测坑） | **高** |

合成一个 → V21 炸了，`user_version` 没提交 → V19 的四列和 V20 的回填全部作废，下次启动重跑全部。拆开后 V21 失败只丢 V21，前两段已提交可用。

代价是多两个版本号，几乎零成本。

### 6.3 V20：分面合表

```rust
/// V20：分面单一事实源（低风险段）。settings.aiFacetConfigs 的语义搬进 tag_facets。
/// 幂等：add_column_if_missing + UPDATE 回填（可重跑）。
fn migrate_v20(conn: &Connection) -> AppResult<()> {
    let now = chrono::Utc::now().timestamp_millis();

    // ① 加列。SQLite 的 ALTER ADD COLUMN 不能带 CHECK（实测 tag_facets 已有 3 个 CHECK，
    //    但只能建表时声明）→ input_mode 靠 Rust 层 validate 兜底。
    add_column_if_missing(conn, "tag_facets", "input_mode",
                          "TEXT NOT NULL DEFAULT 'ai_and_manual'")?;

    // ② 回填。实测你的库：6 个 enabledForAi=true → ai_and_manual；color(false) → manual_only。
    //    hint 并入 description（拼接不覆盖，instr 守卫防重跑重复拼）。
    let s = settings::get_settings(conn)?;
    for cfg in &s.ai_facet_configs {
        let mode = if cfg.enabled_for_ai { "ai_and_manual" } else { "manual_only" };
        conn.execute(
            "UPDATE tag_facets SET
                input_mode = ?2,
                description = CASE
                    WHEN ?3 = ''                    THEN description
                    WHEN trim(description) = ''     THEN ?3
                    WHEN instr(description, ?3) > 0 THEN description
                    ELSE description || char(10) || ?3
                END,
                display_name = COALESCE(NULLIF(trim(?4), ''), display_name),
                updated_at = ?5
              WHERE key = ?1",
            params![cfg.facet_key, mode, cfg.hint.trim(),
                    cfg.display_name.as_deref().unwrap_or(""), now])?;
    }

    // ③ 无 aiFacetConfigs 条目的分面（实测你的库：purpose / technical / custom 三个）
    //    保持列默认 ai_and_manual。但 purpose / technical 天然是手工类 → 修正。
    //    守卫：只改「还没有任何标签」的分面，不覆盖已在用的配置。
    //    （实测这三个分面标签数均为 0，会被修正）
    conn.execute(
        "UPDATE tag_facets SET input_mode='manual_only', updated_at=?1
          WHERE key IN ('purpose','technical') AND is_system=1
            AND NOT EXISTS (SELECT 1 FROM tags WHERE facet_key = tag_facets.key)",
        params![now])?;

    // ④ 清空 JSON 侧（此后 Settings.ai_facet_configs 为 skip_serializing）
    let mut s2 = settings::get_settings(conn)?;
    s2.ai_facet_configs.clear();
    settings::save_settings(conn, &s2)?;
    Ok(())
}
```

**实测预期结果**（可直接作为验收断言）：

| key | input_mode | 依据 |
|---|---|---|
| subject / scene / style / composition / lighting / people | `ai_and_manual` | `enabledForAi: true` |
| color | `manual_only` | `enabledForAi: false`（且 `status=inactive`，哪里都不显示） |
| purpose / technical | `manual_only` | 无配置条目 + 0 标签 → 走 ③ 修正 |
| custom | `ai_and_manual` | 无配置条目，列默认值。**这是对的** —— custom 是 AI 未知词的落脚点 |

### 6.4 V21：FTS 触发器补分面状态联动

**当前缺陷**：触发器只看 `tags.status`，不看 `tag_facets.status`。停用分面后，该分面下的标签**仍能被全文搜到** —— 与「停用标签立即消失」语义不一致。

```rust
/// V21：FTS 触发器加分面状态联动（高风险段）。独立版本号使其可单独延后。
fn migrate_v21(conn: &Connection) -> AppResult<()> {
    rebuild_fts_triggers_with_facet_status(conn)?;
    conn.execute_batch("INSERT INTO assets_fts(assets_fts) VALUES('rebuild');")?;
    Ok(())
}
```

两处改动：

**① 聚合子查询加分面条件**（`trg_at_ai` / `trg_at_ad` / `trg_tags_au` / `trg_tag_alias_*` 全部）：

```sql
WHERE at.asset_id = <ref> AND t.status = 'active'
  AND EXISTS (SELECT 1 FROM tag_facets f
               WHERE f.key = t.facet_key AND f.status = 'active')
```

**② 新增分面状态触发器**：

```sql
CREATE TRIGGER trg_facet_status_au AFTER UPDATE OF status ON tag_facets BEGIN
  UPDATE fts_content SET tag_names = (<同上聚合子查询>)
   WHERE asset_id IN (
     SELECT at.asset_id FROM asset_tags at JOIN tags t ON t.id = at.tag_id
      WHERE t.facet_key = new.key
   );
END;
```

**铁律**：① **复制现有 SQL 再改**，不要手写新聚合；② 改完立即 `rebuild`；③ 先在内存库跑通全部 FTS 测试再上真库。

### 6.5 驱动层 + V1 事务修复

```rust
pub fn migrate(conn: &Connection) -> AppResult<()> {
    let version: i64 = conn.query_row("PRAGMA user_version", [], |r| r.get(0))?;
    if version < 1 {
        // W0-8：V1 建库包事务。全裸 CREATE TABLE 非幂等，
        // 首装中途崩溃 → 重跑报 "table already exists" → 启动永久阻断。
        let tx = conn.unchecked_transaction()?;
        tx.execute_batch(SCHEMA_V1)?;
        tx.commit()?;
        conn.pragma_update(None, "user_version", 1)?;
    }
    // ... v2..v18 不动 ...
    if version < 19 { migrate_v19(conn)?; conn.pragma_update(None, "user_version", 19)?; }
    if version < 20 { migrate_v20(conn)?; conn.pragma_update(None, "user_version", 20)?; }
    // V21 = FTS 触发器（高风险）。独立版本号使其可单独延后。
    if version < 21 { migrate_v21(conn)?; conn.pragma_update(None, "user_version", 21)?; }
    Ok(())
}
```

| **为什么放在 `assign_inner` 而不是各调用点** | 五个调用点分别处理必然漏一个；`assign_inner` 是收口位置。且它已经有 `source` / `batch_id` 参数，语义天然 |
| 撤销正确性 | `undo_batch` 按 `tag_ops` 倒序反向操作。同源写入各有独立流水行 → 撤销自动覆盖两条，无需特殊处理 |

## 10. 全局不变量

施工期禁止破坏。**每次提交前对照检查。**

### 架构层
1. 前端禁止直连 `invoke`，必须走 `src/api/*.ts`
2. commands 是薄壳（校验 + 锁 + 事件），services 持业务，db 只管 SQL
3. **DB 写操作必须短暂持锁；网络/解码放锁外**
4. 旧字段迁移用 `skip_serializing` 只读模式，禁止新旧双源并行写

### 数据层
5. **`COLUMNS` 是位置映射，新列只能追加末尾**（插中间静默错位，编译和测试都不报错）
6. `PRAGMA foreign_keys=ON` 是全部 CASCADE 的前提（`db/mod.rs:28`），必须有测试守护
7. 删除关联必须**先删 `asset_tags` 再删 `tags`**（让 FTS 触发器有机会跑）
8. 合并标签走 DELETE+INSERT 而非 UPDATE 改挂（同上理由）
9. **手工覆盖必须清 `source_batch_id`**（D-1/D-2），否则撤销 AI 批次误删手工标签
10. FTS 短语必须加双引号；写入侧与查询侧必须用同一 `cjk_bigram`
11. 外部工具连此库**只能 SELECT**（缺 `cjk_bigram` 函数，DELETE/UPDATE 会报错）

### 分面协议层
12. **`tag_facets.key` 永不可改**，显示名可本地化
13. `selection_mode` / `max_items` 只以 DB 为准；**`max_items = NULL` 表示不限，不得回退到 3**
14. **AI 打标与 AI 搜索必须读同一个 `FacetPromptContext`**（有交叉测试守护）
15. **`resolve_facet_key` 是唯一的分面 key 路由入口**；`key_for_legacy_name` 只查中文旧名表
16. AI 返回未知 key 必须产生 warning，不允许静默丢进 custom

### 同源文件层（W5h 之后生效）
17. **同源关系是从 `file_path` 派生的，不存储**。禁止建表、禁止加 `kinship_group_id` 列
18. **数据层两条 `assets` 记录永远独立**。合并只发生在打标层（语义）与浏览层（显示），不发生在数据层
19. **同源标签同步只能在 `asset_tags::assign_inner` / `remove` 里做**（唯一收口位置），禁止在各调用点分别处理
20. **同源写入必须为每条真实写入各记一行 `tag_ops`**，否则 `undo_batch` 无法对称回滚
21. **合并显示只做前端折叠**，禁止改后端 `build_where` / `total` / `list_ids` / 分面 COUNT 的语义

### AI 层
22. **确认前的 AI 建议绝不写入 `asset_tags`**（防污染标签体系）
23. 拒绝/删除不做物理删除，翻转状态（`rejected` 可恢复，标签 `deprecated`）
24. **用户所选素材完整进入逻辑批次，不做静默截断**；`batchLimit` 只是执行层分块
    - **W5h 例外**：同源去重不是「截断」—— 代表确认后标签会同步给同源文件，最终两条都有标签。UI 必须明示合并了多少组

### 搜索层
25. AI 只输出 `SearchIntent`，不输出 tagId / SQL / 列名 / 分页 / trashOnly
26. **列名与 op 只来自白名单 `match`，值 100% 参数绑定**
27. 日期左闭右开、大小字节、时长毫秒、NULL 不命中 —— 已冻结
28. 排序尾缀必须加 `a.id DESC`（分页稳定）
29. **`AssetFilter.expr` 与扁平字段严格二选一**，expr 存在时后端完全忽略扁平字段
30. 超级搜索默认不查回收站；AI 搜索零数据库写入

### 12.4 W5h 已定案（原「待确认」）

**你的答复（2026-08-31）**：「不用独立管理，算同一张照片。因为它们是同样的内容，所以打标时可以省点力。但素材库里还是要独立显示，加一个开关让用户自己选是否合并显示。」

这个答复比我预设的两个选项都更准确 —— 它把「同一张照片」这件事按**层**拆开了，而我原来是当成一个整体在问。据此定案的三层边界（见 W5h）：

| 层 | 你的要求 | 实现 | 默认 |
|---|---|---|---|
| 打标 | 「算同一张照片」「省点力」 | 批次去重（410→205 次请求）+ 标签自动同步 | 开 |
| 浏览 | 「还是要独立显示」 | 素材库仍渲染 410 项 | — |
| 开关 | 「用户自己选是否合并」 | `appearance.kinship.mergeInLibrary`，前端折叠 | 关 |

**这个拆分带来一个我原本没想到的收益**：因为数据层完全不动（两条 `assets` 记录独立），合并显示可以做成纯前端折叠 —— 不需要碰 `build_where` / `total` / `list_ids` / 分面 COUNT 这五处计数语义。如果按我原来「合并成一张照片」的理解去做，就必须动后端查询层，风险高一个量级。

**排期变更**：W5h 从「最后 optional」提到「W5 第二位、必做」。两个依赖迫使它必须前置：
- W5a（提示词）的完成条件是「同一批 20 张图对比三指标」—— 先改提示词再改批次去重，基准会漂
- W5d（phash）的 `scan_similar_groups(exclude_kinship)` 需要 `kinship_key()`；且不排除同源的话，205 组 RAW+JPG 会淹没真正的连拍重复

### 12.5 这次改动我自己不确定的一处

**W5h-d 的「选中代表 → 批量操作作用于整组」这条语义，我不确定是否符合你的直觉。**

场景：合并显示开启时，你选中一个代表（JPG），点「删除」。我的设计是删除整组（JPG + RAW），弹窗明示「将删除 N 组共 M 个文件」。

另一种可能是你只想删代表。但那会留下孤立的 RAW（合并显示下它不可见 → 变成看不见的残留），比删整组更糟。

所以我选了「作用于整组 + 明示数字」。**如果你实际用起来觉得不对，这条改起来很便宜**（只是 `AssetGridView` 的选中集展开逻辑），不影响其他任何部分。
