## 1. 结论先行

这批反馈不是几个孤立的样式问题，而是四条基础链路没有完全闭环：

```text
媒体交互链路
  点击/缩放 -> DOM 生命周期 -> 图片/视频舞台 -> 错误边界 -> 返回素材库

素材展示链路
  入库清单/素材卡片 -> 缩略图 -> 内嵌视频预览 -> 完整查看器

搜索理解链路
  自然语言 -> 词典/分面匹配 -> 颜色等视觉属性 -> 查询执行 -> 结果滚动与筛选

本地 AI 链路
  设置 -> 服务启动 -> 模型加载 -> 请求 -> 空闲卸载 -> 服务停止 -> 内存回收
```

当前代码已经具备一些正确方向，例如：`MediaViewport` 使用 `clientX/clientY + getBoundingClientRect()`、`AssetGridView` 使用 TanStack Virtual、视频元数据服务有 ffprobe 超时和结构化字段、AI 搜索已有 `SearchIntent` 与后端标签解析。但用户反馈说明这些能力在运行时、入口一致性和生命周期管理上仍然不完整，尤其是：

1. 生产构建仍可能执行旧的 `offsetX` 路径，或存在未覆盖的空 DOM 引用路径。
2. 设置页没有全局页面级 Error Boundary，任何子组件异常都可能被用户感知为白屏。
3. Ollama 当前只有“启动”能力，没有由应用拥有并可回收的服务句柄、空闲卸载和停止策略。
4. 超级搜索只把自然语言转成有限字段，尚未把“建筑 + 红色”拆成“主体标签 + 主体色”，且标签词典每分面只取 30 个词，召回不稳定。
5. 筛选条件区域采用固定顶部布局，条件变多时直接挤压结果网格，没有“滚动时收缩、上滑时恢复”的闭环。
6. 设置页右侧内容被 `max-w-xl` 限制，导致大屏上出现“小框挤大区域”的观感。
7. 视频打标开关虽然存在于当前源码，但错误文案、入口路径、保存状态和后台实际配置之间没有统一的可验证契约，因此用户会看到“设置里没有，执行时却提示未开启”。

## 3. P0-01 查看器缩放空引用崩溃

### 3.1 用户现象与风险

用户点击图片进入查看器，再放大时出现：

```text
TypeError: Cannot read properties of null (reading 'offsetX')
```

这是 P0，因为它会把局部交互错误升级为页面不可用。错误发生在放大操作，最可能涉及鼠标/指针事件、图片或舞台节点卸载、异步回调晚于组件生命周期执行等情况。

### 3.2 当前代码事实

当前工作区的 `MediaViewport.tsx` 已经不直接读取 `offsetX`，而是通过：

```text
stageRef.current?.getBoundingClientRect()
clientX/clientY - 舞台中心
```

计算缩放锚点，见 `MediaViewport.tsx:84-96`。因此当前源码与用户报错不完全一致，必须把“源码、开发服务器、打包产物、用户实际运行版本”视为四个待核对对象。`dist/assets/index-hFj5IFiB.js` 是已生成的旧/当前构建产物，不能因为源码已经改过就假设用户运行的二进制已经包含修复。

可能根因分为三类：

1. **旧构建产物仍含旧实现**：用户启动的是未重新构建的 dist 或旧安装包。
2. **另一个查看器/预览路径仍读取空对象**：例如媒体预览浮层、旧组件、事件回调中的 `target`/`currentTarget` 在卸载后变成 null。
3. **生命周期竞态**：指针按下后切换素材、关闭查看器或错误边界重置，异步/原生事件回调仍执行；回调内部直接读取节点属性。

### 3.3 推荐方案

采用“稳定容器坐标 + 代际保护 + 错误边界”的三层方案：

**第一层：坐标计算单一化**

- 所有缩放和平移入口统一调用 `getPointerInStage(clientX, clientY, stageElement)`。
- 只接受 `clientX/clientY`，不依赖 React SyntheticEvent 的扩展属性，也不读取 `event.target.offsetX`。
- 计算前检查 `stageRef.current`、`getBoundingClientRect()` 和宽高是否有效。
- `offsetX/offsetY` 只允许作为兼容层，不得成为业务状态字段或 DOM 节点属性读取路径。

**第二层：生命周期与代际保护**

- 每次 `assetId` 变化、关闭查看器、图片源变化时递增 `viewGeneration`。
- 原生 wheel、pointer、图片加载回调捕获 generation；回调执行前检查 generation 仍有效。
- 卸载时移除 wheel listener、释放 pointer capture、清空拖拽起点。
- 双击缩放、Alt+滚轮、触摸 pinch 使用同一 reducer/状态机，避免多个实现互相覆盖。
- 图片节点使用稳定 `key={assetId}`，切换素材时重置 `scale/offset/mode`。

**第三层：局部错误恢复**

- 查看器错误不应卸载整个 App。
- 错误页必须提供“重新加载当前素材”“返回素材库”两个明确动作。
- 重试应重新拉取素材 URL/高清图，而不是只 `window.location.reload()`；整页重载作为最后兜底。
- 错误日志需包含 `assetId`、文件名、事件类型、scale、节点是否存在、构建版本。

### 3.4 验收标准

- 图片 1x、2x、8x、缩小到 0.2x 均不抛异常。
- 放大后拖拽到舞台外再松开，不会卡在 `panning` 状态。
- 缩放过程中快速切换上一张/下一张，旧回调不会修改新素材状态。
- 关闭查看器后再触发延迟事件，不出现 null 引用。
- 开发构建与生产构建各执行一次同样的 Playwright/桌面手工流程。
- 错误页可在不重启应用的情况下返回素材库继续使用。

### 3.5 外部依据

- React 关于 `offsetX` 的长期讨论指出，`SyntheticEvent` 不保证提供 `offsetX`；推荐使用 `nativeEvent` 或用目标容器的 `getBoundingClientRect()` 计算：<https://github.com/facebook/react/issues/4431>
- MDN 定义 `MouseEvent.offsetX` 是相对事件目标节点的坐标，事件目标变化时语义也会变化：<https://developer.mozilla.org/en-US/docs/Web/API/MouseEvent/offsetX>
- 一个可读性较好的 React pan/zoom 实现把平移、缩放和容器矩形计算拆成独立状态机：<https://jkettmann.com/jr-to-sr-refactoring-react-pan-and-zoom-image-component>

## 4. P0-02 异常恢复与错误边界

### 4.1 问题定义

用户给出的文案“页面数据或某个模块出现异常，可以重新加载，或返回素材库继续使用”本质上是产品级错误恢复要求，而不是普通 Toast。当前 `settingsStore` 有 `loadError` 重试，但 `App.tsx` 没有页面级 Error Boundary；任何设置、查看器或子组件 render 异常都可能让整个 React 树进入白屏。

### 4.2 推荐的错误分层

| 层级 | 捕获范围 | 恢复动作 |
| --- | --- | --- |
| App 边界 | 路由、标题栏、底栏 | 重新加载应用、返回素材库 |
| 页面边界 | 设置、超级搜索、AI 打标、入库 | 重试页面数据、返回上一页 |
| 模块边界 | Ollama 面板、视频预览、标签树 | 重试模块、隐藏非关键模块 |
| 请求错误 | IPC、HTTP、ffprobe、媒体加载 | 重试请求、切换降级路径 |

错误状态要区分：

- `loading`：正在读取，不显示错误。
- `request-error`：数据请求失败，可重试。
- `render-error`：组件渲染失败，保留错误 ID 和返回入口。
- `media-error`：单个文件不可预览，不影响其他素材。
- `configuration-error`：设置缺失或不兼容，需要跳转设置。

### 4.3 重要设计约束

- 错误边界中不要再次渲染可能抛错的原页面。
- “重新加载”必须真正重新请求并清理旧状态，不能只把 `error` 设为 null。
- 返回素材库要保留网格筛选和滚动位置；当前 `AssetGridView` 已有 `gridScrollTop`，应作为恢复契约。
- 错误日志仅写本地诊断目录，用户界面展示可读原因，不展示完整堆栈。

## 5. P0-03 本地模型、服务和内存治理

### 5.1 当前缺口

当前 `ollama_start_service` 最终调用 `start_service_inner()`，在 Windows 上执行 `cmd.spawn()` 后立即丢弃子进程句柄，见 `src-tauri/src/services/ollama_installer.rs:812-827`。这意味着应用无法可靠判断：

- 该服务是否由本应用启动；
- 当前是否还有 AI 请求；
- 模型是否仍驻留 RAM/VRAM；
- 空闲多久后可以卸载；
- 应用退出时是否应该停止该服务。

Ollama 官方 API 已提供模型生命周期参数：`keep_alive` 默认约 5 分钟，设置为 `0` 可在请求结束后卸载模型；`/api/generate` 和 `/api/chat` 都支持该参数：

- <https://docs.ollama.com/api/generate>
- <https://docs.ollama.com/api/chat>
- <https://github.com/ollama/ollama/blob/main/docs/api.md>

当前项目的 `ai_cloud.rs:162-180` 已有一次异常后 `keep_alive=0` 的卸载补救，但这只是“模型输出退化时的自愈”，不是正常业务生命周期管理。

### 5.2 目标行为

用户不使用本地 AI 时：

1. 不自动启动 Ollama，除非用户点击“本地打标/本地搜索”或开启明确的自动打标策略。
2. 首次使用时检查服务；已安装但未运行才启动。
3. 请求结束后不立即杀服务，采用短暂 idle grace period，避免连续批次反复启动。
4. 空闲达到阈值后先卸载模型，再按策略停止由应用启动的服务。
5. 如果服务原本由用户或系统启动，应用不得擅自停止，只能卸载自己使用的模型。
6. 应用退出时取消排队任务、卸载模型、停止应用拥有的服务进程。

### 5.3 推荐架构：Local AI Runtime Manager

新增一个后端运行时管理器（报告阶段只定义方案，不修改代码）：

```text
LocalAiRuntimeManager
  ├── ownership: none | app_owned | external
  ├── process: child handle / pid / start time
  ├── active_requests: atomic counter
  ├── active_model: model name
  ├── last_activity_at
  ├── memory_budget: RAM/VRAM soft limit
  ├── idle_unload_timer
  └── state events: starting/ready/busy/unloading/stopped/error
```

推荐生命周期：

```text
idle
  -> ensure_ready()             // 仅在真正需要时
starting
  -> ready
ready + request
  -> busy
busy + request_count=0
  -> grace period (默认 60~180s)
grace timeout
  -> POST /api/generate {model, keep_alive: 0}
  -> unloaded
  -> stop app-owned service (可选)
```

### 5.4 请求层改造原则

- 对 Ollama 原生接口明确传 `keep_alive`，不要依赖默认值。
- 图片/视频打标请求完成后传 `keep_alive: 60s` 或产品设置的短时值；批量连续执行时由运行时管理器延长 lease。
- 空闲卸载调用原生 `generate`/`chat` 的空消息 + `keep_alive: 0`，并验证响应中的 `done_reason=unload`。
- OpenAI 兼容端点不一定透传 `keep_alive`，本地档案应提供原生 Ollama 地址或专用卸载命令。
- 单进程最多加载一个大视觉模型；切换模型前先卸载旧模型。
- 并发请求默认为 1，批量通过队列而非并发复制模型实例。

### 5.5 内存预算与性能指标

建议设置页提供“本地 AI 资源策略”，默认值如下：

| 指标 | 默认建议 | 超限动作 |
| --- | ---: | --- |
| 同时运行的本地 AI 请求 | 1 | 排队 |
| 图片编码上传上限 | 1920px、JPEG quality 80~85 | 超过则缩放/压缩 |
| 视频抽帧数量 | 3 帧 | 不增加模型并发 |
| 预览视频时长 | 5 秒 | 到时暂停并卸载元素 |
| 模型空闲卸载 | 120 秒 | `keep_alive=0` |
| 应用拥有服务空闲停止 | 300 秒 | 停止服务进程 |
| 缩略图缓存 | 现有设置值 | LRU 清理 |
| 视频代理缓存 | 有上限、可清理 | 超限按 LRU 删除 |

必须观测：应用 RSS、WebView JS heap、Ollama 进程 RSS、GPU 显存、缩略图缓存字节数、视频代理缓存字节数、IPC payload 大小、队列长度。

### 5.6 安全边界

- 只停止 `ownership=app_owned` 的进程。
- 启动时若端口已有服务，标记为 `external`，不杀进程。
- 服务停止失败不阻塞应用退出，但要记录 warning。
- 模型卸载失败时展示“模型可能仍占用内存”的可执行提示，而不是假装已释放。

## 6. P0-04 视频 AI 打标设置与运行时错误脱节

### 6.1 当前事实

设置页当前在“AI 设置 -> 自动打标”路由中渲染：

```text
src/pages/SettingsPage.tsx:549-552
label = 视频 AI 打标
value = draft.ai.videoTagging
```

后端在 `ai_cloud.rs:769-774` 读取 `cfg.video_tagging`，关闭时返回带有路径的错误。问题不在于完全没有字段，而在于用户实际体验中的链路可能断裂：

```text
设置页异常/路由不明显/修改未保存
  -> 前端看不到或无法持久化开关
  -> 后端读取旧配置
  -> 视频批次提示“未开启”
```

此外，当前错误文案把路径写死为“设置 → 在线打标”，而设置页实际 IA 是“设置 → AI 设置 → 自动打标”，文案与 UI 不一致会进一步增加误解。

### 6.2 推荐方案

**单一配置事实源**

- `videoTagging` 只在 settings store/数据库保留一份。
- 设置页、AI 打标页、批次预检、后端执行全部读取同一份配置。
- 保存后立即重新读取并显示 revision/timestamp，证明后端已接受。

**批次启动前预检**

```text
批次包含视频？
  否 -> 直接开始
  是 + videoTagging=true + 当前服务支持视觉输入 -> 开始
  是 + videoTagging=false -> 阻止启动，提供“打开设置”
  是 + 本地模型不支持视觉输入 -> 阻止启动，提供“更换模型”
  是 + ffmpeg 缺失 -> 显示安装/关闭视频打标选项
```

**错误文案统一**

- `视频 AI 打标未开启：设置 → AI 设置 → 自动打标 → 视频 AI 打标`。
- `当前本地模型不支持图片输入，请更换视觉模型`。
- `视频抽帧失败：未安装 ffmpeg 或编码不支持`。
- `设置已修改但尚未保存，请先保存`。

**设置页降级**

- Ollama 探测失败只影响“服务管理/本地模型”模块，不影响“视频 AI 打标”开关显示。
- 自动打标路由必须在没有本地服务时仍能编辑云端配置和视频开关。
- 批次页显示当前有效配置摘要，避免用户猜测后台到底读取了什么。

## 7. P1-01 入库与素材库取消大悬浮框，改为卡片内播放

### 7.1 当前问题

`MediaPreviewPopover` 使用 `position: fixed`，默认放在触发器下方，最大宽度约 420px、最大高度 70vh；`VideoPreviewContent` 使用固定 `h-64 w-full`。这与用户要的“就在它自己小小的框里，视频自己播放，像素材库一样”不一致：

- 浮层脱离卡片上下文；
- 会遮挡邻近素材；
- 卡片尺寸与预览尺寸不一致；
- 滚动时固定定位需要持续重算；
- 多个悬浮组件同时挂载可能造成视频解码和内存浪费。

### 7.2 推荐交互

```text
卡片容器 relative aspect-ratio: 1
  ├── 封面/缩略图 absolute inset-0
  ├── 视频层 absolute inset-0（仅 hover/focus 后挂载）
  └── 角标、时长、文件名 overlay
```

规则：

1. 视频只在指针停留 250~350ms 后挂载，避免快速扫过大量卡片时创建 `<video>`。
2. 播放层覆盖原卡片，不默认移动到上下方。
3. 尺寸默认 1:1；如需放大，仅在卡片中心以 1.15~1.3 倍放大，并由容器裁剪，不能使用固定 420px。
4. `muted + playsInline + preload="metadata"`，播放失败退回封面并显示轻量状态。
5. 离开卡片立即 `pause()`、清空 `src` 或卸载视频元素，释放解码器。
6. 同一时间最多允许 1 个悬浮视频播放；键盘 focus 与触摸设备采用点击预览，不使用 hover。
7. 双击仍进入完整 Viewer，悬浮播放不能抢占双击事件。

当前 `AssetCard.tsx` 的注释已经表达“素材库禁止大图/视频 hover 预览”，而旧的 media preview 组件仍存在，说明代码基线可能处于迁移中。实施前应先清理入口，避免一部分页面走旧 Popover、另一部分页面走卡片内层。

### 7.3 性能控制

- 虚拟列表只对可见卡片注册 hover 监听。
- 预览视频不生成 1024px 高清图，不自动转码。
- 使用 `IntersectionObserver` + hover intent 双重门槛。
- 对同一文件的预览 URL 做短期缓存，但不缓存 `<video>` 实例。
- 记录预览播放失败率、平均首帧时间、同时解码数量。

### 7.4 参考案例与依据

成熟素材/商品网格普遍把预览限制在内容上下文内，使用轻量首帧、静音短播和离开即停；搜索结果页也建议用 LQIP/骨架和可控的渐进加载，而不是让大型浮层持续占据视口：<https://prateeksha.com/blog/crafting-the-perfect-search-a-guide-to-results-page-ui-ux-design>

## 8. P1-02 超级搜索：正确理解“红色建筑”

### 8.1 用户意图拆解

“有建筑，然后红色的建筑”不是一个必须存在于标签词典中的复合标签“红色建筑”，而是多个条件的组合：

```text
建筑 -> subject/scene 分面中的已有标签候选
红色 -> color 分面中的已有标签候选，或视觉颜色条件
关系 -> 同一素材同时满足两个条件；若可用，颜色应作用于主体区域
```

系统不能把整句原样拿去精确匹配，否则必然找不到“红色建筑”这个标签。

### 8.2 当前代码缺口

当前 `collect_tag_dictionary()` 每个分面只读取前 30 个标签，见 `super_search_ai.rs:289-310`；prompt 虽然要求标签只写文字和 facet key，但没有明确要求“先把查询拆成多个原子概念，再对每个概念查词典”。解析后 `resolve_tag_condition()` 主要依赖精确名、别名或唯一候选，见 `super_search_ai.rs:138-205`。这会造成：

- 复合短语被当作单标签；
- “红/红色/鲜红/暖红”等颜色同义词召回不稳定；
- 词典只取 30 条导致常用词不在 prompt；
- 没有主体区域颜色约束，可能把“画面有红色”误当“建筑是红色”；
- 未识别概念只放入全文 search，缺少用户可见解释和候选修正。

### 8.3 推荐的两阶段解析器

**阶段 A：语言理解只负责原子意图**

要求模型输出：

```json
{
  "concepts": [
    {"text":"建筑","role":"subject","facetHint":"subject"},
    {"text":"红色","role":"color","facetHint":"color"}
  ],
  "relation":"AND",
  "unresolved":[ ]
}
```

不要让模型直接输出 tagId 或 SQL。

**阶段 B：本地词典解析与查询编译**

对每个 concept 执行：

1. 规范化：繁简、大小写、全半角、同义词、停用词。
2. 精确匹配：canonical name、alias、normalized name。
3. 词干/包含匹配：只在候选数量可控时使用。
4. 分面约束：`建筑`优先 subject，`红色`优先 color。
5. 候选评分：`exact > alias > prefix > token overlap > embedding similarity`。
6. 置信度阈值：高于阈值自动选中；中间区间展示候选让用户确认；低于阈值进入全文 search 并给出 warning。
7. 将同一条自然语言条件编译成多个 AND 子条件。

### 8.4 颜色处理策略

分三档实现，避免一开始把颜色模型做得过重：

**档 1：标签颜色**

- 优先查 `color` 分面中的“红/红色/鲜红”等词。
- 适合已有人工/AI 色彩标签的素材。

**档 2：全图主色**

- 对缩略图提取 HSV/Lab 主色，存储 `dominant_color` 和色相区间。
- 适合没有颜色标签的新素材。
- 使用低分辨率图和 SIMD/并行批处理，不在搜索时重复解码原图。

**档 3：主体颜色**

- 只有在接入视觉 embedding/区域检测后启用。
- 需要明确表达“红色建筑”与“画面里有红色”的差异。
- 结果可标记为“视觉相似/推断”，不要伪装成确定标签。

### 8.5 混合检索与排序

推荐采用：

```text
候选集 = BM25/FTS 标签与文件名
       ∪ 词典解析后的 facet 过滤结果
       ∪ 可选向量召回

最终分数 = 0.45 * facet_exact
         + 0.25 * keyword_bm25
         + 0.20 * semantic_similarity
         + 0.10 * color_match
```

实际权重应通过离线查询集调参。对明确的标签条件，精确分面必须优先于向量相似度，避免“看起来像建筑”的结果压过真正带建筑标签的结果。

Sage Image Search 的公开方案采用 caption、向量搜索、关键词/BM25 和 reranker 的混合方式；这说明语义召回和关键词精确匹配应互补，而不是二选一：<https://sagecontinuum.org/labs/image-search>

### 8.6 用户可见反馈

AI 解析完成后在搜索框下方显示可关闭的条件 chips：

```text
主体：建筑 ✓   颜色：红色 ✓   关系：全部满足   未识别：无
```

如果没有命中：

```text
未在标签词典中找到“赭红”，已按颜色近似搜索；点击可改为“红色”。
```

用户修改 chip 后，不必重新调用 AI，可直接更新查询。

## 9. P1-03 超级搜索筛选区与滚动逻辑

### 9.1 当前问题

`SuperSearchPage` 将搜索框和 `QueryBuilder` 放在 `shrink-0` 的顶部区域，结果网格单独占剩余空间；条件一多，顶部区域变高，图片可见区域变少。用户期望的是：

- 向下滚动结果时，条件区域一起向上收起；
- 向上滚动时，条件区域恢复；
- 滑到底部仍能快速修改筛选；
- 修改后可以快速收回，不破坏浏览位置。

### 9.2 推荐布局

```text
页面根容器
  ├── 顶部标题栏（固定，40px）
  ├── 结果滚动容器
  │   ├── sticky 搜索/筛选摘要条（32~40px）
  │   ├── 可折叠详细条件抽屉（默认展开，滚动下收起）
  │   └── 虚拟化结果网格
  └── 可选底部“筛选”按钮/抽屉入口
```

桌面端：详细条件在顶部展开；滚动下隐藏为摘要 chips，滚动上恢复。  
窄屏端：详细条件改为右侧抽屉或底部 sheet，应用/清除动作固定在 sheet 底部。

### 9.3 滚动方向算法

- 滚动监听必须是 `{ passive: true }`。
- 用 `requestAnimationFrame` 合并事件，每帧最多写一次方向状态。
- 只有累计移动超过 12~20px 才改变状态，避免抖动。
- CSS 只动画 `transform/opacity`，不动画 height，避免结果网格重排。
- 300~400ms 是可接受的恢复动画范围；用户聚焦筛选输入框时强制显示。
- 键盘 Tab 进入隐藏筛选区时立即恢复，避免焦点落在不可见控件上。

滚动方向感知的 sticky header 设计建议使用 rAF + 单一 data 属性，视觉动画只使用合成器安全属性：<https://www.css-scroll-driven.com/scroll-driven-view-transition-implementation-patterns/sticky-header-navigation-transitions/>

### 9.4 筛选状态与分页一致性

- 筛选条件改变时清空当前结果页，保留滚动容器位置或回到顶部，二者必须有明确产品规则。
- 旧请求通过 request sequence 丢弃，当前 store 已有 `requestSeq`，需确保摘要 chips 与同一 sequence 绑定。
- 条件修改后显示结果数量预估；重查询期间保留旧结果并显示轻量 loading，而不是白屏。
- 底部“继续加载”优先于无限滚动自动加载，避免用户在错误条件下不断拉取数据；素材库探索页可保留自动加载，但要有最大页数/内存预算。

### 9.5 参考依据

搜索结果页常见的成熟模式是“sticky filter summary + 可折叠 facets + 移动端 bottom sheet”，并明确提供清除全部、单个撤销、结果数反馈：<https://prateeksha.com/blog/crafting-the-perfect-search-a-guide-to-results-page-ui-ux-design>

## 10. P1-04 设置页布局改造

### 10.1 当前问题

设置页右侧内容使用：

```text
flex-1 overflow-y-auto p-6
内层 max-w-xl
```

在宽屏下，右侧大面积空间被浪费，表单内容集中在小框内；字段采用 `justify-between`，当提示文字较长或控件较宽时容易挤压。

### 10.2 推荐布局

- 右侧内容区域最大宽度提高到 960~1120px，按设置类型选择宽度。
- 取消“卡片套卡片”的视觉结构：页面使用无框分区，只有危险操作、模型列表、日志等真正需要框定的重复项使用边框。
- 采用 2 列网格：左列标签/说明，右列控件；宽屏下可将相关字段排列为两列，窄屏降为一列。
- 保存栏在右侧内容底部 sticky，但高度控制在 48px 内，不遮挡最后一行。
- AI/本地模型设置使用 tabs/segmented control，避免把所有字段垂直堆叠。
- 复杂模块（服务管理、模型列表、日志）允许占满内容宽度。

建议断点：

| 宽度 | 布局 |
| ---: | --- |
| < 720px | 单列，保存栏底部固定 |
| 720~1100px | 标签/控件两列，内容宽度 100% |
| > 1100px | 内容最大 1040px，模型/日志可双栏 |

### 10.3 验收

- 1440px 窗口右侧不再出现只占约一半宽度的小框。
- 复杂提示文字换行后不挤压输入控件。
- 100%/125% Windows 缩放下无横向滚动条。
- 设置页加载错误时，错误恢复视图仍居中且不依赖右侧窄容器。

## 11. P2-01 全链路内存和性能方案

### 11.1 现有优点

`docs/PERFORMANCE.md` 已定义：

- 内嵌预览优先；
- 图像解码依赖 dev O3；
- 4 许可并发解码信号量；
- 缩略图 LRU；
- TanStack Virtual；
- DB 锁外解码和网络请求。

这些原则应保留，并扩展到视频、搜索和模型服务。

### 11.2 分层预算

| 层 | 主要对象 | 控制方法 |
| --- | --- | --- |
| WebView | React state、虚拟列表、图片元素 | 稳定 key、memo、虚拟化、请求代际保护 |
| 图片/视频 | 解码缓冲、预览视频、ffmpeg 临时帧 | 并发信号量、离开卸载、临时目录清理 |
| IPC | Asset 数组、标签聚合、搜索结果 | ids-only、分页上限、禁止全量对象传输 |
| 数据库 | FTS、标签、元数据 | 只建真实查询索引、查询计划、短锁 |
| Ollama | 模型权重、KV cache、服务进程 | keep_alive、单并发、idle unload、服务 ownership |
| 磁盘 | 缩略图、视频代理、安装包 | LRU、大小上限、显式清理入口 |

### 11.3 关键指标

- 3 万素材网格：滚动帧时间 P95 < 16ms，白块持续时间 < 500ms。
- 首次缩略图：JPG 320px P95 < 5ms；RAW 320px P95 < 100ms，沿用现有性能手册指标。
- 超级搜索：输入停止后 300ms 内显示解析状态；本地数据库查询 P95 < 300ms。
- 入库 100 个文件：UI 保持可交互，单个失败不阻塞全批次。
- 本地 AI：同一模型串行处理；空闲卸载后 Ollama 进程/模型内存可观测下降。
- 连续 2 小时“导入 + 滚动 + 搜索 + 打标”：RSS、JS heap、代理缓存均不持续单调增长。

### 11.4 防止内存回归的工程门禁

- 每次修改媒体/网格代码必须跑真实大库滚动。
- 每次新增解码/编码依赖必须加入 dev O3 清单。
- 每次新增 IPC 接口必须定义分页、上限和 payload 大小。
- 每次新增异步请求必须定义取消、代际丢弃和卸载清理。
- CI 构建后用 source map/字符串扫描确认生产产物不存在旧 `offsetX` 路径。

## 12. P2-02 构建产物与测试补强

### 12.1 为什么当前测试可能“全绿但用户仍报错”

现有单元测试覆盖了很多纯函数和 store，但以下场景仍容易漏掉：

- 真实 WebView2 PointerEvent 与 jsdom 差异；
- 生产构建是否包含旧代码；
- 组件卸载后原生事件回调；
- Ollama 真正的进程与 GPU/RAM 生命周期；
- 浏览器实际视频编解码能力；
- 设置页子组件 render 异常；
- 组合自然语言查询的词典召回质量。

### 12.2 必补测试矩阵

**查看器**

- 双击放大、Alt+滚轮、拖拽、快速切图、关闭后延迟事件。
- `stageRef.current = null` 时所有 handler 安全返回。
- 旧 asset generation 回调不能改写新素材。

**错误恢复**

- 页面 render throw 显示错误边界。
- 点击重试重新请求数据。
- 点击返回保留素材库筛选和滚动位置。

**视频预览**

- 卡片内播放，不创建 fixed popover。
- hover 离开立即暂停/卸载。
- H.264、HEVC、不支持编码、损坏文件分别验证降级。

**超级搜索**

- “红色建筑”解析为两个原子条件并以 AND 执行。
- “红色的建筑，不要夜景”包含 subject、color、exclude scene/lighting。
- 词典无命中时展示 warning，不静默丢失。
- 颜色标签和主色 fallback 的结果排序可解释。

**滚动筛选**

- 下滚收起、上滚恢复、抖动不闪烁。
- 输入框 focus 时不隐藏。
- 到底部仍可打开筛选抽屉，应用后结果不重复。

**模型生命周期**

- 应用启动不自动拉起 Ollama。
- 首次请求只启动一次。
- 连续请求复用服务。
- 空闲卸载模型；应用拥有的服务停止；外部服务不停止。
- 取消批次后临时帧、HTTP 请求、模型 lease 全部释放。

**设置**

- Ollama 检测失败不影响视频开关显示。
- 修改视频开关后未保存时有明确状态。
- 保存后重新读取，后端批次预检与前端一致。
- 1440px、1024px、768px、手机窄屏截图验收。

## 14. 不建议采用的方案

1. **不要只把 `offsetX` 改成 `nativeEvent.offsetX`**：这可能绕过当前报错，但仍然绑定事件目标，无法解决卸载竞态和多层 DOM 目标变化。
2. **不要用整页刷新替代错误恢复**：它会丢失素材库筛选、滚动位置和未保存状态。
3. **不要为每个 hover 视频生成大尺寸转码**：会把浏览操作变成高 IO/高 CPU 任务。
4. **不要把 `durationMs != null` 当作视频类型唯一依据**：视频元数据缺失时会被误判为图片；当前项目已有 `isVideoAsset()` 统一判断函数，应继续作为事实源。
5. **不要把“红色建筑”创建成新标签**：这会污染词典，且无法覆盖“蓝色建筑/黄色建筑”等组合。
6. **不要用向量相似度替代明确标签过滤**：用户输入明确分面条件时，精确匹配应占主导。
7. **不要在每次搜索滚动事件中 setState**：必须 passive + rAF + 方向阈值，并把动画交给 CSS transform。
8. **不要应用退出时无条件杀 Ollama**：外部服务可能被其他程序使用；只停止应用拥有的进程。
9. **不要把所有设置内容继续限制在 `max-w-xl` 小框里**：应按信息密度和屏幕宽度使用弹性布局。
