| # | 冲突点 | ② Qoder 计划 | ③ 分面改造书 | **裁决** | 理由 |
|---|---|---|---|---|---|
| D1 | 提示词何时改 | 波次 1（T14）立即改 | 阶段 5（在分面合表之后） | **③ 胜**：合表后改 | T14 要「每分面拼入 `description`」，而 ③ 要把 `hint` 合并进 `description`。先做 T14 → 提示词读的是「description + hint 两个字段」；合表后又要改成「一个字段」。**同一段代码写两遍。** |

## 5. 施工顺序总览与依赖图

### 5.1 为什么是这个顺序

一条原则：**先立契约，再建功能。** 契约（分面表结构、`FacetPromptContext`、`QueryExpr` 叶子类型）一旦被功能代码大量引用，再改就是全库返工。

```
W0 止血 + 基线冻结          ← 独立，无依赖，可立即开工
 │  修 4 个确定性 bug、清死代码/死配置、日志落文件、V1 事务、去重入口
```

### 6.2 为什么 V19 / V20 / V21 分三段而不合成一个

② 的原则是「单一 V19 迁移统一承载全部 schema 变更」。**我建议拆成三段，理由三条：**

1. **失败粒度**（最重要）。三段风险不同量级：V19 = 纯 `ALTER ADD COLUMN`（几乎不会失败）；V20 = 读写 `settings` JSON 回填（中风险）；V21 = 重建 FTS 触发器（**高风险**，触发器体系经 V1→V3→V8→V17 演进，注释记录了两个实测坑）。合成一个 → V21 段炸了，V19 的四个列和 V20 的回填全部回不去（`user_version` 没提交）→ 下次启动重跑全部。拆开后 V21 失败只丢 V21，前两段已提交可用。
2. **并行度**。V19 先落地，W5b（收藏评级）/W5d（phash）不用等分面合表完成。
3. **可读性**。V19 = 加数据列，V20 = 分面契约，V21 = FTS 联动，语义各自单一。合成后迁移函数 150+ 行做三件不相关的事。

代价是多两个版本号，几乎零成本。

### 6.3 V20 + V21：分面合表（对应 ③）

> **复盘 R4 修正**：原计划把「数据回填」与「FTS 触发器重建」写在一个 `migrate_v20` 里。触发器重建风险高一个数量级，一旦失败连回填也回不去。**拆成 V20（低风险，必做）+ V21（高风险，可延后）两个版本号。**

```rust
/// V20：分面单一事实源（低风险段）。settings.aiFacetConfigs 的语义搬进 tag_facets。
/// 幂等：add_column_if_missing + 回填用 UPDATE（可重复执行）。
fn migrate_v20(conn: &Connection) -> AppResult<()> {
    let now = chrono::Utc::now().timestamp_millis();

    // ① 加列。SQLite 的 ALTER TABLE ADD COLUMN 不能带 CHECK（实测 tag_facets 已有 3 个 CHECK，
    //    但只能建表时声明）→ input_mode 靠 Rust 层 validate 兜底（复盘 R3 选项 A）。
    add_column_if_missing(conn, "tag_facets", "input_mode",
                          "TEXT NOT NULL DEFAULT 'ai_and_manual'")?;

    // ② 回填：enabled_for_ai=false → manual_only；hint 并入 description（不覆盖，拼接）
    let s = settings::get_settings(conn)?;
    for cfg in &s.ai_facet_configs {
        let mode = if cfg.enabled_for_ai { "ai_and_manual" } else { "manual_only" };
        conn.execute(
            "UPDATE tag_facets SET
                input_mode = ?2,
                description = CASE
                    WHEN ?3 = ''                    THEN description
                    WHEN trim(description) = ''     THEN ?3
                    WHEN instr(description, ?3) > 0 THEN description   -- 已含，防重跑重复拼
                    ELSE description || char(10) || ?3
                END,
                display_name = COALESCE(NULLIF(trim(?4), ''), display_name),
                updated_at = ?5
              WHERE key = ?1",
            params![cfg.facet_key, mode, cfg.hint.trim(),
                    cfg.display_name.as_deref().unwrap_or(""), now])?;
    }

    // ③ 系统分面默认归组修正：purpose / technical 天然手工类。
    //    守卫：只改「还没有任何标签」的分面，不覆盖用户已在用的配置。
    conn.execute(
        "UPDATE tag_facets SET input_mode='manual_only', updated_at=?1
          WHERE key IN ('purpose','technical') AND is_system=1
            AND NOT EXISTS (SELECT 1 FROM tags WHERE facet_key = tag_facets.key)",
        params![now])?;

    // ④ 清空 JSON 侧（此后 Settings.ai_facet_configs 为 skip_serializing）
    let mut s2 = settings::get_settings(conn)?;
    s2.ai_facet_configs.clear();
    settings::save_settings(conn, &s2)?;
    Ok(())
}

/// V21：FTS 触发器加分面状态联动（高风险段，见 §6.4）。
/// 独立版本号：若此段失败，V20 的回填已提交并可用，V21 可单独延后处理。
fn migrate_v21(conn: &Connection) -> AppResult<()> {
    rebuild_fts_triggers_with_facet_status(conn)?;
    conn.execute_batch("INSERT INTO assets_fts(assets_fts) VALUES('rebuild');")?;
    Ok(())
}
```

`visible_in_workbench=false` 的处理见 §18-Q1（待拍板）。

### 6.4 FTS 触发器补分面状态联动

**当前缺陷**：触发器只看 `tags.status`，不看 `tag_facets.status`。所以停用一个分面后，该分面下的标签**仍然能被全文搜到** —— 与「停用标签立即消失」的语义不一致。

两处改动：

**① 聚合子查询加分面条件**（`trg_at_ai` / `trg_at_ad` / `trg_tags_au` / `trg_tag_alias_*` 全部）：

```sql
WHERE at.asset_id = <ref> AND t.status = 'active'
  AND EXISTS (SELECT 1 FROM tag_facets f
               WHERE f.key = t.facet_key AND f.status = 'active')
```

**② 新增分面状态触发器**：

```sql
CREATE TRIGGER trg_facet_status_au AFTER UPDATE OF status ON tag_facets BEGIN
  UPDATE fts_content SET tag_names = (<同上聚合子查询>)
   WHERE asset_id IN (
     SELECT at.asset_id FROM asset_tags at JOIN tags t ON t.id = at.tag_id
      WHERE t.facet_key = new.key
   );
END;
```

**风险提示**：这一步改的是 V1/V3/V8/V17 层层演进过的触发器体系，且 `migrations.rs` 注释明确记录了「幻影 token」「VTAB 267」两个实测坑。**必须**：
- 复制现有触发器的完整 SQL 再改（不要手写新的聚合逻辑）
- 改完立即 `INSERT INTO assets_fts(assets_fts) VALUES('rebuild')`
- 补 3 条测试：停用分面搜不到、恢复搜得到、`asset_tags` 行数不变

### 6.5 迁移驱动层改造（① S2）

```rust
pub fn migrate(conn: &Connection) -> AppResult<()> {
    let version: i64 = conn.query_row("PRAGMA user_version", [], |r| r.get(0))?;
    if version < 1 {
        // S2 修复：V1 建库包进事务。全裸 CREATE TABLE 非幂等，
        // 首装中途崩溃 → 重跑报 "table already exists" → 启动被永久阻断。
        let tx = conn.unchecked_transaction()?;
        tx.execute_batch(SCHEMA_V1)?;
        tx.commit()?;
        conn.pragma_update(None, "user_version", 1)?;
    }
    // ... v2..v18 不动 ...
    if version < 19 { migrate_v19(conn)?; conn.pragma_update(None, "user_version", 19)?; }
    if version < 20 { migrate_v20(conn)?; conn.pragma_update(None, "user_version", 20)?; }
    // V21 = FTS 触发器加分面状态联动（高风险段）。独立版本号使其可单独延后。
    if version < 21 { migrate_v21(conn)?; conn.pragma_update(None, "user_version", 21)?; }
    Ok(())
}
```

## 16. 全局不变量（施工期禁止破坏）

这些是代码注释与设计文档里的硬约束，违反会直接产生 bug。**每次提交前对照检查。**

### 架构层
1. 前端禁止直连 `invoke`，必须走 `src/api/*.ts`
2. commands 是薄壳（校验 + 锁 + 事件），services 持业务，db 只管 SQL
3. **DB 写操作必须短暂持锁；网络/解码放锁外**
4. 旧字段迁移用 `skip_serializing` 只读模式，禁止新旧双源并行写

### 数据层
5. **`COLUMNS` 是位置映射，新列只能追加末尾**（插中间会静默错位）
6. `PRAGMA foreign_keys=ON` 是全部 CASCADE 的前提（`db/mod.rs:28`），必须有测试守护
7. 删除关联必须**先删 `asset_tags` 再删 `tags`**（让 FTS 触发器有机会跑）
8. 合并标签走 DELETE+INSERT 而非 UPDATE 改挂（同上理由）
9. **手工覆盖必须清 `source_batch_id`**（D-1/D-2），否则撤销 AI 批次误删手工标签
10. FTS 短语必须加双引号；写入侧与查询侧必须用同一 `cjk_bigram`
11. 外部工具连此库**只能 SELECT**（缺 `cjk_bigram` 函数，DELETE/UPDATE 会报错）

### 分面协议层
12. **`tag_facets.key` 永不可改**，显示名可本地化
13. `selection_mode` / `max_items` 只以 DB 为准
14. **AI 打标与 AI 搜索必须读同一个 `FacetPromptContext`**（有交叉测试守护）
15. AI 返回未知 key 必须产生 warning，不允许静默丢进 custom

### AI 层
16. **确认前的 AI 建议绝不写入 `asset_tags`**（防污染标签体系）
17. 拒绝/删除不做物理删除，翻转状态（`rejected` 可恢复，标签 `deprecated`）
18. **用户所选素材完整进入逻辑批次，不做静默截断**；`batchLimit` 只是执行层分块

### 搜索层
19. AI 只输出 `SearchIntent`，不输出 tagId / SQL / 列名 / 分页 / trashOnly
20. **列名与 op 只来自白名单 `match`，值 100% 参数绑定**
21. 日期左闭右开、大小字节、时长毫秒、NULL 不命中 —— 已冻结
22. 排序尾缀必须加 `a.id DESC`（分页稳定）
23. **`AssetFilter.expr` 与扁平字段严格二选一**，expr 存在时后端完全忽略扁平字段
24. 超级搜索默认不查回收站；AI 搜索零数据库写入

## 17. 复盘：这份计划本身的 14 个问题

我把上面的计划当成别人写的东西又审了一遍。以下是发现的问题，**其中 R1 是阻断级 —— 不解决它，用户的核心需求（自建分面）根本不成立。**

### R1【阻断级】`key_for_legacy_name` 把所有用户自建分面路由到 `custom`

**这是三份材料都没发现的最严重问题。** 我做了完整的调用链追踪：

```rust
// db/tag_facets.rs：用户自建的 key 落到 _ 分支
key_for_legacy_name("clothing_color") → "custom"

// db/ai.rs:37 categorized_tag_ids
facet_key = "custom"
category("clothing_color") == facet_key("custom") ? NO
→ else 分支：find_or_create_facet_root(conn, "custom", "clothing_color")
  = 在 custom 分面下建一个名为 "clothing_color" 的根标签（!!）
→ find_or_create_child(parent, "红色")
  = "红色" 成为 "clothing_color" 的子标签，facet_key 继承 "custom"
```

三个调用点全部受影响：`ai.rs:37`（写标签）、`ai.rs:194`（写 `ai_suggestion_items.facet_key`）、`ai.rs:402`（`final_pairs` 反查 —— 会**查不到刚建的标签**，因为它按 `facet_key='custom'` 查而实际标签在 custom 分面下但名字对不上）。

**后果**：用户建了「人物服装颜色」分面，AI 按提示词正确返回 `{"clothing_color":["红色"]}`，结果标签落进 `custom` 分面、还多建了一个叫 `clothing_color` 的垃圾标签。**筛选、搜索、工作台全部错位。**

前端 `tagStore.ts:124` 的 `keyForLegacyName` 有同样的问题（`normalizeTagKeys` 会把自建分面的标签归到 `custom` 显示）。

**修法（必须加进 W2）**：

```rust
/// 把 AI 返回的分类键归一为稳定 facet key。
/// 顺序：① DB 里存在该 key → 原样返回（用户自建分面走这条）
///      ② 中文旧名映射表 → 映射后的 key（历史数据兼容）
///      ③ 都不匹配 → custom + warning
pub fn resolve_facet_key(conn: &Connection, raw: &str) -> AppResult<(String, Option<String>)> {
    let k = raw.trim();
    if facet_exists(conn, k)? {
        return Ok((k.to_string(), None));
    }
    let mapped = key_for_legacy_name(k);
    if mapped != "custom" && facet_exists(conn, mapped)? {
        return Ok((mapped.to_string(), None));
    }
    Ok(("custom".into(), Some(format!("未知分类「{k}」已归入自定义"))))
}
```

`key_for_legacy_name` 降级为「只查中文旧名表」的纯函数，**不再作为路由入口**。三个调用点全部改成 `resolve_facet_key`。前端同理：`normalizeTagKeys(tags, knownFacetKeys)` 增一个已知 key 集合参数。

**排期影响**：这一项加进 **W2-10**，且 **W5a 必须在它之后**（提示词让 AI 输出自建 key，路由不修等于白做）。

### R2【重要】`Workbench` 的 `maxItems ?? 3` 硬编码回退

`Workbench.tsx:153/299` 两处 `f.maxItems ?? 3`。`tag_facets.max_items` 允许 NULL（= 不限），但前端把 NULL 当成 3。用户建一个「不限数量」的分面，工作台只让填 3 个。
