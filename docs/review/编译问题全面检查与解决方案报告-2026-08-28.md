## 0. 结论摘要（TL;DR）

「软件编译不了」的**直接原因只有一个**：`src-tauri/src/db/search_query.rs:598` 的测试代码在 `CompiledMetadata` 未实现 `Debug` 的情况下调用了 `unwrap_err()`，导致 `cargo test`（以及任何 `--all-targets` 编译路径）**编译期失败**。软件本体（`cargo build`、`cargo check --release`、`npm run build`、`tauri dev`）全部正常。

但这只是冰山一角。编译错误修复后，还有 **2 个测试会在运行期必然失败**；更重要的是，**FB2-08「算法色板」整条功能链路是半成品**：数据库写入端做完了，读取端（Asset 结构体 / 查询列 / 前端 DTO）、设置 UI、回算入口、色条点击搜索**全部缺失**——即使用户编译通过跑起来，色条功能也完全不工作。

## 2. 问题详情与解决方案

### A-1【编译阻断】`CompiledMetadata` 未实现 `Debug`，`unwrap_err()` 无法编译

**位置**：`src-tauri/src/db/search_query.rs:598`（commit `e05ae83` 新增的测试）

**报错原文**：

```text
error[E0277]: `CompiledMetadata` doesn't implement `Debug`
   --> src\db\search_query.rs:598:21
    |
598 |         let err = c.unwrap_err().to_string();
    |                     ^^^^^^^^^^ the trait `Debug` is not implemented for `CompiledMetadata`
    = note: add `#[derive(Debug)]` to `CompiledMetadata` or manually `impl Debug for CompiledMetadata`
```

**原因**：`Option<T>::unwrap_err()` 要求 `T: Debug`（失败时打印 Ok 值）。`CompiledMetadata` 定义于 `search_query.rs:35`，只有 `sql` 和 `params` 两个字段，未派生 `Debug`。

**解决方案**（二选一，推荐方案 1）：

1. **给 `CompiledMetadata` 派生 `Debug`**（一行改动，且对后续所有测试都有益）：

   ```rust
   #[derive(Debug)]
   pub struct CompiledMetadata {
       pub sql: String,
       pub params: Vec<Value>,
   }
   ```

   `rusqlite::types::Value` 实现了 `Debug`，可直接派生。

2. 不动结构体，改写测试断言（避免依赖 `Debug`）：

   ```rust
   let err = match compile_metadata(&between("dominant_unknown", 0, 359)) {
       Err(e) => e.to_string(),
       Ok(_) => panic!("未知 dominant key 应报错"),
   };
   assert!(err.contains("未知元数据字段"), "实际：{}", err);
   ```

**验证**：`cd src-tauri && cargo test --no-run` 编译通过。

### B-1【测试必失败】V16 测试 fixture 缺 `hint` 列，`migrate_v16` 运行时报「no such column」

**位置**：`src-tauri/src/db/migrations.rs:1210-1218`（fixture 建表）与 `migrations.rs:943`（`UPDATE tag_facets SET hint = ...`）

**原因**：测试用最小 fixture 手工建 `tag_facets` 表，建表语句里**没有 `hint` 列**；而 `migrate_v16` 第 2b 步会执行：

```sql
UPDATE tag_facets SET hint = hint || '。风格描述不包含颜色…' WHERE key = 'style' AND instr(hint, '不包含颜色') = 0
```

SQLite 对不存在的列直接报 `no such column: hint`，`migrate_v16(&c).unwrap()` 将 panic。**该错误在 A-1 修复后立即暴露**（当前被编译错误挡住，运行不到）。

**解决方案**（fixture 补列）：

```sql
CREATE TABLE tag_facets (
  id INTEGER PRIMARY KEY, key TEXT NOT NULL, display_name TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '', min_items INTEGER, max_items INTEGER,
  status TEXT NOT NULL DEFAULT 'active', updated_at INTEGER NOT NULL,
  hint TEXT NOT NULL DEFAULT '');   -- ← 补这一列
```

更稳妥的长期做法：fixture 不手写建表，改为「跑完整 `migrate()` 到 V15 再执行 `migrate_v16`」，避免最小 fixture 与真实 schema 漂移（V16 测试断言里还查了 `hint` 列的值，说明写测试时默认了它存在）。

**验证**：`cargo test v16` 通过。

### B-2【测试必失败】`half_black_half_white_yields_two_clusters` 与实现矛盾（黑白像素全被丢弃）

**位置**：`src-tauri/src/services/palette.rs:225-240`；丢弃逻辑在 `palette.rs:50`

**原因**：极端像素预筛条件为：

```rust
if (lum < 0.02 && sat < 0.5) || (lum > 0.96 && sat < 0.05) { discarded; continue; }
```

- 纯黑 `(0,0,0)`：lum=0 < 0.02 且 sat=0 < 0.5 → **丢弃**
- 纯白 `(255,255,255)`：lum=1 > 0.96 且 sat=0 < 0.05 → **丢弃**

于是「左半黑、右半白」的图**所有像素都被丢光**，`compute_palette` 返回空 vec，`assert!(!p.is_empty())` 必然失败。同文件 `all_black_returns_empty_not_panic` 测试恰恰确认了「全黑 → 空」的语义，两个测试互相矛盾——写 `half_black_half_white` 用例时没有意识到白色同样在丢弃范围内。

**解决方案**：改写测试为**非极端双色**（深蓝 vs 浅黄这类会被保留的颜色）：

```rust
#[test]
fn half_dark_half_light_yields_two_clusters() {
    let mut img = image::RgbaImage::new(40, 40);
    for (x, _, px) in img.enumerate_pixels_mut() {
        *px = if x < 20 {
            image::Rgba([20, 30, 90, 255])    // 深蓝（非极端）
        } else {
            image::Rgba([230, 210, 120, 255]) // 浅黄（非极端）
        };
    }
    let p = compute_palette(&DynamicImage::ImageRgba8(img));
    assert!(!p.is_empty());
    assert!(p.len() >= 2, "双色各半应聚出 ≥2 簇，实际 {}", p.len());
}
```

同时把原用例改名为「黑白各半 → 空色板」并入 `all_black_returns_empty_not_panic` 的语义（黑白图色板为空是当前设计的**有意行为**，见 D-1）。

**验证**：`cargo test palette` 通过。

### C-1【P0 功能断裂】读取链路缺失：`Asset` 结构体 / `COLUMNS` / `from_row` 没有 palette 字段

**位置**：`src-tauri/src/db/assets.rs:15-61`（struct）、`assets.rs:185-193`（COLUMNS）、`assets.rs:195`（from_row）

**现状**：V16 迁移加了 6 列（`palette_json`、`palette_version`、`palette_scanned_at`、`dominant_hue`、`dominant_sat`、`dominant_lum`），`set_palette` 也能写入；但：

- `Asset` 结构体没有对应字段；
- `COLUMNS` 常量没有这 6 列（SELECT 不查它们）；
- `from_row` 不解析它们。

**后果**：`list_assets` 返回的 JSON 里永远没有 `palette` / `dominantHue` 等字段 → 前端 `asset.palette` 恒为 `undefined` → **`AssetCard` 里的色条条件 `asset.palette?.length` 永远为假，色条永不渲染**（即使设置开关全部打开）。

**解决方案**：

1. `Asset` 结构体追加字段：

   ```rust
   pub palette_json: Option<String>,
   pub palette_version: Option<i64>,
   pub palette_scanned_at: Option<i64>,
   pub dominant_hue: Option<i64>,
   pub dominant_sat: Option<i64>,
   pub dominant_lum: Option<i64>,
   ```

2. `COLUMNS` 追加这 6 列（注意保持 `from_row` 的列序一致，`from_row` 用 `row.get("palette_json")` 按名取更抗列序漂移，建议趁机统一）。

3. `from_row` 解析后，`palette_json` 需反序列化为 `Vec<PaletteSegmentDto>` 再进 DTO（或在命令层转换；`Asset` 上的 `Serialize` camelCase 会自动产出 `paletteJson`，与前端期望的 `palette: PaletteSegmentDto[]` 不一致，需要定义一个中间 DTO：`palette: Option<Vec<PaletteEntry>>`）。`rescan_assets_palette`（`media_refill.rs:257-265`）写入的 JSON 形状是 `[{hex,r,g,b,ratio}]`，与前端 `PaletteSegmentDto` 一致，反序列化直接可用。

**验证**：回算一条素材后，`list_assets` 的返回体里能看到 `palette` 数组。

### C-2【P0 功能断裂】`rescan_asset_palette` 命令没有前端调用入口

**位置**：`src/api/assets.ts`（无对应函数）；`src/pages/SettingsPage.tsx`（无回算 UI）

**现状**：后端命令 `rescan_asset_palette`（`media_cmd.rs:70`）已注册进 `lib.rs:170`，但 `src/api/assets.ts` 里只有 `rescanAssetMetadata` / `cancelMediaRefill`，没有任何代码 invoke `rescan_asset_palette`。

**后果**：**色板永远算不出来**——入库不自动算（见 C-5），设置页没有「回算色板」按钮，唯一能写 `palette_json` 的路径用户根本触达不了。指导书 §14.7 的「色板回算命令」验收（「整库补算秒级」）无法执行。

**解决方案**：

1. `src/api/assets.ts` 追加：

   ```ts
   export function rescanAssetPalette(ids: number[], scope: "all" | "missing" | "ids"): Promise<RescanResult> {
     return invoke<RescanResult>("rescan_asset_palette", { ids, scope });
   }
   ```

2. 在 `SettingsPage` 现有「媒体元数据回填」区块旁增加「算法色板回算」入口（复用 `media_refill://progress` 事件流与现有进度 UI，`RefillProgress` 结构完全相同）。注意取消标志复用问题见 D-3。

**验证**：设置页点「回算色板」→ 进度事件流动 → 完成后网格卡片出现色条（需 C-1 先修复）。

### C-3【P0 功能断裂】色条点击搜索不可达：`onSearchDominant` 没有任何调用方

**位置**：`src/components/library/ColorStrip.tsx:58-66`（prop 定义）；全仓库 grep 仅组件自身引用

**现状**：`AssetCard.tsx:138` 使用 `<ColorStrip palette={...} height="thin" />`，**没有传 `onSearchDominant`**。按组件约定「不传则主色段也不可点」，色条是纯展示。

**后果**：指导书 §14.9 方案 A 的验收标准「色条可点搜」不成立；配合 C-4 的默认关闭，用户没有任何方式发起 `dominant_hue` 检索（超级搜索页面、普通素材库分面均无 dominant 入口——`SuperSearchPage` / `list_metadata_facets` 全文无 `dominant` 关键字）。

**解决方案**：

1. `AssetCard` 接收并下传 `onSearchDominant`，由 `AssetGridView` → `LibraryPage` 提供实现：以被点击色的 HSV 为中心构造 `dominant_hue` ± 15°（跨 0° 时 min > max，正好落到后端已实现的 hue-wrap 双区间 OR）+ `dominant_sat` 区间的 `MetadataFilter`，写入当前搜索过滤器并刷新。
2. 若本轮不做点击搜索，则应在文档中明确「色条点击搜索 = 未实现」，避免验收误判。

**验证**：点击红色主色段 → 过滤器出现 `dominant_hue between 345~15` → 命中红色系素材（含 hue=350 与 hue=10）。

### C-4【P1 功能断裂】色条设置无 UI 入口，且默认关闭 → 用户无法开启色条

**位置**：`src/pages/SettingsPage.tsx`（全文无 `colorStrip`/「色条」字样）；`src/utils/normalizeSettings.ts:144-165`

**现状**：`normalizeSettings` 已支持 `colorStrip` 归一化（enabled 默认 true，但 `showInLibraryGrid` 默认 **false**），`AssetCard` 读取 `colorStrip.enabled && colorStrip.showInLibraryGrid` 才渲染色条——而设置页没有任何控件能改这两个值。

**后果**：色条对用户永远不可见（即便 C-1/C-2 修好）。指导书 §14.10「设置开关」未落地。

**解决方案**：在 `SettingsPage` 的「素材框外观」设置组（FB2-01/02 已建）内追加色条区块：开关（启用）、显示位置（素材库网格 / 入库网格，后者接入 `PendingList`）、高度（thin/normal/thick 映射 `HEIGHT_PX`）、分段模式（按占比/等宽）、显示条数（4/6/8）。

顺带修 E-3：`ColorStrip` 组件当前不消费 `count` 与 `height` 设置（`AssetCard` 写死 `height="thin"`、组件 `slice(0,8)` 写死），设置生效需要把 `colorStrip.height / colorStrip.count` 传入。

### C-5【P1 功能断裂】入库链路不计算色板，新素材依赖手动回算（而回算又无入口）

**位置**：`src-tauri/src/commands/import_cmd.rs`、`src-tauri/src/services/thumbnail.rs`（全文无 `compute_palette` 调用）

**现状**：`compute_palette` 只被 `media_refill.rs:252`（手动回算）调用。入库生成 placeholder 缩略图时顺手提色是最自然的时机（图片已在手上，多耗时可忽略），指导书 §14.6 的取材设计（placeholder 优先）也暗示了这个方向，但入库路径没有接。

**后果**：每批新入库素材都要用户手动全量回算；「missing」scope 虽能增量补，但没有入口（C-2）。

**解决方案**：在入库生成 placeholder 成功后（短锁内拿到 placeholder 路径、锁外 `compute_palette` + `dominant_from_rgb`、短锁 `set_palette`），批量导入建议复用 `rescan_assets_palette` 的「missing」scope 做入库后自动补算，避免改动导入热路径。

### C-6【P1】`rescan_assets_palette` 的 skipped 语义与注释/指导书不符

**位置**：`src-tauri/src/services/media_refill.rs:255-278`

**现状**：函数头注释写「色板为空（如全黑图极端像素丢光）→ 计 skipped、不覆盖」，但代码：

```rust
let ok = match palette {
    Some(palette) if !palette.is_empty() => { ... }
    _ => false,          // 空色板 / 解码失败都落到这里
};
if ok { summary.success += 1; } else { summary.failed += 1; }
```

空色板（用户素材本身无彩色，非错误）与解码失败（真错误）**混计入 failed**。用户全库黑白摄影素材回算时会看到大面积「失败」，误导排查。

**解决方案**：三分支计数：

```rust
match palette {
    Some(p) if !p.is_empty() => { /* set_palette；成功→success，写库失败→failed */ }
    Some(_) => summary.skipped += 1,   // 空色板：素材本身无有效彩色，不算失败
    None => summary.failed += 1,       // 解码失败：真错误
}
```

### D-1【P1 设计缺陷】黑白照片 / 低饱和素材的主色永远是空

**位置**：`src-tauri/src/services/palette.rs:44-58`

**现状**：极端像素预筛（近纯黑/近纯白/低饱和）是为「黑边白底不吃掉主色」设计的，但**没有回退机制**：一张黑白照片的全部像素都会被丢光 → 空色板 → C-6 场景；更现实的是大量真实照片以黑白灰为主体，色板会只剩零星高饱和色或为空，「主色检索」对这类素材失效。

**解决方案**：加回退——丢弃后若剩余样本 < 原样本的 10%（阈值可调），回退使用全样本（黑白摄影的「主色」就是黑/白/灰，这是正确答案）：

```rust
if (rgb_samples.len() as f32) < (total_px as f32 * 0.1) {
    rgb_samples = all_px; // 回退全样本，不过筛
}
```

同时 B-2 的「黑白各半」用例在回退机制下自然变成「聚出黑、白两簇」的有效断言（可保留原测试意图）。

### D-2【P2】`merge_clusters` 累计舍入损失精度

**位置**：`src-tauri/src/services/palette.rs:175-179`

**现状**：每次合并执行 `m.ratio = (m.ratio * 100.0).round() / 100.0;`，多次合并时舍入误差会累积，且最终输出（`palette.rs:139`）还会再舍入一次——两次舍入叠加可能出现 `ratio` 总和明显偏离 1（色条宽度失真）。

**解决方案**：合并过程中保留原始 f32 累加，仅在最终输出（第 7 步）做一次舍入。`m.ratio >= c.ratio` 的判断因输入已降序恒真，可以删掉（已降序保证 m 先入、占比 ≥ 后来者）。

### D-3【P2】色板回算与元数据回填共用取消标志，并发互踩

**位置**：`src-tauri/src/commands/media_cmd.rs:71` 与 `media_cmd.rs:44-64`（两条命令都操作 `state.media_refill_cancel`，且开头 `cancel.store(false)`）

**现状**：两个长任务共用一个 `AtomicBool`：

- 任务 A 运行中，用户启动任务 B → B 的 `store(false)` 把 A 的取消能力复位（影响很小，但语义脏）；
- 用户点「取消元数据回填」→ 若此时在跑色板回算，会把色板回算一起取消（或反之）。

**解决方案**：`AppState` 增加 `palette_refill_cancel: Arc<AtomicBool>` 与独立命令 `cancel_palette_refill`；或至少在启动任一回填前检查另一个是否在运行并拒绝并发（返回「已有回填任务进行中」）。低风险做法是后者（一条 `is_running` AtomicBool 互斥即可）。
