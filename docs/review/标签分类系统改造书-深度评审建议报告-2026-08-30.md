## 1. 总体评价

### 1.1 诊断准确性：高（关键声称全部经代码验证属实）

改造书对现状的诊断准确率很高，以下关键声称均已在源码中逐一核实：

| 改造书声称 | 核实结果 |
|---|---|
| `tag_facets` 表与 `settings.app_settings.aiFacetConfigs` JSON 双数据源是万恶之源 | ✅ 属实。`build_prompt_context(&conn, &[AiFacetConfig])` 以 JSON configs 为遍历源（`db/tag_facets.rs:574`），DB 查不到的分面直接 skip |

| 触发器只看 `tags.status` 不看 `tag_facets.status`（停用分面的标签仍可被搜到） | ✅ 属实 |

### 1.2 可施工性：良好，但存在五处必须先修订的硬伤

改造书的优点：

- **需求还原（R1–R12）忠实**，逐条可追溯到用户原话，验收标准 A1–A12 与需求一一映射；
- **分阶段路线（阶段 0–7）**独立可验收、可回滚，强制顺序合理；
- **测试矩阵**覆盖到级联的每一行，`foreign_keys_pragma_is_on` 守护测试的意识尤其可贵（rusqlite 默认关闭外键，`db/mod.rs:30` 靠手动开启）；
- `delete_tag_facet` 的级联顺序设计（先删 `asset_tags` 让 FTS 触发器跑，再删 `tags`）正确。

但存在 **五个「施工前必须修订」项**（详见 §2 阻断级），涉及数据迁移安全与既定设计原则冲突，照单施工将产生不可逆数据丢失或推翻已验收的既定决策。

### 1.3 与业界实践的差距与契合

对照外部调研（详见 §6 来源）：

- **契合业界共识**：受控词表进提示词（P-10）、JSON Schema enum 收窄（P-11）、解析失败降级而非报错、「人工确认后才写正式标签」的候选区模型（本项目 `ai_confirm_suggestion` 架构天然符合，是既有优势）；
- **落后于业界**：无置信度与来源标记（PhotoPrism 全套实践）、无「打子见父」层级查询语义的规划、治理视图（未打标/低频标签清单）缺失；
- **改造书 §5 行业对照自认受网络限制存在盲区**（原文注明「未能抓取到一手文档页面」），本报告以外部调研一手来源补齐，其中 §5.2 删除语义的「部分确定」可由本报告 §3.1/§4.4 升级为确定。

### 1.4 总体结论与处置建议

**结论：改造书方向正确、诊断扎实，应当实施；但五个阻断级问题修订后方可进入施工。** 用户授权的数据库重建窗口正好是解决双数据源这一架构顽疾的最佳时机，错过此窗口，后续以扩展新功能为主的迭代期将再难动此根基。

## 2. 问题诊断

按严重度分级：**阻断级**（不修订不得施工）、**重要**（施工中必须处理）、**一般**（建议处理）。

### 2.1 阻断级（5 项）

#### B1. 目标 schema 两态与现存三态（含 `deprecated`）冲突

- **事实**：改造书 §4.1 目标表定义 `CHECK(status IN ('active','inactive'))`；但 v13 迁移已将 `tag_facets.status` 拓宽为三态（`src-tauri/src/db/migrations.rs:657`：`CHECK(status IN ('active', 'inactive', 'deprecated'))`，评审人亲自核实）。`db/tags.rs` 的 `deactivate` 亦会把标签递归置 `deprecated`。
- **风险**：改造书 §6.1 若按「增列」方式回避表重建，则 `deprecated` 存量行与目标语义无着落；若未来任何迁移收紧为两态 CHECK，存量 `deprecated` 行将导致重建失败或数据被静默丢弃。
- **修订要求**：v18 必须先定义 `deprecated` 的归宿。评审建议见 §4.2（推荐保留三态）。

#### B2. `aiFacetConfigs` 的 5 条 JSON 写入路径未全点名，存在迁移回退风险

- **事实**：改造书 §6.1 只描述「清空 JSON」，未点名全部写入路径。经核实共 5 条：
  1. `normalize_ai_facet_defaults`（`db/settings.rs:525`）——**configs 为空时自动播种 8 个默认分面**，在 `get_settings` 读取链路上执行；
  2. `migrate_tag_categories_to_facets`（`db/settings.rs:492`）——旧中文分类迁移；
  3. `ensure_color_facet_config`（`db/settings.rs:545`）——补齐 color 配置；
  4. `tag_facets::seed_ai_config`（`db/tag_facets.rs:217`）——新建分面时补 JSON 条目；
  5. v16 式 SQL 直改 JSON（`db/migrations.rs:960-964` 在迁移内改 `aiFacetConfigs` 数组）。
- **风险**：迁移清空 JSON 后，只要第 1 条播种逻辑仍在，**下一次 `get_settings` 就会用默认 hint 重新播种全部 8 个分面**——用户多年定制的 hint/显示名不可逆丢失，且表面看像「迁移回退」，排查成本极高。
- **修订要求**：播种逻辑的删除必须与迁移同批交付，完整清单见 §4.3，并附「重复读取不回种」回归测试。

#### B3. §7.4「剔除 + warning」与既有「报错不折叠」设计直接冲突

- **事实**：`db/query_expr.rs:266-268` 与 `:294-298`（评审人亲自核实）对未知分面 / 跨分面 tag_id **明确报错**，注释明示这是 §12.5「不静默折叠」的有意设计；且有既有测试 `rejects_unknown_facet_key_not_silent_custom`（`query_expr.rs:589`）守护。改造书 §7.4 主张改为「剔除 + warning」，全文未引用该注释，也未意识到这是对既定决策的反转。
- **风险**：两种语义各有道理（报错=快速暴露数据损坏；剔除=用户查询永不失败，对应 R9），但不能不明不白地反转。直接施工会与既有测试基线冲突，且掩盖「分面被删后残留查询条件」这一真实数据治理信号。
- **修订要求**：显式决策。评审建议：**区分来源**——来自实时构造（QueryBuilder/AI 解析）的条件采用「剔除 + warning」（面向用户体验，R9）；直接来自持久化查询的回放保留报错能力或降级为「该条件失效 + 明显提示」。无论选哪种，必须同步改写 `query_expr.rs:266` 处注释与既有测试，并更新 `super-search-contract` 文档。

#### B4. `get_impact` 的 `ai_config_count` 恒为 0 的现存隐患未纳入改造

- **事实**：`db/tag_facets.rs:355-358` 的 `get_impact` 查询 `SELECT COUNT(*) FROM settings WHERE key = 'ai_facet_configs' AND value LIKE ...`，但 settings 表唯一 key 是 `'app_settings'`（`db/settings.rs:480`，评审人亲自核实）——**FacetManagePanel 停用前展示的「AI 配置数」永远显示 0**。
- **风险**：改造书新增 `FacetDeleteReport` 与改 `get_tag_facet_impact` 返回结构（§7.1 已提出 `aiConfigCount → aiSuggestionItemCount`），但未点明现有查询本身就是错的。若施工时沿用旧查询逻辑改名字段，错误会延续进新的删除确认弹窗——而删除是本次改造中唯一的不可逆操作，影响数字必须精确。
- **修订要求**：施工时将计数改为对正确对象的查询（`ai_suggestion_items` 按 `facet_key` 计数、`tag_ops` 计数），并加单测守护。此项建议提前到阶段 0 修复（见 §4.6）。

#### B5. 后端 `key_for_legacy_name` 对历史批次的依赖不可随前端硬编码删除

- **事实**：改造书 §10.1 对前端 `keyForLegacyName` 的处理是「保留但降级（仅解析历史 JSON）」，方向对；但未声明**后端** `db/tag_facets.rs key_for_legacy_name`（26 条中文→key 映射）的去留边界。经核实，`db/ai.rs` 的 `categorized_tag_ids`（:37、:194、:402，评审人亲自核实）在**用户确认历史批次建议**时依赖它解析中文分类名。
- **风险**：若任何阶段削弱或删除该映射，所有未确认的历史批次建议将在确认时无法落库（中文分类名解析失败），这是静默的数据功能丢失。
- **修订要求**：明确写进改造书：**前端映射可删（降级后），后端映射必须保留到「历史批次数据清零或用户显式放弃」为止**。判定清零的可执行查询见 §4.5。

### 2.2 重要级

#### M1. 行号引用偏差，反映基线非最新

改造书引用 `ai_cmd.rs` 中 `build_prompt_context` 调用点为约 :113，实际为 **:159**；`super_search_cmd.rs` 引 47 实为 54；`db/mod.rs` `foreign_keys` 称 :28 实为 **:30**（均经评审人亲自核实）。不影响结论正确性，但施工团队按改造书行号定位会扑空，**建议施工前以本报告 §4 核实行号为准**。

#### M2. 打标词典与搜索词典双规格漂移

改造书 P-10 提出打标词典参数（每分面 20 词 / 无别名 / 1500 字符 / `asset_count` 降序），与搜索侧现存 `collect_tag_dictionary`（50 词 / 5 别名 / 6000 字符 / `sort_order,id` 序，`super_search_ai.rs:647`）**排序与规格均不同，且未说明理由或复用策略**。两套并存必然维护漂移；`asset_count` 降序还需新增聚合查询（`asset_tags` JOIN + GROUP BY），实现路径与性能未给。评审方案见 §3.2。

#### M3. 系统分面删除策略缺失，`deactivate` 双轨不一致

`tag_facets::deactivate` 拒绝系统分面，但 v16 迁移用 SQL 直接把 color（系统分面）置 `inactive`——行为双轨。改造书 §16.3 把「系统分面允许删除吗」留作待拍板，但未给施工默认值。**评审建议**：系统分面保持「不可删、可停用」；color 这类已停用系统分面维持 `inactive` 现状，不引入「强制删除」开关（一旦可删，`key_for_legacy_name`、文档、提示词示例中的系统 key 引用都会成为地雷）。用户若坚持要删，走「先停用、数据清零后由迁移脚本移除」的受控路径，而非 UI 开关。

#### M4. AI 打标与分面删除/停用的并发一致性无设计

- **事实**：`ai_cmd.rs:158-159`（核实）为「短锁读配置快照 → 锁外跑网络 → 短锁写回」。打标请求期间分面被删除/停用是真实窗口。
- **风险**：写回确认时 `categorized_tag_ids` 会为已删分面的 key 走旧协议路径**重建分面根标签**，或折叠进 `custom`，产生用户刚删掉的标签死灰复燃。
- **修订要求**：`confirm_suggestion_inner` / `ai_apply_tags` 写回时在事务内校验分面存在且 `status='active'`，不满足则该分面的标签项跳过并计入 warning；`build_prompt_context` 快照过期可接受（提示词略旧无伤），写回期必须严格。
- **附带**：`delete_tag_facet` 级联先删 `tag_ops` 虽防住 `undo_batch` JOIN 丢行，但**同时放弃了该分面所有历史批次的撤销能力**，属真实数据损失，必须在 `FacetDeleteReport` 与删除确认弹窗中明示（如「该分类的 N 条打标历史将不可撤销」）。

#### M5. `facet_missing` 与 `Untagged` 语义未区分；与废弃字段 `missing_facet_keys` 关系未澄清

改造书 §10.3③ 称 `facet_has_any`/`facet_missing` 是 `missing_facet_keys` 字段（`super_search_ai.rs:136` 仍在类型中流转）的「正主」，但未说明：
1. `facet_missing`（该分面没有任何标签）与既有 `Untagged`（素材完全没有标签）必须在协议注释与 UI 文案中显式区分，否则用户搜「没有场景标签的图」和「没打过任何标的图」会混淆；
2. `ResolvedQuery.missing_facet_keys` 废弃字段是删除、保留还是复用，未表态。评审建议：本次一并删除该字段（前端已无消费者），避免协议歧义。

#### M6. 三个待拍板问题的评审建议

改造书 §16.3 留下三问，评审建议如下供用户拍板：
1. **`visible_in_workbench=false` 分面**：同意改造书方案（统一按参与 AI 处理），理由充分（该状态本身无意义且危险）；
2. **系统分面可否删**：不同意开放删除，见 M3；
3. **「打标时机=自动」**：同意本轮删除死配置，自动打标独立立项（涉及入库管线、失败重试、批次归属一整套问题）。

#### M7. enum 收窄对本地小模型的失败率风险未评估

改造书 §16.2 把「老服务商不支持 `json_schema` → 降到 Plain」评为低风险，但忽略了**本地 Ollama 小模型即使收到 schema 提示也大概率不遵守**的情形（外部调研：PhotoPrism 明确记录 reasoning 模型不关 think 导致 JSON 前缀思考内容、解析失败）。本项目是「云端 + 本地双模式」，本地模式是 enum 收窄的薄弱点。修订要求见 §3.3：三级降级必须保留并实测，且本地 profile 增加 `think` 关闭项。

## 3. 改进建议

以下建议结合外部对标调研（2024–2026 来源，详见 §6），区分**业界共识**与**争议项**。

### 3.1 标签建模：层级标签与分面（facet）的关系

**业界共识**：层级标签是自托管照片管理 2024–2026 的明确演进方向（Immich v1.113 起专门为此引入，部分动机是承接 digiKam 迁移用户）。

**建模建议**：

1. **树用 `parent_id` 存储，路径仅作展示层**。本项目 `tags` 表已是 `parent_id` 自引用树，方向正确，保持。**反模式警示**：绝不可把 `a/b/c` 路径字符串当存储主键——移动/重命名子树时全库刷写，代价巨大（外部调研反模式第 3 条）。
2. **分面与层级的职责分工，参照 Immich**：facet = 分组/命名空间（对标 Eagle 标签群组、Lightroom Keyword Sets、Hydrus 命名空间），承担「筛选收敛」职责；层级树承担「浏览细化」职责。树用于侧栏浏览，分面用于搜索过滤器——这与本项目现状（TagTree 按分面分组、QueryBuilder 按分面过滤）结构吻合，改造书的 optgroup 分组方案（P-09）与此一致，支持。
3. **「打子见父」语义（争议项，建议本版不实施）**：子标签自动蕴含父标签是层级系统核心语义，但实现方式有分歧——digiKam 物理写入（打子标签连带写父标签，XMP 层级写入），Hydrus 虚拟推导（父关系不落盘，查询时推导，删除关系即消失）。**评审建议当前版本两者都不做**：本项目触发器体系只按 `tags.status` 维护 FTS，引入物理父标签会让确认流写入翻倍、撤销流水复杂化；虚拟推导则需要在 `compile_tag_leaf` 引入递归 CTE，收益（搜索召回略增）不抵本版架构稳定性优先的目标。预留方案见 §3.4。
4. **别名机制对齐业界**：`tag_aliases`（`alias_type='old_name'` 等）对应 Lightroom synonyms / Hydrus siblings 的 n→1 归并，`merge_preserve_alias`（同分面才可合并、旧名进别名）是正确的治理方向，保持。**建议补强**：打标解析侧消费别名做归一（见 §3.2 第 5 条）。
5. **Hydrus 的告诫值得写进开发守则**：「act from need, not toward purpose」——层级、多父、虚拟关系按需而建，防过度工程。本项目单用户、数百到数万素材规模，当前「分面 + 单父树 + 别名」的组合已够用。

### 3.2 AI 打标治理（对照 PhotoPrism Ollama 集成全套实践）

外部调研中证据最详实的对标是 PhotoPrism 的 Ollama 集成（2025–2026 持续更新的开发文档），与本项目「云端 + 本地双模式」高度同构。**以下各条均为业界共识**：

1. **受控词表约束（最重要）**：改造书 P-10 的词典方案方向正确，评审批准，但需修订三处：
   - **统一实现**：打标词典不要另写一套，改为给现有 `collect_tag_dictionary` 传参数化 profile（`DictProfile { per_facet_cap, include_aliases, char_cap, order_by }`），搜索侧用现值，打标侧用 `{20, false, 1500, AssetCountDesc}`，单一实现防双规格漂移（对应 M2）；
   - **`asset_count` 聚合**：一条 `SELECT tag_id, COUNT(*) FROM asset_tags GROUP BY tag_id` 预聚合进内存再排序即可，素材规模下无性能问题；为长期稳定，可在 `tags` 表维护冗余计数列（本版不做，仅记录）；
   - **词表与解析归一规则必须一致**：PhotoPrism 的关键教训——单字模式下 "ferris wheel" 被词表归约为首个可解析词导致语义丢失，「错配才是丢标签的根因」。本项目词典给的是中文短词（2–6 字），解析侧归一规则（trim、全半角、大小写）必须与词典生成规则同函数产出，避免「词典里有但解析认不出」。
2. **别名归一是词典方案的必要配套**：改造书打标词典「不给别名」的理由（别名让模型困惑）成立，但**解析侧必须补别名→规范名归一**：模型输出「海滨」时，若 `tag_aliases` 中「海滨→海边」存在，应归一为「海边」复用而非新建。否则词典收敛效果打折。现状 `parse_categorized_checked` 无此逻辑，建议列入阶段 5。
3. **结构化输出**：打标侧目前靠自由 JSON + 本地解析。建议与搜索侧一致，云端路径优先走 Structured Outputs（JSON Schema），schema 定义 `{"description": string, "tags": {facet_key: string[]}}` 且 `tags` 的 propertyNames 用 enum 收窄到现有分面 key。本地路径不支持时降级为现有解析（保留 `parse_categorized` 链）。业界注记：强 JSON 约束可能损害复杂推理任务质量，但分类打标类任务受影响小（OpenAI 2024 文档 + 后续研究）。
4. **置信度阈值与来源标记**：PhotoPrism 输出字段为 `name / confidence / topicality`，并给 Ollama 生成标签打 `ollama` metadata source。本项目建议：
   - `ai_suggestion_items` 增加 `confidence REAL NULL` 与 `source TEXT`（`ai_cloud`/`ai_local`/`manual`）两列（v18 同批迁移，增列幂等）；
   - 低置信标签在确认界面降权显示（排序靠后 + 灰显），高置信映射词表的标签置顶；
   - 来源标记为后续治理（按来源统计、按来源批量撤销）奠基。本版只做落库与展示排序，不做阈值自动拒绝（保守，避免误杀）。
5. **不强制标签数量**：PhotoPrism 实测——强制 8–15 个标签会使集合膨胀 1.9–3.5 倍、延迟翻倍、多词噪声上升；其内置 prompt 故意不指定数量。改造书目标提示词「没有合适标签的分类给空数组 []」符合此原则，保持；`parse` 侧 `.take(5)` 硬上限改为「按分面 `max_items` 截断（无 max 的分面保留 5 上限）」，与改造书 §11.4 一致。
6. **reasoning 模型关 think**：PhotoPrism 踩坑记录——Qwen3 系列在 JSON 前拼思考内容导致解析失败。本项目本地模式大量使用 Qwen 系，**建议 `ApiProfile`（本地）增加 `disable_think: bool` 配置项，请求体带 `chat_template_kwargs: {"enable_thinking": false}` 或等价参数**，并在设置页服务管理处暴露开关。
7. **降级链设计**：打标侧补一条与搜索侧对称的链：结构化输出失败 → 宽松 JSON 解析（现有 `parse_categorized`）→ 逐分面空数组 + warning。**任何单图解析失败不得使整批失败**（现状 `run_cloud_batch` 逐图处理已基本满足，补显式约定）。
8. **候选区/人工确认而非自由创建（业界共识，本项目已具备）**：DAM 行业公认「AI 无约束自由造标签 = 标签爆炸风险源」，主流做法是映射既有词表或候选区待确认。本项目「AI 产出 → `ai_suggestions` 暂存 → 用户确认才写 `asset_tags`」的架构天然符合，是相对多数竞品的优势，**保持并强化**：配合第 4 条的置信度排序，把确认界面做成真正的「候选区」。改造书 §16.1「AI 候选逐条审计 UI 本次不做」同意，但删除分面清 `ai_suggestion_items` 已在级联表内（§8.1），正确。
9. **治理视图（建议列入下一版）**：Eagle「未分类视图」+ DAM 词表修剪思路——未打标/低频/疑似重复标签清单。本版以 `facet_missing` 查询能力（§3.3）部分覆盖，完整治理页独立立项。

### 3.3 超级搜索

1. **`intent_schema(facets)` 参数化与 enum 收窄——批准实施，但须正视本地小模型失败率**：
   - 云端路径收益明确：支持 `json_schema` 的服务商在服务端拒绝非法 key，是「不报错」最有效的一层；用户新建分面后 enum 自动包含，零代码改动（R1 直接收益）；
   - **本地路径是本方案的薄弱点**：小参数模型（7B 级）对长 enum + `additionalProperties:false` 的遵守率显著下降，enum 随用户分面增长还会变长。缓解：metadata key 的 enum 用常量白名单（`search_query` 22 个 key，不变）；分面 enum 超过阈值（建议 20）时保持 enum 但在提示词中用词典段落替代全量罗列；
   - **三级降级（Structured → JsonObject → Plain）必须原样保留**，且新增第 3 层「关键词兜底永不失败」；配置类错误（401/连接失败）保持真报错（改造书 §12.1 最后一条正确）。
2. **`facet_has_any` / `facet_missing` 语义定义**：
   - `facet_has_any(facet_key)`：`EXISTS (SELECT 1 FROM asset_tags at JOIN tags t ON t.id=at.tag_id WHERE at.asset_id=assets.id AND t.facet_key=? AND t.status='active')`；
   - `facet_missing(facet_key)`：上述取反——「该分面下没有任何活跃标签」；
   - **与 `Untagged` 的区分必须写进协议注释与 UI 文案**：`Untagged` = 素材没有任何标签；`facet_missing` = 有标签但缺某个分面。UI 文案建议「此分类未标注」 vs 「完全未打标」；
   - 停用分面（`inactive`）在 `facet_has_any` 下的行为：按「分面停用则其标签退出活跃语义」与新触发器（改造书 §6.4）保持一致，即停用分面的标签不计入 `facet_has_any`；
   - 废弃字段 `missing_facet_keys` 本次删除（见 M5）。
3. **中文分词现状评估（逐字 vs trigram）**：
   - 现状：自注册 `cjk_bigram` 分词器 + 外部内容表 `fts_content`→`assets_fts`；`db/search.rs` 已做多路径兜底（≤2 字走 LIKE 含标签名/别名 EXISTS；纯 CJK ≥4 字走 2 字块 AND；3 字走 FTS 短语；混排走 FTS∪LIKE 并集），全部支持 `SearchScope` 列前缀；
   - 外部调研结论：**对标签这类短文本，逐字/双字 + 前缀即可覆盖多数查询**；trigram 子串匹配能力强但索引体积与写入开销显著增大；jieba 方案在 Rust 生态的 `sqlite-simple-tokenizer` 0.5.0 起已移除（时效注记），引入成本高收益低；
   - **评审结论：维持现状 `cjk_bigram`，本版不换分词器**。可选增强（低优先级）：若自动补全出现前缀查询慢，按 FTS5 官方实践给 `assets_fts` 加 `prefix='2 3'` 索引（需重建表，排入后续版本）。
4. **提示词补强**：改造书 §12.5 两点（「分类清单是封闭的」显式约束句 + 元数据字段清单）均批准，元数据清单须与 `search_query` 白名单常量同源生成（防清单与编译白名单漂移）。

### 3.4 未来演进预留：混合检索与模型更换（本版只预留、不实施）

用户要求架构稳定优先，评审明确：**当前版本不实施向量检索**，但利用本次重建窗口落下三个预留点，成本极低、不引入新依赖：

1. **嵌入表设计预留（文档级）**：在 `ARCHITECTURE.md` 记录未来 `embeddings(asset_id, model_name, dim, vec BLOB, created_at)` 表设计。关键原则来自 Immich 教训：**`model_name` 列必备——换模型需全库重嵌，且需清理旧模型残留**，多模型向量并存不可混查；
2. **批处理任务框架复用**：换模型重嵌是典型的长批处理任务。`video_proxies` 已有 `queued/running/ready/failed/canceled` 状态机（`migrations.rs:689`），taskStore 已有全局任务胶囊——未来重嵌任务应复用同一状态机与进度设施，本版不新建第二套任务框架；
3. **检索协议预留**：混合检索（关键词 + 向量）业界标准融合算法是 **RRF（Reciprocal Rank Fusion）**（Elastic/Manticore/Redis 2024–2026 共识：向量擅长语义模糊匹配，关键词擅长精确标识符/文件名，互补而非替代）。预留动作仅为：搜索返回结构未来扩展 `score`/`source` 字段的空间保留在契约文档中，**本版不改动 `QueryExpr` 与现有返回结构**（避免过度工程）；
4. **架构差异注记**：Immich 向量检索依赖 Postgres 扩展（VectorChord），本项目 SQLite 单机，届时需自行引入（如 sqlite-vec），选型留给立项时点。

### 4.2 v18 迁移：表重建步骤与崩溃可重入顺序

改造书 §6.1 采用「增列 + Rust 层校验」回避表重建。**评审改为表重建**：CHECK 约束变更在 SQLite 中只能重建表（改造书自己也承认此限制），且 v13 已有成熟的表重建先例；重建还能一次性解决 B1 的三态问题。

**`deprecated` 归宿决策（B1 修订）**：保留三态 `active|inactive|deprecated`。理由：① 存量行零风险；② `tags.rs` 的 `deactivate` 递归置 `deprecated`（标签层语义）与分面层 `inactive` 本就分层，压缩为两态会混淆两表词汇；③ 两态收益（枚举更简）不抵重建风险。`input_mode` 与 `status` 正交：`manual_only` 表达「AI 不产出」，`inactive` 表达「整体停用」，互不替代。

**迁移步骤（单事务内，崩溃可重入）**：

```
① CREATE TABLE tag_facets_new（含 input_mode 列、三态 CHECK、input_mode CHECK）
② 先建触发器：trg_facet_status_au 及全部既有 tag_facets 触发器挂到 _new
   （第五轮评审 D1 教训：触发器必须先于回填就位，否则回填期 FTS 不同步）
③ INSERT INTO tag_facets_new SELECT ... FROM tag_facets
   （回填 input_mode：enabledForAi=false → manual_only；hint 并入 description 的
     CASE 逻辑沿用改造书 §6.1 ②，含 instr 防重复拼接守卫）
④ ALTER TABLE tag_facets RENAME TO tag_facets_old;
   ALTER TABLE tag_facets_new RENAME TO tag_facets;
   DROP TABLE tag_facets_old;
⑤ 清空 settings JSON 的 aiFacetConfigs + 同批删除 5 条写入路径（§4.3）
⑥ purpose/technical 无标签时置 manual_only（沿用改造书 §6.1 ④ 的
   NOT EXISTS 守卫，避免覆盖用户配置）
⑦ 最后置 PRAGMA user_version = 18
```

**可重入原则**：任何一步崩溃后重启必须收敛——① 用 `IF NOT EXISTS`；④ rename 原子；⑤ 以「JSON 中无 `aiFacetConfigs` 键」为完成标记而非读中间态；⑦ `user_version` 最后置位，未完成则整体重跑（故全部步骤必须幂等）。建议 `ai_suggestion_items` 增 `confidence`/`source` 列也在 v18 同批（`add_column_if_missing` 幂等）。

### 4.4 `delete_tag_facet`：单事务级联顺序与性能

级联顺序改造书 §7.2 设计正确，评审确认并补充：

```
系统分面守卫（拒绝）→ 收集 tag_ids
→ ① DELETE asset_tags（必须先于 tags，让 trg_at_ad 逐行重算 fts_content）
→ ② DELETE tag_ops（防 undo_batch JOIN 丢行；同时明示撤销能力丢失）
→ ③ DELETE ai_suggestion_items（facet_key 裸 TEXT 无外键）
→ ④ DELETE tag_aliases（显式删，不依赖 CASCADE）
→ ⑤ DELETE tags → ⑥ DELETE tag_facets → commit
全程单事务；前置 get_tag_facet_impact（修正后的计数，B4）
```

**性能注意**：
- `asset_tags` 逐行删除会逐行触发 FTS 触发器并重写索引。当前 259 素材规模无感；**合成 1 万素材 × 1000 标签分面**压测下若超过阈值（评审建议 ≤15 秒），则前端在 `impact` 超阈值（如 `assetCount > 5000`）时于确认弹窗提示「删除可能需要数秒，期间界面短暂无响应」，并在命令内记录耗时日志；
- 长事务期间全局 `Mutex<Connection>` 阻塞其他读写，单用户场景可接受，但不得在事务内做任何网络/文件 IO；
- `FacetDeleteReport` 增加字段：`undo_lost_ops`（被删流水数，文案明示「N 条打标历史不可再撤销」）。

### 4.5 前端硬编码删除的前置校验（B5 落地）

删除前端 `keyForLegacyName` / `BASE_FACET_DEFAULTS` / `WORKBENCH_DEFAULT_KEYS` 前：

1. **校验云端返回 key 与 `tag_facets.key` 完全一致**：抓取真实云端返回样本（含本地 Ollama），确认提示词下发的是 `tag_facets.key` 且模型原样返回；若存在返回中文分类名的存量行为，前端 `normalizeTagKeys` 必须保留到该行为消失；
2. **后端 `key_for_legacy_name` 保留边界**：保留到历史批次清零。清零判定查询（可做成设置页「数据与缓存」信息项）：
   `SELECT COUNT(*) FROM ai_suggestions WHERE status='pending' AND suggested_tags LIKE '%中文分类名样本%'` 或更稳妥地按批次逐条试解析；用户也可依 R12 授权直接放弃全部未确认历史批次（提供一键「放弃所有待确认批次」按钮，清空后即满足删除条件）；
3. 删除后 `buildWorkbenchFacets` 空 facets 兜底：显示「还没有分类，去设置页新增」引导文案，配合 `seed_system_facets_if_empty()`，防白屏（改造书 §16.2 已列风险，评审确认兜底测试 `buildWorkbenchFacets_no_hardcoded_fallback` 必须写）。

### 4.7 回滚与数据备份策略

### 7.2 各项的业界做法与实施建议（业界调研报告摘要 + 评审落地方案）

#### 7.2.1 缺口①：颜色筛选 —— 走「内容色检索」路线，优先以色相分桶分面进入元数据面板（低成本）

**业界参考做法**（两条路线必须区分，不可混为一个功能）：

- **手动色标路线**（Lightroom / Adobe Bridge）：颜色标签是用户手动打的 5 色标记，属选片工作流，与图片内容无关——**不适合本项目定位，不采用**；
- **内容色检索路线**（Eagle / digiKam）：基于图片实际颜色。Eagle 的 Color Search 为内置色板点选/拖拽取色（含推荐色 + 自定义取色器 + 容差滑块），秒级返回含该色相的素材，是素材库类应用的主流做法——**与本项目定位最匹配，作为目标形态**；
- 算法层面业界共识为 K-Means 聚类提取主色（Apple Accelerate 官方文档即以 k-means 计算主导色），每图存 3–5 个主色 + 占比；查询在感知均匀空间（Lab/ΔE 或 HSV 色相环）做距离阈值匹配，常配 12/24 色相分桶索引加速。争议项：HSV 色相环距离实现简单但蓝色区域感知失真，Lab/ΔE 更准但计算稍贵——本项目已在 Lab 空间做 k-means 与 ΔE 簇合并，路线正确；
- 反面参考：Immich 的智能搜索是 CLIP 向量检索 + 独立元数据筛选器两条链路，不做自然语言翻译，与本缺口无直接可比性，不参照。

**本项目实施方案**（属补齐展示层，不是新建能力——算法已有 `palette.rs` 的 k-means 调色板与 `dominant_hue` 入库，缺的只是可点选入口）：

1. **一期（低成本，本轮实施）**：在 `list_metadata_facets` 增加**色相分桶分面**（如 12 桶，复用现有 `bucketToFilter` 模式），`MetadataPanel` 即可自动呈现点选式颜色筛选；后端复用既有 `dominant_hue` between 环形语义（跨 0° 红区由编译层双区间处理），无需新增查询能力；
2. **二期（可选演进）**：升级为 Eagle 式交互——色板点选 + 自定义取色器 + 容差滑块。数据基础已就绪（`palette_json` 已存最多 8 主色 + 占比，前端已渲染色条），届时补交互即可；
3. **不做**：hue→颜色名标签化。会引入标签生成/同步与一致性维护成本，且与 v16「color 退出标签体系」的既定决策冲突；
4. 若未来需要手动色标工作流，另立功能，与内容色检索严格分离。

**注意事项**：色相分桶边界须与提示词中的色相区间映射（红 345–15、橙 15–45、黄 45–70、绿 70–155、青 155–225、蓝 225–295、紫 295–345）保持一致，避免「UI 选红色」与「AI 说红色」结果不一致；低饱和素材（灰/黑/白）按 `dominant_sat lte 10` 归入独立的「无彩色」桶。

#### 7.2.2 缺口②：AI 复合元数据查询 —— 结构化约束 + 三级容错降级（对齐本报告 §3.3，落地具体字段教学）

**业界参考做法**（业界共识）：

- **JSON Schema 严格模式优先**：OpenAI Structured Outputs 可保证输出 100% 符合给定 Schema；已知限制——最多 5 层嵌套、不支持 pattern/format 校验、单 Schema enum 上限约 500 个值（社区实测）——对「字段枚举有限」的搜索查询场景完全够用；
- **字段清单教学**：Anthropic 官方最佳实践——工具/参数描述要「extremely detailed」，比任何花哨提示都有效；复杂工具配 2–4 个正例显著降低错误率。本地小模型有实测表明把 schema 中的 `$ref` 全部展开后，结构化成功率从 20% 提升到 72%（Philipp Schmid，Llama 3.1 8B 实测）——**本项目本地模式务必展开 $ref**；
- **封闭域字段用 enum、开放域用自由字符串**是主流划分（字段名/操作符等封闭域用 enum；关键词/标签用自由字符串），enum 需在描述里给出每个值的含义；**单位与格式必须显式写死**在字段 description（日期给 ISO 8601 示例、文件大小给字节约定），不能指望模型推断；
- **容错降级的分层策略**：schema 校验失败 → 携带错误信息原地重试 1 次（「self-healing pipeline」，2026 年 NL2SQL 领域标准做法）→ 仍失败则降级，而不是整体报错；「丢弃单个非法条件、保留合法条件」是文献中常见的部分降级手段，前提是条件间相互独立（本项目查询表达式模型天然满足）；
- 争议项：整体重试次数——多数实践限定 1 次（本地小模型重试收益递减且延迟翻倍），也有方案 0 重试直接降级；标签词表很大时全量 enum 会撑爆上下文且模型幻觉非法值——评审明确**标签不进 enum**。

**本项目实施方案**：

1. **schema 收紧**：`intent_schema` 给 `metadata_item.key` 加 enum（与 `search_query` 白名单常量同源生成，防清单与编译白名单漂移，同 §3.3 第 4 条），`op` 加操作符 enum；字段名/单位/格式写死在提示词：`file_size`（**字节**，支持 `between`）、`taken_at`（`YYYY-MM-DD`，本地时区、左闭右开）、`duration_ms`（毫秒）、`width/height/resolution`，并配示例输出；
2. **三级容错**（替换现状「猜错整体报错」）：① 校验失败 → 携带错误信息重试 1 次；② 仍失败 → **丢弃非法条件、保留合法条件** + warning；③ 全部条件非法 → 降级为全文搜索 + 黄字提示用户。配置类错误（401/断连）保持真报错（与 §3.3 第 1 条一致）；
3. **标签大词表不进 enum**：标签走自由字符串 + 后端归一（经 `resolve_concept` 精确/别名/唯一前缀匹配，既有链路），避免 enum 膨胀与幻觉；
4. 前端体积筛选同步补齐任意区间输入（现 `metadataConvert.ts` 仅固定 4 档：小于 1MB / 1–10MB / 10–100MB / 大于等于 100MB，选不出 10~105MB 这类任意区间），与 AI 侧能力对齐。

**注意事项**：三级容错与本报告 §3.3 的「三级降级（Structured → JsonObject → Plain）」是不同层面的两条链——§3.3 管「输出格式」降级，本节管「条件合法性」降级，施工时两条链叠加生效、互不替代；「丢弃非法条件」必须伴随对用户可见的 warning（黄字），不得静默。

#### 7.2.3 缺口③：GPS 定位 —— 对标 Immich 本地优先模式；本期决策：先存原始经纬度，反解作为二期可选

**业界参考做法**：

- **Immich = 完全本地反向地理编码（最佳对标）**：使用 GeoNames 数据集，随每次小版本升级导入，所有反解在用户自己的设备上完成，零在线调用、隐私友好——是离线单机应用最直接可抄的模式；
- **PhotoPrism = 云端反解（反例/对照）**：反解依赖官方后端 `places.photoprism.app`（为隐私做了 S2 cell 模糊化，不传精确坐标）；「完全离线运行」自 2020 年 issue #180 起长期被用户要求但未落地。说明离线反解有门槛，本地 GeoNames 是公认答案；
- **digiKam**：在线 GeoNames 反解 + 反解结果回写为图片 tag 可检索，但依赖公网服务，不适合本项目；
- **元数据格式（共识）**：图片走 EXIF——`GPSLatitude/GPSLongitude` 为三个有理数（度/分/秒）+ `N/S`、`E/W` Ref 半球标记，ExifTool 惯例归一化为带符号十进制度；iPhone 视频不走 EXIF，走 QuickTime `mdta` 键 `com.apple.quicktime.location.ISO6709`（Apple 官方 QuickTime File Format 规范），格式如 `+37.3349-122.0090+10.000/`（纬度/经度/高程，符号定界、无分隔符），另有 `location.body/note/date` 辅助键；
- **转码陷阱**：FFmpeg ticket #4209 记录 iOS GPS 元数据在 MOV→MP4 转码中丢失——**本项目未来若做视频转码，必须保留 `location.ISO6709` 拷贝**；
- **隐私取舍（共识）**：存原始经纬度作为唯一事实源 + 反解行政区划存为可搜索文本；不做街道级、不调在线反解。GeoNames 免费数据即可覆盖到城市级，许可为 CC-BY 4.0（**需在文档署名**）；
- 争议项：反解粒度——Immich 只到 City/State/Country，digiKam 用户普遍抱怨 GeoNames 粒度不够、想要街道级（讨论 #6137）；离线场景建议接受「城市级」上限。

**本项目实施方案（实施路径，五步）**：

1. **提取**：`exif_meta.rs` 增加 `Tag::GPSLatitude/GPSLongitude`（有理数三元组 + Ref 半球换算为带符号十进制度）；视频侧从已保留的 `raw_json`（`format.tags`）解析 `location`/`com.apple.quicktime.location.ISO6709`；
2. **存储**：V18 迁移给 `assets` 增 `latitude REAL / longitude REAL`（幂等 `add_column_if_missing`）+ 索引；
3. **写入**：`importer.rs::write_meta` 与 `media_refill.rs` 存量回填路径各补写入；
4. **检索**：`search_query.rs` 的 `key_spec / allowed_ops / value_expr` 三处同步加经纬度字段进白名单（数值区间）；
5. **展示**：`list_metadata_facets` 增加位置分面，`MetadataPanel` 自动呈现；Viewer 详情区展示原始经纬度；`build_system_prompt` 补充位置字段用法（纳入 §7.2.2 的元数据能力清单）。

**注意事项**：凡涉及视频转码的后续功能必须保留定位元数据（FFmpeg ticket #4209）；经纬度入库前做合法性校验（纬度 ±90°、经度 ±180°，`0,0` 空岛坐标视为无效）。

**本期决策：先存原始经纬度、不做反解，反解作为二期可选。** 理由：① 原始经纬度是唯一事实源，反解文本可由经纬度后补、反之不可逆推——先保事实源最安全；② 内嵌 GeoNames 数据集（即便城市级）有分发体积与导入维护成本，本轮数据库重建窗口应聚焦表结构收口，不扩大迁移面；③ 有经纬度后「按区域范围筛选」（bbox/距离）即刻可用，而「杭州」式城市名检索可由既有 `scene` 标签（定义为素材发生的环境或地点）与内容描述兜底过渡，二期反解落地后再升级为城市文本列供 FTS5 与筛选使用。二期反解预定方案：本地离线、GeoNames 城市级、CC-BY 署名、全程零网络调用。

**验收提示**：二期反解落地前，不要将「城市名精确检索」（如搜「杭州」按经纬度命中）列入本期验收指标。

#### 7.2.4 缺口④：视频拍摄时间 —— 按 UTC 解析 `creation_time`，严防设备不合规陷阱

**业界参考做法**：

- **标准做法**：读 `format.tags.creation_time`（ffprobe JSON 输出）。MP4/MOV 容器按 ISO 14496-12 规定 mvhd 创建时间以 UTC 存储（1904 纪元），FFmpeg 读取后统一输出为 `YYYY-MM-DDTHH:MM:SS.ffffffZ` 形式，**即可安全地当作 UTC**（注意：历史版本 FFmpeg 读出的 UTC 不带 Z 标识，旧版输出需自行补 Z）；
- **重点警示——设备不合规是最大陷阱**（FFmpeg 官方工单 #5673 实测记录）：Canon / Nikon 相机把 `creation_time` 写成**本地时间**；Samsung 手机写 UTC；iPhone 遵循规范写 UTC。也就是说同一套解析逻辑面对不同来源视频会差出时区偏移，**且没有任何字段能标识这份 `creation_time` 到底是 UTC 还是本地时间**；
- 时区信息可能在 XMP 中（`-export_xmp` 可导出），或根本不存在；图片侧的 EXIF OffsetTime 系列在视频上基本不可用；iOS 视频另有 `com.apple.quicktime.creationdate` 等键，ExifTool 对 QuickTime CreateDate/MediaCreateDate 有专门修正逻辑（部分相机 MediaCreateDate 是本地时间），解析时应以 ffprobe/ExifTool 修正后字段为准；
- **业界无完美方案**：Google Photos 用启发式（含 GPS 时按拍摄地时区、否则推测）——2025 年仍有大量用户投诉「带 GPS 的照片/视频被错误按本地时间解读」；Apple Photos 对非 Apple 相机来源的时区也常误判，需用户手动「调整日期时间」。**启发式 + 允许用户手动校正**是通行做法。

**本项目实施方案**：

1. `importer.rs` 视频分支解析 `format.tags.creation_time`，**一律按 UTC 解析**（兼容旧版输出补 Z），写入 `taken_at`；
2. **疑似本地时间检测**：计算 `creation_time` 与文件 mtime 的差值，若差值为**整小时且 |差值| ≤ 14h**，判定为「疑似设备本地时间伪装成 UTC」，**提示用户确认，不静默修正**；
3. **无 `creation_time` 时回退文件 mtime**，并在元数据中标记「推测时间」，前端展示时注明，避免与真实拍摄时间混淆；
4. 保留用户级「时区偏移校正」入口的能力预留（参考 Apple/Google 的手动调整），本版可只留接口不做完整 UI。

**注意事项**：本项修复后，缺口②的「拍摄于 8 月」类日期查询才可能命中视频；存量视频需经 `media_refill.rs` 回填 `taken_at`（与缺口③的经纬度回填同批），回填任务复用既有后台补算设施（参照 `rescan_assets_palette` 模式）。
