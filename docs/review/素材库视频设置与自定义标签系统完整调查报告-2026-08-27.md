## 1. 执行摘要

本轮调查最终确认了三个直接阻断用户体验的基础缺陷，以及两个需要系统性补齐的产品能力缺口。

### 1.1 三个必须立即修复的确定性缺陷

#### P0-1：设置页违反 React Hook 调用顺序，页面必然崩溃

真实运行态已经复现，错误文本为：

```text
Rendered more hooks than during the previous render.
```

根因位于 `src/pages/SettingsPage.tsx`：组件在 `draft` 为空时于第 93 行附近提前返回，但 `manageOpen` 对应的 `useState` 位于第 150 行附近，也就是条件返回之后。第一次渲染不执行这个 Hook，设置加载后第二次渲染又执行这个 Hook，React 因两次渲染的 Hook 数量不同而直接抛错。

这也解释了为什么页面上的“重新加载”没有任何作用：错误边界只是再次尝试渲染同一个违反 Hook 规则的组件，根因没有消失。

#### P0-2：视频大图查看器使用错误的类型判断，当前视频全部被当成图片

`src/components/library/ViewerPage.tsx` 当前使用：

```tsx
const isVideo = current.durationMs != null;
```

但是素材卡片已经使用统一的 `isVideoAsset(asset)`，会按照 MIME、时长和扩展名进行兜底判断。大图查看器没有复用这套逻辑。

当前数据库中的 35 个视频，其 `duration_ms` 全部为空，因此这 35 个视频进入大图查看器时全部被判断为图片，`VideoPlayer` 根本不会挂载。这个问题不是播放器控件不工作，而是播放器在多数情况下没有被渲染。

#### P0-3：ffprobe 的标准输出被丢弃，视频元数据探测实际无法成功

`src-tauri/src/services/video.rs` 调用 ffprobe 时配置了：

```rust
.stdout(std::process::Stdio::null())
```

随后又尝试解析：

```rust
serde_json::from_slice(&out.stdout)
```

标准输出已经被送往空设备，`out.stdout` 必然为空，JSON 解析自然失败。因此即使系统中的 ffprobe 可以正常读取视频，应用也拿不到输出。

使用当前真实视频样本直接运行 ffprobe，可以读取到完整的 4K、HEVC Main 10、10-bit、59.94fps、约 89Mbps、BT.709 等信息。这说明不是文件缺少元数据，而是应用探测链路丢失了输出。

### 1.2 两个系统性能力缺口

#### P1：文件属性模型不足以支撑专业图片和视频管理

当前视频只存储：

- 宽度
- 高度
- 时长
- 视频编码
- 音频编码

这远不足以支撑素材管理。色彩空间、传输曲线、色彩原色、像素格式、位深、帧率、码率、编码 Profile、容器、声道、采样率、旋转、HDR 等字段都没有进入数据模型。

图片和视频又共用一个简单的“文件”区域，没有形成“通用、图片、视频”三个清晰的数据视图。

#### P1/P2：标签系统已有稳定分面基础，但还不能真正由用户增加或减少大类

当前代码已经具备以下正确基础：

- `tag_facets.key` 作为稳定机器协议
- AI 打标与 AI 搜索共用分面提示上下文
- 标签支持父子结构、别名、移动、合并和停用
- 超级搜索支持分面条件和表达式树
- 工作台支持通过配置控制分面是否显示

但是设置页目前只能编辑已有 `aiFacetConfigs`，后端没有完整的“新增分面、修改分面、停用分面、恢复分面、排序分面、迁移分面”命令。`TagManageDialog` 管理的是分面内部的标签，不是分面大类本身。

因此，“用户新增人物衣服颜色、商品材质、镜头运动等大类，并让素材库、AI 打标、超级搜索和条件公式自动支持”目前还没有闭环。

### 1.3 推荐总顺序

```text
先恢复可用性
  设置页 Hook 错误
  视频识别错误
  ffprobe 输出错误
        ↓
再修数据
  重新扫描现有 35 个视频
  扩展视频元数据模型
        ↓
再修展示
  大图播放兼容策略
  图片/视频属性分栏
  标题栏设置入口
        ↓
最后补平台能力
  自定义分面治理
  搜索/公式/AI/工作台全链路一致性
```

## 5. 素材库滚动闪烁和串图

### 5.1 用户现象

向下滚动素材库时，部分卡片的空白背景或图片区域会闪烁，短暂变成其他照片，再恢复或继续变化。

这类现象通常不是单一的“图片读取慢”，而是以下几类问题叠加：

1. 虚拟列表复用 DOM 节点。
2. React 复用组件状态。
3. 图片请求异步返回顺序与当前素材身份不一致。
4. 占位图和高清图双层切换时保留了旧状态。
5. GPU 合成和透明度动画放大了短暂错误画面。

### 5.2 当前网格实现

`AssetGridView` 采用“按行虚拟化、行内 CSS Grid”的方式：

```text
Virtualizer 管理 row 0、row 1、row 2...
每个 row 再渲染 columns 个 AssetCard
```

核心计算：

```tsx
const columns = Math.max(2, Math.floor((width + GAP) / (MIN_CARD + GAP)));
const rowCount = Math.ceil(items.length / columns);
```

虚拟器当前未配置 `getItemKey`：

```tsx
const virtualizer = useVirtualizer({
  count: rowCount,
  getScrollElement: () => ref.current,
  estimateSize: ...,
  overscan: 3,
});
```

渲染时使用：

```tsx
key={row.key}
```

TanStack Virtual 默认 key 通常基于虚拟索引。索引本身并不代表稳定的素材身份。

### 5.3 风险一：动态列数会改变“某一行代表哪些素材”

假设初始为 4 列：

```text
row 0 = asset 1,2,3,4
row 1 = asset 5,6,7,8
```

窗口变化后变成 3 列：

```text
row 0 = asset 1,2,3
row 1 = asset 4,5,6
```

此时 `row 1` 的 key 仍可能是索引 1，但内部素材集合已经完全不同。React 会尝试在相同父节点位置复用子树，虽然 `AssetCard` 有素材 ID key，但父级行节点、图片 DOM、动画和观察器都可能经历一次旧新内容切换。

快速滚动、侧栏宽度变化、窗口最大化/还原、滚动条出现与消失，都可能触发宽度和列数变化。

### 5.4 风险二：缩略图状态不是当前 props 的纯函数

`Thumbnail` 内部保存：

```tsx
const [hdUrl, setHdUrl] = useState<string | null>(null);
const [hdReady, setHdReady] = useState(false);
const [placeholderUrl, setPlaceholderUrl] = useState(...);
const [placeholderFailed, setPlaceholderFailed] = useState(false);
```

这些状态具有以下隐患：

#### 5.4.1 `placeholderPath` 变化时没有完整重置

当前 Effect 只在 `placeholderUrl` 为空时设置：

```tsx
if (!placeholderUrl && placeholderPath) {
  setPlaceholderUrl(toFileUrl(placeholderPath));
}
```

如果组件在某种复用路径下已经持有旧的 `placeholderUrl`，新的 `placeholderPath` 不会替换旧值。

#### 5.4.2 `assetId` 变化时没有统一清理状态

没有一个集中 Effect 执行：

```text
assetId 改变
→ 清空 hdUrl
→ hdReady=false
→ placeholderFailed=false
→ 更新 placeholderUrl
→ 取消旧请求
```

#### 5.4.3 异步请求只有 mounted 级清理，没有请求代际

高清图请求：

```tsx
getThumbnailUrl(assetId, "hd", 512).then(setHdUrl)
```

没有保存请求对应的素材 ID，也没有在回调时验证“当前组件仍然展示这个 assetId”。

即使正常列表 key 已经降低了复用概率，排序、过滤、组件逻辑变化和未来重构仍可能让旧请求覆盖新状态。

#### 5.4.4 高清图淡入可能放大串图感知

高清图采用 300ms 透明度过渡：

```tsx
transition-opacity duration-300
```

如果 URL 或 ready 状态不属于当前素材，用户会明显看到旧图淡入或闪现，而不是一帧难以察觉的错误。

### 5.5 风险三：虚拟滚动自身会频繁挂载和卸载可见项

TanStack Virtual 官方资料明确说明：可见范围改变时，虚拟项会添加和删除，滚动开始/结束状态也可能触发重渲染。这是虚拟列表的正常行为。

因此不能依赖“组件通常不会被复用”来保证正确性。虚拟化环境中的图片组件必须满足：

- 素材身份稳定。
- 所有异步回调可取消或可判定过期。
- 旧图片不能在新素材占位阶段继续显示。
- 列表重排后状态必须跟随素材而不是跟随位置。

### 5.6 推荐修复方案

#### 方案 A：保持按行虚拟化，小范围修复

适合快速止血。

1. 为虚拟行配置显式 `getItemKey`。
2. 行 key 由该行当前素材 ID 组合生成，而不是只用行索引。
3. key 应包含 `columns` 或布局版本，列数变化时强制建立新行身份。
4. 列数改变时调用虚拟器重新测量。
5. `Thumbnail` 在 `assetId/placeholderPath` 改变时完整重置。
6. 每次异步高清请求使用递增 token 或 `AbortController` 等价机制。
7. 回调仅在 token 与当前 token 相同时更新。
8. 图片 `onLoad/onError` 也要验证当前 URL。
9. 移除不必要的状态冗余，尽量由 props 直接计算 placeholder URL。

示意身份：

```text
row key = `${columns}:${assetIdsInRow.join(',')}`
```

注意：这不是最终性能最优解，但能显著减少错误复用。

#### 方案 B：改为按素材虚拟化

长期更推荐。

虚拟器直接管理每个素材：

```text
virtual item key = asset.id
position = 根据 index 和 columns 计算 row/column
```

优点：

- 素材身份天然稳定。
- 不再需要让“行身份”代表多个素材。
- 列数变化时只重新计算位置。
- 单个卡片生命周期更清晰。
- 更容易对单卡片做预加载、测量和缓存。

缺点：

- 需要重新处理二维网格定位。
- 需要谨慎验证不同宽度下的总高度。

#### 方案 C：降低滚动时 React 工作量

在稳定性修复之后再考虑：

- 评估 TanStack Virtual 新版 `directDomUpdates`。
- 将纯位置变化交给虚拟器直接更新 DOM。
- 保持卡片 `memo`。
- 避免滚动期间父组件因无关状态重渲染。
- 适当提高 overscan，但不能把 overscan 当成修复串图的手段。

### 5.7 不建议的临时方案

- 仅增加 `overscan`：只会多渲染一些卡片，不能修复身份和异步竞态。
- 取消高清图：会降低质量，但旧占位图仍可能复用。
- 去掉淡入动画：会降低闪烁可见度，但错误仍然存在。
- 把虚拟列表全部取消：小库可能暂时正常，大库性能会明显退化。
- 给 URL 加随机 query：可能绕开浏览器缓存，但会破坏缓存效率且不能解决状态复用。

### 5.8 网格专项验收

1. 1000 个以上素材连续快速滚动 3 分钟，无其他照片闪入当前卡片。
2. 在滚动中最大化、还原窗口，无串图和跳行。
3. 2/3/4/5/6 列之间变化时，卡片内容与文件名始终对应。
4. 改变排序后立即滚动，不显示旧排序中的图片。
5. 切换图片/视频筛选，不显示上一筛选结果的旧图。
6. 占位图读取失败时只显示当前素材的失败占位。
7. 高清图请求乱序返回时，仅当前素材结果生效。
8. 清理缓存后滚动，不能出现已删除缓存的旧 DOM 残影。

## 6. 视频大图预览不能播放

### 6.1 当前组件关系

```text
素材卡片悬停
  AssetCard
    → isVideoAsset(asset)
    → VideoHoverOverlay
    → 卡片内部播放

双击大图
  ViewerPage
    → durationMs != null
      true  → VideoPlayer
      false → 图片/缩略图逻辑
```

素材卡片与大图查看器使用了两套不同的视频判断标准，这是能力不一致的根本原因。

### 6.2 已确认的类型判断错误

`src/utils/assetKind.ts` 已经提供：

```text
MIME 为 video/*
→ 否则 durationMs 有值
→ 否则扩展名在视频集合中
```

这能覆盖：

- 元数据探测失败但 MIME 正确的视频。
- MIME 异常但时长已读取的视频。
- MIME 和时长都异常但扩展名明确的视频。

然而 `ViewerPage` 仍使用旧逻辑：

```tsx
const isVideo = current.durationMs != null;
```

必须统一改为同一个类型函数，并同步检查：

- 大图主区域。
- 胶片条“视频/图片”文字。
- 属性面板的视频字段分支。
- 可能存在的 AI 工作台或导入预览分支。

### 6.3 当前真实数据对该错误的放大

当前数据库：

```text
视频总数 = 35
duration_ms 为空 = 35
```

因此当前不是“部分特殊视频无法播放”，而是现有 35 个视频都会进入错误的图片分支。

### 6.4 视频播放器本身的第二层风险

即使修复类型判断，播放器仍需处理下列问题。

#### 6.4.1 自动播放策略

当前大图播放器：

```tsx
<video src={src} autoPlay playsInline />
```

没有 `muted`。Chromium/WebView2 通常会限制带声音自动播放。当前代码也没有在挂载后显式调用：

```tsx
video.play().catch(...)
```

因此可能发生：

- 视频已加载但没有自动播放。
- `playing` 状态仍为 false。
- 用户误认为播放器坏了。
- 只有再次点击画面或播放按钮才开始。

建议：

- 默认静音自动播放，用户操作后允许开启声音；或
- 大图默认不强制自动播放，显示明确的大播放按钮；
- 无论选哪种，都必须处理 `play()` Promise 拒绝。

#### 6.4.2 编码兼容性

当前真实样本：

```text
container      mov,mp4,m4a,3gp,3g2,mj2
video codec    HEVC / H.265
profile        Main 10
codec tag      hvc1
resolution     3840 × 2160
pixel format   yuv420p10le
frame rate     60000/1001，约 59.94fps
bit rate       约 88.8 Mbps 视频流
color range    pc
color space    bt709
color transfer bt709
color primaries bt709
audio codec    AAC
audio sample rate 48000Hz
audio channels 2 / stereo
```

MP4 只是容器，真正决定能否播放的是 HEVC Main 10 等编码参数。Windows WebView2 是否能播放取决于：

- Windows 是否具有 HEVC 解码组件。
- 当前显卡和驱动是否支持 10-bit HEVC。
- WebView2 版本。
- 编码 Profile、Level、像素格式和色彩信息。
- 系统媒体扩展是否完整。

因此，应用不能承诺“所有导入视频都直接用 `<video>` 原文件播放”。

### 6.5 推荐播放架构

#### 第一层：原文件直接播放

1. 根据元数据构造完整 MIME + codec 字符串。
2. 使用 `canPlayType()` 做粗筛。
3. 有条件时使用 `navigator.mediaCapabilities.decodingInfo()` 判断：
   - supported
   - smooth
   - powerEfficient
4. 尝试原文件加载。
5. 监听 `loadedmetadata/canplay/error/stalled/waiting`。

#### 第二层：兼容预览代理

原文件不支持时，生成只用于预览的代理：

```text
MP4
H.264
AAC
8-bit yuv420p
1080p 或按原视频限制最大边
合理码率
faststart
```

代理文件只用于应用内预览：

- 不覆盖原视频。
- 导出仍使用原视频。
- 缓存在媒体预览目录。
- 缓存 key 包含源文件路径、大小、修改时间和转码版本。
- 后续可按 LRU 清理。

#### 第三层：明确失败状态

播放器需要向用户显示真实状态：

```text
正在读取视频信息
正在加载原始视频
当前编码不受系统支持
正在生成兼容预览
兼容预览已就绪
视频文件损坏
源文件不存在
解码失败
```

必须提供：

- 重试。
- 打开原文件所在位置。
- 使用系统默认播放器打开。
- 查看失败详情。

### 6.6 关于悬浮预览的产品约束

当前视频预览已使用 `VideoHoverOverlay` 覆盖在原卡片内部，这符合“在素材卡片框内预览，不弹出额外悬浮组件”的要求。

后续应冻结规则：

```text
视频悬停预览：只在卡片内部
视频大图预览：只在独立 ViewerPage 主区域
不得创建脱离卡片的浮动视频窗
不得在滚动列表外跟随鼠标展示视频
```

当前图片悬停仍使用 `MediaPreviewPopover`。如果未来“不使用悬浮组件”的要求也扩展到图片，则图片也应改成卡片内高清替换或只保留双击查看；本报告本轮主要按用户对视频预览的明确描述处理。

## 7. 视频元数据读取严重不足

### 7.1 已确认的 ffprobe 实现错误

当前代码意图：

```text
运行 ffprobe
→ 输出 JSON
→ serde_json 解析
→ 写入 VideoMeta
```

实际代码：

```text
stdout → null
→ output.stdout 为空
→ JSON 解析失败
→ probe 返回 None
→ importer 不写视频元数据
```

必须先修复这个错误，否则增加再多字段也没有意义。

### 7.2 注释中的“30 秒超时”与 probe 实现不一致

`video.rs` 定义了：

```rust
const FFMPEG_TIMEOUT: Duration = Duration::from_secs(30);
```

抽帧使用 `spawn + try_wait + kill` 实现了真正超时。

但是元数据 probe 使用 `Command::output()`，没有使用这个超时常量。对于损坏文件、网络盘卡顿、异常容器，probe 仍可能长期阻塞。

因此视频探测应同样改成：

```text
spawn
→ 定时 try_wait
→ 超时 kill
→ 读取 stdout/stderr
→ 解析 JSON
```

### 7.3 当前 `VideoMeta` 字段

```rust
pub struct VideoMeta {
    pub width: Option<i64>,
    pub height: Option<i64>,
    pub duration_ms: Option<i64>,
    pub video_codec: Option<String>,
    pub audio_codec: Option<String>,
}
```

这只能满足最基础的文件列表展示，不能支撑专业素材库。

- 迁移频繁。

- 每次补一个厂商字段就要改前后端协议。

### 7.6 ffprobe 与 MediaInfo/ExifTool 的组合建议

#### 首选：ffprobe

优点：

- 已经依赖 ffmpeg 抽帧。
- JSON 输出结构化。
- 视频流、音频流和标准色彩字段足够丰富。
- 适合转码和播放预判。

#### 可选补充：MediaInfo

MediaInfo 对以下信息的用户可读名称较好：

- ColorSpace。
- Transfer characteristics。
- Mastering display。
- 编码商业名称。
- 多轨道信息。

但是增加另一个外部二进制会提高打包和维护成本。本项目一期可以先把 ffprobe 读取完整，再评估是否确有字段缺口。

#### 可选补充：ExifTool

适合读取：

- QuickTime 厂商 tag。
- 相机品牌私有信息。
- GPS。
- 部分 Log/色彩模式声明。
- 图片 EXIF、XMP、ICC。

同样不建议一期立即把三套工具都做成强依赖。合理顺序：

```text
先修好 ffprobe
→ 确认缺失字段
→ 对确实缺失的专业元数据再增加 ExifTool 可选增强
```

### 7.7 现有视频元数据回填

修复 probe 以后，旧素材不会自动获得数据。必须设计重新扫描流程：

```text
扫描全部视频
→ 每个视频计算是否需要重扫
→ ffprobe
→ 解析和校验
→ 短事务回写
→ 记录失败原因
→ 进度事件
```

需要支持：

- 单个素材重新读取。
- 当前筛选结果重新读取。
- 全库重新读取。
- 只扫描元数据缺失项。
- 元数据版本升级后重新扫描旧版本。
- 取消任务。
- 失败重试。

## 9. 设置页完全无法显示

### 9.1 真实复现过程

1. 启动当前 Vite 开发服务。
2. 启动当前 Tauri debug 程序。
3. 素材库正常显示当前 258 个素材。
4. 点击“设置”。
5. 页面 Error Boundary 显示“页面暂时无法显示”。
6. 开发环境错误详情显示：

```text
Error: Rendered more hooks than during the previous render.
```

因此设置页错误已经由真实运行证明。

### 9.2 精确根因

`SettingsPage` 前半部分执行多个 Hook，然后：

```tsx
if (!draft) {
  return ...;
}
```

但是后面又出现：

```tsx
const [manageOpen, setManageOpen] = useState(false);
```

React 要求同一组件每次渲染按完全相同的顺序调用 Hook。当前流程：

```text
第一次渲染
draft = null
→ 提前 return
→ 不调用 manageOpen Hook

第二次渲染
settings 已加载
draft 被设置
→ 不提前 return
→ 调用 manageOpen Hook

结果
第二次比第一次多一个 Hook
→ React 抛错
```

### 9.3 为什么现有测试没有发现

目前只有 `normalizeSettings.test.ts`，它验证归一化函数可以处理缺字段，但没有渲染 `SettingsPage`。

类型检查不会检查运行时 Hook 调用顺序。ESLint 的 Hooks 规则通常可以发现部分问题，但当前脚本中没有看到独立 lint 检查作为构建门禁。

必须补充：

- `SettingsPage` 初始 loading 渲染测试。
- 模拟设置 Promise resolve 后的二次渲染。
- 断言页面正常显示在线打标表单。
- 断言不进入 Error Boundary。

### 9.4 现有“重新加载”为什么无效

`PageErrorBoundary.reset()`：

```tsx
this.setState({ hasError: false, ... });
this.props.onReset();
```

`App.tsx` 传入：

```tsx
onReset={() => setPage(page)}
```

这里存在两个问题：

1. 根因代码仍然违反 Hook 规则，再渲染必然再崩。
2. `setPage(page)` 设置的是相同值，不保证页面组件重新挂载，也不会重新加载设置。

### 9.5 推荐修复结构

#### 最小修复

把 `manageOpen` 等所有 Hook 移到任何条件返回之前。

同时全文件审计：

- 所有 `useState`。
- 所有 `useEffect`。
- 所有 `useMemo`。
- 所有 `useCallback`。
- 所有 Zustand store hooks。

#### 推荐重构

```tsx
function SettingsPage() {
  // 所有页面级 Hook 固定调用

  if (loading) return <SettingsLoading />;
  if (error) return <SettingsLoadError />;
  return <SettingsForm settings={...} />;
}
```

`SettingsForm` 接收一份已经运行时校验成功的完整 `Settings`，内部不处理“可能不存在”的数据。

### 9.6 真正的设置重试

重试动作应：

1. 清空 `loadError`。
2. 将 store 切换到 loading。
3. 重新调用后端 `get_settings`。
4. 执行 `normalizeSettings`。
5. 执行更严格的运行时 schema 校验。
6. 重建 draft。
7. 重新获取数据目录和当前子模块状态。
8. 对失败模块局部展示错误，不让非关键模块拖垮整个设置页。

### 9.7 设置数据安全建议

当前后端遇到无法解析的设置 JSON 时使用：

```rust
serde_json::from_str(&raw).unwrap_or_default()
```

这会将损坏配置静默替换成默认配置。虽然避免崩溃，但风险是用户随后保存默认配置，覆盖原有内容。

更安全的设计：

```text
解析成功
→ 迁移
→ 校验
→ 返回

解析失败
→ 返回明确错误
→ 保留原始 JSON
→ 禁止保存覆盖
→ 提供导出/修复/恢复默认值的显式操作
```

建议为设置 JSON 增加：

```json
{
  "schemaVersion": 12,
  "...": "..."
}
```

并保存最近一份可用备份。

## 11. 自定义标签大类与分面系统

### 11.1 用户目标

软件本体提供一套通用分类，但不同用户可以根据自己的内容类型增加、减少和调整大类，例如：

- 人物衣服颜色。
- 人物年龄段。
- 商品材质。
- 镜头运动。
- 项目客户。
- 授权状态。
- 内容平台。
- 修图状态。

这些自定义大类必须同时服务于：

- 素材库侧栏筛选。
- 手动打标。
- AI 打标提示词。
- AI 标签结果归类。
- 超级搜索。
- 条件公式。
- 标签管理。
- 导出和历史数据。

### 11.2 当前架构的正确部分

#### 稳定 `facetKey`

`tag_facets.key` 已被设计为稳定机器协议。显示名称可以本地化或修改，但 key 不应随显示名改变。

这是正确方向。机器协议不应该使用中文显示名，否则用户把“人物属性”改成“人物”后，搜索、AI 和历史条件都会断裂。

#### `tag_facets` 是结构事实源

当前代码明确规定：

- `selection_mode` 来自数据库。
- `max_items` 来自数据库。
- `description` 来自数据库。
- `aiFacetConfigs` 只覆盖 AI 开关、提示词、显示名和工作台显隐。

这种单一事实源设计应继续保持。

#### 标签治理基础

标签本身已经支持：

- 创建。
- 重命名。
- 父子层级。
- 移动。
- 合并。
- 别名。
- 停用。
- 影响统计。

但这些操作针对分面内部的标签节点，不等于管理分面大类。

### 11.3 当前设置页实际只能编辑什么

设置页当前循环：

```tsx
draft.aiFacetConfigs.map(...)
```

用户可以编辑：

- hint。
- displayName。
- enabledForAi。
- visibleInWorkbench。

用户不能编辑：

- 新增一个 facet。
- 停用或删除一个 facet。
- 设置 single/multi。
- 设置 maxItems。
- 设置排序。
- 设置描述。
- 设置是否系统分面。
- 查看删除影响。
- 将旧 facet 的标签迁往新 facet。

因此当前 UI 实际是“AI 分面覆盖设置”，不是完整的“标签大类管理”。

### 11.4 后端缺少分面治理命令

当前 `tags_cmd.rs` 有：

- `list_tag_facets`
- `list_tags_by_facet`
- `create_canonical_tag`
- `add_tag_alias`
- 标签移动、合并、停用等

没有完整的：

- `create_tag_facet`
- `update_tag_facet`
- `deprecate_tag_facet`
- `restore_tag_facet`
- `reorder_tag_facets`
- `get_tag_facet_impact`
- `migrate_facet_tags`

所以即使前端添加“新增大类”按钮，也没有可靠的持久化和约束入口。

### 11.5 `custom` 兼容逻辑不能替代真正的用户自定义分面

当前 `keyForLegacyName` 对未知名称返回：

```text
custom
```

这适合一次性迁移旧中文分类，因为旧数据没有稳定 key，只能将未知项放进兜底分面。

但不能用于新系统中的用户自定义分类。

例如用户新建：

```text
人物衣服颜色
人物服装材质
人物配饰
```

如果都归为 `custom`，会发生：

- 三个大类在机器层无法区分。
- AI 输出无法稳定归类。
- 超级搜索无法按指定大类筛选。
- 工作台只能显示一个混合区。
- 同名标签冲突更难管理。

新建分面必须创建真实的稳定 key，例如：

```text
people_clothing_color
people_clothing_material
people_accessory
```

### 11.6 推荐的分面模型

`tag_facets` 建议至少具备：

| 字段 | 说明 |
|---|---|
| key | 稳定机器 key，创建后不可修改 |
| display_name | 用户可修改显示名 |
| description | 用途说明 |
| selection_mode | single/multi |
| max_items | 多选上限，null 表示不限 |
| sort_order | UI 排序 |
| is_system | 系统分面不可删除，只能隐藏或恢复默认 |
| status | active/deprecated |
| created_at | 创建时间 |
| updated_at | 修改时间 |

可选增强：

- `icon`：选择有限内置图标，不存任意 SVG。
- `color`：用于 UI 识别，但避免过度彩色化。
- `applies_to`：image/video/all。
- `value_type`：tag/enum/text/number/date，第一期可只支持 tag。
- `allow_user_values`：是否允许在打标时创建新标签。

### 11.7 系统分面与用户分面规则

#### 系统分面

例如：

- subject
- scene
- purpose
- style
- color
- composition
- lighting
- people
- technical
- custom

建议：

- key 永久稳定。
- 不允许物理删除。
- 可以改显示名。
- 可以隐藏工作台。
- 可以关闭 AI。
- 可以停用非关键分面，但应允许恢复默认。

#### 用户分面

建议：

- 创建时生成稳定 key。
- 创建后 key 不允许修改。
- 显示名可修改。
- 有数据后不允许直接物理删除。
- 可以停用。
- 可以迁移标签到其他分面。
- 可以恢复。

### 11.8 新建分面 UI

设置页“标签分类”建议拆成两个层次：

```text
标签大类
  大类列表
  新增大类
  排序
  启用/停用
  AI 与工作台开关

标签内容治理
  打开标签管理
```

新增大类表单：

- 显示名称。
- 稳定 key 自动生成预览。
- 描述。
- 单选/多选。
- 数量上限。
- 适用媒体类型。
- 是否参与 AI。
- 是否显示在人工工作台。
- AI 提示词。

用户不熟悉机器 key 时，应自动从名称生成并允许创建前调整，但创建后锁定。

### 11.9 停用和删除流程

不能直接提供一个危险的“删除大类”按钮。

点击停用前应展示：

```text
该分面有多少标签
多少素材已关联
多少别名
多少 AI 待确认项
多少保存的查询或条件公式引用它
```

处理选择：

1. 仅停用：保留历史数据和查询兼容。
2. 迁移到另一分面后停用。
3. 合并进另一分面。
4. 无任何数据时允许物理删除用户分面。

### 11.10 AI 打标联动

AI 提示词必须从当前 active 分面动态生成，不允许在代码里固定输出分类名称。

每个分面上下文应包含：

```json
{
  "key": "people_clothing_color",
  "displayName": "人物衣服颜色",
  "description": "人物主要服装颜色",
  "hint": "如黑色、白色、红色；无人物则留空",
  "selectionMode": "multi",
  "maxItems": 2
}
```

AI 返回必须使用 key：

```json
{
  "people_clothing_color": ["黑色", "白色"]
}
```

不应返回显示名作为机器字段。

### 11.11 手动打标联动

工作台应动态读取 active 分面：

- 按 sortOrder 排序。
- respect visibleInWorkbench。
- respect selectionMode。
- respect maxItems。
- 搜索候选限定在当前 facetKey。
- 用户 Enter 新建标签时创建在当前分面。
- 单选分面选择新值时替换旧值。

当前 `buildWorkbenchFacets` 已经具备部分基础，但存在两个问题：

1. 前端仍有一份 `BASE_FACET_DEFAULTS`，与数据库形成潜在的第二结构源。
2. 对数据库不存在的基础分面会前端合成，这会让 UI 看似支持，但设置和后端管理实际没有该分面。

长期应以数据库返回为唯一事实，前端默认值只用于初始化迁移或后端不可用的只读降级，不参与正常业务写入。

## 12. 超级搜索和条件公式的兼容性

### 12.1 当前已有能力

超级搜索当前支持：

- 文本搜索。
- 图片/视频类型。
- 未打标。
- 标签分面。
- 排除标签。
- 父标签包含后代。
- 同分面 any/all。
- 元数据比较。
- AND/OR/NOT 表达式。
- 排序。
- AI 自然语言解析。
- warning。
- AI 结果回填 UI。

### 12.2 用户自定义分面对搜索的要求

新增一个分面后，必须自动出现在：

- QueryBuilder 字段选择。
- 标签候选选择器。
- AI 搜索提示上下文。
- 搜索结果条件芯片。
- 素材库侧栏。
- 已保存公式编辑器，若后续实现。

不允许每新增一个分面就修改前端常量。

### 12.3 当前 QueryBuilder 的动态程度

标签条件已经携带：

```text
facetKey
tagIds
mode
includeDescendants
```

这是正确的协议形态。

但是要保证候选分面来自 `list_tag_facets()`，并过滤：

- status=active。
- 适用当前媒体类型，若未来支持 appliesTo。
- 当前用户可见。

### 12.4 表达式执行的 facetKey 校验缺口

Rust `query_expr.rs` 编译标签叶子时当前模式类似：

```rust
LeafCond::Tag {
    facet_key: _f,
    tag_ids,
    ...
} => compile_tag_leaf(...)
```

也就是说 `facet_key` 被忽略，真正执行只依赖 `tag_ids`。

正常 UI 生成的 tagId 通常属于正确分面，因此多数情况下结果正确。但是：

- 历史条件可能引用已迁移标签。
- 手工修改或异常数据可能让 facetKey 与 tagId 不一致。
- 分面合并后旧条件可能陈旧。
- 前后端协议无法真正保证“这个标签属于这个分面”。

建议执行前校验：

```text
所有 tagIds 均存在
所有 tagIds 均属于 facetKey
标签状态允许被查询
不一致时返回明确 warning/error
```

### 12.5 分面停用后的查询语义

推荐：

- 新建条件不再显示停用分面。
- 历史查询仍可加载。
- UI 标记“已停用”。
- 执行可以继续使用历史关联，或由产品规则决定阻止。
- 不允许静默删除条件。
- 提供替换/迁移入口。

### 12.6 AI 超级搜索

AI 搜索当前通过 `FacetPromptContext` 接收分面信息，这个方向正确。

自定义分面接入后，应保证：

- 仅 enabledForAi 的分面进入提示词。
- 使用稳定 key。
- 描述和 hint 帮助 AI 理解用户术语。
- AI 返回未知 key 时给 warning，不创建数据库内容。
- AI 返回显示名时可做兼容解析，但最终解析为稳定 key。
- 不允许未知分类全部自动写进 custom。

### 12.7 文件元数据条件扩展

视频元数据补齐后，可逐步增加白名单字段：

```text
frame_rate
video_bit_rate
bit_depth
pixel_format
color_space
color_transfer
color_primaries
color_range
video_profile
container_format
audio_sample_rate
audio_channels
```

每增加字段必须同时更新：

1. SQLite 列或 JSON 提取策略。
2. Rust `MetadataFilter` 白名单。
3. key × op 合法矩阵。
4. TypeScript union。
5. QueryBuilder 展示。
6. AI 搜索 schema。
7. 单位和 NULL 语义。
8. 测试矩阵。

- `container_format`
- 可能的 `frame_rate` 派生查询

不要为所有元数据列一次性建索引。应先观察数据量和查询计划。

### 14.3 重新扫描不应放在迁移事务中

数据库迁移只负责：

- 增加字段。
- 设置默认值。
- 更新 schema version。

不要在启动迁移中同步 ffprobe 全部视频，否则：

- 启动时间不可控。
- 单个坏文件可阻塞迁移。
- 用户无法看到进度。
- 崩溃恢复困难。

应在应用启动后创建可取消的后台重扫任务。

## 18. 风险、边界与不建议采用的方案

### 18.1 不要把所有视频都预先强制转码

这会造成：

- 入库极慢。
- 大量磁盘占用。
- 用户导入几百 GB 视频时不可接受。

应按需生成预览代理，并缓存。

### 18.2 不要把视频是否可播等同于扩展名

`.mp4` 内可以是 H.264、HEVC、AV1 等完全不同的编码。必须读取 codec/profile/pixel format。

### 18.3 不要把 Log 曲线当成必然可读取字段

只能显示文件明确声明或厂商元数据能够证明的信息。无法读取时应显示“未提供”，不能猜测。

### 18.4 不要重新使用分类显示名作为机器协议

显示名可以变，协议 key 必须稳定。

### 18.5 不要物理删除已有数据的分面

应停用、迁移或合并，保留历史关联和查询兼容。

### 18.6 不要用前端默认分面长期掩盖数据库缺失

前端合成默认分面会造成“看起来有，实际上无法设置或持久化”的假能力。正常业务应以数据库为唯一事实源。

### 18.7 不要在数据库迁移中同步重扫所有媒体

重扫应该是有进度、可取消、可恢复的后台任务。

### 18.8 工作区当前有大量未提交改动

调查时工作区有大量已有修改和新增文件，覆盖本报告涉及的多数模块。后续实施必须：

- 以当前工作区为真实基线。
- 不回退用户已有改动。
- 小步提交。
- 每个阶段先重新读取相关文件。
- 避免把旧报告中的代码状态直接当成当前实现。

## 19. 外部资料调研结论

### 19.1 TanStack Virtual

参考：

- <https://tanstack.com/virtual/latest/docs/api/virtualizer>
- TanStack Virtual React 文档和相关 flicker discussion

主要结论：

- 虚拟列表会在可见范围变化时挂载/卸载项目。
- item key 应稳定代表业务实体。
- overscan 不能解决业务状态复用错误。
- 新版本提供 `directDomUpdates` 降低滚动时 React 重渲染，但稳定身份仍是前提。

### 19.2 React 状态与 Hook 规则

参考：

- <https://react.dev/learn/preserving-and-resetting-state>
- <https://react.dev/reference/react/useState>

主要结论：

- React 状态绑定于渲染树的位置。
- `key` 用于给组件显式身份并控制状态重置。
- 同一组件每次渲染必须以相同顺序调用 Hook。
- 条件 return 之后新增 Hook 会直接造成运行时错误。

### 19.3 Tauri asset protocol

参考：

- <https://v2.tauri.app/reference/javascript/api/namespacecore/>
- <https://v2.tauri.app/security/asset-protocol/>

主要结论：

- `convertFileSrc()` 只解决本地路径转 WebView URL。
- CSP 必须允许 media-src。
- asset protocol scope 必须允许对应文件。
- 路径可加载不等于编码可解码。

当前项目已经在 `list_assets/get_asset` 返回路径时动态 allow file，CSP 也包含 media-src，因此当前大图完全不进入播放器的第一根因不是 scope，而是错误的 `durationMs` 类型判断。编码兼容仍是后续第二层问题。

### 19.4 MDN 媒体能力

参考：

- <https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/canPlayType>
- <https://developer.mozilla.org/en-US/docs/Web/API/MediaCapabilities/decodingInfo>

主要结论：

- `canPlayType` 只返回大概的容器/编码支持概率。
- MediaCapabilities 可以结合 codec、分辨率、码率和帧率返回 supported/smooth/powerEfficient。
- 最终仍要以真实加载和 error 事件为准。

### 19.5 FFmpeg/ffprobe

参考：

- <https://ffmpeg.org/ffprobe.html>
- <https://ffmpeg.org/ffprobe-all.html>

主要结论：

- `-show_format` 提供容器信息。
- `-show_streams` 提供各音视频流信息。
- 标准 JSON 已包含像素格式、帧率、码率、色彩空间、传输曲线、色彩原色等大量字段。
- side data 可继续提供 HDR、Dolby Vision、Mastering Display 等增强信息。

### 19.6 MediaInfo

参考：

- <https://mediaarea.net/en/MediaInfo/Support/Fields>

主要结论：

- MediaInfo 对 ColorSpace、colour_range、transfer_characteristics、colour_primaries、MasteringDisplay 等提供了成熟字段定义。
- 可作为后续增强或字段命名参考。

### 19.7 分面分类系统

调研的成熟做法普遍包含：

- 稳定 ID/key 与可变显示名分离。
- 分面/词表与具体标签词条分离。
- 支持层级、别名、停用和合并。
- 分面基数约束 single/multi。
- 软停用而不是直接删除。
- 变更后对搜索索引和缓存进行定向失效。
- 历史引用通过稳定 ID 保持兼容。

当前项目的 `tag_facets + tags` 基础方向正确，缺的是分面生命周期管理和全部消费者的动态联动。

## 最终结论

这批用户反馈并不是若干互不相关的小 UI 问题，而是三条基础链路没有完全统一：

```text
素材身份链路
  虚拟列表 → 卡片 → 占位图 → 高清图

媒体能力链路
  类型识别 → 元数据探测 → 数据库存储 → 播放判断 → 属性展示

标签协议链路
  分面定义 → 设置 → 打标 → 搜索 → 条件公式 → 历史兼容
```

最合理的处理方式不是分别在页面上补判断，而是先统一事实源和协议：

1. 素材卡片以稳定素材 ID 管理状态和异步请求。
2. 图片/视频类型由统一字段或统一解析器决定。
3. 视频元数据由可靠的探测服务一次读取、结构化保存并保留原始 JSON。
4. 播放采用原文件优先、兼容代理兜底。
5. 图片与视频属性分开呈现。
6. `tag_facets.key` 继续作为稳定协议，并补齐真正的用户分面生命周期管理。
7. 设置、素材库、AI 打标、超级搜索和条件公式全部动态读取同一份分面定义。

按本报告的阶段顺序实施，可以先快速恢复设置页和视频基础可用性，再逐步完成专业媒体属性和用户自定义标签这一核心特色，避免在当前多套判断和多套默认数据并存的情况下继续累积兼容问题。
