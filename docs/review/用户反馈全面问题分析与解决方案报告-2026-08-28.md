## 2. 逐项核实结果

### 2.1 P0-01 查看器缩放空引用崩溃 —— ⚠️ 判定：方向正确，验证不完整

**核实结果**：

- ✅ 属实：`src/components/viewer/MediaViewport.tsx` 当前源码确实不读事件 `offsetX`，坐标用 `clientX/clientY + getBoundingClientRect()`（:84-96）。文件中残留的 `offsetX/offsetY` 是 `ViewState` 的**状态字段名**（:18-23、:92-94、:138、:148、:215），不是 DOM 读取路径。
- ✅ 属实：`MediaViewport.tsx` **没有** generation / 代际保护（grep 无 `generation`），快速切图时旧回调竞态的风险真实存在，报告推荐的生命周期保护是有效增量。
- ⚠️ **报告的验证方法有缺陷**：报告以"dist 中存在 offsetX"暗示可能含旧实现。实测 `dist/assets/index-hFj5IFiB.js` 含 8 处 `offsetX`，但 minifier 会保留对象属性名，这些正是 `ViewState.offsetX` 属性序列化后的正常残留，**不能作为"旧事件读取路径存在"的证据**。正确的验证方式是扫描新实现的特征指纹（如 `getBoundingClientRect` 与缩放锚点计算的组合）或构建 hash 比对。
- ❌ **遗漏最高概率根因**：用户运行的可能是**旧安装包/未重新分发的二进制**。dist 构建时间（08-27 21:16）晚于最后一次源码提交，且 dist 中包含 `PageErrorBoundary`（见 2.2），说明当前 dist 是新的；用户报错更可能来自更早的分发版本。报告把它归入"旧构建产物"一笔带过，未区分"开发 dist"与"用户安装包"两个概念。

**结论**：错误原因基本找对（旧版本 + 竞态两类候选成立），三层方案（单一坐标函数 + 代际保护 + 局部错误恢复）技术正确、可直接施工；但 CI 字符串扫描 `offsetX` 的门禁设计需改为特征指纹扫描，否则永远误报。

### 2.2 P0-02 缺少错误恢复闭环 —— ❌ 判定：实锤事实错误

**核实结果**（这是本次审核最重要的发现）：

- ❌ 报告断言"`src/App.tsx` 无页面级 Error Boundary"——**与代码直接矛盾**：
  - `src/App.tsx:10` 导入 `PageErrorBoundary`，`:85-91` 以 `<PageErrorBoundary key={page} onReset={() => setPage(page)} onBack={() => setPage("library")}>` 包裹页面切换；
  - `PageErrorBoundary.tsx` 完整实现了报告要求的两个动作：「重新加载」（onReset）与「返回素材库」（onBack），错误文案正是用户引用的"页面数据或某个模块出现异常，可以重新加载，或返回素材库继续使用"；
  - 已有配套测试 `PageErrorBoundary.test.tsx`；
  - dist 产物中同样包含该组件（1 处命中），生产构建已覆盖。
- 该能力来自 2026-08-27 提交链（`5d356bf` 等阶段 1+3 P0 修复）——**报告写作于 08-28，基线应包含这些提交，但没有核对**。
- 附带核实：用户反馈的"重新加载，或返回素材库"文案正是 PageErrorBoundary 的现有输出（:55、:67、:73），说明**用户看到的是错误边界正常工作的证据，而非缺失**。真正待查的是"哪个子组件在抛错"，报告把方向完全搞反了。

**结论**：此问题不成立。正确动作是把 P0-02 改写为"定位触发 PageErrorBoundary 的上游异常源"（结合 P0-01 的 null 引用，两者很可能是同一事件）。

### 2.3 P0-03 本地模型生命周期 —— ✅ 判定：代码事实全部属实，方案好但可分级落地

**核实结果**：

- ✅ `ollama_installer.rs` `start_service_inner()`（现约 :812-827）确实 `cmd.spawn()` 后丢弃 `Child` 句柄，应用无法管理/停止自己启动的服务。
- ✅ `ai_cloud.rs:162-180` 确实只有异常自愈路径的 `keep_alive: 0` 卸载；正常请求链路 grep 全仓无任何 `keep_alive` 传参——"只有补救、没有生命周期管理"的判断准确。
- ✅ 外部依据核实无误：Ollama 原生 `/api/generate`、`/api/chat` 支持 `keep_alive`（`0` 即请求后卸载）；另有环境变量 `OLLAMA_KEEP_ALIVE` 可在服务级设定全局空闲驻留时长（阿里云开发者社区与 Ollama 环境变量文档均确认：模型按需加载、闲置自动卸载，保留时间由 OLLAMA_KEEP_ALIVE 控制）。

**更好的解决方法（报告遗漏的分级路径）**：

1. **第一级（半天的低成本止血）**：在 `start_service_inner` 的 `cmd.env()` 中注入 `OLLAMA_KEEP_ALIVE`（例如 `2m`）。这一步**不引入任何新架构**，即可让"模型空闲 2 分钟自动卸载"，直接解决用户"不用时仍占内存"的主诉。当前函数已有注入 `HTTPS_PROXY/HTTP_PROXY` 的先例，改动模式完全一致。
2. **第二级**：保存 `Child` 句柄（替换 `spawn()` 丢弃写法），实现 ownership 判定与应用退出时清理。Windows 上 `CREATE_NO_WINDOW` 启动的进程需注意用 `taskkill /PID <pid> /T` 兜底（子进程树）。
3. **第三级**：报告提出的 `LocalAiRuntimeManager` 完整状态机（ownership / active_requests / idle_unload_timer）。设计合理，但作为第三级而非第一步——报告把它当成唯一方案，对一个 MVP 阶段的项目偏重。5.3 的状态机与 5.5 的预算表可以保留为目标态。

**结论**：错误原因找对，方案方向正确但应拆分出"环境变量级止血 → 进程句柄管理 → 完整运行时管理器"三级路径，前两级可在阶段 1 内完成，第三级放入阶段 2。

### 2.4 P0-04 视频打标设置与运行时脱节 —— ✅ 判定：属实，且报告还漏了一个实锤 bug

**核实结果**：

- ✅ `SettingsPage.tsx:551` 存在 `draft.ai.videoTagging` 开关；`ai_cloud.rs:771-774` 的错误文案确实写死"设置 → 在线打标"，与设置页实际 IA（AI 设置）不一致。
- 🔍 **审核新发现（报告未发现）**：`ai_cloud.rs:761` 注释声称"命令层 ai_start_batch 已在预检拦截同场景，此处为直接服务层调用的兜底"，但核对 `ai_cmd.rs:72` 起的 `ai_start_batch` 预检代码——**并没有任何 `video_tagging` 检查**（预检只覆盖 manual 模式、processing 状态、pending 判定、档案绑定、local 一致性）。注释与实现不符，说明"批次启动前预检"不是可选优化，而是**本应存在但缺失的承诺**。报告 6.2 的预检方案因此更有必要，且应顺手修正该误导性注释。
- ✅ 报告的"单一配置事实源 + 保存后回读 revision + 批次页显示有效配置摘要"方案合理，符合该项目已有的 settingsStore single-flight 模式。

**结论**：错误原因找对；补充上述注释-实现不一致问题后，可直接按报告 §6.2 施工。

### 2.5 P1-01 取消大悬浮框、卡片内播放 —— ⚠️ 判定：代码事实半对，方案与既定产品决策冲突

**核实结果**：

- ✅ 属实：`MediaPreviewPopover.tsx` 仍是 `position: fixed`、`max-w-[420px]`、`max-h-[70vh]`；`VideoPreviewContent.tsx` 仍是固定 `h-64`。
- ⚠️ **关键遗漏**：该 Popover 目前**只被导入页 `PendingList` 使用**（grep 确认唯一消费者是 `HoverPreviewTrigger`，且 HoverPreviewTrigger 仅出现在 `src/components/import/PendingList.tsx`）。**素材库 AssetCard 的 hover 预览已于 08-27 阶段 2 整体删除**（commit `8fa88be`，综合实施报告明确记录："素材库禁止所有大图/视频 hover 预览，双击后进入 Viewer"，并有 AssetCard.test 断言无 video / 无 fixed 层）。报告 §7.2 末尾提到"代码基线可能处于迁移中"，说明作者看到了线索但没有查证到底。
- ❌ **方向性冲突**：用户说"像素材库一样，视频自己播放"——但素材库的现状是**完全没有 hover 播放**。报告由此推导出"统一改为卡片内视频层"的方案，实际上**推翻了 08-27 刚定的产品决策**（该决策本身来自 08-27 的用户反馈："删除素材库大图/视频 hover 预览"）。两个需求相互矛盾，这是**产品决策问题，不是技术方案问题**，报告把它当纯技术问题处理了。

**更好的处理方式**：

1. 先向老板确认需求仲裁：素材库到底要不要 hover 预览？（08-27 用户说不要；08-28 用户说"像素材库一样在卡片里播"——后者描述的可能只是**导入页**期望，因为素材库本来就没有悬浮框。）
2. 若仅导入页改造：Popover → 卡片内 `absolute inset-0` 视频层，报告 §7.2 的规则（250-350ms hover intent、muted/playsInline、离开即卸载、单实例播放）全部适用且质量不错，直接施工。
3. 若素材库也要加：必须先评估与 08-27 "禁止 hover 预览 + 缩略图滚动稳定"决策的兼容性，避免来回翻烧饼。

**结论**：错误原因部分找对（组件事实对、使用范围判断错）；方案技术细节优秀，但适用范围需先经产品仲裁。

### 2.6 P1-02 超级搜索"红色建筑" —— ✅ 判定：代码事实属实，方案是全报告最优章节

**核实结果**：

- ✅ `super_search_ai.rs` `collect_tag_dictionary()` 确实 `LIMIT 30` 每分面（:289-310 区域核实无误）。
- ✅ `resolve_tag_facet()` / `resolve_tag_condition()` 确实只有"精确名/别名 → 唯一候选"两级，无同义词归一、无候选评分、复合短语必然落到"未识别标签"warning——"红色建筑"整句进词典必失配的机理分析正确。
- ✅ 两阶段解析器（LLM 只出原子 concept，本地词典解析编译为 AND 条件）设计正确，明显优于让 LLM 直接输出 tagId 的现行模式；颜色三档（标签色 → 主色 → 主体色）分级务实。

**结论**：错误原因找对，方案可直接进入施工设计。优先补"标签规范化 + 别名/同义词索引"（阶段 4 第 1 条），这是其余一切的地基。
