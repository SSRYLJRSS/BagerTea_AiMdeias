# 超级搜索方案评审与落地建议

> 日期：2026-08-24
> 评审对象：`docs/review/super-search-research-and-design-2026-08-24.md`
> 评审方式：逐条核对当前代码（截至 640898d）+ 外部资料补查
> 结论：**方案总体成立，架构判断全部正确；但报告的代码现状盘点有三处过时，P0 工作量可缩水；AI 智能搜的输出可靠性策略建议升级为「API 级结构化输出优先 + 三级降级」**

---

## 一、代码核对：报告三处已过时

### 1.1 「两个半成品」已经不存在了

报告 §2.5 说 `metadata_filters` 是死参数、`list_metadata_facets` 命令缺失。核对当前代码，**两项都已实现**：

| 报告论断 | 当前代码实际 |
|---|---|
| Rust `AssetFilter` 没有 `metadata_filters` | `assets.rs:110` 已有 `metadata_filters: Vec<MetadataFilter>`，`build_where:310` 已编译 |
| `assets_cmd.rs` 没有 `list_metadata_facets` | `assets_cmd.rs:68` 已实现，`lib.rs:107` 已注册 |
| 没有 UI 使用 `metadataFilters` | `MetadataPanel.tsx`（左侧元数据面板）+ `SelectedFilterTags.tsx`（条件芯片）+ `metadataStore.ts` 全链路已通 |

DB 迁移也已推进到 v8（报告按 v7 估算）。报告写于代码大合并（775980c "Phase3 AI/导出增强 + 标签系统重构"）之前或期间，**报告 P0 中「补 command handler」的工作已经免掉**。

### 1.2 真正的缺口：现有元数据筛选是「集合匹配版」，撑不起超级筛选

现有 `MetadataFilter` 只有 `{key, values: Vec<String>}`，语义仅 `IN` 精确匹配，且只支持 9 个 key：

```
taken_month / camera / lens / iso / aperture / shutter / focal / file_ext / resolution
```

三个硬伤：

1. **没有数值比较**。宽高、分辨率、文件大小、视频时长、ISO 范围全是「精确值集合」，表达不了「大于 5MB」「10 秒以上」「5MB 以上」——这些恰恰是 AI 智能搜示例句的核心谓词。
2. **没有时间范围**。只有 `taken_month`（按月字符串），表达不了「2025 年」「去年夏天」这种区间，更没有 `last_n_days` 相对时间。
3. **`resolution` 是 `"1920x1080"` 字符串匹配**。用户不可能记得精确分辨率，AI 更不该输出它。应升级为 `width * height` 数值比较（报告 §4.3 的定义是对的）。

所以：报告 §4.2/§4.3 的 `MetadataFilter {key, op, min/max/value/values}` 升级方案**不仅成立，而且是当前唯一真正的 P0**。这是本次超级搜索后端的核心增量。

### 1.3 现有能力比报告记录的略多

- `sort_by` 已支持 `name / modified_at`（报告只列了 created_at/taken_at/size/resolution），超级筛选的排序面板可以直接多给两项。
- `request_tags` 里已有本地档案连接失败引导、Ollama runner 损坏自愈（卸载重载）、退化检测——这套容错经验直接搬给 AI 搜索请求复用，`super_search_ai.rs` 不用从零写错误处理。

**结论：报告的 P0 从「补死参数 + 实现 op 化」缩水为「op 化升级 + v9 索引 + 测试」，预计省半天。**

## 二、外部资料增量：AI 输出可靠性应升级为「三级降级」

报告 §4.5/§4.8 的策略是「prompt 约束 + 宽容解析 + 失败重试一次」。这是 2024 年的主流做法，2025 年后各家 API 都已支持**API 级结构化输出**，应该优先用上。补查结果：

| 端点类型 | 结构化输出机制 | 关键细节 |
|---|---|---|
| OpenAI 兼容云端（含阿里百炼 qwen） | `response_format: {type: "json_schema", json_schema: {..., strict: true}}`；最低配也有 `json_object` | 阿里云百炼文档确认 qwen 支持 JSON Mode / structured output（2026-05 更新）；用户云端档案基本都走这条 |
| Anthropic | 无 JSON mode 标志，生产模式 = **tool use + `tool_choice` 强制调用**，把 SearchQuery 定义成 tool 的 input_schema | Claude 官方推荐路径，2026 年无变化 |
| Ollama 本地 | 原生 `/api/chat` 的 `format` 参数直接传 JSON Schema（0.5.0+） | 注意：**Ollama Cloud 不支持**；且本项目本地档案现在走的是 OpenAI 兼容 `/v1/chat/completions`（见 `request_tags` 实现），该兼容端点对 `response_format` 的支持不完整，**需实测，很可能要走降级** |

### 建议的三级降级策略

```
第 1 级：API 级结构化输出
  anthropic 档案   → tool use + tool_choice forced，schema = SearchQuery
  openai 兼容云端  → response_format json_schema（strict）
  请求前探测/失败时降级，不硬性要求服务商支持

第 2 级：json_object + prompt 内嵌 schema
  只约束「必须是合法 JSON」，字段约束写在 system prompt 里
  （覆盖不支持 json_schema 的 OpenAI 兼容服务商与 Ollama 兼容端点）

第 3 级：纯 prompt + 宽容解析（现有 parse_categorized 同款思路）
  整串解析失败 → 截取首个 {} 片段 → 仍失败带错误原因重试一次
```

这样做的收益：

- **后端校验白名单永远不变**（报告 §4.5 的安全设计是底线，API 级 schema 只是让合法率从「尽力」变「保证」，不是替代校验）；
- 三种档案类型（openai / anthropic / local）一条代码路径，探测逻辑在 `ai_cloud.rs::request_text_json` 里一次封装；
- json_schema 的 strict 模式有限制（所有字段 required、`additionalProperties: false`），写 schema 时把可选字段声明为 `nullable`/`anyOf` 即可，别为了 strict 把 schema 写得面目全非——**宁可第 1 级用宽松版，也别牺牲 schema 可读性**。

### 其他资料要点

- **标签词典注入规模**：每分面 top 30 标签 + 高频别名，10 个分面约 300~400 词条，加 system prompt 总计约 3~4K token，对云端和本地 7B 模型都可控。超过 50 个标签/分面时收益急剧下降，不建议全量注入。
- **小模型能力边界**：qwen3-7b / llama3.1-8b 级本地模型做「自然语言 → JSON 筛选」是可行区（这是结构化抽取任务，不是推理任务），但**别名/模糊标签匹配**建议一律走后端 `tags::search_candidates` 兜底解析，不指望模型自己对齐——报告 §4.4 已经这么设计了，保持。
- **竞品无新变化**：Eagle AI Search 仍是「搜已有文字信息 + 以图搜图」，Immich 语义搜索仍是 CLIP embedding 路线。报告「AI 只做自然语言→筛选条件、不假装理解像素」的边界判断依然正确。

## 三、对报告四个决策点的表态

| 决策 | 建议 | 理由 |
|---|---|---|
| 1. AI 输出中间 JSON，不生成 SQL | **同意，无保留** | 这是全行业成熟路线（Notion/Airtable 同款），且与现有后端白名单编译天然衔接 |
| 2. AI 解析后自动执行 + 芯片可改 | **同意** | 竞品（Eagle/Pixcall）心智都是「筛选即结果」；加一步确认打断流。芯片可删已经给了后悔药 |
| 3. 保存筛选放二期 | **同意** | 一期先把查询协议立稳；`saved_filters` 表二期加，UI 结构（芯片 + 面板）已经为它留好位置 |
| 4. 沿用全局选中集 | **同意** | 批量打标/导出/删除零重写，退出不清选中与现有行为一致 |

### 补充三个报告没问、但需要拍板的点

1. **`MetadataFilter` 类型升级是内部协议破坏性改动，直接升，不留兼容**。`{key, values}` → `{key, op, ...}` 改动波及前端 `MetadataPanel / SelectedFilterTags / libraryStore` 和后端 `build_where`。好在它不是持久化数据（不落库、不进 saved_filters），一次性升级即可，**不要**搞 untagged 双形态兼容——那是给二期 saved_filters 留的坑。
2. **`taken_month` 保留为 UI 专用**，AI 不生成它（AI 生成 `taken_at between` 区间即可）；人工筛选面板继续用月份多选（现成交互，好用）。
3. **索引取舍**：v9 不必全加报告 §4.9 列的 6 个。`file_ext` 基数极低，SQLite 优化器大概率不走索引；建议只加 `taken_at / camera / file_size / (width, height)` 四个，`duration_ms` 等真出现慢查询再说。3 万行级别，先加四个已经是过度保障。

## 四、修订版实施计划

> 相对报告 §5 的变化：P0 砍掉「补半成品」，P2 强化降级策略，其余保持。

### P0：查询协议升级（约 1 天，原 1~1.5 天）

1. `MetadataFilter` 升级为 `{key, op, min, max, value, values}`（serde camelCase，与 TS 对齐）；
2. `build_where` 按白名单 key 编译数值/时间/集合三类分支，全部参数绑定；`resolution` 改为 `width*height` 数值比较；新增 `width / height / file_size / duration_ms / mime_type / video_codec / audio_codec` 与 `taken_at / created_at / modified_at` 的 `between / gte / lte / last_n_days`；
3. v9 迁移：4 个索引（`taken_at / camera / file_size / (width,height)`）；
4. Rust 单测：每个 key×op、非法 op 拒绝、NULL 语义（缺值素材在数值筛选下应被排除还是保留——**建议排除**，与现有 `taken_month` 分面只列非空一致）。

### P1：超级筛选 UI + 双击入口（约 2 天，不变）

报告 §4.6/§4.7 结构照抄即可。两点提醒：

- `AssetGrid` 数据源解耦选**方案 A**（抽通用 `AssetGridView`），方案 B 的「快照恢复」在防抖刷新、翻页竞态下必出 bug，不值当省那点改动；
- `useDoubleAction` 延迟建议 220~250ms，双击后必须取消 pending 的单击导航——这是唯一容易翻车的交互点，单测要覆盖「其他页双击素材库不闪切」。

### P2：AI 智能搜（约 1.5 天，含降级链）

1. `ai_cloud.rs` 抽 `request_text_json(profile, system, user, schema) -> Value`：
   - anthropic 分支：tool use + forced tool_choice；
   - openai 兼容分支：先带 `response_format: json_schema`，响应报错（400/unknown field）自动降级 `json_object` 再降级裸请求；
   - 本地档案连接失败/退化自愈逻辑从 `request_tags` 搬过来复用；
2. `services/super_search_ai.rs`：标签词典装配（每分面 top 30 + 别名）→ prompt 组装 → 三级降级请求 → 后端白名单校验 + 标签解析 → `{query, explanation, warnings, resolved}`；
3. 命令 `ai_parse_search_query`（spawn_blocking，60s 超时，不持 DB 锁）；
4. 前端 AI 输入框 + 解析摘要 + warnings + 芯片回填，无 AI 配置时显示引导不报错。

### P3：收尾（约 0.5~1 天，不变）

Esc / Ctrl+Shift+F / 双击提示 / 示例快捷输入 / 三关回归 / 文档更新（**先改 PRD 和 PROGRESS 再动代码，项目铁律**）。

## 五、风险清单

| 风险 | 等级 | 对策 |
|---|---|---|
| Ollama OpenAI 兼容端点不支持 json_schema，本地档案只能走第 2/3 级降级 | 中 | 降级链已兜住；一期不为此单独接原生 /api/chat，实测后若 qwen3-8b 在 json_object 下解析率高就不再折腾 |
| 小模型（7B 级）JSON 输出不稳定，warnings 频发 | 中 | 标签解析全走后端兜底；warnings 是正常产品行为不是错误；云端档案始终可用作对照组 |
| 数值筛选 NULL 语义不一致（如有素材无 EXIF） | 低 | P0 单测明确「缺值即排除」，前后端一致 |
| 双击入口与单击导航竞态 | 低 | useDoubleAction 单测覆盖；进入超级搜索后底栏保持「素材库」高亮 |
| MetadataFilter 升级漏改调用点 | 低 | 全局仅 MetadataPanel / SelectedFilterTags / libraryStore / assets.rs 四处，`tsc` + cargo test 双关兜底 |

## 六、一句话总结

**报告的架构决策（一个 SearchQuery、两条入口、AI 不碰 SQL、白名单编译）全部照单执行；代码盘点按本评审修正——P0 砍成「op 化升级」一件事；AI 链路在报告的「宽容解析」之上加一层「API 级结构化输出优先、三级降级」，其余按报告 P1~P3 推进。总量约 4.5~5.5 天。**
