## 2. 测试报告没发现的真缺陷（本轮核查新挖出）

### 2.1 真缺陷 1（P0·B/C 类）：优先满足区没有拖拽手柄，用户无法排序

**位置**：`src/components/supersearch/QueryBuilder.tsx` 340-368 行（优先区渲染）

**证据链**：
- `DragHandle` 组件（718-739 行，`draggable` 属性在 723 行）**只被 `GroupEditor`（必须区/排除区）渲染**——全文件 grep `draggable` 仅 723 行一处
- 优先区行渲染（345-364 行）：`序号{ i+1 }` + 字段 + 运算符 + 值 + `MoveMenu`（跨区移动菜单）+ 删除按钮——**没有 DragHandle、没有 DropLine、没有任何上移/下移入口**
- `MoveMenu`（916-941 行）的菜单项只有"移到「必须满足」/移到「排除」"，**没有区内排序功能**
- 新添加的优先条件恒 append 到末尾（367 行 `[...shouldList, {...}]`）

**违反契约**：
- §11 验收清单第 7 条（355 行）："优先区无且/或、无权重、无匹配开关、无'至少 N 项'；**拖拽改顺序后排序随之变化**"
- P3 施工项（314 行）："优先区有序拖拽清单……**拖拽手柄 + 序号**；提交按位置自动 weight"
- §6.2（296 行）场景："想让竖构图更优先就**拖到第 1 行**"

**危害定性（C 类"看似可行实际不可用"）**：区域标题明晃晃写着"越靠上越优先"（343 行），序号 1/2/3 也渲染了，但用户**没有任何手段改变顺序**——功能承诺了却给不出操作路径，这正是测试指导书 C 类问题的教科书案例。

**修复建议**：
1. 优先区每行行首加 `DragHandle`（复用现有组件，传入合成 id 如 `should-{i}`）
2. 行间加 `DropLine`（复用现有组件），drop 时 `setShould(reorder(shouldList, from, to))`
3. 现有 `DragState`（234-236 行）直接复用，无需新状态
4. 预估 30-50 行改动，配套测试见 SS-03 修改建议

### 2.2 真缺陷 2（P0·B 类）：按位置递减权重未实现，"越靠上越优先"是空头承诺

**位置**：前端 `QueryBuilder.tsx:367` / `superSearchStore.ts:492,512-520`；后端 `src-tauri/src/db/search_plan.rs:262,383`

**证据链**：
- 契约（方案 168 行）："`should[]` 顺序 = 拖拽顺序；**提交时按位置自动生成递减权重，UI 不编辑**"
- 实现一（QueryBuilder.tsx 367 行）：新增优先条件 `{ cond, weight: 1, label: "" }` ——**恒 1，无位置逻辑**
- 实现二（superSearchStore.ts 492 行）：跨区移入 should `{ cond: node.cond, weight: 1, ... }` ——**恒 1**
- 实现三（superSearchStore.ts 512-520 行 `setPlanShould`）：**原样存储，无任何权重重算**
- 全库检索"递减"（前端 + 后端）：**零命中**
- 后端评分（search_plan.rs 383 行）：`score_terms.push(format!("{m} * {w}", w = fmt_weight(sc.weight)))` ——SQL 评分 = 命中数 × weight，**should 数组顺序完全不参与排序**
- 后端校验（search_plan.rs 262 行）：`ALLOWED_SHOULD_WEIGHTS = {0.5, 1.0, 2.0}` ——三档权重枚举仍在，说明后端能力在等前端喂数据

**危害推演**：即使补上真缺陷 1 的拖拽，用户拖完顺序**结果排序纹丝不动**（所有 should weight 都是 1，评分相同，最终顺序退回 ranking 字段默认的 created_at desc）。两个缺陷叠加 = 优先区整体退化为"仅作展示的标签堆"。

**修复建议**（二选一）：
- **方案 A（契约内）**：提交/持久化 plan 时按位置生成权重，映射到后端三档枚举——如前 1/3 条 weight=2.0、中间 1.0、末段 0.5（或首条 2.0、其余 1.0 的简化版）。落点：`setPlanShould` 内或 `scheduleRefresh` 提交前。
- **方案 B（更简）**：后端 383 行评分公式改为 `weight * (N - index)`（顺序天然递减），前端只需保序。改动最小但要动后端契约注释。
- 推荐方案 A：不动后端，前端一处函数搞定，且后端三档枚举本来就是为此保留的。

### 3.5 K-03 唯一解码入口 —— 规则过时，代码基本合规
