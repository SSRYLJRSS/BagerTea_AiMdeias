  3.2 测速逻辑 probe_source
测什么：不是 HEAD（拿不到带宽），而是 Range 拉 1MB 真实数据：


    
      rust
      

      
pub fn probe_source(src: &DownloadSource) -> SourceProbe {

    // 1) GET + Range: bytes=0-1048575，connect_timeout 3s，总超时 6s

    // 2) 记录 t0 = send 前；ttfb = 首次 read 返回数据的时刻 - t0

    // 3) 持续读满 1MB 或 6s 总超时；speed_bps = 已读字节 / (now - 首字节时刻)

    //    —— 注意速度分母用"首字节之后"的时间，排除 RTT 对带宽估计的稀释

    // 4) HTTP 416（Range 不可满足）：说明文件小于 1MB 或不支持，退化为

    //    无 Range 请求读最多 256KB，仍可得到 ttfb + speed

    // 5) HTTP 405/不支持 Range（返回 200 全量）：读满 256KB 后立即 abort 连接

    //    （reqwest blocking 中 drop response 即断开），避免拉满 900MB

}

    

  要点：


下载 256KB~1MB 即断开，流量可控（3 源最多 ~3MB）

reqwest::blocking + spawn_blocking，三源可用 std::thread 简单并发（不引 tokio 依赖复杂度）

3.4 换源续传一致性校验（防损坏文件，必须做）
现有 download_one 盲续 .part。新增前置校验：


    
      rust
      

      
// download_one 内，发 Range 请求前：

// 1) 若 .part 存在且 size > 0，先带 Range: bytes={existing}- 发请求

// 2) 得到 206 时：total = existing + content_length，正常续传（现状不变）

// 3) 得到 200（不支持 Range）时：现有逻辑已从头写（现状不变）

// 4) 新增：下载完成后，除现有 Content-Length 校验外，

//    若本次是"换源后的第一次下载"，比对 .part 起始时记录的源 id：

//    在 .part 同目录写 <name>.part.meta（JSON: {source_id, total_hint}），

//    源 id 与本次不同 → 删 .part 重下，进度事件标记 "源已切换，重新下载"

    

  .meta 文件随 .part 一起清理（remove_installer 同步删 .part 和 .part.meta——当前 remove_installer 没删 .part，这是个顺手要修的 bug：失败的半截文件会永久残留占磁盘）。

  3.6 持久化决策（有一个设计取舍）
按“单一数据源”约定，源选择应走 draft → 保存设置。但自定义源有个体验矛盾：用户添加自定义源后，不点“保存设置”就点“一键安装”，自定义源会查不到。

决策：自定义源单独走 settings_cmd 即时落库（低风险、低频写），源选择 ollamaSourceId 走 draft（因为它影响的是“下一次下载行为”，与 AI 配置语义一致）。理由：自定义源更像“素材库/标签分类”级别的独立资产而非 AI profile 配置，且安装向导的动线不应强迫用户先保存设置。

3.7 校验规则（后端兜底）

URL：必须 http(s):// 开头，长度 ≤ 512，禁止包含空格/控制字符

label：trim 后非空，≤ 24 字符

自定义源数量上限 5 个（防注册表膨胀）

测速并发上限：一次最多测 8 个源（内置 3 + 自定义 5）
